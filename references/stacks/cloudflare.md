# Cloudflare (Workers and Pages)

## detection signals
`wrangler.toml`, `wrangler.json`, or `wrangler.jsonc` at the repo root — the defining signal. `wrangler` in devDependencies, a `.wrangler/` directory (gitignored local state), `.dev.vars` (local secrets, must be gitignored), `worker-configuration.d.ts` (generated by `wrangler types`), or `@cloudflare/workers-types` in the TypeScript config. Framework adapters: `@cloudflare/next-on-pages`, `@opennextjs/cloudflare`, `@sveltejs/adapter-cloudflare`, `nitro` with a `cloudflare-pages` preset, `hono` with a Workers entry.

**Establish which product is in play**, because the answers differ:

- **Workers** — a script (or a set of them) deployed with `wrangler deploy`, with `main` and `compatibility_date` in `wrangler.toml`. Everything is code; there is no static publish directory unless the Assets binding is configured.
- **Pages** — a static site plus optional Pages Functions in a `functions/` directory, deployed from a git integration or `wrangler pages deploy`. Supports `_headers`, `_redirects`, and `_routes.json` in the output directory. Cloudflare has been steering new projects toward Workers with static assets, and Pages is in maintenance for new features, so a new project on Pages is worth a note (REL-013) rather than a finding.
- **A Cloudflare-proxied origin** — the app runs somewhere else entirely (Fly, a VPS, Vercel) and Cloudflare is only DNS plus CDN plus WAF. In that case most of this file does not apply, but the **SSL/TLS mode** and **Transform Rules** sections do, and they matter a great deal.

Environment detection from inside a Worker: there is **no built-in equivalent of `VERCEL_ENV`**. Workers get whatever you put in `[vars]`, so a project without an explicit `ENVIRONMENT = "production"` variable has no way to tell where it is running, which is worth flagging on its own. Pages injects `CF_PAGES=1`, `CF_PAGES_BRANCH`, `CF_PAGES_COMMIT_SHA`, and `CF_PAGES_URL` into the build, and `CF_PAGES_BRANCH` is the correct branch for "is this production" on that product.

Request-side context is on `request.cf` (colo, country, TLS version, bot score where the plan includes it) and in the `cf-connecting-ip`, `cf-ray`, and `cf-ipcountry` headers. `cf-connecting-ip` is the real client IP — `request.headers.get('x-forwarded-for')` on Cloudflare is attacker-controllable in a way `cf-connecting-ip` is not, which matters for any rate limiter or audit log keyed on IP (SEC-015).

## dev server
```bash
wrangler dev                          # local by default, with Miniflare emulating the bindings
wrangler dev --remote                 # runs on Cloudflare's edge against real bindings
wrangler pages dev <output dir>       # for a Pages project
wrangler whoami                       # is the CLI authenticated?
wrangler versions list                # deployed versions of a Worker
wrangler deployments list
```

Local secrets go in **`.dev.vars`** (a dotenv-format file read only by `wrangler dev`), which must be gitignored — it is the local mirror of `wrangler secret put` and a common place for a real production key to end up committed (SEC-001).

`wrangler dev` local mode emulates KV, D1, R2, Durable Objects, and Queues with local storage under `.wrangler/state/`. That is fast and safe but it is **not** the production data or the production limits: local mode does not enforce the CPU ceiling, does not enforce the subrequest limit, and does not exercise KV's eventual consistency. `--remote` runs the real thing against real bindings, which means a `wrangler dev --remote` session can write to production KV or D1 if the bindings are the production ones — check which environment the command resolves to before running it, and never run `--remote` against production during an audit.

**Do not measure headers, caching, CPU limits, or performance against local `wrangler dev`.** Everything in "known traps" is a production-only behaviour.

## build
For a plain Worker the "build" is esbuild inside `wrangler deploy`; `[build] command` in `wrangler.toml` runs a custom step first. For a framework the adapter compiles the app into a Worker or into Pages Functions.

```bash
wrangler deploy                       # deploys the top-level (production) environment
wrangler deploy --env preview         # deploys the [env.preview] configuration
wrangler deploy --dry-run --outdir=.pre-launch/cf-build   # compile without deploying — read the output, change nothing
wrangler pages deploy dist --project-name <name>
```

`--dry-run --outdir` is the audit-safe way to see what actually ships, including which secrets got inlined by a bundler mistake. Point `--outdir` outside the project tree, as above.

**Configuration facts that bite at build time:**

- **`compatibility_date`** pins the runtime's behaviour. An old date means the Worker runs on old semantics — missing APIs, different `Request`/`Response` behaviour, no `nodejs_compat` niceties — and the app silently behaves differently from the docs everyone is reading. A `compatibility_date` two years stale is a REL-013 finding. `compatibility_flags = ["nodejs_compat"]` is what makes Node built-ins available at all; without it a dependency that imports `node:crypto` fails at deploy or at runtime.
- **Script size limit.** A Worker's compressed bundle has a hard ceiling (commonly quoted at 1 MB on the free plan and 10 MB on paid — check the current limits). A framework app that grows past it fails to deploy with no runtime symptom, and the usual culprit is a large dependency pulled in transitively.
- **Source maps.** `upload_source_maps = true` in `wrangler.toml` uploads source maps to Cloudflare so stack traces in Workers Logs and Tail are readable. They are **not** served publicly, which is the right shape. The SEC-007 question on this stack is therefore about the *client* bundle: a `.map` sitting in a Pages output directory or in the Assets binding is served verbatim and is public source. Fetch one to check rather than reading a config.
- **`[assets]`** (Workers) or the Pages output directory is what gets served statically. `_headers`, `_redirects`, and `_routes.json` must be in that directory to have any effect — a `_headers` file at the repo root that the build does not copy is silently ignored, which is the single most common reason a Cloudflare project has no security headers despite having a `_headers` file.

**Certificates and domains (REL-017).** Cloudflare provisions and auto-renews Universal SSL for a proxied zone, and `*.workers.dev` / `*.pages.dev` are covered automatically. That half of REL-017 is a pass by construction — name the platform. What still needs checking is the **canonical host** (apex-to-www or the reverse), which on Cloudflare is a Redirect Rule or a Page Rule in the dashboard rather than anything in the repo, so an absence of redirects in `wrangler.toml` is not evidence. Confirm with `curl -sI` on both hosts.

And the one that is not automatic: the **SSL/TLS encryption mode** for the zone. "Flexible" encrypts browser-to-Cloudflare and then talks **plain HTTP to your origin** — the padlock is real and the second hop is not. On a Workers-only project there is no origin and this does not apply; on a proxied origin it is a serious finding and it is dashboard-only (SEC-034). "Full (strict)" is the correct setting. Check it and say you checked it.

## env vars
Three kinds of value, and conflating them is the main SEC-001 finding on this platform:

1. **`[vars]` in `wrangler.toml`** — plaintext, committed to the repo, and visible in the dashboard. Correct for a public API base URL, a feature flag, an `ENVIRONMENT` marker. **A secret here is a committed secret** (SEC-001) — and it is easy to do because `[vars]` and secrets are read identically from `env` in the Worker, so the code gives no hint which one a value came from.
2. **Secrets** — `wrangler secret put NAME` (or the dashboard), encrypted at rest, injected into `env` at runtime, and **not readable back**. `wrangler secret list` prints names only. This is the shape ACC-007 passes.
3. **`.dev.vars`** — local only, must be gitignored.

```bash
grep -n -A20 '^\[vars\]' wrangler.toml wrangler.jsonc 2>/dev/null
wrangler secret list                              # names only
wrangler secret list --env preview
git check-ignore -v .dev.vars                     # is it actually ignored?
grep -rn 'SECRET\|TOKEN\|_KEY\|PASSWORD' wrangler.toml wrangler.jsonc 2>/dev/null
```

**Environments** are named blocks in `wrangler.toml`:

```toml
name = "my-worker"
main = "src/index.ts"
compatibility_date = "2025-01-01"

[vars]
ENVIRONMENT = "production"

[[kv_namespaces]]
binding = "CONFIG"
id = "abc123"

[env.preview]
name = "my-worker-preview"

[env.preview.vars]
ENVIRONMENT = "preview"

[[env.preview.kv_namespaces]]
binding = "CONFIG"
id = "def456"
```

**The inheritance rule is the trap and it is worth stating precisely: `vars`, `kv_namespaces`, `r2_buckets`, `d1_databases`, `durable_objects`, and the other binding blocks are *not* inherited by a named environment — they must be redeclared in full.** An `[env.preview]` block that only overrides `name` gets **no** vars and **no** bindings at all, and the Worker fails at runtime on the first `env.CONFIG` access. The inverse mistake is the DAT-017 one: a team that works around this by copying the production `d1_databases` id into `[env.preview]` has pointed the preview Worker at the production database, in a committed file, where it is easy to see once you look. Read every `[env.*]` block and compare its binding ids and `[vars]` against the top-level ones:

- D1 `database_id`, KV `id`, R2 `bucket_name`, Hyperdrive `id`, Queue names
- any `DATABASE_URL`, `SUPABASE_URL`, `REDIS_URL` in `[vars]`
- `STRIPE_SECRET_KEY` and every other payment key — these are secrets, so compare `wrangler secret list --env preview` against the production list by name and confirm the *values* are different by some means other than reading them
- `RESEND_API_KEY` / `SENDGRID_*` — real mail from a preview

Identical ids or identical values between production and preview is the fail. What passes: a separate D1 database, a separate KV namespace, a separate R2 bucket per environment, or no preview environment at all — which is a pass by absence and should be recorded as such. Secrets are stored **per Worker name**, and a named environment produces a differently named Worker, so `wrangler secret put --env preview` is genuinely separate storage — that part is safe by construction.

**Pages** has its own model: environment variables are set per **Production** and **Preview** in the dashboard, with an encrypted flag for secrets. The default when a variable is added to only one environment is that the other has nothing — the opposite failure from Vercel and Netlify, where the default is sharing. Check for a preview build that fails or misbehaves because a variable is missing, as well as for the shared-production-value case.

**HYG-001's scoping half:** for each externally configured URL — OAuth redirect URIs, the auth provider's site URL and redirect allowlist, webhook endpoints — check that the production value is the custom domain and not a `*.workers.dev` or `*.pages.dev` URL. A `*.workers.dev` subdomain stays reachable unless it is explicitly disabled (`workers_dev = false` in `wrangler.toml`), which means the app has a second live hostname nobody is monitoring — see "known traps".

## routes and handlers
A Worker is a single fetch handler; routing inside it is your code's business (Hono, itty-router, a framework adapter, or a hand-written `switch` on `url.pathname`). What Cloudflare decides is **which requests reach the Worker at all**:

```toml
routes = [
  { pattern = "example.com/api/*", zone_name = "example.com" },
  { pattern = "example.com/*", zone_name = "example.com" }
]
workers_dev = false          # disable the *.workers.dev hostname
```

Or a custom domain binding in the dashboard. For Pages, `functions/**` maps to paths file-by-file (`functions/api/users.ts` → `/api/users`), with `functions/_middleware.ts` applying to everything beneath it, and `_routes.json` in the output directory deciding which paths invoke a Function versus being served as a static asset. A misconfigured `_routes.json` `exclude` is why an API path sometimes returns a static 404 instead of running.

```bash
grep -n 'routes\|workers_dev\|pattern\|main\|compatibility' wrangler.toml
ls functions/ 2>/dev/null && find functions -name '*.ts' -o -name '*.js' | head -30
cat dist/_routes.json 2>/dev/null | python3 -m json.tool
```

**The Worker handlers to inventory**, because they answer several checks at once:

| export | what it is | checks |
|---|---|---|
| `fetch(request, env, ctx)` | every HTTP request | the whole SEC domain's surface |
| `scheduled(event, env, ctx)` | Cron Trigger invocation | SEC-014, REL-019 |
| `queue(batch, env, ctx)` | Queue consumer | PERF-013, REL-019 |
| `email(message, env, ctx)` | Email Routing | an input surface people forget to validate |
| `tail(events, env, ctx)` | Tail Worker, consuming another Worker's logs | REL-015 |

**Access control at the edge.** Cloudflare Access (part of Zero Trust) is the platform's way to put an identity check in front of a hostname — the mechanism for protecting a preview or a staging domain. It is dashboard state and invisible in the repo. If a project relies on it, note that a Worker behind Access still receives requests directly if the Worker's `*.workers.dev` hostname or its route is reachable another way, and that the proper server-side check is verifying the `Cf-Access-Jwt-Assertion` header against the team's public keys rather than trusting that Access is in front.

**WAF, Rate Limiting Rules, and Bot Management** are also dashboard state, and they are relevant to SEC-015: a project may legitimately answer "rate limiting is at the edge" rather than in code. Verify it rather than accepting the claim, and note that edge rate limiting does not protect a path reachable on `*.workers.dev`.

## auth
Not applicable for this stack in the application sense — Cloudflare has no notion of your users, and the app's session handling belongs to the framework's stack file. Three platform surfaces matter:

- **Cloudflare Access** (above) — an identity gate in front of a hostname, the right way to protect a preview or staging URL, and dashboard state.
- **API tokens.** `CLOUDFLARE_API_TOKEN` in CI, or a global API key. A global key can do everything on the account and cannot be scoped; a scoped API token with only the permissions the deploy needs is the correct shape, and a global key in a CI secret is a finding on its own (ACC-007, SEC-001). Check `.github/workflows/*` for `cloudflare/wrangler-action` and which credential it uses.
- **Account access** — who can deploy, change secrets, or edit DNS. ACC-001's territory, entirely dashboard state, and on Cloudflare it includes DNS for the whole zone, which is a larger blast radius than most deploy platforms.

## webhook handlers
An ordinary `fetch` handler. Cloudflare facts that change whether one works:

1. **The CPU ceiling applies, but wall time usually does not.** A handler awaiting a slow database or a slow upstream is *not* burning CPU and will not be killed for waiting (see "known traps" for the precise shape). What kills a webhook handler here is heavy synchronous work — a large JSON parse, a big crypto loop, image processing.
2. **The subrequest limit applies.** A handler that fans out to many upstream calls hits a per-invocation cap (commonly 50 on free, 1000 on paid — check the current limits) and the excess calls throw.
3. **`ctx.waitUntil()`** lets you return 2xx immediately and finish the work after — which is the correct shape for a webhook handler that must acknowledge fast — but the work still runs under the same CPU budget and gets no retry and no durability. Anything that must not be lost goes to a Queue.
4. **Read the raw body once.** `request.text()` or `request.arrayBuffer()` consumes the stream; calling `request.json()` first makes signature verification impossible (SEC-051). `request.clone()` is the escape hatch and has its own memory cost.
5. **Node crypto is not there by default.** Signature verification must use WebCrypto (`crypto.subtle`) unless `nodejs_compat` is enabled — which is why a Stripe integration copied from a Node example fails on Workers with a synchronous-crypto error, and why `stripe.webhooks.constructEventAsync` with a `Stripe.createSubtleCryptoProvider()` exists.

Cloudflare's own **notification webhooks** (health-check alerts, security events) post to a URL you configure with a `cf-webhook-auth` header carrying a secret Cloudflare generates. If a project consumes those, compare that header constant-time; a notification endpoint with no check accepts forged alerts.

## webhook verification snippet
WebCrypto HMAC, which is the shape every provider's verification takes on this runtime:

```ts
async function verify(rawBody: string, header: string, secret: string) {
  const key = await crypto.subtle.importKey(
    'raw', new TextEncoder().encode(secret),
    { name: 'HMAC', hash: 'SHA-256' }, false, ['sign'],
  )
  const mac = await crypto.subtle.sign('HMAC', key, new TextEncoder().encode(rawBody))
  const expected = [...new Uint8Array(mac)].map(b => b.toString(16).padStart(2, '0')).join('')
  // constant-time compare — never `expected === header` on a secret (SEC-052)
  if (expected.length !== header.length) return false
  let diff = 0
  for (let i = 0; i < expected.length; i++) diff |= expected.charCodeAt(i) ^ header.charCodeAt(i)
  return diff === 0
}

export default {
  async fetch(req: Request, env: Env) {
    const raw = await req.text()                     // raw bytes, before any JSON parse
    const sig = req.headers.get('x-signature') ?? ''
    if (!await verify(raw, sig, env.WEBHOOK_SECRET)) return new Response('bad signature', { status: 401 })
    const event = JSON.parse(raw)
    // ... handle, then dedup on the event id before any incremental write (PAY-003)
    return new Response('ok')
  },
}
```

For Stripe specifically, use `constructEventAsync` with `Stripe.createSubtleCryptoProvider()` — the synchronous `constructEvent` throws on this runtime. See stripe.md for the tolerance and dedup rules, which are unchanged.

## data access
Cloudflare's own stores, each a **binding** in `wrangler.toml` rather than a connection string — which is a genuinely better shape, because there is no URL to leak:

| store | binding block | what to check |
|---|---|---|
| **D1** (SQLite) | `[[d1_databases]]` with `database_id` | per-environment ids (DAT-017); migrations in `migrations/`, applied with `wrangler d1 migrations apply` |
| **KV** | `[[kv_namespaces]]` with `id` and optional `preview_id` | **eventual consistency** — see below |
| **R2** (object storage) | `[[r2_buckets]]` with `bucket_name` | public access — see below |
| **Durable Objects** | `[[durable_objects.bindings]]` plus a `[[migrations]]` block | strong consistency, single-threaded per object; the right home for a counter or a lock |
| **Queues** | `[[queues.producers]]` / `[[queues.consumers]]` | retries, DLQ, batch size |
| **Hyperdrive** | `[[hyperdrive]]` with an `id` | pooling and caching in front of an external Postgres |
| **Vectorize / AI / Analytics Engine** | their own blocks | the AI domain's territory |

**KV is eventually consistent.** A write is visible immediately in the colo that made it and propagates globally over a window commonly documented as up to about 60 seconds; cached reads can return stale values for the TTL you set. That is fine for configuration and disastrous for anything that must be read-after-write correct — a session store, an idempotency ledger, a rate-limit counter, a "has this webhook already been processed" record. If KV is being used for any of those, that is the finding, and Durable Objects or D1 is the answer (PAY-003 for the webhook case, SEC-015 for the rate limiter). It also has a direct consequence for REL-010: a KV-backed kill switch takes up to that propagation window to take effect everywhere, which is fast enough for most incidents but must be stated rather than assumed instant.

**R2 buckets are private by default.** They become public two ways: enabling the managed `r2.dev` development subdomain, or attaching a custom domain. Both are dashboard state and neither is visible in `wrangler.toml`, so DAT-005 has to be answered in the dashboard or by fetching an object URL. If user uploads land in a bucket with public access on, every object is readable by anyone with the URL, and the URL is often guessable (a sequential id, a filename). Check it explicitly — this is the platform's sharpest data-exposure shape.

**External databases.** Workers cannot open raw TCP sockets in the general case; `connect()` from `cloudflare:sockets` exists and drivers like `postgres.js` and Neon's serverless driver build on it, and Hyperdrive is the supported path for pooling in front of a real Postgres. Without Hyperdrive or an HTTP driver, every isolate opening its own connection exhausts a small instance exactly as on any serverless platform (DAT-008, PERF-018).

**Caching.** The Cache API (`caches.default`) and `fetch(request, { cf: { cacheTtl, cacheEverything } })` cache at the edge under your control, and Cloudflare's zone-level caching rules cache without it. `cacheEverything: true` on a request that returns per-user data, or a cache rule matching an authenticated path, serves one user's response to the next (SEC-036, SEC-011). Zone cache rules are dashboard state; check them, because they are invisible in the repo and they override what your code intended.

## file uploads
There is no framework-imposed body limit on a Worker — the ceiling is Cloudflare's zone-level **maximum upload size**, commonly documented at 100 MB on the Free plan and higher on paid tiers (check the current plan limits). That is far larger than the serverless-function limits on other platforms and it is the reason an upload proxied through a Worker is more often viable here.

R2 is the natural target. Two shapes:

- **Proxied through the Worker** — `await env.BUCKET.put(key, request.body)`, streaming, which works up to the zone limit. Validate content type and size in the handler; the platform will not do it for you below its own ceiling.
- **Presigned direct-to-R2** — R2's S3-compatible API supports presigned URLs, generated by the Worker with the account's access key, so the bytes never touch your code. This is the shape that scales and it is what PERF-020's fix path recommends.

For multipart uploads over the single-request ceiling, R2's multipart API is the mechanism.

DAT-005 applies to the destination bucket, above.

## background jobs
**Cron Triggers.** Declared in `wrangler.toml` and handled by the `scheduled` export:

```toml
[triggers]
crons = ["0 3 * * *", "*/15 * * * *"]
```
```ts
export default {
  async scheduled(event: ScheduledController, env: Env, ctx: ExecutionContext) {
    ctx.waitUntil(doTheJob(env))       // waitUntil, or the isolate may be torn down early
  },
}
```

The platform fact that decides SEC-014 here: **a Cron Trigger invokes the `scheduled` handler internally. It is not an HTTP request, there is no public URL for it, and there is no shared secret to check.** That makes SEC-014 a pass by construction for a Cron Trigger — record it with the mechanism named rather than as an unexplained pass. The `scheduled` handler is genuinely unreachable from the internet; the only way to invoke it externally is `wrangler dev` with `--test-scheduled`, which is a local development affordance.

**Check the other half, though.** If the project instead exposes a job as an HTTP path (`/api/cron/*`) called by GitHub Actions, an external scheduler, or a `curl` in someone's crontab, that path is fully public and does need a secret guard exactly as SEC-014 describes, with a constant-time comparison (SEC-052). Both shapes appear on this platform, and the second is common where the job needs to outlive a Worker invocation.

Other REL-019 properties:
- Cloudflare does not retry a failed `scheduled` invocation and does not alert on one. Unless the handler pings a dead-man's-switch (Cronitor, Healthchecks.io, Sentry Cron Monitors), a job that stopped running two weeks ago is indistinguishable from one that works. Its absence is the finding. Workers Logs and the dashboard's Cron Triggers view show past invocations, which helps after the fact but alerts nobody.
- The number of cron triggers per Worker and the finest granularity are plan-dependent — check the current limits.
- A cron invocation runs under the same CPU budget as a request. Long or heavy work belongs in a Queue.
- Overlap: a slow job whose next scheduled invocation begins before the previous finished simply runs twice. There is no platform lock; a Durable Object is the right place to build one (REL-019).

**Queues** (`[[queues.producers]]` / `[[queues.consumers]]`) are the real durable-work mechanism: configurable batch size, batch timeout, `max_retries`, and a dead-letter queue. If a project has long or unreliable work and no queue, that is PERF-013's recommendation. If it has a queue with no `dead_letter_queue` configured, failed messages are dropped after the retry count — worth a line.

**Kill switch (REL-010).** The natural shape is a value in KV read at the top of the `fetch` handler, or a `[vars]` value (which needs a redeploy — seconds on Workers, but still a deploy). KV is the right choice, with the caveat above: propagation is quick but not instantaneous, and a `cacheTtl` on the read multiplies that delay by the TTL. Say which the project has and what its actual latency is; "we can turn it off" meaning "within a minute, per colo" is a fine answer as long as it is the stated one. A Durable Object read gives strong consistency at the cost of a round trip on every request.

## error handling and logging
**Logs.**
```bash
wrangler tail                                  # live stream of a Worker's requests, logs, and exceptions
wrangler tail --format=json --status=error
wrangler tail --env preview
wrangler pages deployment tail --project-name <name>
```

`wrangler tail` is live-only: it shows what happens while it is attached and nothing before. **Persistent logs need Workers Logs enabled** (`[observability] enabled = true` in `wrangler.toml`, with a configurable `head_sampling_rate`) or **Logpush** to an external destination on paid plans. Retention for Workers Logs is short and plan-dependent — check the current figure. For REL-015 the consequence is concrete: with no `[observability]` block and no Logpush, the day after an incident there is nothing to read, and that is the finding regardless of how good the log lines are.

```bash
grep -n -A5 'observability' wrangler.toml
```

`console.log` in a Worker goes to Tail and to Workers Logs when enabled. There is no request id you get for free beyond the `cf-ray` header — attach it (`request.headers.get('cf-ray')`) to every log line, or concurrent invocations interleave into nonsense (REL-015).

**Uncaught exceptions.** A Worker that throws returns Cloudflare's error page with a `1101` (Worker threw an exception) or `1102` (exceeded CPU) code and no application error. Those codes are the diagnostic: a `1102` in the logs is PERF-020's CPU ceiling, not a bug in your handler's logic. Wrap the handler in a try/catch that reports to the error tracker and returns your own response, or the user sees Cloudflare's page and your tracker never runs.

**Error tracking (REL-001).** `@sentry/cloudflare` or Toucan-JS. The Workers runtime is neither Node nor a browser, so the generic Node SDK will not work — check the right SDK is installed. `ctx.waitUntil(sentry.flush())` matters here more than elsewhere: the isolate can be torn down the moment the response is returned, and an unflushed event is simply lost. A Sentry setup with no flush in `waitUntil` reports intermittently and looks like a flaky integration.

**Tail Workers** (a Worker with a `tail` export, bound to another Worker) let you process another Worker's logs in code — a legitimate way to ship structured logs somewhere on a plan without Logpush.

**Source maps (SEC-007).** `upload_source_maps = true` sends Worker source maps to Cloudflare, not to the public — that is correct and is not the finding. The finding is a client-side `.map` in the static assets directory, which is served verbatim:
```bash
curl -s -o /dev/null -w '%{http_code}\n' https://example.com/assets/<bundle>.js.map
```

## security headers
Three places, and which one applies depends on whether the response came from the Worker or from static assets:

1. **In the Worker**, on the `Response` — the only place a per-request CSP nonce can be generated, and the only place that covers dynamic responses:
```ts
const res = await handle(request)
const out = new Response(res.body, res)
out.headers.set('Content-Security-Policy', `default-src 'self'; frame-ancestors 'none'; base-uri 'self'; object-src 'none'`)
out.headers.set('Strict-Transport-Security', 'max-age=63072000; includeSubDomains; preload')
out.headers.set('X-Content-Type-Options', 'nosniff')
out.headers.set('Referrer-Policy', 'strict-origin-when-cross-origin')
out.headers.set('Permissions-Policy', 'camera=(), microphone=(), geolocation=()')
return out
```
2. **`_headers`** in the Pages output directory (or the Workers Assets directory), for static responses:
```
/*
  X-Content-Type-Options: nosniff
  Referrer-Policy: strict-origin-when-cross-origin
```
The file must be **in the published output directory**, not at the repo root — a `_headers` at the root that the build does not copy is silently ignored, and that is the most common reason a Cloudflare project has no headers despite appearing to configure them.
3. **Transform Rules / Managed Transforms in the dashboard**, which add or modify response headers at the zone level for every request through Cloudflare — including requests to an origin that is not a Worker at all. **This is invisible in the repo**, so a header can be present in production with nothing in the code explaining it, and equally a header the code sets can be stripped or overridden. Read the actual response before concluding anything:

```bash
curl -sI https://example.com/ | tr -d '\r'
curl -sI https://example.com/favicon.ico | tr -d '\r'         # the static half
curl -sI https://example.com/api/<a safe GET> | tr -d '\r'    # the dynamic half
```

For SEC-031 and SEC-033, check all three sources before reporting a header absent, and say which one you found it in. Cloudflare also has **Managed Transforms** presets ("Add security headers") that set a subset automatically when enabled — another dashboard-only explanation for headers that appear from nowhere.

HTTPS: Universal SSL covers a proxied zone and `workers.dev`/`pages.dev`, and an "Always Use HTTPS" zone setting handles the redirect. SEC-034's redirect half is usually a pass; confirm with `curl -sI http://example.com` and check the SSL/TLS mode as described under "build" — a Flexible zone is the finding that matters.

## known traps
- **CPU time, not wall time, is what Workers limit.** The commonly quoted figures are 10 ms CPU per invocation on the Free plan and a 30-second CPU default on paid, raisable via a `[limits] cpu_ms` setting up to a plan ceiling. **Check the current plan limits.** The consequence is the opposite of every other serverless platform: a handler that awaits a slow database for twenty seconds is fine (it is not using CPU), while a handler that parses a large JSON payload or runs a crypto loop can be killed in milliseconds. Exceeding it produces a `1102` error. PERF-020 — and note in evidence that the ceiling is CPU, because a duration-based analysis of the handlers will reach the wrong conclusion here.
- **Request body limit** at the zone level, commonly documented at 100 MB on the Free plan and higher on paid tiers. Check the current plan limits. PERF-020.
- **Subrequest limit per invocation**, commonly quoted at 50 on the free plan and 1000 on paid. A handler that fans out over a list will throw partway through, and the failure looks like an intermittent upstream error. Check the current limits. PERF-020's "other ceilings" clause.
- **Script size limit** (commonly 1 MB compressed on free, 10 MB on paid — check current). A framework app that grows past it fails to deploy, with no runtime symptom to debug.
- **`[env.*]` does not inherit `vars` or bindings.** A named environment must redeclare all of them, and the workaround — copying the production `database_id` or KV `id` into `[env.preview]` — points the preview at production data in a committed file: DAT-017. Read every `[env.*]` block and diff the ids.
- **`[vars]` holding a secret**: SEC-001, committed and visible in the dashboard. The code reads `[vars]` and secrets identically, so nothing in the handler tells you which a value came from — the config file is the only place to look. `.dev.vars` committed is the same finding.
- **Workers have no built-in environment marker.** Without an explicit `ENVIRONMENT` var, code cannot tell production from preview, so every "only in development" guard is either always on or always off. Pages gets `CF_PAGES_BRANCH`, Workers get nothing. HYG-001, DAT-017.
- **`*.workers.dev` stays live unless `workers_dev = false`.** The Worker is reachable on a second hostname that bypasses your custom domain's Access policy, WAF rules, rate limiting rules, and any Transform Rule that adds security headers. This is one of the more consequential platform defaults and it is one line in `wrangler.toml`. SEC-010 for the access-control half, SEC-031 for the headers half, SEO-004 for the duplicate-content half — a `*.workers.dev` or `*.pages.dev` host serving the same content as the production domain is indexable and can outrank it unless it is disabled or noindexed.
- **`*.pages.dev` preview deployments are publicly reachable and indexable by default.** Cloudflare Access is the mechanism for gating them, and it is dashboard state. Verify with a logged-out `curl -I` on a preview URL and check for `x-robots-tag` rather than assuming a default. A public preview holding production data is DAT-017 and SEC-010 together; an indexable one is SEO-004.
- **KV eventual consistency.** Writes propagate over a window commonly documented at up to about a minute, and a `cacheTtl` on a read extends it. KV used for a session store, an idempotency ledger, a rate-limit counter, or a "already processed this webhook" record is the finding — PAY-003 for the webhook case, SEC-015 for the rate limiter. Durable Objects or D1 for anything read-after-write.
- **A KV-backed kill switch is not instant.** State the real latency. REL-010.
- **R2 public access is dashboard state.** A bucket with the `r2.dev` subdomain enabled or a custom domain attached serves every object to anyone with the URL, and `wrangler.toml` shows nothing. DAT-005 — check the dashboard or fetch an object URL.
- **`caches.default` / `cacheEverything` on a per-user response**, or a zone cache rule matching an authenticated path: SEC-036, SEC-011. Zone cache rules are invisible in the repo and override your code's intent.
- **SSL/TLS mode set to Flexible** on a proxied origin: the browser-to-Cloudflare hop is encrypted and the Cloudflare-to-origin hop is plain HTTP. The padlock is real and the connection is not. SEC-034 — dashboard-only, and it does not apply to a Workers-only project.
- **`x-forwarded-for` trusted instead of `cf-connecting-ip`.** The former is client-supplied and forgeable; the latter is set by Cloudflare. Any rate limiter, audit log, or geo-gate keyed on the wrong one is trivially bypassed: SEC-015.
- **A stale `compatibility_date`** means the Worker runs old runtime semantics while everyone reads current docs: REL-013. A missing `nodejs_compat` flag is why a dependency importing `node:*` fails.
- **Node crypto assumed available.** Signature verification must use WebCrypto unless `nodejs_compat` is on; Stripe's synchronous `constructEvent` throws on this runtime and `constructEventAsync` with a SubtleCrypto provider is the fix. SEC-051.
- **Cron Triggers are internal and have no public URL**, which makes SEC-014 a pass by construction for them — record it with the mechanism named. But **an HTTP job path called by an external scheduler is fully public** and does need a guard, with a constant-time compare (SEC-014, SEC-052).
- **Nothing monitors a `scheduled` invocation.** No retry, no alert; unless the handler pings a dead-man's-switch, a job that stopped two weeks ago looks identical to one that works: REL-019.
- **A Queue with no `dead_letter_queue`** drops messages after `max_retries`: REL-019.
- **`ctx.waitUntil()` treated as a queue.** It extends the invocation past the response but shares the CPU budget and offers no retry, ordering, or durability: PERF-013.
- **Sentry without `ctx.waitUntil(flush())`** loses events when the isolate is torn down at response time, which looks like a flaky integration rather than a configuration bug: REL-001.
- **No `[observability]` block and no Logpush** means logs exist only while `wrangler tail` is attached: REL-015.
- **`_headers` / `_redirects` / `_routes.json` outside the published output directory** are silently ignored: SEC-031, SEC-033.
- **Transform Rules and Managed Transforms set headers invisibly**, so the repo is not the whole answer for SEC-031/SEC-033 in either direction. Read the response.
- **Connection exhaustion against an external Postgres** without Hyperdrive or an HTTP driver: DAT-008, PERF-018.
- **Much of this platform is dashboard state.** R2 public access, Access policies, WAF and rate-limiting rules, cache rules, Transform Rules, SSL/TLS mode, DNS, and Logpush have no repo representation. `not determinable from the repo; confirm in the Cloudflare dashboard` is a legitimate and honest finding — an invented default is not.

## runtime probe hints
**Establish what you are probing and where it runs.**
```bash
wrangler whoami                                  # authenticated? which account?
wrangler deployments list
wrangler versions list
wrangler secret list                             # names only, no values
grep -n 'compatibility_date\|workers_dev\|routes\|main\|observability' wrangler.toml
curl -sI https://example.com/ | tr -d '\r'
```
Useful response headers: `cf-ray` (the request handle — its suffix names the colo that served it), `cf-cache-status` (`HIT`, `MISS`, `DYNAMIC`, `BYPASS` — the caching probe for SEC-036), `server: cloudflare`, and `age`.

**Is the `workers.dev` or `pages.dev` host live?** This is the highest-value probe on this platform, because a live one bypasses everything configured on the custom domain:
```bash
curl -sI https://<worker-name>.<subdomain>.workers.dev/ | tr -d '\r' | head -20
curl -sI https://<project>.pages.dev/ | tr -d '\r' | head -20
curl -sI https://<branch>.<project>.pages.dev/ | tr -d '\r' | grep -iE 'HTTP/|x-robots-tag|cf-access'
```
A 200 with your app on any of those means the app has a second public hostname. Compare its headers against the custom domain's — missing security headers there is SEC-031, and reachability there when the custom domain is behind Access is SEC-010.

**CPU ceiling, measured rather than assumed** (against a preview environment, never production, and only on an endpoint safe to call):
```bash
curl -s -o /dev/null -w 'status=%{http_code} total=%{time_total}\n' https://<preview>/api/<a compute-heavy but safe endpoint>
wrangler tail --env preview --format=json --status=error       # watch for 1102 (CPU exceeded) and 1101 (exception)
```
A `1102` in the tail output is the ceiling being hit. Record the observed behaviour alongside the documented limit and say which is which.

**Body limit.** Opt-in: ask before generating a file this large.
```bash
head -c 120000000 /dev/zero | tr '\0' 'a' > .pre-launch/probe-body.bin   # just over 100 MB
curl -s -o /dev/null -w '%{http_code}\n' -X POST https://<preview>/api/<upload> \
  -H 'content-type: text/plain' --data-binary @.pre-launch/probe-body.bin
rm -f .pre-launch/probe-body.bin
```
A 413 from Cloudflare rather than your handler confirms the zone limit. Delete the file afterwards, as the last line does.

**Job endpoints (SEC-014).** A Cron Trigger has no public URL, so there is nothing to probe — record that as the mechanism. For any HTTP job path, call it with no `Authorization` header and expect 401:
```bash
curl -s -o /dev/null -w '%{http_code}\n' https://example.com/api/cron/<path>
```
A 200, or any evidence the job ran, is the finding. Do not then call it with the real secret.

**R2 public access (DAT-005).** If a bucket has a public `r2.dev` subdomain or a custom domain, an object URL will resolve without credentials:
```bash
curl -sI https://<public bucket host>/<a known object key> | tr -d '\r' | head -5
```
A 200 on a user-uploaded object is the finding. If no public host is configured, the bucket is private and the check passes — say which you established and how.

**Headers (SEC-031, SEC-033).** Check a static path, a Worker-generated path, and — if reachable — the `workers.dev` host, since all three can differ:
```bash
for u in https://example.com/ https://example.com/api/health https://<worker>.<sub>.workers.dev/; do
  echo "== $u"; curl -sI "$u" | tr -d '\r' | grep -iE 'content-security-policy|strict-transport|x-content-type|referrer-policy|permissions-policy'
done
```

**Domains, certificates, and SSL mode (REL-017, SEC-034).**
```bash
curl -sI https://www.example.com | tr -d '\r' | head -5
curl -sI http://example.com | tr -d '\r' | head -5
echo | openssl s_client -connect example.com:443 -servername example.com 2>/dev/null | openssl x509 -noout -dates -issuer
```
Universal SSL renews automatically, so the `notAfter` date is informational. The SSL/TLS **mode** cannot be read from the outside — a Flexible zone looks identical to a Full one from the browser's side, which is exactly why it is dangerous. It is dashboard-only; say so.

**Logs.** `wrangler tail` is live-only and shows nothing that happened before you attached. If `[observability]` is off and there is no Logpush, then "what happened at 3am yesterday" has no answer, and that is REL-015's finding rather than a failure to investigate.

**Never** run `wrangler deploy`, `wrangler secret put`, `wrangler d1 execute` against a production database, `wrangler kv key put`, or `wrangler dev --remote` bound to production resources during an audit. Everything above is read-only apart from the deliberate negative probes, and those run against a preview environment.
