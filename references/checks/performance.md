# Performance checks (PERF)

Read `agents/domain-auditor.md` for procedure. Blocks below are checks; consult stack references for locations. Tools: `npx autocannon` on Node projects or `k6 run` elsewhere (PERF-001, 002, 015); `npx lighthouse` (PERF-011, 018); a bundle analyser — `npx source-map-explorer`, `@next/bundle-analyzer`, `npx vite-bundle-visualizer` (PERF-006, 007); `curl` for single-response headers and `python3 scripts/probe_url.py <url>` when a full header dump is wanted (PERF-003, 004, 005, 010, 016); the stack's slow-query log or `explain (analyze, buffers)` (PERF-012).

**This domain runs last, and that ordering is a safety property, not a preference.** These are the only checks that deliberately generate traffic. Run them earlier and they exhaust the shared test account's rate limits (SEC-015, SEC-017 exist precisely to make that happen) and every later domain probes an app that is throttling it, turning real findings into false failures. Nothing scheduled after this domain needs the test account un-throttled, so spending its budget here is safe. Stay inside the budget anyway: if a limiter returns 429 for most of a load run, you have measured the limiter, not the app — record that, lower the concurrency, and say so in evidence.

**Load goes to `local.url` only. Never `remote.url`.** A staging or preview deployment normally shares a database, a rate limiter, a mail provider, an AI account, or a payment sandbox quota with production, and load against it is an outage you caused with your own hands. The remote-tier checks in this file (PERF-005, PERF-010, PERF-016) are single requests or a handful of them, spaced out — never a load. If `local.url` is not in the live tiers, a load-generating check does not fall back to remote; it falls back to its `static` entry with `verified_by: static-fallback`.

**What may go in the load set.** Only GET or otherwise idempotent endpoints. Never an endpoint that mutates state or spends money: checkout, subscribe, invite, email or SMS send, AI/LLM calls, export or PDF generation, file upload, anything that writes a row per call. Two thousand requests at a checkout route is two thousand payment intents and a support ticket; the same at an AI route is a bill. Where a paid-provider or write endpoint has to be measured at all, measure it with one or two timed single requests under the test account, and only when the environment's keys are detectably test-mode (stack ref: "env vars": `sk_test_`, a sandbox or test API key, a mail catcher such as Mailhog/Mailpit as the SMTP host). If the keys look live, do not send the request at all — record `error: live keys detected` for that endpoint and keep the rest of the run.

**Measure a production build, never the dev server.** `local.start` defaults to something like `npm run dev`, and a dev server is a different application for every purpose in this file: it does not compress, it serves assets `no-cache` on purpose, its bundles are unminified with dev-only warning machinery, and it compiles each route on first request so the first hit is many times slower than the second. Applying production thresholds to it produces false failures on PERF-001, 003, 004, 011, and 018. So before any local-tier measurement in this domain: build and start the app in production mode on a port you record — `npm run build && PORT=<port> npm start` with `NODE_ENV=production` for a typical Node stack, and the equivalent for this one (stack ref: "build" for the build and production start commands, "dev server" for the port convention) — and use *that* URL for every measurement in this domain, noting it in evidence alongside `local.url`. If a production build cannot be run (the build fails, a required env var is missing, the stack has no separate production mode), do not silently measure the dev server as if it were production: record every local measurement in this domain as `dev-server only` in `notes`, and do not fail the app on compression, cache headers, bundle minification, or Web Vitals on that basis — report the numbers as indicative and say what could not be built.

**Missing tools.** If a load tester, Lighthouse, or an analyser is absent and the user declined installing it (config `tools.declined`), do not stop and do not mark the whole check `error`. Run the block's `static` entry, decide from that evidence, and set `verified_by: static-fallback` with a note naming the tool you did not have. A static-fallback `pass` is weaker than a measured one; say so in `notes`.

### PERF-001 Load test key endpoints; record p50/p95/p99 and error rate
severity: high
tier: local
fix: none
why: The first real traffic spike is the wrong time to learn that the dashboard query takes four seconds under ten concurrent users. This check produces no fix of its own — it produces the numbers that PERF-002, PERF-011, PERF-012, and PERF-015 all cite, so run it even when you expect it to pass.
verify:
  static: Identify the five endpoints that matter and record them in evidence even when the local tier is unavailable: the landing page, the authenticated home or dashboard, the heaviest list endpoint (the one joining the most tables or rendering the most rows — see DAT-010 and DAT-011), the checkout or primary conversion action, and one write endpoint (stack ref: "routes and handlers"). For each, note the method, path, whether it needs a session, and whether it is idempotent. Mark each one `load-safe` (GET or idempotent, no paid provider in its path) or `single-request only` (writes, bills, or sends). That classification is the load set; everything not marked `load-safe` stays out of it.
  local: Against `local.url` only — never `remote.url`, and against a production build per the header rule, not the dev server, whose per-route compile inflates the first request and whose latency is not the app's. Node projects: for each load-safe endpoint run `npx autocannon -c 20 -d 20 -H "cookie: <test session cookie>" <local.url><path>`, where `-c` is concurrent connections and `-d` is duration in seconds. Add `--renderStatusCodes` to get the non-2xx breakdown if your version has it (`npx autocannon --help`). Non-Node stacks, or where autocannon is unavailable: `k6 run --vus 20 --duration 20s <script>` with a script that hits the same paths and sets the same cookie; check `k6 --help` for the summary-statistics flag your version uses, since the percentile output is configurable. Record requests/sec, p50, p95, p99 latency, and the non-2xx count per endpoint. For each `single-request only` endpoint, send one timed request instead (`curl -s -o /dev/null -w '%{time_total}\n'`) under the test account and only with test-mode keys, and label the row `single request, not load-tested`. Status is `pass` when every load-safe endpoint's p95 is under 1000 ms and its error rate is under 1%; `fail` otherwise. Record the numbers either way — a passing run still feeds four other checks. If neither autocannon nor k6 is available and the user declined installing them, do not mark this `error`: report the endpoint inventory and classification from the static entry, note that no latency was measured, and set `verified_by: static-fallback` so PERF-002 knows what it is reading.
evidence: one table row per endpoint — method, path, rps, p50, p95, p99, non-2xx count, and `load` or `single request`; plus the tool name, its exact flags, the concurrency used, and whether any run hit a 429 wall.

### PERF-002 Slowest endpoints and single-dependency bottlenecks identified
severity: high
tier: local
fix: guided
why: A p95 of three seconds is a symptom; the cause is almost always one thing — an unindexed query, a synchronous third-party call, or an AI request sitting in the request path. Naming the specific line is the difference between a fix and a rewrite.
verify:
  static: Take the two or three slowest endpoints and read their handlers end to end (stack ref: "routes and handlers"). Trace every outbound call in the request path and list it: database queries (count them; a number that grows with rows is DAT-010's N+1), HTTP calls to third parties, storage reads, cache lookups, auth or session verification round trips, and anything awaiting an AI provider. For each, note whether it is sequential or parallel — a handler doing four independent `await`s in a row costs their sum, not their max, and `Promise.all` (or `asyncio.gather`, `Async::Barrier`) makes it the max. Flag any single dependency the whole request blocks on: one slow provider call with no timeout is both this check's bottleneck and PERF-014's finding. Work that does not need to be in the request path at all is PERF-013's finding; cross-reference rather than duplicating.
  local: Read PERF-001's evidence table and rank the endpoints by p95. If PERF-001 ran only its static entry — the load tester was missing or `local.url` was not live — do not skip this check and do not invent numbers: rank instead by the static complexity you can see (query count, number of outbound calls, absence of pagination), state in `notes` that the ranking is static and unmeasured, and set `verified_by: static-fallback`. Where PERF-001 did produce numbers, confirm the cause by timing the parts: log or instrument the handler's individual awaits for a few single requests against `local.url` (a `console.time`/`performance.now()` pair, the framework's server-timing header, or the ORM's query log with timestamps), then re-request that one endpoint a handful of times. Do not re-run a full load test for this; PERF-001's numbers are the load measurement.
evidence: per slow endpoint — `<method> <path> p95=<n>ms` then the ranked contributors with file:line and measured or estimated cost each (`db query at api/orders/route.ts:42 — 1400ms of 1800ms`); explicitly note when the ranking is static-only.
fix_hint: Fix the single largest contributor first and re-measure before touching anything else — parallelise the independent awaits, add the index (DAT-009), or move the work off the request path (PERF-013). Re-run PERF-001 on that one endpoint afterwards so the report carries a before and after.

### PERF-003 Text responses including JSON compressed (brotli/gzip)
severity: medium
tier: local
fix: easy
why: HTML, JS, CSS, and JSON compress by roughly 70-90%, so an uncompressed API response costs the user four times the bytes and the mobile user four times the wait. It is one config line and people still ship without it.
verify:
  static: Find where compression is configured (stack ref: "build", "routes and handlers"): Next.js `compress` in `next.config`, `compression()` middleware in Express, `GZipMiddleware` in FastAPI, `Rack::Deflater`, `django.middleware.gzip.GZipMiddleware`, `gzip on`/`brotli on` in an nginx or Caddy config, or the CDN's edge compression setting. Note which layer is expected to do it — that matters for reading the local result.
  local: Against `local.url`, and against a production build per the header rule — most dev servers do not compress at all, so measuring one here is a guaranteed false fail. Request one page and one JSON API response and read the headers: `curl -s -o /dev/null -D - -H 'Accept-Encoding: br, gzip' <local.url>/` and the same for an API path. Use `-D -` on a GET rather than `-I`, because some servers skip compression on HEAD and you will get a false fail. Pass requires `content-encoding: br` or `gzip` on every `text/*` and `application/json` response larger than about 1 KB. Already-compressed binaries (images, video, fonts, zip) correctly have no `content-encoding` and are not a fail. If compression happens only at the CDN edge, the local response legitimately shows none — record that, verify the CDN setting in config, and mark it `pass` with a note rather than a fail.
evidence: per response — `GET <path> → content-encoding: <value or absent>, content-type, content-length`; plus the config file:line and which layer compresses.
fix_hint: Enable the stack's compression middleware or the platform's edge compression, prefer brotli with gzip as the fallback, and exclude already-compressed content types so you are not spending CPU to make images slightly larger.

### PERF-004 Cache-Control correct per asset type; hashed static assets immutable
severity: medium
tier: local
fix: easy
why: A content-hashed bundle can be cached forever and never needs revalidating; served with `no-cache` it is re-downloaded on every visit. The mirror-image mistake is worse: an HTML page or a private API response cached for a year, so users see stale content and shared caches may hand one user's data to another.
verify:
  static: Find where cache headers are set (stack ref: "build", "security headers", "routes and handlers") — framework defaults, a `headers()` config block, CDN rules, or explicit `res.setHeader` calls. List which paths each rule covers.
  local: Against `local.url`, and against a production build per the header rule — a dev server deliberately serves everything `no-cache` and has no hashed asset filenames to test, so it cannot answer this check at all. Dump headers for one of each kind: a hashed static asset from the build output (a `.js` or `.css` with a hash in the filename), an unhashed public asset (a logo, a favicon), an HTML page, and an authenticated JSON API response. Use `curl -s -o /dev/null -D - <url>` for each; send the test session cookie on the authenticated one. Expected: hashed assets `public, max-age=31536000, immutable`; unhashed public assets a short max-age with revalidation (`public, max-age=3600` plus an `etag` or `last-modified`); HTML `no-cache` or a short max-age plus revalidation so a deploy is visible immediately; authenticated or user-specific JSON `private, no-store` (or at minimum `private, no-cache`). Fails: any authenticated response with `public` in `cache-control` — that is a shared-cache leak and worth calling out loudly; a hashed asset with `no-cache`; HTML with a long max-age and no revalidation. Note whether a CDN header (`age`, `x-vercel-cache`, `cf-cache-status`) is present, which is PERF-005's evidence too.
evidence: per asset type — `GET <path> → cache-control: <value>` with the expected value beside it; the config file:line for each rule; any authenticated response marked `public`.
fix_hint: Set `public, max-age=31536000, immutable` on the hashed build output path, `private, no-store` on authenticated API routes, and leave HTML at `no-cache` with an ETag; put the rules in the framework's headers config so the CDN inherits them rather than setting them per handler.

### PERF-005 Static assets served via CDN
severity: medium
tier: remote
fix: guided
why: Serving your own JS, CSS, and images from the origin means every user in another continent pays a full round trip per file, and a traffic spike hits your server for bytes that never change.
verify:
  static: Read the deploy configuration (stack ref: "build", "known traps") for a CDN in front of the app — Vercel and Netlify put one there by default, Cloudflare in front of a custom origin, CloudFront over an S3 bucket, a `assetPrefix`/`base`/`ASSET_HOST` setting pointing at a CDN hostname. Also note where user-uploaded media is served from (stack ref: "file uploads"): a storage bucket read directly by the browser without a CDN in front is the common gap.
  remote: Single requests only — this is not a load test and `remote.url` is never load-tested. Fetch the deployed page (`curl -s <remote.url>`), extract the `src`/`href` of the first-party scripts, stylesheets, and a couple of images, and request two of them twice each with `curl -s -o /dev/null -D - <asset url>`. Look for a CDN cache header and a hit on the second request: `x-vercel-cache: HIT`, `cf-cache-status: HIT`, `x-cache: Hit from cloudfront`, `x-nf-request-id` plus an `age` that increments, or a `server` header naming the CDN. `MISS` on both requests for the same immutable asset means it is not being cached; a complete absence of any CDN header means the origin is serving it. Check the uploaded-media host the same way. Space the requests out; a handful is enough.
evidence: per asset — `GET <asset url> → <cdn header>: <value>, age: <n>` for both requests; the asset hostnames; the config file:line naming the CDN or its absence.
fix_hint: Put the static asset path and the media bucket behind the platform's CDN (or Cloudflare in front of the origin), confirm PERF-004's `immutable` header is set so the CDN can actually keep them, and re-request twice to see a HIT.

### PERF-006 CSS/JS minified; production build used
severity: medium
tier: static
fix: easy
why: A development build ships unminified source, dev-only warning machinery, and in React's case a runtime several times larger and measurably slower. Shipping one is usually an environment variable nobody set, not a decision.
verify:
  static: Run the project's production build (stack ref: "build") if a build output directory is not already present, then inspect it. Minification: the largest JS and CSS files should be near-single-line with mangled identifiers; readable multi-line code with comments and original variable names is a fail. Production mode: grep the built JS for development markers — the string `process.env.NODE_ENV` left unreplaced, React's `react-dom.development.js` or its "You are running a development build" warning text, Vue's `__VUE_PROD_DEVTOOLS__` enabled, `__DEV__` truthy, verbose `console.debug` scaffolding. Confirm the deploy actually runs the production command and not the dev server: check the CI/deploy config and any `Dockerfile` `CMD` for `next dev`, `vite`, `nodemon`, `FLASK_DEBUG`, `DEBUG = True` in Django settings, or Rails `RAILS_ENV` unset. A Django `DEBUG = True` in production is also a security finding; note it and let the security domain own it.
evidence: the build command run and its output directory; file and size of the largest JS/CSS bundles with a one-line excerpt showing minified or unminified content; file:line of any development marker or dev start command in the deploy config.
fix_hint: Build with the framework's production command and `NODE_ENV=production` (or the stack's equivalent), change the deploy or container start command to the production server, and rebuild so the shipped artifact is the minified one.

### PERF-007 Bundle size within budget; code splitting; no dev deps in prod bundle
severity: medium
tier: static
fix: guided
why: JavaScript is the most expensive kind of byte — it has to be downloaded, parsed, and executed before the page responds to a tap, and a mid-range phone does that several times slower than your laptop. One accidental import of a charting library into the landing page can double the entry bundle.
verify:
  static: Build (stack ref: "build") and measure. List the largest chunks with their raw and gzipped sizes; `find <build dir> -name '*.js' -size +100k -exec ls -lh {} +` gets you started, and the framework's own build summary (Next.js prints First Load JS per route; Vite prints per-chunk gzip sizes) is better where it exists. Then attribute the weight: `npx source-map-explorer '<build dir>/**/*.js'`, `ANALYZE=true <build command>` with `@next/bundle-analyzer` if it is installed, or `npx vite-bundle-visualizer`. Budgets to judge against, gzipped, for the entry/first-load JS: under about 200 KB for a marketing or content page, under about 300 KB for an authenticated app shell. State the budget you used. Code splitting: confirm heavy, below-the-fold, or route-specific things are lazily loaded (`next/dynamic`, `React.lazy`, dynamic `import()`, route-level chunks) rather than all in the entry — rich text editors, chart libraries, map SDKs, PDF generators, and date-picker suites are the usual passengers. Finally, dev dependencies in the production bundle: check the analyser output and `package.json` for test, mock, or fixture libraries (`@faker-js/faker`, `msw`, testing-library, `chai`) reachable from app code, and for whole-library imports where a subpath exists (`import _ from 'lodash'`, `import moment from 'moment'` with all locales, all of `@aws-sdk` for one call). A dev-only package listed under `dependencies` is not itself a fail unless something in the shipped graph imports it — say which.
evidence: the largest chunks with gzipped sizes and the budget you compared against; the top contributors from the analyser with their sizes; per offender — `<package> — <size> gzipped, imported at file:line`; the lazily-loaded routes or components you confirmed.
fix_hint: Lazy-load the heaviest non-critical modules behind a dynamic import, switch whole-library imports to subpath or per-function imports, replace `moment` with a smaller date library or drop its locales, and re-run the analyser to confirm the entry chunk actually shrank.

### PERF-008 Images compressed, modern formats, responsive srcset, lazy below fold, dimensions set
severity: medium
tier: static
fix: easy
why: Images are usually most of a page's bytes, and an unoptimised hero is normally the LCP element — so it is the single thing that decides PERF-011's headline number. Missing width and height is the other half: the browser cannot reserve the space, so everything below jumps when the image lands, which is the layout shift users feel and CLS measures.
verify:
  static: Find every image the app serves — the `public`/`static` directory, imported assets, and the components that render them (stack ref: "file uploads" for user-uploaded media). Four things per image: (1) Weight and format. `find <public dir> -type f \( -name '*.png' -o -name '*.jpg' -o -name '*.jpeg' \) -size +200k -exec ls -lh {} +` lists the obvious offenders; anything over a few hundred KB for a web image is a fail. Modern formats — WebP or AVIF, either directly or via the framework's image component which negotiates them — should be in use for photographic content; a PNG screenshot at full resolution is the classic miss. (2) Responsive sources: a `srcset` with `sizes`, a `<picture>` with sources, or a framework image component (`next/image`, `nuxt-img`, `astro:assets`, Cloudinary/imgix URL transforms) that generates them. A single 2400px-wide file sent to a phone is a fail. (3) Lazy loading: `loading="lazy"` (or the framework component's default) on everything below the fold, and explicitly *not* on the LCP hero — a lazy-loaded hero delays the very metric it is being measured on, and `fetchpriority="high"` on it helps. (4) Intrinsic dimensions: `width` and `height` attributes, a CSS `aspect-ratio`, or a framework component that emits them, on every image. Also check the framework's image optimiser is actually enabled and not bypassed (`unoptimized`, `next.config` `images.unoptimized: true`).
evidence: per offending image — `<path> — <size>, <format>, <dimensions>` and which of the four requirements it misses, with the rendering file:line; the components or config you confirmed handle it correctly.
fix_hint: Route images through the framework's image component so format negotiation, `srcset`, and dimensions come for free; re-encode the oversized originals to WebP or AVIF at the largest size actually displayed; add `loading="lazy"` below the fold and `fetchpriority="high"` to the hero.

### PERF-009 Fonts preloaded, display swap, subset
severity: low
tier: static
fix: easy
why: A web font blocks text from painting until it downloads, so an unpreloaded font on a slow connection is a page of invisible text for several seconds, and a late-swapping font is a visible reflow. Shipping four weights of a full Unicode family when the site uses two is a few hundred KB of nothing.
verify:
  static: Find the font declarations — `@font-face` rules, `<link>` tags to Google Fonts or another host, or the framework's font helper (`next/font`, `@nuxt/fonts`, `@fontsource/*`). Check: (1) `font-display: swap` (or `optional`) on every `@font-face`, so text paints immediately in the fallback; a missing `font-display` means the browser's default block period hides the text. Framework font helpers usually set this — confirm which value rather than assuming. (2) The font files are preloaded (`<link rel="preload" as="font" type="font/woff2" crossorigin>` — the `crossorigin` attribute is required even same-origin or the preload is wasted and fetched twice) or self-hosted through a helper that emits the preload. A render-blocking `@import` inside a CSS file is the worst case: it is discovered only after the stylesheet parses. (3) Subsetting: `unicode-range` on the `@font-face`, a Google Fonts URL with `&text=` or a subset parameter, or a helper's `subsets` option. (4) Count the weights and styles actually shipped against the ones the CSS actually uses; each unused weight is a whole file. (5) Format is `woff2`; shipping `ttf` or `otf` to browsers is roughly double the bytes. A site using only system font stacks passes trivially — say so and move on.
evidence: per font family — file(s), format, size, weights shipped versus used, and which of `font-display`, preload, and subsetting are present, with file:line for each declaration.
fix_hint: Move the fonts to the framework's font helper (it self-hosts, subsets, preloads, and sets `font-display: swap` in one step), drop the weights nothing references, and convert any remaining `ttf`/`otf` to `woff2`.

### PERF-010 Third-party scripts deferred; total weight known
severity: low
tier: remote
fix: easy
why: Analytics, chat widgets, session recorders, and tag managers are code you did not write, executing on your main thread, from servers you do not control — and a synchronous third-party tag that is slow to respond blocks your page from rendering at all. Most teams cannot say how many they have.
verify:
  static: Grep the app shell, layout, and `<head>` for third-party script tags and loader snippets: analytics (GA/gtag, Plausible, Segment, PostHog, Amplitude), tag managers, chat and support widgets (Intercom, Crisp, Drift), session recording (Hotjar, FullStory, LogRocket), ad and conversion pixels, A/B testing snippets, and any CDN-hosted library. For each, record whether it is `async`, `defer`, injected after load, or synchronous and render-blocking — a bare `<script src>` in `<head>` with neither attribute is the fail. Framework helpers give you a strategy to check (`next/script` `strategy="afterInteractive"` or `"lazyOnload"`; `"beforeInteractive"` should be rare and justified). Note anything loaded on every page that is only needed on one.
  remote: Single requests only — never load-test `remote.url`. Fetch the deployed HTML (`curl -s <remote.url>`), list every script whose host is not your own, and for each get its transfer size with `curl -s --compressed -o /dev/null -w '%{size_download} %{time_total}\n' <script url>`. `--compressed` is not optional here: it sends an `Accept-Encoding` header and reports what actually crosses the wire, and without it you are comparing uncompressed bytes against compressed budgets and will overstate every script by roughly three times. Sum them: that total is the "weight known" half of this check, and it belongs in evidence whether or not it is a fail. The budgets below are transfer bytes, compressed as served — a single third party over about 100 KB transferred, or a total over about 300 KB transferred, deserves a named justification. Note that a loader snippet often pulls further scripts at runtime, so a curl of the snippet understates the real cost — say so, and use the Lighthouse report from PERF-011 (its third-party summary, if the version you ran emits one) as the cross-check.
evidence: a table of third-party host, purpose, loading strategy, transfer size, and pages it loads on; the summed total; file:line for each tag.
fix_hint: Add `defer` or the framework's `lazyOnload` strategy to every third-party tag that is not needed for first paint, load the page-specific ones only on their page, and delete the ones nobody has looked at since they were added.

### PERF-011 Core Web Vitals within thresholds (LCP, CLS, INP)
severity: high
tier: local
fix: guided
why: These three metrics are what a user actually experiences — how long until the main content appears, whether the page jumps under their thumb, and how long a tap takes to do anything. They are also a ranking input, so a slow page costs traffic as well as conversions.
verify:
  static: From PERF-007, PERF-008, and PERF-009, predict the likely offenders: entry bundle size drives interaction delay, an unoptimised or lazy hero image drives LCP, images and ads without reserved space and late-loading fonts drive CLS. Record the prediction so the measured result either confirms or corrects it.
  local: Against `local.url` only, and against a production build per the header rule — Lighthouse on a dev server measures unminified bundles and a route being compiled while it watches, which is not a number about your app. Run `npx lighthouse <local.url> --only-categories=performance --output=json --output-path=.pre-launch/lighthouse-<page>.json --quiet --chrome-flags="--headless"` and pull the three numbers out of the saved report rather than printing it — the JSON is several megabytes and must never be `cat`ed into your context: `jq '.audits["largest-contentful-paint"].numericValue, .audits["cumulative-layout-shift"].numericValue, .audits["total-blocking-time"].numericValue' .pre-launch/lighthouse-<page>.json`. Thresholds: LCP under 2.5 s, CLS under 0.1, INP under 200 ms. Be precise about INP: a standard Lighthouse lab run does not measure INP — it needs real interactions or field data — so use Total Blocking Time as the lab proxy (under 200 ms is good, 200-600 ms needs work) and label it in evidence as `TBT (INP proxy)` rather than reporting it as INP. Run the most important authenticated page too if you can pass the session (Lighthouse can take extra headers; check `npx lighthouse --help` for the flag name in your version). Run each page twice and take the second run — the first pays for a cold start or a first-request compile and will read worse than reality. Note in evidence exactly what you measured, because build mode is the dominant source of error here and it dwarfs the machine: a dev-server run is wrong by a large multiple and its numbers cannot be compared to these thresholds at all, whereas a local production build differs from the deployed one mainly by missing the CDN, the real network, and production data volumes. So a production-build local pass is meaningful but optimistic — treat a marginal one as a fail worth investigating — and a dev-server number is not a result, only a hint. Without Lighthouse (declined install), fall back to the static prediction above, say the vitals are unmeasured, and set `verified_by: static-fallback`.
evidence: per page — `LCP <n>s / CLS <n> / TBT <n>ms (INP proxy)` with the pass threshold beside each; the LCP element as Lighthouse identifies it; the top opportunities Lighthouse lists with their estimated savings; the exact command run.
fix_hint: Fix the named LCP element first — usually preload the hero image, remove its lazy loading, and give it `fetchpriority="high"`; for CLS add dimensions or `aspect-ratio` to whatever shifts (PERF-008) and reserve space for late-injected banners; for blocking time cut or defer entry JavaScript (PERF-007, PERF-010). Re-run Lighthouse after each change.

### PERF-012 Slow query log reviewed; EXPLAIN on top queries
severity: medium
tier: local
fix: guided
why: Under load, one query is almost always most of the latency, and it is rarely the one people suspect. The database will tell you which — but only if you ask it, and only while traffic is running.
verify:
  static: Read the data access layer (stack ref: "data access") and list the queries behind the endpoints PERF-002 ranked slowest. Look for the shapes that go quadratic: a filter or join on an unindexed column (DAT-009), `select *` pulling wide rows or large text/JSON columns for a list view, a `count(*)` over a whole table on every page load, `order by` on an unindexed column, `like '%term%'` where a full-text index belongs, and an aggregate computed per request that could be materialised. Also check whether a statement timeout is set at all — a query with no timeout can hold a connection until the pool is empty.
  local: Turn the database's own instrumentation on against the local database, then generate traffic against `local.url` only. Postgres: `alter database <db> set log_min_duration_statement = 200;` and read the log. Never edit `postgresql.conf` or any other config file — this domain does not modify project or machine files, and a session-scoped `alter database` is undone by one statement. Or use `pg_stat_statements` if the extension is available: `select calls, mean_exec_time, total_exec_time, query from pg_stat_statements order by total_exec_time desc limit 20;`. Read those existing top queries *first* — they are usually the answer on their own, and they are cumulative across everything the developer has run. `select pg_stat_statements_reset();` throws that history away permanently, so only run it if you need clean attribution for your own traffic and the user has said yes. MySQL: record the current values first (`select @@global.slow_query_log, @@global.long_query_time;`), then `set global slow_query_log = ON; set global long_query_time = 0.2;`.
  **Restore what you changed, always.** Before you finish this check — including when it fails, errors, or you run out of budget — put the settings back: `alter database <db> reset log_min_duration_statement;` for Postgres, and `set global slow_query_log = <previous>; set global long_query_time = <previous>;` for MySQL using the values you recorded. Leaving a database logging every 200 ms query is a slow disk fill and a confusing surprise for whoever next opens the log. Record in evidence that you restored it, or that you could not and what is still set. Supabase: the same Postgres settings on the local instance, or the dashboard's query performance view for a hosted one. Drive the traffic by re-running PERF-001's load-safe endpoints, or by replaying a few page loads if the load tester is unavailable. Then take the top three queries by total time and run `explain (analyze, buffers) <query>` on each. Only ever run `analyze` on a select — it executes the statement, so a mistyped update actually updates; use plain `explain` for writes. In the plan, look for `Seq Scan` on a table with meaningful row counts, a row-estimate that is wildly off the actual count, a `Nested Loop` over thousands of rows, and `Sort` spilling to disk (`Sort Method: external merge`).
evidence: the top queries by total time with calls and mean time, the query text truncated and parameters redacted; the relevant plan lines for each (`Seq Scan on orders (cost=<n> rows=<n>) actual rows=<n>`); the file:line where each query is built; whether a statement timeout exists.
fix_hint: Add the index the plan is missing (DAT-009 owns the migration shape, including `concurrently`), narrow `select *` to the columns the view uses, replace a per-request `count(*)` with an estimate or a cached counter, and set a statement timeout so a pathological query cannot take the pool down. Re-run `explain (analyze)` to confirm the plan changed.

### PERF-013 Slow work (email, PDF, AI, exports) in background jobs, not request path
severity: high
tier: static
fix: guided
why: Work that takes seconds should not happen while a user waits and a connection is held. Worse, it makes the request non-retryable in the way that matters: if the provider is slow and the platform's function timeout fires (PERF-020), the user gets an error even though the email was already sent.
verify:
  static: Read every handler (stack ref: "routes and handlers", "background jobs") and find work that does not belong in a request: sending email or SMS, generating a PDF or an invoice, calling an AI or LLM provider for anything longer than a chat token stream, building a CSV or data export, processing or resizing an uploaded image or video, syncing to a third-party CRM or analytics system, fanning out webhooks, and any loop over more than a handful of rows doing IO per row. For each, record whether it is awaited inline or handed to a queue. Then check what queue actually exists (stack ref: "background jobs"): a real worker (BullMQ, Celery, Sidekiq, Inngest, Trigger.dev, QStash, a platform queue, a cron route) versus the two impostors — a floating promise that is never awaited (in a serverless function the process may be frozen the moment the response is sent, so the work simply never finishes; `waitUntil` is the platform-supported version and is a pass for short work), and a `setTimeout` scheduling work in a process that will not exist by then. Streaming an AI response directly to the client is a legitimate exception — the user is waiting on purpose and sees tokens; note it and pass. Where work is queued, confirm the user-visible path tells them so (a job id, a status the UI polls, an email when it is done) rather than pretending it finished.
evidence: per item — `<work> at <file:line> — inline` or `queued via <mechanism> at <file:line>`, with the measured or documented typical duration where PERF-001 or PERF-002 has it; the queue implementation you found, or `none found`.
fix_hint: Move the work into the stack's job queue, return immediately with a job id or a pending status, and notify on completion; where no queue exists yet, adding one is the fix — a fire-and-forget promise in a serverless handler is not, because the runtime may freeze before it runs.

### PERF-014 Timeouts and bounded retries on all outbound calls
severity: high
tier: static
fix: easy
why: A call with no timeout does not fail — it hangs, holding a connection, a worker, and eventually the whole pool, so one slow third party takes your app down while your own servers are idle. Unbounded retries then turn their brief outage into your sustained attack on them.
verify:
  static: List every outbound call (stack ref: "routes and handlers", "data access", "background jobs"): `fetch`, axios, `requests`, `httpx`, `HTTParty`, provider SDKs (Stripe, OpenAI, Supabase, S3, Twilio, Resend/SendGrid), and the database driver. For each, confirm an explicit timeout. Node `fetch` has no request timeout you can rely on — whatever the underlying client's internal socket timeouts happen to be, the call needs an explicit `AbortSignal.timeout(<ms>)` or an `AbortController`. Python `requests` has no default timeout either; `timeout=` is required. Axios treats `timeout: 0` (its default) as no timeout. Provider SDKs usually accept a `timeout`/`maxRetries` option and their defaults vary by SDK and version, so do not assume — check the SDK's documented default and set it explicitly anyway, which is what makes the value reviewable. Then check the retry policy: a bounded attempt count (2 or 3, not a `while (true)`), exponential backoff with jitter rather than a fixed delay, retry only on timeouts, connection errors, and 5xx/429 — never on a 4xx, which will fail identically forever — and honouring `Retry-After` when the response sets it. Retrying a non-idempotent call needs an idempotency key or it duplicates the side effect; a retried charge without `Idempotency-Key` is a double charge, and a retried email is a duplicate email. Also confirm the total of timeout multiplied by attempts fits inside the platform's function timeout (PERF-020) — three 10-second attempts inside a 10-second function is a guaranteed failure.
evidence: a table of call site (file:line), destination, timeout value or `none`, retry policy, and idempotency handling for the non-idempotent ones.
fix_hint: Set an explicit timeout on every outbound call — a shared wrapper or a preconfigured client instance is less to maintain than one per call site — cap retries at two or three with jittered exponential backoff on retryable statuses only, and attach an idempotency key to anything that charges, sends, or creates.

### PERF-015 Memory stable under sustained load
severity: medium
tier: local
fix: guided
why: A leak is invisible in development, where the process restarts every few minutes, and obvious in production at 3am, where the container hits its limit, gets OOM-killed, and restarts mid-request. The shape you are looking for is memory that never comes back down after the load stops.
verify:
  static: Look for the usual accumulators: a module-level `Map`, `Set`, array, or plain object that is written to per request and never evicted (a hand-rolled cache with no TTL or size cap is the classic); event listeners or subscriptions added per request and never removed; a database, Redis, or HTTP client instantiated per request instead of once (this also exhausts connections — cross-reference DAT-008); an unbounded in-memory queue or buffer; a whole file or query result read into memory rather than streamed (PERF-019); and in a long-lived process, timers or intervals that are never cleared. Note the container or platform memory limit if the deploy config states one.
  local: Against `local.url` only — never `remote.url`. Start the app with the production build if you can (`NODE_ENV=production` and the production start command), find its pid, and record a baseline RSS: `ps -o rss=,vsz= -p <pid>`. Then run a sustained load with the load-safe endpoints only — `npx autocannon -c 20 -d 120 <local.url><path>`, or the k6 equivalent — while sampling RSS every 5 seconds in a second shell (`while true; do ps -o rss= -p <pid>; sleep 5; done`). After the load stops, keep sampling for another 60 seconds. Pass is memory that rises under load and returns to within roughly 20% of baseline afterwards; fail is a line that keeps climbing during the run and stays high after it. If you have a second run's worth of budget, repeat the load — a leak shows as a higher floor after each cycle, which is more convincing than one rising line. Node projects can confirm with `node --expose-gc` and a heap snapshot before and after, or by reading `process.memoryUsage().heapUsed` from a debug route if one exists. Two minutes of load is not proof of no leak; a pass here means "no leak large enough to see in two minutes", and evidence should say exactly that.
evidence: baseline RSS, peak RSS, RSS 60 seconds after load, and the sample interval; the endpoint and load parameters used; the file:line of any accumulator found statically.
fix_hint: Bound whatever grows — give the hand-rolled cache a max size and TTL or replace it with the platform's cache, move per-request client construction to module scope, remove listeners when their request ends — then repeat the load cycle twice and confirm the post-load floor no longer rises.

### PERF-016 Serverless cold start measured and acceptable
severity: low
tier: remote
fix: guided
why: On a serverless platform an idle function is a container that has to be created, and the user who triggers that pays for the whole import graph before a line of your handler runs. For a low-traffic app most users are that user.
verify:
  static: Confirm the deployment is actually serverless (stack ref: "build", "known traps") — Vercel functions, Lambda, Cloud Functions, Cloud Run scaled to zero, Netlify functions; a long-lived server has no cold start and this check passes as not applicable, which you should say rather than leaving blank. Then read what the function does at module scope, before the handler: SDK clients constructed at import time, a Prisma or ORM client generated and connected, a large dependency imported for one code path, a JSON or ML asset loaded from disk, environment validation that hits the network. Note the deployed function bundle size if the platform reports it — cold start scales with it. Also note the runtime: an edge runtime starts far faster than a Node one, and a function pinned to a region far from users adds latency that looks like cold start but is not.
  remote: A handful of single requests, spaced out — this is explicitly not a load test, and `remote.url` is never load-tested. Pick a lightly used API route (a health path from stack ref "runtime probe hints" is ideal because it does no work), leave it untouched for long enough that its container is likely recycled (the platform's idle window; several minutes is usually enough), then send one request and time it: `curl -s -o /dev/null -w 'total=%{time_total} connect=%{time_connect} ttfb=%{time_starttransfer}\n' <remote.url><path>`. Immediately send three more. The first request's TTFB minus the median of the warm ones is your cold-start cost. Judge it against under about 1 s good, 1-3 s worth fixing, over 3 s a fail. Repeat once if you have the budget, because one sample can catch an unrelated network hiccup. If `remote.url` is not configured, do not substitute `local.url` — a local dev server has no cold start and the number would be meaningless; record the static findings and set `verified_by: static-fallback`.
evidence: cold TTFB, the three warm TTFBs, and the difference; the route used and how long it had been idle; the module-scope work found, file:line each; the function bundle size and runtime if the platform reports them.
fix_hint: Move heavy SDK construction inside the handler or behind a lazy getter so it only runs on the paths that need it, trim the import graph for the cold path, consider the edge runtime for small latency-sensitive routes, and only reach for provisioned concurrency or a warming ping once the import graph is genuinely minimal — paying to keep a bloated function warm is treating the symptom.

### PERF-017 No race conditions on payment, credit, or inventory decrement
severity: critical
tier: static
fix: guided
why: Read a balance, subtract in application code, write it back — and two concurrent requests both read the same starting value, so the user spends the same credit twice. This is not a theoretical concurrency puzzle: it is how people get free API usage, oversold inventory, and double-granted seats, and it is trivially reproducible by double-clicking a button.
verify:
  static: Find every numeric field that represents money, credits, tokens, quota, stock, or seats (stack ref: "data access") and read every write to it. The fail pattern is read-then-write across a gap: a `select`/`findUnique` followed by application arithmetic followed by an `update` setting the computed value, with no transaction, no row lock, and no atomic expression — `const u = await db.user.findUnique(...); await db.user.update({ data: { credits: u.credits - 1 } })` is the canonical bug, and the same shape appears as `user.credits -= 1; user.save()` in every ORM. The safe forms, any of which pass: an atomic database-side update (`update users set credits = credits - 1 where id = ? and credits >= 1` and then checking the affected row count), the ORM's atomic helper (Prisma `{ decrement: 1 }`, Django `F('credits') - 1`, Rails `decrement!`/`update_counters`, SQLAlchemy `Model.credits - 1` as an expression), a transaction with `select ... for update` on the row, or a database constraint that makes the bad state impossible (`check (credits >= 0)`, a unique index on the thing being double-created). Note that a transaction alone is not sufficient at the default read-committed isolation level — a plain `select` inside a transaction does not lock the row; it needs `for update` or the atomic expression. Beyond decrements, check three neighbours: seat and quota limit checks (`if (count < plan.limit)` then insert, with no unique constraint or lock, lets two requests both pass the check); webhook-driven credit or subscription grants without an idempotency key or a processed-event table, which double-grant when the provider retries (cross-reference the payments domain); and any "check then create" for a uniquely-named resource that lacks a matching unique index. Also flag decrement paths with no floor — a credit balance that can go negative under concurrency is the same bug with a visible symptom.
evidence: per site — `<field> at <file:line>` with the read line and the write line quoted, and which safe form is missing; the constraints and unique indexes you found or their absence; the webhook handlers checked for idempotency.
fix_hint: Replace each read-modify-write with a single conditional atomic update (`update ... set credits = credits - 1 where id = ? and credits >= 1`) and treat zero affected rows as "insufficient balance" rather than an error; add the database constraint (`check (credits >= 0)`, a unique index on the limited resource) so the invariant holds even if a future code path forgets; make webhook grants idempotent on the provider's event id.

### PERF-018 Primary flow usable on throttled 3G
severity: medium
tier: local
fix: guided
why: A meaningful share of real users are on a bad connection at least some of the time, and the difference between a slow site and an unusable one is whether anything is on screen while they wait. Everything looks fine on office wifi with a warm cache.
verify:
  static: Identify the primary flow — landing to signup to the first useful screen, or whatever the app's main conversion is (stack ref: "routes and handlers"). For each step, note what must arrive before the user sees anything real: is there server-rendered content or is the page an empty div waiting on JavaScript, then waiting on a client-side fetch? Check for loading states and skeletons on every async boundary, and for a visible response to a submit button — an unresponsive button on a slow connection is what makes users click it three times, which is PERF-017's problem too.
  local: Against `local.url`, and against a production build per the header rule — an unminified dev bundle over a throttled connection fails this check on bytes the user would never have downloaded. Run Lighthouse under a slow-network profile: `npx lighthouse <local.url> --only-categories=performance --output=json --output-path=.pre-launch/lighthouse-3g-<page>.json --quiet --chrome-flags="--headless"` already applies mobile emulation with network and CPU throttling by default, so first read what it actually applied — `jq '.configSettings.throttling' .pre-launch/lighthouse-3g-<page>.json` — and record those numbers rather than assuming them. To push it to a 3G-like profile explicitly, add `--throttling-method=devtools --throttling.rttMs=300 --throttling.throughputKbps=700 --throttling.cpuSlowdownMultiplier=4`; confirm the flag names against `npx lighthouse --help` for your version, and again record what the report says was applied. Judge usability, not just the score: read `jq '.audits["speed-index"].numericValue, [.audits["screenshot-thumbnails"].details.items[].timing]' <report path>` and, for the frames themselves, open the saved report in a browser rather than printing the base64 thumbnails — was there meaningful content on screen within about 5 seconds, or blank? Then walk the next step of the flow the same way if it has its own URL. Where a browser automation tool is available, driving the real flow with the same throttling is better evidence than a page-level report — but a filmstrip showing a blank screen at 5 seconds is enough to fail this check on its own.
evidence: the throttling settings the report says were applied; per step — Speed Index, first frame with real content from the filmstrip, and whether the step was blank or usable at 5 s; the file:line of any async boundary with no loading state.
fix_hint: Server-render or statically render the first meaningful content of the primary flow so something real paints without waiting on JavaScript, add skeletons and disabled-with-spinner states at every async boundary, and cut the entry bundle (PERF-007) since on a throttled connection it is the long pole.

### PERF-019 No blocking synchronous I/O in request path
severity: medium
tier: static
fix: easy
why: In a single-threaded runtime — Node's event loop, an async Python worker — one synchronous read blocks every other in-flight request on that process, not just its own. Under concurrency a 50 ms sync call becomes everyone's 50 ms, which is why the numbers look fine on one request and collapse on twenty.
verify:
  static: Grep the request path (stack ref: "routes and handlers", "background jobs" for what should be there instead) for blocking calls. Node: `readFileSync`, `writeFileSync`, `readdirSync`, `existsSync` in a hot path, `execSync`, `spawnSync`, `bcrypt.hashSync`/`compareSync`, `crypto.pbkdf2Sync`, `zlib.gzipSync`, `deasync`, and `JSON.parse`/`JSON.stringify` on anything large. Python async frameworks (FastAPI, async Django, Starlette): a blocking `requests.get`, a sync database driver, `open()`/`read()`, `time.sleep`, or a CPU-heavy loop inside an `async def` — these block the loop, and the correct forms are the async client, `await asyncio.sleep`, or `run_in_executor`/`asyncio.to_thread` for the unavoidable ones. Ruby and Rails are less exposed per-process but a sync shell-out still occupies the worker. Also flag CPU-bound work in the request path regardless of the language — image resizing, PDF rendering, large CSV parsing, cryptographic key derivation at high cost factors, big sorts — which belongs in a job (PERF-013). Startup-time sync reads (a config file loaded once at module scope) are fine; the check is about per-request work, so distinguish the two and say which each hit is. Streaming matters here too: reading an entire uploaded file or query result into memory before responding is both a blocking pattern and PERF-015's leak risk — prefer a stream.
evidence: per hit — `<call> at <file:line> — per request` or `— startup only`, with the enclosing handler named; any CPU-bound work in a handler with an estimate of its cost.
fix_hint: Swap each per-request sync call for its async form (`fs/promises`, the async HTTP client, `await asyncio.sleep`), move genuinely CPU-bound work to a queue or a worker thread, and stream large file and query responses instead of buffering them.

### PERF-020 Platform function timeout and payload limits respected (e.g. serverless 10s/4.5MB)
severity: medium
tier: static
fix: guided
why: A handler that streams a large upload or waits on a slow AI call runs into a platform ceiling nobody chose and few people read, and the failure is opaque: a 504 or a truncated response with no application error, so the logs show nothing and the user sees a broken page.
verify:
  static: Read the actual limits for this deployment from the stack reference (stack ref: "known traps", "build") rather than from memory — they differ by platform, by plan, and by runtime, and they change. The commonly quoted examples (a serverless function capped around 10 s on a default plan, a request body capped around 4.5 MB, a Lambda synchronous payload around 6 MB) are illustrations to check against the real numbers, not values to assert; if the stack file does not state them, record what you did check and say the limit is unconfirmed. Then find every handler that could exceed one: (1) Duration — anything awaiting an AI or LLM completion, generating a PDF or a report, running a data export or a bulk import, processing video or images, calling a slow third party, or doing a long database migration or backfill from a request. Add up the timeout budget from PERF-014: retries multiply, and three 5-second attempts do not fit in a 10-second function. Where a handler configures its own limit (`maxDuration`, Lambda `timeout`, `functions` config), record the configured value and check it is inside the plan's ceiling. (2) Payload — every upload route (stack ref: "file uploads") and every endpoint accepting a large JSON body, and whether the size is validated before the platform rejects it. Direct-to-storage uploads via a presigned URL bypass the function limit entirely and are a pass; an upload proxied through the function is where the ceiling bites. Also check response size limits and whether large responses stream. (3) Other ceilings the stack file names — memory, concurrent executions, the edge runtime's smaller CPU and API surface, response header size. For each risky handler, note whether the code degrades sanely (a job plus a status poll) or simply fails at the ceiling.
evidence: the platform limits with their source (stack ref or config file:line), or `unconfirmed`; per handler — `<file:line> — <what it does> — worst-case <duration or payload> vs limit <n>`; the presigned or streaming paths you cleared.
fix_hint: Move the long work into a background job and return a job id the client polls (PERF-013), raise the handler's `maxDuration` only where the plan actually allows it and the work is genuinely bounded, switch proxied uploads to presigned direct-to-storage, and validate body size in the handler so an oversized request gets a clear 413 instead of a platform error.
