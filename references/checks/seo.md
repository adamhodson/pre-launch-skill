# SEO checks (SEO)

Read `agents/domain-auditor.md` for procedure. Blocks below are checks; consult stack references for locations. Tools: `python3 scripts/probe_url.py <url>` is this domain's main instrument (SEO-001, 003, 004, 005, 006, 007, 008, 009, 010, 013, 015, 017); `curl` for everything the probe does not fetch (SEO-002, 011, 012, 016 and every page-level check beyond the home page); `python3` with only the standard library for parsing JSON-LD, sitemaps, and image headers. Nothing here needs an installed package, so there is no static-fallback path for a missing tool — only for a tier that is not live.

**Run the probe once per base URL and read the same JSON for every block.** `probe_url.py` fetches `/`, `/robots.txt`, `/sitemap.xml`, `/llms.txt`, `/__prelaunch_missing__`, and the sensitive-path list in one pass. Run it once against `local.url` (the production build's URL, per the next rule) and once against `remote.url` if that tier is live, save each to a file — `python3 scripts/probe_url.py <url> > /tmp/prelaunch-seo-local.json` — and read fields out of the saved file in every block rather than re-fetching. Twelve blocks in this domain quote the same home-page parse; probing twelve times is twelve chances for a cold cache, a rate limiter, or a deploy mid-audit to make two blocks disagree about the same page.

**Measure a production build, never the dev server.** This is the same rule the performance domain states, and it changes verdicts here too: many frameworks inject dev-only markup, skip the sitemap and robots routes entirely in development, serve `X-Robots-Tag: noindex` on purpose while `NODE_ENV` is not production, and render metadata differently under fast refresh. So before any local-tier work in this domain, build and start the app in production mode on a port you record — `npm run build && PORT=<port> npm start` with `NODE_ENV=production` for a typical Node stack, and the equivalent for this one (stack ref: "build" for the build and production start commands, "dev server" for the port convention) — and point every probe and `curl` in this file at that URL, noting it in evidence alongside `local.url`. SEO-003, SEO-004, SEO-009, SEO-015, and SEO-016 are the blocks where a dev server produces a confident wrong answer. If the production build cannot be run, do not silently audit the dev server as if it were production: mark those five checks `dev-server only` in `notes`, and report what could not be built.

**Sampling pages beyond the home page.** The probe parses SEO fields for the home page only, so every per-page check works from a sample you build once and reuse. From the home-page probe's `links` list: resolve each href against the base URL, drop `mailto:`, `tel:`, `javascript:`, and bare `#` fragments, drop anything whose host is not the base host, strip fragments and query strings, deduplicate paths, and take up to ten — preferring one of each route shape over ten of the same one (a marketing page, a blog or docs page, a dynamic detail page such as `/blog/<slug>` or `/products/<slug>`, a pricing or contact page, a legal page). Record the exact ten in the first block that samples them and cite that list in the others rather than choosing a new sample per block. For each sampled page, `curl -s <url>` once, save the HTML, and grep the saved file; do not re-request the same page in four different blocks. The greps below assume double-quoted HTML attributes, which is what every mainstream template engine emits; if this stack emits single-quoted attributes, swap the quote character in the pattern rather than concluding the tag is absent.

**A local build has localhost URLs by design, and that is not a finding.** A production build running on `http://localhost:3000` legitimately emits `<link rel="canonical" href="http://localhost:3000/">` and `og:url` pointing at localhost when the site URL comes from an environment variable that is localhost in this environment. SEO-006 and SEO-007 therefore judge the *source of the URL*, not the value observed locally: find the configured production domain (config `remote.url` when it is the production host, or a `SITE_URL`-style env var — `NEXT_PUBLIC_SITE_URL`, `PUBLIC_SITE_URL`, `SITE_URL`, `URL`, `metadataBase`; stack ref: "env vars") and fail only when the code hardcodes `localhost` or a staging host, or when the production value of that variable is unset, wrong, or still a placeholder. A value that is localhost here and reads from the variable is a pass with a note naming the variable and where its production value is set. If you cannot determine the production domain from config or env at all, that is itself the finding — say so rather than guessing.

**`noindex` is judged against the URL you are actually probing.** The local production build must not be noindexed: a `noindex` there almost always means the flag is unconditional and will ship. A `remote.url` that is clearly a staging or preview host (`staging.`, `preview.`, `dev.`, `*.vercel.app`, `*.netlify.app`, `*.pages.dev`, a numbered preview subdomain) *should* be noindexed, and its absence is the fail. Never conclude "production is noindexed" from a staging probe, and never conclude "staging is exposed" from a local one; name the host you tested in evidence every time.

**Never modify project files.** Everything in this domain is a read or a request. Do not add a `robots.txt`, fix a canonical, regenerate a sitemap, or write an `llms.txt` while auditing — findings and `fix_hint` text are the output, and the fix workflow applies them later with the user watching.

### SEO-001 Unique, descriptive titles and descriptions; sane lengths
severity: medium
tier: local
fix: easy
why: The title is the clickable line in the search result and the tab label, and the description is the sales pitch under it. A site where every page is titled "Create Next App" is not merely unoptimised — search engines collapse duplicate titles, so the pages compete with each other and most of them never surface at all.
verify:
  static: Find where titles and descriptions are set (stack ref: "routes and handlers"): Next.js `metadata` exports and `generateMetadata` in `layout.tsx`/`page.tsx`, `next-seo` config, `react-helmet`/`@unhead` components, `<svelte:head>`, Nuxt `useHead`/`definePageMeta`, Astro layout props, Rails `content_for :title` with a `yield` in the layout, Django `{% block title %}`, or a raw `<title>` in a single shared template. Two failures to look for. First, framework defaults still in place: `Create Next App`, `Vite + React`, `Document`, `React App`, `My Site`, `Home`, `Untitled`, an empty `<title>`, or a description that is the framework's boilerplate one-liner. Second, a layout that sets one title and no route ever overrides it, which gives every page the same title — check whether the dynamic routes (`[slug]`, `[id]`) build a title from their data or inherit the static one. Record which routes set their own and which inherit.
  local: From the saved home-page probe, read `title` and `description`. Then for each of the ten sampled pages (header rule), `curl -s <url> > page.html` and pull both with `python3 -c "import re,sys; h=open(sys.argv[1]).read(); t=re.search(r'(?is)<title[^>]*>(.*?)</title>', h); d=re.search(r'(?is)<meta[^>]+name=[\"\x27]description[\"\x27][^>]+content=[\"\x27]([^\"\x27]*)', h); print(len(t.group(1).strip()) if t else 0, repr(t.group(1).strip()) if t else None); print(len(d.group(1)) if d else 0, repr(d.group(1)) if d else None)" page.html`. Judge four things per page: a title exists and is not a framework default; it is roughly 30-60 characters (under 30 wastes the slot, over 60 gets truncated in the result, neither is a hard fail on its own but both belong in evidence); a description exists and is roughly 70-160 characters; and the title and description are unique across the sample. Duplicates are the real fail here — two pages sharing a title is worth more than either being three characters too long. A missing description is a medium finding; search engines will synthesise one, but you have handed them the choice.
evidence: one row per page — path, title, title length, description, description length — for the home page plus the ten sampled; the list of sampled paths so later blocks cite the same one; every duplicate title or description grouped with the paths that share it; the file:line where each default or inherited title comes from.
fix_hint: Give every route its own title and description from its own content (a `generateMetadata` per dynamic route, not one layout-level constant), keep titles near 50-60 characters with the brand appended once, and replace any framework default in the root layout with the real site name.

### SEO-002 Favicon and apple-touch-icon present
severity: low
tier: local
fix: easy
why: A missing favicon shows the browser's blank-page glyph in every tab, bookmark, and history entry, and a missing apple-touch-icon gives an iOS home-screen shortcut a blurry screenshot of the page instead of an icon. Neither affects ranking; both make a launched product look unfinished at the exact moment someone decides to keep it.
verify:
  static: Look for the icon files and their declarations (stack ref: "routes and handlers", "build"): Next.js App Router conventions (`app/favicon.ico`, `app/icon.png`, `app/icon.svg`, `app/apple-icon.png`, which are auto-linked), `public/favicon.ico`, `public/apple-touch-icon.png`, `static/favicon.ico`, or explicit `<link rel="icon">`, `<link rel="apple-touch-icon">`, and `<link rel="manifest">` tags in the root layout or base template. If a web app manifest exists (`site.webmanifest`, `manifest.json`), read its `icons` array and note the sizes it promises, because a manifest referencing icons that do not exist is a broken install prompt. Confirm the files are actually committed rather than only referenced.
  local: The probe does not collect icon links, so read them from the saved home-page HTML: `curl -s <local.url>/ | grep -oiE '<link[^>]+rel="[^"]*icon[^"]*"[^>]*>'`. Take the `href` from each tag it prints, and for those plus `/favicon.ico` and `/apple-touch-icon.png` whether or not they were declared, run `curl -s -o /dev/null -w '%{http_code} %{content_type}\n' -L <resolved url>`. Pass needs a 200 with an `image/*` content type for at least one `rel="icon"` and one `rel="apple-touch-icon"`. Watch for the two quiet failures: an SPA that returns 200 with `text/html` for `/favicon.ico` because its catch-all route swallowed the request (that is a missing icon, not a present one — check the content type, not the status), and an `apple-touch-icon` that is not 180x180, which iOS will scale badly. Check that size the same way SEO-007 reads image dimensions.
evidence: per icon — `GET <path> → <status> <content-type>` and the declaring `<link>` tag or `auto-linked from app/icon.png`; the apple-touch-icon's pixel dimensions; any manifest icon entry whose file 404s.
fix_hint: Add a favicon (ICO or SVG plus a 32x32 PNG) and a 180x180 `apple-touch-icon.png` using the framework's file convention so the tags are generated for you, and make sure any manifest `icons` entry points at a file that exists.

### SEO-003 sitemap.xml valid; canonical 200 URLs only; referenced from robots
severity: medium
tier: local
fix: easy
why: A sitemap is how a new site tells search engines which URLs exist before anyone links to them, and at launch nobody links to you. One full of redirects, 404s, or localhost URLs is worse than none: it spends the crawl budget on dead ends and teaches the crawler your list is unreliable.
verify:
  static: Find how the sitemap is produced (stack ref: "routes and handlers", "build"): Next.js `app/sitemap.ts` or `next-sitemap.config.js`, a `sitemap.xml.ts` route, SvelteKit `src/routes/sitemap.xml/+server.ts`, Nuxt `@nuxtjs/sitemap`, Astro `@astrojs/sitemap`, `django.contrib.sitemaps`, Rails `sitemap_generator`, or a hand-written `public/sitemap.xml`. A static file in `public/` is the one to read closely — it goes stale the day after it is written, so check whether anything regenerates it in the build. Read the generator for two things: which routes it enumerates (does it include the dynamic pages, or only the static ones it could see at build time?) and which it excludes (authenticated routes, drafts, paginated duplicates — the exclusion list is SEO-017's evidence too). Note where the URL host comes from, which is the same env-var question as SEO-006.
  local: From the saved probe, read `pages["/sitemap.xml"]`. A non-200 status is the fail; note that some stacks serve a sitemap index at `/sitemap.xml` pointing at `/sitemap-0.xml`, which is correct — follow the `<loc>` entries one level down and audit those. Confirm the XML actually parses rather than trusting the regex the probe used: `curl -s <local.url>/sitemap.xml | python3 -c "import sys,xml.etree.ElementTree as ET; r=ET.parse(sys.stdin).getroot(); print(r.tag, len(list(r)))"` — a parse error, a stray BOM, or an HTML error page served with a 200 all show up here. Then check the URLs: every `<loc>` must be absolute (not `/about`), must use the production host per the env-var rule in the header, and must be the canonical form (no tracking parameters, no session ids, no mixed trailing-slash styles within one file). Sample up to twenty `<loc>` values — spread across route shapes, not the first twenty alphabetically — and request each with `curl -s -o /dev/null -w '%{http_code} %{url_effective}\n' <loc>` *without* `-L`, so a redirect shows as its own 301/302 rather than being followed into a 200. Anything that is not a bare 200 is a finding: a 3xx means the sitemap lists the pre-redirect URL, a 404 means it lists a page that no longer exists. Finally confirm `pages["/robots.txt"]["body"]` contains a `Sitemap:` line with the absolute sitemap URL; a sitemap nothing points at is only discovered if you submit it manually (SEO-014).
evidence: `GET /sitemap.xml → <status>`, the root tag and URL count, and whether it is an index; the sampled `<loc>` values with their status codes and any `url_effective` that differed; the `Sitemap:` line from robots.txt or `absent`; the generator file:line and its exclusion list.
fix_hint: Generate the sitemap from the same route source the app uses rather than maintaining a static file, emit absolute production URLs in their canonical trailing-slash form, drop every URL that redirects or 404s, and add the `Sitemap:` line to robots.txt.

### SEO-004 robots.txt exists; does not block render assets; prod not noindex; staging noindex
severity: high
tier: local
fix: easy
why: This is the single check in the domain that can make a site invisible. A `Disallow: /` left over from pre-launch, or a `noindex` meta that was meant for staging and shipped, removes the entire site from search — and because nothing errors, it is typically discovered weeks later when someone asks why there is no traffic. The mirror image is as bad in a quieter way: a staging deployment with no `noindex` gets indexed, competes with production for the same queries, and can outrank it.
verify:
  static: Find robots (stack ref: "routes and handlers"): `app/robots.ts`, `public/robots.txt`, `static/robots.txt`, a `/robots.txt` route handler, or a platform-level rule. Read it for a blanket `Disallow: /` and for anything blocking render assets — `Disallow: /_next/`, `/static/`, `/assets/`, `/*.js`, `/*.css`, `/build/` — which stops the crawler fetching the JS and CSS it needs to render the page, so it judges your site on an unstyled skeleton. Separately, grep the source for every way this stack can emit `noindex` (stack ref: "routes and handlers", "security headers"): Next.js `robots: { index: false }` or `robots: "noindex"` in a `metadata` export, a literal `<meta name="robots" content="noindex">` in a layout or base template, an `X-Robots-Tag` header set in middleware, a `headers()` config block, `vercel.json`, `netlify.toml`, or an nginx/Caddy config. For each occurrence, read the condition around it: one guarded by an environment check (`process.env.VERCEL_ENV !== 'production'`, `NODE_ENV !== 'production'`, a `SITE_ENV` flag) is the correct pattern; an unconditional one is the shipping-a-noindex fail even if today's probe happens to look fine.
  local: From the saved probe, read `pages["/robots.txt"]`: status must be 200 (a 404 is a fail, though a low-consequence one — crawlers assume "allow all"), and `body` must not contain a `Disallow: /` under `User-agent: *` or under `Googlebot`, and must not disallow the render-asset paths listed above. Then check noindex on the URL you actually probed, per the header rule: read the home-page HTML for a robots meta (`curl -s <local.url>/ | grep -oiE '<meta[^>]+name="robots"[^>]*>'`) and read the response headers for `x-robots-tag` (the probe's `pages["/"]["headers"]` already has it, lowercased). On the local production build, any `noindex` is a fail — report the file:line the static entry found and say whether it is environment-guarded, because an unguarded one will ship. Then, only if `remote.url` is set and its host is clearly a staging or preview host, run one extra request against it — `curl -sI <remote.url>/ | grep -i x-robots-tag` plus a grep of `curl -s <remote.url>/` for the robots meta — and invert the expectation: the *absence* of `noindex` there is the fail. Say which host each verdict came from.
evidence: `GET /robots.txt → <status>` with the full body quoted (it is short, quote it rather than summarising); the robots meta tag and `x-robots-tag` header for each host tested, named by host; the file:line of every noindex source with its guard condition or `unguarded`.
fix_hint: Ship a robots.txt that allows crawling, blocks only genuinely private paths, and names the sitemap; never disallow the JS/CSS asset directories; and make every `noindex` conditional on a deploy-environment variable so staging is noindexed and production is not, rather than on a constant someone has to remember to flip.

### SEO-005 llms.txt exists and is accurate
severity: low
tier: local
fix: easy
why: `llms.txt` is the emerging convention for telling an LLM-driven agent what a site is and where its important documents live, in one markdown file it can read without crawling and rendering the whole site. It is not yet a ranking factor and no search engine requires it; it is cheap, it is increasingly how AI assistants summarise a product, and a wrong one is worse than none because it will be quoted verbatim.
verify:
  static: Look for `public/llms.txt`, `static/llms.txt`, an `app/llms.txt/route.ts`-style handler, or a generator in the build (stack ref: "build", "routes and handlers"). If found, note whether it is hand-maintained or generated from the same source as the docs, because a hand-maintained one drifts from the product within a release or two. If the project is an internal tool or a private app that should not be summarised by anything, this check is a candidate for the config `skip` list rather than a fail — say so instead of recommending a file nobody wants.
  local: From the saved probe, read `pages["/llms.txt"]`. A 404 is the finding, at low severity — report it as an opportunity, not a defect. If it is 200, audit `body` for accuracy rather than existence, which is the whole point of the check: it should open with an H1 naming the actual product, follow with a short blockquote or paragraph summarising what the product does, and then list links under H2 sections. Compare that summary against the home page's `title` and `description` from the same probe and against the README — if the file describes a different product, an older positioning, or a feature set that no longer ships, that is the fail. Extract the links (`python3 -c "import re,sys; print('\n'.join(re.findall(r'\]\((https?://[^)]+|/[^)]*)\)', sys.stdin.read())))"` over the body) and request up to five of them with `curl -s -o /dev/null -w '%{http_code} %{url_effective}\n' -L`; a file whose links 404 is actively misleading. Also confirm the content type is `text/plain` or `text/markdown` rather than `text/html`, since an SPA catch-all returning the app shell with a 200 looks like a present file and is not one.
evidence: `GET /llms.txt → <status> <content-type>`; the H1 and summary line quoted; each sampled link with its status; a plain statement of any claim in the file that the site no longer supports.
fix_hint: Add a short `llms.txt` at the site root with an H1 product name, a one-paragraph summary matching the home page's own description, and H2 sections linking the docs, pricing, and API pages; generate it from the same source as the docs nav so it cannot drift.

### SEO-006 Canonical tags point to production domain
severity: medium
tier: local
fix: easy
why: The canonical tag is how you tell search engines which URL is the real one when several serve the same content. Pointed at localhost or a staging host, it tells them the real page lives somewhere they cannot reach, and the production page can be dropped from the index entirely — this is one of the most common and most expensive launch mistakes.
verify:
  static: Find where the canonical is built (stack ref: "routes and handlers", "env vars"): Next.js `metadataBase` plus `alternates.canonical`, a `<link rel="canonical">` in the root layout or base template, `next-seo`'s `canonical` prop, a `useHead` entry, or a Rails/Django template helper. Then trace the host it uses back to its source. Pass shape: an environment variable (`NEXT_PUBLIC_SITE_URL`, `PUBLIC_SITE_URL`, `SITE_URL`, `URL`, `VERCEL_PROJECT_PRODUCTION_URL`) with its production value set in the deploy config. Fail shapes: a hardcoded `http://localhost:3000` or a staging hostname in the source; a variable with no production value set anywhere (only in `.env.example`); `VERCEL_URL` used directly, which is the *per-deployment* hostname and so gives every preview its own canonical and production a deployment-specific one rather than the domain. Also check that dynamic routes build a self-referencing canonical from their own path rather than inheriting the layout's home-page canonical, which silently canonicalises every page to `/`.
  local: From the saved probe, read `canonical` on the home page, and pull the same tag from each of the ten sampled pages (`grep -oiE '<link[^>]+rel="canonical"[^>]*>'` over each saved HTML file). Per the header rule, a localhost host here is expected and is not the finding — judge the *source*. Report `pass` with a note when the tag is absolute, self-referencing (its path matches the page's own path), unique on the page, and its host comes from the env var whose production value you found; report `fail` when the source is hardcoded, when the production value is unset, or when a page canonicalises to a different page's path. Three page-level errors to check while you have the HTML: more than one canonical tag on a page (search engines ignore all of them), a relative canonical (`href="/about"` — legal but widely mishandled, and it cannot express the http/https or www choice), and a trailing-slash form that disagrees with the URL the site actually serves, which is SEO-012's problem showing up here.
evidence: per page — the raw canonical tag and the page's own path beside it; the env var name, the file:line that reads it, and where its production value is set (or `unset`); the production domain you compared against and where you got it.
fix_hint: Set the canonical base from one environment variable holding the production origin, set that variable in the deploy environment, and build each page's canonical from the base plus its own path so every page self-references; never use a per-deployment hostname variable as the canonical base.

### SEO-007 OG and Twitter tags; OG image exists at 1200×630 and returns 200
severity: medium
tier: local
fix: easy
why: These tags are the entire preview when your link is pasted into Slack, iMessage, LinkedIn, or X. Missing or broken, the link renders as bare grey text and the click-through on every share you will ever get drops immediately. A 404ing OG image is the usual version of this failure, and it is invisible from the site itself.
verify:
  static: Find where the tags are set (stack ref: "routes and handlers", "env vars"): a Next.js `metadata.openGraph`/`metadata.twitter` block, `next-seo`, explicit `<meta property="og:...">` tags in the layout, or a dynamic OG image route (`app/opengraph-image.tsx`, `@vercel/og`, a Satori or Puppeteer renderer). Confirm the image URL is absolute and built from the same site-URL environment variable as the canonical — a relative `og:image` is the most common cause of a broken preview, because the scrapers do not all resolve it. If the image is generated at request time by a route, note that: it can 200 locally and fail in production on a missing font, a missing env var, or a cold-start timeout, so check that route's dependencies too.
  local: From the saved probe, read the `og` and `twitter` dicts on the home page and repeat for the sampled pages by grepping their saved HTML. Required: `og:title`, `og:description`, `og:image`, `og:url`, `og:type`; plus `twitter:card` (`summary_large_image` for a 1200x630 image), and `twitter:title`/`twitter:description` or an explicit reliance on the OG fallbacks. Then verify the image itself, which is the part everybody skips. Resolve `og:image` against the base if relative, then `curl -sI '<image url>'` and require a 200 with an `image/*` content type — an HTML error page or a 302 to a login is the fail. For dimensions, download the first bytes and read the header rather than installing anything: `curl -s -o /tmp/og.img '<image url>'`, then `python3 -c "import struct; d=open('/tmp/og.img','rb').read(); print(struct.unpack('>II', d[16:24]) if d[:8]==b'\x89PNG\r\n\x1a\n' else next(((struct.unpack('>HH', d[i+5:i+9])[1], struct.unpack('>HH', d[i+5:i+9])[0]) for i in range(2, len(d)-9) if d[i]==0xFF and d[i+1] in (0xC0,0xC1,0xC2)), 'unknown'))"`. PNG puts width and height as two big-endian 4-byte integers at bytes 16-23, immediately after the 8-byte signature and the IHDR chunk header, so a fixed slice reads them. JPEG has no fixed offset — the size lives in a start-of-frame segment (SOF0 `0xFFC0`, SOF1 `0xFFC1`, or progressive SOF2 `0xFFC2`) that can appear anywhere after the two-byte SOI, so use python's `struct` to walk the bytes to the first SOF marker and read the two 16-bit values at offsets +5 and +7 from it, which are height then width in that order. Expected 1200x630, or the same 1.91:1 ratio at a larger size. Report the actual dimensions rather than asserting a specific scraper's cutoff, since each platform documents its own minimum and they change: the reliable statements are that a small image gets rendered as a compact thumbnail instead of the large card `summary_large_image` asks for, and that a square or portrait image is cropped to the card's ratio unpredictably. A wrong-sized image is a note with the numbers; a non-200 image is the fail. Judge the image host the same way as SEO-006: a localhost image URL derived from the site-URL variable is fine, a hardcoded one is not.
evidence: the full `og` and `twitter` tag list per page with missing keys named; `GET <og:image> → <status> <content-type>`; the decoded `<width>x<height>` and the format it was read from; the file:line building the image URL and the variable it uses.
fix_hint: Set `og:title`, `og:description`, `og:url`, `og:type`, and an absolute `og:image` built from the site-URL variable, add `twitter:card: summary_large_image`, and ship a 1200x630 image; if the image is generated per request, make sure its fonts and env vars exist in the production environment and cache the response.

### SEO-008 Structured data present, relevant, and valid (Organization, WebSite, FAQ, Product, LocalBusiness, Review as applicable)
severity: medium
tier: local
fix: easy
why: Structured data is what turns a plain blue link into a result with a price, a rating, a FAQ accordion, or a sitelinks search box. It is also the one area where being wrong is punished: markup that describes content not visible on the page is a documented reason for a manual spam action, and invalid JSON is simply ignored, so you carry the maintenance cost and get nothing.
verify:
  static: Find where JSON-LD is emitted (stack ref: "routes and handlers"): a `<script type="application/ld+json">` in a layout or component, `next-seo`'s JSON-LD components, `schema-dts`-typed objects, a Django or Rails template partial. Note which types the app claims and on which routes. Then ask the relevance question before the validity one: does the type match the page? A `Product` schema on a marketing page with no product, a `FAQPage` whose questions are not rendered on the page, or a `Review`/`AggregateRating` about your own business on your own site (self-serving reviews are ineligible for rich results) are all findings even when the JSON is perfectly valid. Note also whether anything is emitted at all — for most sites the baseline is an `Organization` and a `WebSite` on the home page and nothing else, and that baseline being absent is the common case.
  local: From the saved probe, read the `jsonld` list for the home page and grep the sampled pages for their own blocks. Any entry containing the key `_invalid` means the probe could not parse it as JSON — that is a hard fail, and the truncated source in that field usually shows why (a trailing comma, an unescaped quote from an interpolated string, or HTML entities where the template escaped the JSON). For each valid entry, walk it with python and check: `@context` is `https://schema.org` or `http://schema.org` (or an object containing it) — a missing or misspelled context means the whole block is ignored; `@type` is present on every node, including nodes nested inside a `@graph` array or a top-level array; and the type's required properties are there. The ones worth knowing by heart: `Organization` needs `name` and `url` (and `logo` for the knowledge panel); `WebSite` needs `name` and `url` (plus `potentialAction` if it claims a sitelinks search box, and that search URL must actually work); `FAQPage` needs `mainEntity` as a list of `Question` nodes each with a `name` and an `acceptedAnswer` of type `Answer` with `text`; `Product` needs `name` and an `offers` node with `price`, `priceCurrency`, and `availability`; `LocalBusiness` needs `name` and a `PostalAddress` with the street, locality, region, and postal code populated; `Article` needs `headline` and `datePublished` (and `author`). Cross-check the values against the rendered page: a `price` in the markup that differs from the price on the page is the mismatch that gets penalised. Finally, note in evidence that the authoritative check is Google's Rich Results Test, which is a browser tool this audit cannot drive — this block verifies syntax, required fields, and honesty, and the eligibility verdict should be confirmed there before launch.
evidence: per page — each `@type` found with `valid` or the specific missing property named; the full text of any block that failed to parse; any value that disagrees with the visible page; `no structured data` where none exists.
fix_hint: Emit one `@graph` per page containing an `Organization` and `WebSite` sitewide plus the page's own type, populate every required property from the same data the page renders so the two cannot disagree, and drop any markup describing content that is not on the page.

### SEO-010 Single H1; logical heading hierarchy
severity: low
tier: local
fix: easy
why: Headings are the document outline both crawlers and screen readers navigate by. Two H1s split the page's stated topic; zero leaves it unstated; and a jump from H2 to H4 makes the outline structurally wrong, which is a screen-reader problem before it is an SEO one.
verify:
  static: Look at how the page shell and its sections are composed (stack ref: "routes and handlers"). The recurring cause of a duplicate H1 is a layout that renders the site name as an H1 in the header and a page that renders its own title as an H1 too; the recurring cause of a missing one is a hero section styled with a large `<div>` or `<p>` instead of a heading. Check whether shared components (hero, section header, card) hardcode a heading level rather than taking it as a prop, since that is what produces skipped levels when a component is reused one level deeper.
  local: From the saved probe, read `h1_count` for the home page — exactly 1 passes, 0 or 2+ is the finding. The probe does not record the other levels, so for the home page and the ten sampled pages extract the outline from each saved HTML: `python3 -c "import re,sys; h=re.sub(r'(?is)<(script|style|noscript)[^>]*>.*?</\1>',' ',open(sys.argv[1]).read()); print([(int(m.group(1)), re.sub(r'<[^>]+>','',m.group(2)).strip()[:60]) for m in re.finditer(r'(?is)<h([1-6])[^>]*>(.*?)</h\1>', h)])" page.html` — strip the script and style blocks first, as that line does, or a heading inside a JSON-LD string or a JS template literal is counted as a real one and you will report a phantom second H1. Read the resulting sequence for two faults: more or fewer than one level-1 heading, and any step that increases by more than one level (an H2 followed by an H4). Ignore decreases — going from H3 back to H2 is a normal new section. Note headings that are empty or contain only an icon, which read as blank in the outline. A heading rendered only after JavaScript runs will be missing here; if the outline looks empty on a page that clearly has headings, that is SEO-016's finding, so check there before reporting an absent H1.
evidence: per page — the ordered list of heading levels with their text truncated, the H1 count, and any level skip named explicitly (`h2 "Pricing" -> h4 "Team plan"`); the component file:line responsible for a duplicated or hardcoded level.
fix_hint: Render exactly one H1 per page carrying that page's topic (the site name in the header should be a link, not an H1), and make shared section components take their heading level as a prop so nesting a component deeper does not skip a level.

### SEO-011 hreflang correct
severity: low
tier: local
fix: easy
when: features.multilingual
why: hreflang tells search engines which language version to show which user. Done wrong it does nothing at all — the annotations are ignored unless they are reciprocal — and the language versions then compete with each other as duplicate content instead of consolidating their authority.
verify:
  static: Find the i18n setup (stack ref: "routes and handlers", "build"): the configured locale list and default locale (`next.config` `i18n`, `next-intl` routing, `nuxt-i18n`, `django.conf` `LANGUAGES`, Rails `I18n.available_locales`), the URL strategy (subdirectory `/es/`, subdomain `es.example.com`, or separate ccTLDs), and where the alternate links are generated — Next.js `alternates.languages` in a `metadata` export, a loop emitting `<link rel="alternate" hreflang>` in the layout, or a sitemap-level `xhtml:link` annotation. Confirm the generator emits a link for *every* locale on *every* localised page including the page's own locale, since a non-self-referencing set is the most common reason the whole annotation is discarded.
  local: For each configured locale, request that locale's home page and one deeper page (`curl -s <base>/<locale>/ > <locale>.html`, or the subdomain/ccTLD equivalent) and extract the annotations: `grep -oiE '<link[^>]+hreflang=[^>]*>' <locale>.html`. Then check four things. Self-reference: each page's set includes its own locale pointing at its own URL. Reciprocity: if `/es/` lists `/fr/` as an alternate, `/fr/` must list `/es/` — a one-way set is ignored entirely, and this is what to spend the time on. Valid codes: BCP-47 with a hyphen and a language subtag first (`es`, `es-MX`, `pt-BR`), not an underscore, not a region alone (`MX` is not a language), and `x-default` present pointing at the locale selector or the default-language page. Consistency with the document: the probe's `lang` field for the home page (and the `<html lang>` of each localised page) must match the locale that page is served as, and every hreflang target must return 200 rather than redirecting to the default locale, which is a redirect loop waiting to happen. Also confirm the pages are actually translated: identical body text under two locale prefixes is duplicate content that hreflang cannot fix.
evidence: per locale page — its URL, its `<html lang>`, and the full list of hreflang values with their targets; a reciprocity matrix or a plain list of the one-way pairs; any invalid code, missing `x-default`, or alternate URL that did not return 200.
fix_hint: Generate the full alternate set from the locale list once, in shared layout code, so every localised page emits every locale including itself plus an `x-default`; use hyphenated BCP-47 codes, make each `<html lang>` match, and point alternates at URLs that return 200 directly.

### SEO-012 No redirect chains; trailing-slash consistency
severity: low
tier: remote
fix: easy
why: Every hop in a redirect chain costs a round trip on the user's connection and a fraction of the crawler's patience, and browsers and crawlers both give up after a handful. The trailing-slash half is the quieter one: when both `/about` and `/about/` return 200, they are two URLs with one page's content, splitting links and rankings between them.
verify:
  static: Find every layer that can redirect (stack ref: "routes and handlers", "build"): the framework's `trailingSlash` setting, a `redirects()` block in `next.config`, `vercel.json` `redirects`/`routes`, a `_redirects` file, middleware that rewrites hosts or appends locales, `nginx` `return 301`/`rewrite`, Rails `constraints` or `redirect`, and the CDN or domain registrar's own apex-to-www forwarding, which is invisible in the repo and is usually the extra hop. Note the intended canonical form: apex or www, slash or no slash, and whether the config agrees with what the canonical tags say (SEO-006).
  remote: Test the four entry points a real visitor or crawler uses, against `remote.url`'s host: `http://<host>/`, `https://<host>/`, `https://www.<host>/`, and the apex if www is canonical. For each, count and inspect the hops with `curl -sIL -o /dev/null -w '%{num_redirects} %{url_effective}\n' <url>`, then dump the chain itself with `curl -sIL <url> | grep -iE '^(HTTP/|location:)'` so each status and target is visible. One hop is normal and expected (http to https, or apex to www). Two or more is the finding: `http://example.com` to `https://example.com` to `https://www.example.com` to `https://www.example.com/` is three hops where one would do. Check the status codes too — a permanent canonicalisation should be 301 or 308, not 302 or 307, which tell crawlers to keep the old URL. Then trailing slash: pick three real paths from the sitemap and request each in both forms without following (`curl -s -o /dev/null -w '%{http_code}\n' <base>/<path>` and again with a trailing slash). Exactly one form should return 200 and the other should 301 to it; both returning 200 is the duplicate-content fail, and both redirecting to each other is an infinite loop that will show as `curl: (47)`. Confirm the surviving form is the one the canonical tag and the sitemap use.
evidence: per entry point — the full hop list with each status and `location`, and the final `url_effective`; per tested path — the status of both slash forms side by side; the canonical form named, and whether robots, sitemap, and canonical tags all agree with it.
fix_hint: Collapse the chain to one hop by pointing the DNS or CDN rule straight at the final origin form (http-to-https and apex-to-www in a single 301), pick one trailing-slash convention in the framework config, and make the sitemap and canonical tags emit that same form.

### SEO-013 No broken internal or external links or images
severity: medium
tier: local
fix: easy
why: A broken internal link wastes crawl budget and dead-ends a reader mid-journey; a broken image leaves a hole in the page. External links rot on their own schedule, and the ones in a launch-day footer are usually the oldest text on the site.
verify:
  static: Read how links are constructed (stack ref: "routes and handlers") before testing them, because the pattern matters more than any one broken href: string-concatenated paths that can produce a double slash, links built from a CMS field that may be empty (`href={post.url}` rendering `href=""`, which links to the current page), hardcoded absolute URLs to your own domain (which bypass client routing and are also HYG-002's finding), and images whose `src` comes from an external host or a CDN with an expiring URL. Note any link list held in config or content files rather than in code, since that is the one nobody re-checks.
  local: Build the link set from the saved home-page probe's `links`, plus the links found in the ten sampled pages' saved HTML, and deduplicate. Resolve relative hrefs against the base; drop `mailto:`, `tel:`, `javascript:`, `data:`, and pure `#` fragments. Split into internal (same host as the base, or originally relative) and external (any other host), and cap the run at 50 internal and 20 external so this does not become a crawl. Write them to a file and loop: `while read u; do printf '%s %s\n' "$(curl -s -o /dev/null -w '%{http_code}' -L --max-time 10 "$u")" "$u"; done < links.txt`. Use `-L` so a link through a redirect is judged by where it lands, and `--max-time 10` so one hanging host does not stall the domain's budget. Then do the same for images: extract the `src` values from the same saved HTML with `python3 -c "import re,sys; print('\n'.join(m.group(1) or m.group(2) or m.group(3) for m in re.finditer(r'(?is)<img[^>]+src=(?:\"([^\"]+)\"|\x27([^\x27]+)\x27|([^\s>]+))', open(sys.argv[1]).read())))" page.html` (a bare `grep` for `src="` misses unquoted attributes and prints tag fragments rather than URLs), resolve them against the base, cap at 20, and request each. Reading the results: any internal link or image returning 4xx or 5xx is a fail, and a `000` from curl means a connection failure or timeout — retry it once before reporting. For external hosts, treat 403 and 429 as `unverified`, not broken: plenty of sites block unknown user agents or rate-limit, and reporting a working link as dead sends someone on a pointless errand. Report those separately with the status you got, and say in evidence that they were not confirmed either way.
evidence: two lists — broken (status, URL, and the page it was found on) and unverified (status, URL, reason); the counts checked in each category so the sampling is visible (`42 of 42 internal, 20 of 63 external`); the file:line of any empty or malformed href found statically.
fix_hint: Fix or remove every internal 4xx (usually a renamed route with no redirect — add the redirect rather than only editing the link), replace dead external links, and guard CMS-driven hrefs so an empty field renders no link instead of a link to nowhere.

### SEO-014 Search Console verification present
severity: low
tier: attest
fix: none
why: Search Console is the only place you can see what search engines actually did with your site — which pages were indexed, which were rejected and why, which queries you appear for, and whether a manual action was applied. Verifying it after launch means the first weeks of indexing data, the ones that tell you whether the launch worked, were never recorded.
verify:
  static: Look for verification artifacts in the repo before asking: a `<meta name="google-site-verification" content="...">` in the root layout or base template, a `verification: { google: ... }` entry in a Next.js `metadata` export, a `google<hash>.html` file in `public/`, a Bing `<meta name="msvalidate.01">`, a Yandex or Baidu equivalent, or a DNS TXT record defined in infrastructure code (a `google-site-verification=` string in a Terraform or Pulumi DNS resource). Note that the most common verification method is a DNS TXT record or a Google Analytics/Tag Manager association, none of which leave a trace in the repo — so finding nothing here is not evidence of absence, and the block must go to the user rather than failing on a missing meta tag.
  attest: Ask the user, and record the answer clause by clause: is the *production* property (the exact protocol-and-domain form users will reach, or a Domain property covering all of them) verified in Google Search Console; has the sitemap been submitted there; and does someone actually receive its notification emails? A property verified on `http://` or on the non-canonical www form reports on a URL set nobody visits, so ask which form. Machinery found in the repo without that confirmation is `attest`, not `pass`. Bing Webmaster Tools is worth the same question in one line, but its absence is a note rather than a finding.
evidence: any verification artifact found with file:line and its method; the user's answer per clause — property form verified, sitemap submitted, notification recipient — or `unconfirmed`.

### SEO-015 Clean URLs; no query-param duplicates without canonical
severity: low
tier: local
fix: easy
why: URLs are read by people in search results and in shared links, and they are the crawler's primary hint about site structure. The bigger half of this check is the duplicate one: when the same page is reachable at a dozen parameter combinations and none of them declare a canonical, a search engine has to guess which is the real one, and it will not always pick yours.
verify:
  static: Read the route definitions (stack ref: "routes and handlers") and note the URL shapes the app produces: slug-based (`/blog/how-we-built-it`) versus opaque ids (`/post?id=8412`), underscores versus hyphens as word separators, mixed or upper case in paths, file extensions left on (`/about.html`, `/index.php`), and any path carrying a session or tracking value. Then list every query parameter that changes what a page renders: `?page=`, `?sort=`, `?filter=`, `?variant=`, `?q=`, and the tracking family (`?utm_*`, `?ref=`, `?fbclid=`, `?gclid=`). For each, decide what the canonical strategy should be and check whether the code implements it: tracking parameters must be stripped from the canonical entirely; filter and sort parameters on a list page should canonicalise to the unparameterised page; and paginated pages should self-canonicalise to their own `?page=2` URL, because canonicalising page 2 to page 1 tells the crawler pages 2 onward do not exist and its contents will not be indexed. That last one is a frequent well-intentioned mistake and worth checking explicitly.
  local: From the saved probe's `links`, list the distinct path shapes and flag any with underscores, uppercase segments, file extensions, or numeric-only identifiers where the content clearly has a title to slug. Then test the parameter behaviour directly: request one real page with a tracking parameter appended (`curl -s '<local.url>/<path>?utm_source=prelaunch&utm_medium=audit' | grep -oiE '<link[^>]+rel=[\"\x27]?canonical[\"\x27]?[^>]*>'`) and confirm the canonical comes back as the clean path with no parameters — a canonical that echoes the tracking parameters back means every shared link creates a new indexable URL. Repeat on a list page with a sort or filter parameter, expecting the canonical to point at the unparameterised page, and on `?page=2` if pagination exists, expecting it to point at itself. Also confirm the same page served with and without a parameter is not returning different canonical hosts or a redirect loop.
evidence: the distinct path shapes with any flagged pattern named; per parameter tested — the requested URL and the canonical that came back, with the expected value beside it; the file:line implementing (or not implementing) the stripping.
fix_hint: Build canonicals from the route's own clean path rather than from the incoming request URL, so tracking and filter parameters are dropped automatically; keep page 2 canonicalising to itself; and use hyphenated lowercase slugs instead of ids or underscores for anything meant to be found.

### SEO-016 Key public pages server-render content for crawlers
severity: medium
tier: local
fix: guided
why: A page whose text only exists after JavaScript runs is a page a crawler may index late, partially, or not at all — rendering is a separate, queued, best-effort pass, and it is not guaranteed for every crawler or every social scraper. If the HTML is an empty root div, the link preview is blank and the search snippet is whatever the crawler could scrape from the shell.
verify:
  static: Determine the rendering mode from the build configuration (stack ref: "build", "routes and handlers"). Server-rendered or statically generated by construction — Next.js App Router server components, `getStaticProps`/`getServerSideProps`, Nuxt universal mode, SvelteKit with SSR on, Astro, Remix, Rails or Django templates, or a static export — passes structurally, and you should say so rather than treating the local probe as the only evidence. Client-only shapes are the finding: a Vite or CRA SPA serving one `index.html` with an empty mount point, SvelteKit with `export const ssr = false`, a Next.js page whose entire content sits under a `dynamic(..., { ssr: false })` import or behind a client-side data fetch in a `useEffect`, or a marketing page gated behind a client-side auth or feature-flag check that renders a spinner on the server. Note which of the key public pages (home, pricing, the main content or blog listing, one detail page) fall into each category.
  local: Against the production build per the header rule, not the dev server, whose HTML differs. Request each key public page as a crawler would: `curl -s -A "Googlebot" <url> > crawl.html`, then count the visible words in the raw HTML with `python3 -c "import re,sys; t=re.sub(r'(?is)<(script|style|noscript)[^>]*>.*?</\1>',' ',open(sys.argv[1]).read()); print(len(re.sub(r'(?s)<[^>]+>',' ',t).split()))" crawl.html`. Compare that count against what the page visibly contains — a pricing page showing three tiers and forty lines of copy should not come back with twelve words. Then grep the same file for the specific things that must be in the HTML: the page's H1 text, one distinctive sentence of body copy, the `<title>`, and the canonical tag. The saved probe is corroborating evidence here — a `title` or `h1_count` of null or 0 for a page that clearly has both in the browser is exactly this failure, since the probe reads raw HTML and runs no JavaScript. Two false alarms to rule out before reporting: a page that legitimately has little text (a login screen, a bare app shell behind auth) is not a public content page and is out of scope for this check, and a site behind a bot-protection layer may serve a challenge to an unfamiliar user agent — if the response looks like a challenge page, say so rather than reporting the site as client-rendered.
evidence: per page — `curl -A Googlebot <path> → <n> words in raw HTML`, whether the H1, title, and a quoted body sentence were present, and the rendering mode from the static entry; the framework setting or file:line responsible for any client-only page.
fix_hint: Move the key public pages onto the framework's server-rendered or statically generated path so their content is in the initial HTML; where a component must stay client-only, render its content on the server and hydrate it rather than fetching it in a `useEffect`, and keep the title, H1, and canonical out of client-side injection entirely.

### SEO-017 Auth-only pages noindexed and excluded from sitemap
severity: medium
tier: local
fix: easy
why: Indexed dashboard and account URLs put a "log in to see your data" page in front of a stranger's search for your product, which is a wasted result, and any of them that render real content unauthenticated is an access-control failure that the search index has now published and cached.
verify:
  static: List the routes that require a session (stack ref: "auth"): the middleware `matcher` or path list, a route group such as `(app)` or `(dashboard)`, `@login_required` decorators, `before_action :authenticate_user!`, a guarded layout, or a server-side session check at the top of each handler. For each, check two things. Does the app mark it noindex — a `robots: { index: false }` in that route group's metadata, a `<meta name="robots" content="noindex">` in the authenticated layout, or an `X-Robots-Tag` set for those paths (stack ref: "security headers")? And does the sitemap generator exclude it (SEO-003's exclusion list)? A generator that enumerates every route file without filtering will happily publish `/settings/billing`.
  local: Against the production build, request each candidate path unauthenticated — with no cookie jar, so nothing from an earlier authenticated check leaks in: `curl -s -o /dev/null -w '%{http_code} %{redirect_url}\n' <local.url><path>` for `/dashboard`, `/account`, `/settings`, `/app`, `/admin`, `/profile`, plus every route the static entry found behind auth. Expected: a 3xx to the login page, or a 200 that *is* the login page, or a 401/403. Also fetch the headers and body of any that return 200 and check for a `noindex` in either the meta tag or `x-robots-tag`, since a login page at `/dashboard` returning 200 with no noindex is still an indexable URL. Then read the saved probe's `pages["/sitemap.xml"]["urls"]` and confirm none of these paths appear in it. The escalation to watch for: a 200 that renders actual application content or user data without a session is not an SEO finding, it is a broken access control — report it here with the evidence you have and cross-reference the security domain's authorization checks rather than filing it as a low-priority indexing note.
evidence: per path — `GET <path> (no cookies) → <status> <redirect target>`, the robots meta or `x-robots-tag` if any, and whether the path appears in the sitemap; the middleware or decorator file:line covering each; any path that returned real content unauthenticated, called out explicitly.
fix_hint: Set `noindex` once on the authenticated layout or via an `X-Robots-Tag` rule covering the authenticated path prefix, filter those prefixes out of the sitemap generator, and confirm the auth middleware actually matches every one of them rather than only the paths someone remembered to list.
