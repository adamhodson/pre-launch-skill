# Payment checks (PAY)

Read `agents/domain-auditor.md` for procedure. Blocks below are checks; consult stack references for locations. Tools: `grep` and the repo's schema files for the static work; the payment provider's own CLI (`stripe prices retrieve` and `stripe checkout sessions list` for PAY-014 and PAY-004, `stripe listen` where a block needs delivery, or the equivalent) **only where it is already installed**; `curl` with the cookie jar written by FLOW-001 for the three local probes that drive the app's own billing endpoints (PAY-004, PAY-012, PAY-014); `python3` with only the standard library for reading a saved JSON response. A browser driver is used **only if the project already depends on one** (`playwright`, `puppeteer`, `@playwright/test`, `cypress`, `selenium` in devDependencies or in a `playwright.config.*`). Never install anything to run this audit, and never sign up for a provider account to answer a question.

**The whole domain is gated on `features.payments` in `SKILL.md`, so no block below carries a `when`.** If the project takes no money, this file does not run at all. Within the domain, several blocks describe machinery that only a subscription product has, and a one-time-purchase product must not be failed for lacking it: where a check's subject is recurring billing — the dunning states of PAY-006, the plan-limit and proration halves of PAY-007, the portal of PAY-012, the trial half of PAY-015, and all of PAY-017 — a product that sells only one-off purchases passes that part with the reason recorded as `n/a — one-time purchases only, no recurring plan found at <file:line>`. That is a pass with a stated reason, not a silent skip and not a fail. Say which plans you found before claiming it: a single `mode: "payment"` checkout with no `price` carrying a `recurring` object, no subscription table, and no cancellation route is the evidence that earns the exemption.

**The second exemption is the shape of the checkout rather than the shape of the plan.** A product can sell entirely through a provider-hosted no-code link — a Stripe Payment Link, a Lemon Squeezy or Paddle checkout URL, a Gumroad or Polar product page — pasted into the markup as an `href` with no server-side creation route behind it. That is a legitimate integration and it removes the code this domain's two request-shaped probes exist to test: there is no endpoint to send twice and no handler choosing a price id, because the provider owns both. Where the static entry finds the checkout entry point is a bare link to a provider domain and no `checkout.sessions.create`, `paymentIntents.create`, or equivalent exists anywhere in the repository, PAY-004 and PAY-014's local halves record `n/a — checkout is a provider-hosted link, no server-side creation route at <the link's file:line>` and each block says which half of it still applies rather than passing wholesale: **PAY-004's idempotency question is genuinely n/a** (the provider deduplicates its own link), while **PAY-014's displayed-price-versus-price-object comparison still applies in full** — the link resolves to one price object, the pricing page states a number, and those two disagreeing is exactly the defect that block is for, so resolve the link's price and compare it. Everything else in the file is unaffected: the webhook, the entitlement grant, the money columns, and the portal all still exist. Confirm the absence by grep before claiming it, since one hardcoded link on the marketing page beside a real checkout route elsewhere is a different situation and earns no exemption.

**Test-mode safety is absolute and it is checked before the probe, not during it.** Every local entry in this file begins the same way: read the payment keys the running environment actually uses (stack ref: "env vars") and confirm they are detectably test-mode — an `sk_test_` or `pk_test_` or `rk_test_` prefix for Stripe, a sandbox host or an explicit sandbox flag for PayPal, Paddle, Lemon Squeezy, or RevenueCat, a test-mode webhook signing secret. If they are not test-mode, or if you cannot tell which they are, the block records `error: live keys detected`, **stops before any request that could reach the provider**, and reports the static entry as its verdict. Use only the provider's published test cards from the stack ref "runtime probe hints" — on Stripe `4242 4242 4242 4242` succeeds, `4000 0000 0000 0002` declines, `4000 0000 0000 0341` attaches and then fails on the next charge, and `4000 0025 0000 3155` forces a 3D Secure challenge — and never a real card number, including your own. Never create a charge outside the provider's test mode, never fire a webhook at a production endpoint, never replay a captured real event, and never read, mutate, or delete a customer record you did not create in this audit. Webhook delivery for a local probe goes through the provider's own forwarder — `stripe listen --forward-to <local.url>/<webhook path>` or the provider's equivalent CLI; if no forwarder or tunnel is available the block records `error: webhook delivery not reachable locally`, quotes the exact command a human should run, and completes only the half that does not need delivery.

**Write blocks provider-agnostic; Stripe is the worked example, not the assumption.** Stripe's names appear throughout because they are the ones most readers recognise, but every rule here has an equivalent elsewhere and the finding must name the one this project actually uses: RevenueCat, Lemon Squeezy, Paddle, Polar, Chargebee, Braintree, Adyen, PayPal. For any provider that is not Stripe, take the API names, event names, dashboard locations, and test credentials from that provider's stack reference rather than translating Stripe's by guesswork — say **see the provider stack ref** in the finding when the specific name is not established there yet, and never assert an event name or a parameter you have not seen in this repo or in that reference. Merchant-of-record providers (Paddle, Lemon Squeezy, Polar, and the app stores behind RevenueCat) change several answers in this file outright rather than renaming them, most visibly for tax (PAY-008) and receipts (PAY-010), and each block says where.

**What the flows own and what this domain owns, so the same work is not done twice.** FLOW-004 through FLOW-007 and FLOW-021 walk the user journey — checkout to grant, cancel to revocation, decline to dunning, trial to conversion, plan change to proration — and they are the runtime evidence. This file owns the mechanism underneath each of them: FLOW-004 proves one legitimate webhook grants access, PAY-002 owns whether the whole event set is handled and PAY-003 owns what happens when the same event arrives twice; FLOW-005 proves access ends at the period end, PAY-012 owns whether the provider's portal is configured to let the user get there; FLOW-021 proves a plan change works, PAY-007 owns whether the limit is enforced on the server at all. Where a flow has already run, cite its finding from `.pre-launch/findings/flows*.json` — the domain writes more than one file, so glob rather than naming one — and do not re-drive the app. Three neighbouring domains own pieces that look like this one's and are not: **SEC-051 owns webhook signature verification and SEC-052 owns constant-time comparison** — PAY-003 owns only deduplication and the replay-timestamp tolerance, and cites those two for whether a signature is checked at all; **COMP-011, COMP-012, COMP-013, COMP-022, and COMP-026 own the policy and disclosure side** of cancellation, auto-renewal consent, reminder cadence, PCI scope, and price transparency, while the blocks here own the code that has to exist for those policies to be true; **PERF-017 owns read-then-write race conditions on credits, quota, and stock**, and PAY-004 owns only the idempotency key on checkout and charge creation. **DAT-013 owns transactions around multi-step writes**, which is the right citation whenever a webhook handler writes two tables without one.

**Artifacts go under `.pre-launch/payments/`, and nothing this domain does modifies a project file.** Create the directory once with `mkdir -p .pre-launch/payments` before the first probe. The names used below are `keys.txt` (the test-mode determination and the prefixes seen, written once and read by every later block), `checkout-body.json`, `idempotency-1.json` and `idempotency-2.json`, `portal.html`, and `prices.txt`. A bare relative filename lands in the project root, and a stray file holding a provider response is both a leak and something that can ship in the next deploy. Findings go where every domain's do: `.pre-launch/findings/payments.json`, one object per check ID. Do not add a key, flip a flag, edit a route, comment out a guard, or change a price to make a check pass — a probe that needs a code change to run is a finding, not a blocker.

### PAY-001 Live webhook endpoint registered for prod URL with live signing secret
severity: critical
tier: attest
fix: guided
why: This is the single point where money becomes access, and it is the one piece of the payment integration that does not live in the repository — so it is the piece that gets forgotten. The two failure shapes are both silent at deploy time and both cost real money. Either no live-mode endpoint was ever created in the provider dashboard, so every production charge succeeds and no event ever arrives and nobody is granted anything; or an endpoint exists but the production environment holds the signing secret from a developer's `stripe listen` session, which is a different secret with the same prefix, so every live event arrives, fails verification, and is discarded with a 400 that only the provider's dashboard records. In both cases the customer is charged, sees a success page, and gets nothing, and the first report comes from support rather than from an alert.
verify:
  static: Establish, from the repository, the exact facts the human has to check against the dashboard, because an attest question that does not name a URL and an environment variable gets answered "yes" without anyone looking. Find the webhook route and its full path (stack ref: "webhook handlers", "routes and handlers"). Find the production origin from configuration rather than assuming it (stack ref: "env vars" — a `NEXT_PUBLIC_APP_URL`, `PUBLIC_URL`, `APP_URL`, `SITE_URL`, or the deploy platform's own domain setting) and compose the full URL that must be registered, for example `https://app.example.com/api/webhooks/stripe`. Find the environment variable the handler reads the signing secret from and name it exactly (`STRIPE_WEBHOOK_SECRET` is the convention, but read the code rather than the convention). Then check three things that are visible from here. Whether the secret is read from the environment at all or is a literal in source, which is a finding on its own and belongs to SEC-001 as well. Whether any committed configuration pins a test-mode value into a production file, which is REL-007's grep and worth reusing rather than repeating. And whether the repo contains any infrastructure-as-code that creates the endpoint (a Terraform `stripe_webhook_endpoint`, a provisioning script, a `webhooks.create` call in a setup task) — where it does, the registration is code and you can read it, and the attest question narrows to whether that code has been applied to the live account. Note also whether more than one endpoint would be needed: a separate preview or staging deployment that shares the production key needs its own endpoint and its own secret, and a project with several webhook routes (payments plus a separate connect or billing-portal route) needs one registration each.
  attest: Ask the user, and record the answer: in the payment provider's **live-mode** dashboard right now, is there a webhook endpoint whose URL is exactly `<the composed production URL>`, is it enabled, is it subscribed to the event types the handler needs (PAY-002 lists them), and is the signing secret shown for **that live endpoint** the value currently set in the production environment as `<the exact env var name>` — not a value copied from a `stripe listen` session and not the test-mode endpoint's secret? All four clauses need a yes. A yes to "we set up the webhook" without the live-mode qualifier is a partial answer; ask again naming live mode, because a test-mode endpoint configured perfectly grants nothing in production. If the provider dashboard shows recent delivery attempts for that endpoint, ask for the last 24 hours' success rate too and record it, since a 100% failure rate there is this check failing with evidence already available. PAY-016 owns whether a failure on that endpoint alerts anyone.
evidence: the composed production webhook URL with the route's file:line and the config value the origin came from; the signing-secret env var name and whether it is read from the environment or hardcoded, with file:line; any infrastructure-as-code that registers the endpoint, with file:line, or `endpoint registered by hand — dashboard only`; every additional webhook route needing its own registration, listed; the user's answer clause by clause — endpoint exists in live mode, enabled, event subscriptions, secret matches production — or `unconfirmed`; the recent delivery success rate if given. Evidence consumed by PAY-016 (which endpoint's failures must alert), FLOW-004 (whether a delivery failure or a logic failure broke the grant), and REL-007 (the live/test key swap).
fix_hint: The implementation note names the exact URL to register in live mode, the event list from PAY-002 to subscribe it to, and the environment variable to paste the live endpoint's signing secret into, and it says explicitly that the secret from a local `stripe listen` session is a different value that must not be used in production. Where the repo already provisions the endpoint in code, the note is about applying that provisioning to the live account rather than about creating anything by hand. Where preview deployments share the production key, the note adds a second endpoint and a second secret rather than pointing both at one. Pair it with PAY-016 so the endpoint that was just registered also alerts when it starts failing.

### PAY-002 Entitlement synced on every relevant event: failed, updated, cancelled, past_due, refund, dispute
severity: critical
tier: static
fix: guided
why: Almost every integration handles the happy path, because the happy path is the one the developer tested with their own card. The events that arrive later are the ones that carry the money back out again, and an unhandled one always fails in the direction of giving the product away: a subscription cancelled in the provider's portal that the app never hears about leaves the user on a paid plan forever; a refunded charge that never reaches the entitlement table means you returned the money and kept serving; a dispute you learn about from the bank rather than from your own webhook is access you are still providing to someone who is contesting the payment. The asymmetry matters — the grant path is exercised on every sale and is therefore correct, and the revoke paths are exercised by a small fraction of customers and are therefore untested.
verify:
  static: Open the webhook handler and list every event type it actually branches on (stack ref: "webhook handlers") — read the `switch` or the dispatch map, not the comment above it, and record for each case what it writes and to which table (stack ref: "data access"). A case that logs and returns, or a case present in the switch whose body is a `TODO`, counts as unhandled and must be named as such rather than ticked off. Then compare that list against the set this product needs. For Stripe the set is `checkout.session.completed`, the renewal-success event, `invoice.payment_failed`, `customer.subscription.updated`, `customer.subscription.deleted`, `charge.refunded`, and `charge.dispute.created`. **`invoice.paid` and `invoice.payment_succeeded` both cover the renewal-success case and handling either one satisfies it** — they fire on the same successful invoice, so report which of the two this handler uses and never list `invoice.paid — absent` when `invoice.payment_succeeded` is handled; handling both is not a defect either, but note it, since two handlers on one event is a duplicate-grant risk that PAY-003's dedup has to absorb. Fail if `customer.subscription.updated`, `customer.subscription.deleted`, `invoice.payment_failed`, or `charge.refunded` is missing, since those four are the revoke path and their absence is the defect this check exists for. For RevenueCat the equivalent set is `INITIAL_PURCHASE`, `RENEWAL`, `CANCELLATION`, `EXPIRATION`, `BILLING_ISSUE`, and `REFUND`, and note that `CANCELLATION` there means the user turned off auto-renew while `EXPIRATION` is the one that actually ends access, so an integration that revokes on `CANCELLATION` cuts off a paying customer early. For Lemon Squeezy the set is `subscription_created`, `subscription_updated`, `subscription_cancelled`, `subscription_expired`, `subscription_payment_failed`, and `order_refunded`. For any other provider, take the set from that provider's stack ref rather than translating these by name. Then check the three things that make a handled event still wrong. The write must be keyed on something stable that ties the provider's object to your user — the provider customer id stored on the user row, or a `client_reference_id` or `metadata.user_id` set at checkout — and not on an email address, which changes. The status the app stores must be able to express `past_due` as a state distinct from both `active` and `cancelled`, or the grace period FLOW-006 tests cannot exist. And `customer.subscription.updated` must be read for what actually changed rather than treated as a cancel signal, since it fires on plan changes, trial ends, and status transitions alike. Finally, note whether the handler returns a 2xx before or after doing the work: acknowledging first and processing asynchronously is fine only if the work is durably queued, and acknowledging after a write that can fail without retry protection is where events get silently dropped.
evidence: the handler file:line and the full list of event types it branches on, each marked `handled — writes <table>.<column>` or `case present, no write` or `absent`; the required set for this provider beside it with the missing ones named, and for Stripe `renewal success handled via <invoice.paid|invoice.payment_succeeded|both|neither>` rather than a per-name absence; the key the write joins on (`stripe_customer_id`, `metadata.user_id`, or `email — unstable`) with file:line; the status values the entitlement column can hold and whether `past_due` is among them; where the 2xx is returned relative to the write; `FLOW-004 evidence reused for the grant case` and `FLOW-005 evidence reused for the cancel case` where those flows ran. Evidence consumed by PAY-001 (the event list to subscribe the live endpoint to), PAY-003, PAY-006, PAY-011, PAY-018, and FLOW-004 through FLOW-006.
fix_hint: The implementation note lists the specific event types to add for this provider, and for each one names the exact write — table, column, and the value it should hold — rather than saying the event should be handled. It keys every write on the stored provider customer or subscription id, adds a `past_due` state distinct from active and cancelled so the dunning window of PAY-006 has somewhere to live, and treats `customer.subscription.updated` as a status and plan reconciliation rather than a cancellation. It cites PAY-003 so the new handlers are idempotent from the start rather than being made idempotent in a second pass, and DAT-013 where a case writes more than one table.

### PAY-003 Webhook events deduplicated and order-tolerant; timestamp replay protection
severity: high
tier: static
fix: guided
why: Providers guarantee at-least-once delivery, which is a promise that duplicates will happen, not a risk that they might. A handler that adds a month of access on `invoice.paid` gives out two months when the provider retries after a timeout, and one that increments a credit balance hands out free credits to anyone who can make the endpoint slow. Ordering is the same problem from a different angle: events are not guaranteed to arrive in the order they occurred, so a `subscription.updated` to `active` that lands after the `subscription.deleted` for the same subscription resurrects a cancelled plan. And replay is what happens when the first two are fixed but the tolerance is not: a valid signed event captured once can be posted back forever if no timestamp window is enforced.
verify:
  static: Read the webhook handler (stack ref: "webhook handlers" for the route and "webhook verification snippet" for the shape verification takes on this stack). This block owns three specific properties and **not** signature verification, which is SEC-051's, nor the constant-time compare, which is SEC-052's; read those findings and cite them, and if no signature is verified at all say so once here and let SEC-051 carry the verdict. Deduplication: find where the handler records that it has seen an event, which should be a table keyed on the provider's own event id (`event.id`, `id`, or the provider's delivery id — take the field name from the provider stack ref) with a unique constraint, checked or inserted before the work rather than after it. The safe shapes are an insert that fails on the unique index and short-circuits, or an `insert ... on conflict do nothing` whose affected-row count decides whether to proceed; the unsafe shape is a `select` that checks for the row followed by the work followed by an insert, which is exactly PERF-017's race and double-processes under concurrent retries — cite PERF-017 when you find it. A handler with no event table at all fails unless every one of its writes is naturally idempotent, and naturally idempotent means setting a value (`status = 'active'`, `plan = 'pro'`), never adding to one; a single `credits += n` or `period_end += 30 days` anywhere in the handler makes the whole thing non-idempotent regardless of what the other cases do, so read every case. Order tolerance: check whether writes are guarded by the event's own timestamp or by the provider object's version — the correct pattern is to ignore an event carrying data older than what is already stored (compare `event.created` or the subscription's `current_period_start` against the row's last-updated marker), or to re-fetch the object from the provider and write the current truth rather than the event's payload, which sidesteps ordering entirely and is the better fix on most stacks. Replay tolerance: on Stripe, `stripe.webhooks.constructEvent(body, sig, secret)` enforces a default tolerance of 300 seconds on the timestamp in the signature header and throws outside it, so the pass condition is that the default is left alone or narrowed; a `tolerance` argument raised to a large number, or a hand-rolled verification that parses the `t=` value and never compares it to the clock, is the fail. For other providers, confirm from the stack ref whether the SDK enforces a window and, where it does not, that the handler compares the event timestamp to now itself. Note the retention question while you are in the table: an events table with no pruning grows forever, which is a smaller problem than double-charging but worth one line.
evidence: the dedup mechanism with file:line and the column it keys on, plus the unique constraint's migration file:line, or `no event table — handler relies on idempotent writes` with each write classified `set` or `increment`; every non-idempotent write quoted with file:line; the order-tolerance mechanism (`timestamp compared at <file:line>`, `object re-fetched from provider at <file:line>`, or `none — event payload written blind`); the replay tolerance as configured, quoted from the verification call, with `default 300s` where the argument is absent; `SEC-051 owns signature verification — <its verdict>`; whether the events table is pruned. Evidence consumed by PAY-002 (whether newly added handlers are safe to retry), PAY-004, PAY-018, and PERF-017; SEC-051 reads the same handler for signature verification.
fix_hint: The implementation note adds a `processed_events` table keyed on the provider's event id with a unique constraint, and makes the handler insert first and return early when the insert conflicts, so the dedup is enforced by the database rather than by a check-then-act in application code. It converts every incremental write in the handler into an absolute one — set the period end from the provider's object rather than adding to the stored value — or moves the increment behind the dedup insert inside the same transaction (DAT-013). For ordering, it re-fetches the subscription or invoice from the provider inside the handler and writes that, rather than trusting the payload's age. For replay, it leaves the SDK's default timestamp tolerance in place and removes any widened value. It states the pruning interval for the events table so the fix does not create a second problem.

### PAY-004 Idempotency keys on charge creation; double-submit cannot double charge
severity: critical
tier: local
fix: guided
why: A user whose first click appeared to do nothing clicks again, and a mobile connection that drops after the request left the phone but before the response came back produces the same shape without anyone clicking twice. Without an idempotency key the provider treats the second request as a second purchase, because from its side that is exactly what it looks like. The result is a double charge, which is the one payment defect that produces a support ticket, a refund, a chargeback risk, and a review, all from one customer, and it is prevented by one parameter.
verify:
  static: Find every call that creates a charge or a purchasable object (stack ref: "routes and handlers" — on Stripe that is `checkout.sessions.create`, `paymentIntents.create`, `subscriptions.create`, `invoices.pay`, and `charges.create` on older integrations; take the equivalents for another provider from its stack ref) and read whether each passes an idempotency key. On Stripe the key goes in the request options rather than the parameters — `stripe.checkout.sessions.create(params, { idempotencyKey })` — which is why it is so often omitted: the call looks complete without it. Then judge the key itself, because a present key can still be worthless. It must be derived from the intent, not from the moment: a hash of user id plus price id plus a client-supplied request id, or a row created before the call whose primary key becomes the idempotency key, both pass. `crypto.randomUUID()` generated inside the handler fails, because a retry generates a new one and the provider sees a new request. A timestamp, likewise. Note the provider's retention window for keys where the stack ref states it, since a key is only good for as long as the provider remembers it. Then check the second half of the defect, which lives in the app rather than at the provider: is the checkout button disabled on submit, and — the half that actually matters, since a client guard is not a control — does the server refuse a second in-flight checkout for the same user and price, through a unique constraint on a pending-order row, a short-lived lock, or by returning the existing open session rather than creating another. Cite PERF-017 for the general read-then-write shape and DAT-013 where the creation writes a local row and calls the provider without a transaction or a reconciliation path. Note explicitly whether a redirect to a hosted checkout page makes double-submission harmless for this integration: a Stripe Checkout session that has not been paid does not charge anything, so two sessions are untidy rather than expensive, while two `paymentIntents.create` calls followed by two confirmations are two charges. Say which shape this is.
  local: **Confirm test-mode keys first per the header rule and write the determination to `.pre-launch/payments/keys.txt`; if they are not detectably test-mode, record `error: live keys detected` and stop before any request.** Where the static entry found no server-side creation route at all because checkout is a provider-hosted link, record `n/a — checkout is a provider-hosted link, no server-side creation route at <file:line>` per the header's second exemption and stop here; the provider deduplicates its own link and there is nothing local to send twice. Otherwise, against the running app as the test account (reuse the cookie jar from `.pre-launch/flows/cookies.txt` where FLOW-001 ran), build the request body from the handler the static entry just read — take the field names and the plan or price identifier from that handler's own parameter parsing rather than guessing, use the cheapest plan, and write it to `.pre-launch/payments/checkout-body.json` so it lands in this domain's directory and not the project root. Then send that body twice in immediate succession — `curl -s -b .pre-launch/flows/cookies.txt -X POST <local.url>/api/checkout -H "Content-Type: application/json" -d @.pre-launch/payments/checkout-body.json` twice, saving the responses to `.pre-launch/payments/idempotency-1.json` and `idempotency-2.json` — and compare the identifiers they return. One session or intent id returned twice is the pass; two distinct ids is the finding, and it is the finding even when the integration is a hosted checkout, because it shows no key is in play. Where the project already has a browser driver, add the human version: click the checkout button twice as fast as the driver can, and record how many objects were created at the provider. Then look at what was created rather than only at what was returned: list the recent test-mode objects for the test customer through the provider's CLI if it is installed (`stripe checkout sessions list --limit 5` or the equivalent) and count them. Record every request as `METHOD /path → STATUS`. Do not complete either checkout — this block is about creation, and FLOW-004 owns the completed purchase.
evidence: `test-mode keys confirmed: <prefixes seen>` or `error: live keys detected`; every charge-creating call with file:line and `idempotency key: <expression>` or `NONE`, with each key classified stable or per-request; `POST /api/checkout → 200 id=<a>` and `POST /api/checkout → 200 id=<b>` with `same id` or `two objects created`; the object count at the provider for the test customer before and after; the server-side double-submit guard with file:line or `client-side disable only` or `none`; whether the integration's shape makes a duplicate session harmless, stated. Evidence consumed by PERF-017 (the concurrency shape), DAT-013 (the local write beside the provider call), and FLOW-004.
fix_hint: The implementation note adds an idempotency key to every charge-creating call, derived from the user id, the price id, and a request id the client sends and reuses on retry — never a UUID generated inside the handler — and names each call site by file:line. It adds the server-side guard the client-side disabled button is standing in for: a unique constraint on an open order or checkout row for that user and price, with the handler returning the existing session rather than creating a second one. Where a local row is written alongside the provider call, it cites DAT-013 for the transaction or, since the two systems cannot share one, for the reconciliation path that the idempotency key makes possible.

### PAY-005 Money stored as integer minor units with currency code
severity: high
tier: static
fix: guided
why: Binary floating point cannot represent most decimal fractions, so a column typed `float` or `double precision` holding 0.1 is holding something slightly other than 0.1, and a sum of a few hundred of those is visibly wrong on a statement. The failure is not theoretical and it is not only cosmetic: totals that disagree with the provider's by a cent make reconciliation impossible, refunds computed from a rounded value over- or under-return, and revenue reporting drifts. The second half of the check is the one people skip entirely: an amount with no currency beside it is not an amount, and the day the product takes its second currency every historical row becomes ambiguous with no way to recover the answer.
verify:
  static: Find every column, field, and variable that holds an amount of money (stack ref: "data access" — the schema files first, then the models): prices, totals, subtotals, tax, discounts, credits denominated in currency, payouts, refunds, invoice line items. For each, record the declared type. The clean pass is an integer type holding minor units — `integer`, `bigint`, `int` — which is also the shape Stripe and most card processors use on the wire, so it needs no conversion at the boundary. Sort everything else into three verdicts rather than one, because the fixes are different sizes and filing them at the same weight buries the one that matters. **The float family is an unconditional fail**: `float`, `real`, `double precision`, `Float`, `Double`, and a JavaScript `number` persisted as JSON are inexact, and no amount of care at the call sites makes them exact. **A fixed-point decimal is a pass with a note when all three of these hold, and a fail when any of them is absent**: the column declares an explicit scale (`numeric(12,2)`, `DECIMAL(12,2)`, a Prisma `@db.Decimal(12,2)`, a Python `Decimal` column with precision and scale set); a currency column sits beside it; and no conversion site on the path between that column and the payment provider passes the value through a float-typed intermediate — grep the read and write sites for `parseFloat`, `Number(`, `parseInt` on a decimal string, a `float()` or `(float)` cast, and any arithmetic that leaves the decimal type before it reaches the API call. Decimal is exact, and not every provider speaks minor units: PayPal's REST API takes decimal strings (`amount.value`), while Stripe, Paddle Billing, and most card processors take minor units — `verify against the provider stack ref`, since the units a given API expects are the kind of detail that changes between a provider's own major versions, as Paddle Classic's major-unit decimals did on the way to Paddle Billing's minor units. So a consistent decimal integration is a legitimate design and must not be failed for not being the other one; what it must do is convert correctly at each provider boundary, in whichever direction that provider needs, and that is the bug it is prone to — which is what the three conditions test. **Unscaled `numeric` is a separate verdict and depends on the engine**, which is why it needs its own line: in Postgres, `numeric` with no precision or scale is exact arbitrary precision and stores cents correctly, so it passes on exactness with the missing scale noted as a schema-hygiene item; in MySQL, a bare `DECIMAL` defaults to `DECIMAL(10,0)` and silently truncates every fractional part, so every stored amount has already lost its cents — that is a fail, and it is a scale bug rather than an inexactness bug, so say so and check the existing data rather than only the schema. Name the engine before deciding. Grep the schema for the type names directly rather than reading every model by hand, then confirm each hit is really a money column. Then the currency half: every stored amount needs a currency alongside it, an ISO 4217 three-letter code in its own column, and a single-currency product is not exempt — it is the case where the column is cheapest to add and most likely to be missed. Check that the code stores the provider's currency value rather than assuming one, and that nothing compares or sums amounts across rows without matching the currency first. Then the minor-unit trap that catches integer-storing code specifically: dividing by 100 to display is wrong for zero-decimal currencies, where the minor unit is the major unit — JPY, KRW, VND, CLP and the others the provider lists — and wrong the other way for the three-decimal ones like BHD, JOD, and KWD. Find the formatting and parsing helpers and check whether they use the currency to decide the exponent (`Intl.NumberFormat` with the currency, or the provider's own helper) or hardcode a division by 100; note it as a finding scaled to whether the product sells in any such currency today. Finally, check rounding: any place a percentage is applied — tax, a discount, a proration, a platform fee — must round explicitly and consistently rather than relying on the language's default cast, and a `Math.round` on a float is not a fix for a float column.
evidence: every money column as `<table>.<column> — <declared type>` with the schema file:line, grouped into `integer minor units — pass`, `decimal, scale <n> — pass with note` or `decimal — FAIL (<missing condition>)`, `float family — FAIL (inexact)`, and `unscaled numeric on <engine> — <pass, scale unset|FAIL, truncates to DECIMAL(10,0)>`, with the database engine named; for a decimal column, every conversion site on the provider path with file:line and `float-typed intermediate: <expression>` or `stays decimal`; the currency column beside each or `no currency stored`; the currency value's source (`taken from the provider's object at <file:line>` or `hardcoded "usd" at <file:line>`); the display and parse helpers with file:line and whether the exponent comes from the currency or is a hardcoded division; every percentage calculation with its rounding, file:line; whether the product sells in any zero-decimal or three-decimal currency today. Evidence consumed by PAY-014 (the amounts it compares across surfaces), PAY-008 (whether tax is stored locally), and COMP-026.
fix_hint: For a float-typed column the note migrates it to an integer of minor units with an explicit `currency char(3)` beside it, and states the migration's two halves rather than only the type change: the backfill that multiplies existing values and the code changes at every read and write site, both of which have to land in the same deploy. For a decimal column the note does not propose a migration — it names the specific condition that failed and fixes only that: add the missing scale, add the currency column, or replace the named float-typed conversion with one that keeps the value in the decimal type all the way to the provider call. For a bare `DECIMAL` on MySQL the note is a data-repair item before it is a schema one, since the cents are already gone: it gives the `ALTER` to `DECIMAL(12,2)` and says the historical rows have to be restated from the provider's own records, which is not something a migration can compute. It replaces every hardcoded divide-by-100 with a currency-aware formatter, naming the zero-decimal currencies that break the old code.

### PAY-006 Dunning: retry schedule, notification, grace period, revocation
severity: high
tier: static
fix: guided
why: Cards expire, get replaced after fraud, and get declined for insufficient funds, so a meaningful percentage of every subscriber base fails a renewal every month. What happens next decides whether those customers are recovered or lost, and both errors are expensive in opposite directions: an app that revokes access on the first decline loses customers who fully intended to pay and were never told, and an app that ignores the failure entirely serves a customer who stopped paying until someone notices manually. The recovery machinery is mostly the provider's, which is why this check reads as configuration rather than code — but the states it produces have to exist in the application or none of it lands.
verify:
  static: A product with no recurring plan passes this block with the reason from the header. Otherwise establish four things and name which of them is missing, because a partial dunning implementation is the normal finding. **The retry schedule**: where is it configured, and is it on? On Stripe this is Smart Retries in the billing settings, which retries on a schedule derived from when the charge is likeliest to succeed, along with a configured number of attempts and a terminal action — cancel the subscription, mark it unpaid, or leave it past due. That configuration lives in the dashboard rather than the repository, so read whatever the repo can tell you (a `subscriptions.create` passing `payment_settings`, a `collection_method`, an infrastructure-as-code billing setting) and where the repo is silent, say so and phrase it as an attest question in the finding — `is Smart Retries enabled in the live-mode billing settings, how many attempts does it make, and what is the terminal action?` — rather than assuming a default is in place. **The notification**: find the code path (stack ref: "webhook handlers", "background jobs") from `invoice.payment_failed` (or the provider's equivalent, `BILLING_ISSUE` on RevenueCat, `subscription_payment_failed` on Lemon Squeezy) to an email or in-app message, and confirm three separate things — a handler is registered for the event, it sends something rather than logging, and the message contains a link that reaches a card-update page that a `past_due` account can actually load. That last one is the specific failure: a dunning email whose update-card link sits behind a paywall the failed payment just closed. Note whether the provider's own dunning emails are enabled instead of or alongside the app's, since two sources sending different things is its own problem. **The grace period**: is there a window between the first failure and revocation during which access continues, is its length defined somewhere readable, and does the entitlement check treat `past_due` as still-entitled? A codebase whose access check is `status === 'active'` has no grace period no matter what the dashboard says, and that is a one-line finding with a file:line. **The revocation**: does anything actually revoke at the end? Find the terminal event the provider sends when retries are exhausted (`customer.subscription.deleted`, or `customer.subscription.updated` to `unpaid` depending on the configured terminal action) and confirm PAY-002's handler writes the revocation on it. An integration with retries, emails, and a grace period but no terminal handler serves the customer forever, which is the same outcome as having none of it. FLOW-006 runs this path against the app; cite its evidence for whichever of the four it observed rather than re-driving it.
evidence: `recurring plans found at <file:line>` or the one-time-purchase exemption with its evidence; the retry configuration as far as the repo shows it, with file:line, plus `retry schedule is dashboard configuration — not verifiable from the repo` where it is not; the failure event's handler file:line and what it sends, or `event handled, nothing sent`, or `event unhandled`; the card-update route and whether a `past_due` session can load it, with the entitlement guard's file:line; the grace period's length and where it is defined, or `none — access check is <expression> at <file:line>`; the terminal event and its handler file:line, or `no revocation on terminal event`; `FLOW-006 evidence reused` where that flow ran. Evidence consumed by FLOW-006, PAY-009 (the same email carries the renewal-authentication link), PAY-012 (whether a past_due account can reach the card-update page), and COMP-013.
fix_hint: The implementation note treats the four parts as one change and names which are missing. It defines `past_due` as an entitlement state that still grants access, for a stated number of days, so the grace period exists in code rather than only in intent; it sends a notification on the first failure whose card-update link lands on a page reachable by a `past_due` session, which usually means moving that route outside the paywall guard; and it revokes on the provider's terminal event through the same handler PAY-002 covers. For the retry schedule it gives the dashboard setting to check by name — Smart Retries and the terminal action on Stripe, the equivalent from the provider stack ref elsewhere — rather than proposing an app-side retry loop, which duplicates what the provider already does better. It cites COMP-013 where the notification's timing is also a statutory question.

### PAY-007 Plan limits enforced server-side; downgrade and proration defined

tier: static
fix: guided
why: A limit that lives in the interface is a suggestion. tier: attest
fix: guided
why: Sales tax and VAT are collected from the customer at the moment of sale or they are paid out of the company's own margin later, and the second one is how a small SaaS discovers it owes several years of VAT on European sales it priced without any.   static: Read what the code does about tax, which is a narrower question than whether the tax position is right. Everything else is not a code change and the note says so plainly: the registration position, the jurisdictions, and the thresholds go to an accountant, and where the provider is a merchant of record the note records that and closes the item rather than proposing registrations the company does not need.

### PAY-009 SCA / 3D Secure supported

tier: static
fix: guided
why: European regulation requires strong customer authentication on a large share of card payments, which means the bank can respond to an otherwise valid charge by demanding the cardholder complete a challenge. An integration that treats every non-success as a decline fails those payments outright, and the customer sees "your card was declined" for a card that works perfectly — so the loss is silent, it is concentrated in one region, and it looks like a fraud-rate problem rather than an integration bug.   static: Establish the integration's shape first (stack ref: "routes and handlers" for the checkout surface, "known traps" for this processor's integration pitfalls), because it decides whether there is anything to check. Where the custom flow must stay, it handles the intermediate action status by calling the provider's confirmation function and re-reading the intent's status on the server, and it changes the failure copy from "declined" to a prompt to confirm with the bank. It adds off-session consent when the card is saved, and handles the renewal-authentication event by emailing the customer a link to complete the challenge, reusing PAY-006's dunning template rather than building a second one.

### PAY-013 Restricted API keys used server-side where provider supports
severity: medium
tier: static
fix: easy
why: A secret key is a key to the whole account: it can read every customer, create charges, issue refunds, and change subscriptions. Most of what an application actually needs is a fraction of that, and the providers that support scoped keys make the reduction a five-minute change. The reason to do it before launch rather than after is that the value of a leaked key is decided at the moment it leaks, and the difference between a scoped key and a full one is the difference between an incident and a rotation.
verify:
  static: Find every provider credential the server reads (stack ref: "env vars") and classify each by what it is: a publishable or client key, which is public by design and belongs in the browser; a full secret key; a restricted key; and a webhook signing secret, which is a different thing again and belongs to PAY-001. On Stripe a restricted key carries the `rk_` prefix against `sk_` for a full secret key, and both have `test` and `live` variants — record the prefix you see rather than the variable name, since a variable called `STRIPE_RESTRICTED_KEY` holding an `sk_live_` value is the exact failure this check catches. Then work out what permissions the code actually needs by listing the API calls it makes: creating checkout sessions, reading subscriptions, creating portal sessions, and issuing refunds are four distinct permissions and most apps need two of them. A key scoped to those, with everything else set to none, is the pass. Then check where each key is used, because a scoped key in one place and a full key in another gains nothing: separate serverless functions, background jobs, a scripts directory, and any admin tooling each read their own credential and each should hold the narrowest one that works. Note where a provider does not support restricted keys at all — several do not — and record that as `provider does not support scoped keys` rather than as a failure; the check is whether the capability was used where it exists, and the provider stack ref is the place to confirm that. Two adjacent findings worth naming while you are here without taking them over: a secret key of any kind referenced from client-side code or a public environment variable is SEC-001's and is critical rather than medium, and the absence of a rotation plan belongs to the security domain too. Say whether the key appears anywhere a browser could reach it and hand it over.
evidence: every provider credential with its env var name, the prefix actually seen (`sk_live_`, `rk_test_`, `pk_live_`), and the surface that reads it, with file:line; the list of API operations the code performs, which is the permission set the key needs; per key, `scoped appropriately`, `full secret key where a restricted one would do`, or `provider does not support scoped keys`; any secret key reachable from client code, named and handed to SEC-001. Evidence consumed by SEC-001 (any secret key reachable from client code) and REL-007 (the production key inventory).
fix_hint: Create a restricted key in the provider dashboard granting only the operations this code performs — name them from the evidence, for example write on Checkout Sessions and Billing Portal Sessions and read on Subscriptions and Customers, everything else none — and replace the full secret key in the server environment with it. Give any background job, script, or admin surface its own key scoped to its own operations rather than sharing one, and delete the full key from every environment that no longer needs it once the replacement is confirmed working.

### PAY-014 Pricing page, checkout, and terms state identical prices
severity: high
tier: local
fix: easy
why: Prices get written in more places than anyone remembers — a marketing page, a pricing component, a plan constant, the provider's own price objects, a comparison table, the terms of service, an FAQ — and they get updated in some of them. The customer sees the discrepancy at the moment they are being asked to pay, which is the worst possible moment: it reads as a bait and switch even when it is a stale constant, and it is a refund request when the charge is the higher number. The second half of the check is the one with teeth: a checkout that accepts an amount from the client lets anyone pay whatever they choose.
verify:
  static: Build the price inventory first (stack ref: "routes and handlers" for the pricing route and the checkout construction). Grep the repository for currency-formatted numbers and for the plan names, and list every place a price appears with its file:line: the marketing and pricing pages, any pricing component or constants file, the terms and any FAQ or comparison table, the metadata on the provider's price objects if the repo pins ids, and the checkout construction itself. Then the mechanism, which decides whether a mismatch is cosmetic or exploitable. The checkout call must reference a price or plan **identifier** defined on the server — `line_items: [{ price: "price_1234", quantity: 1 }]` — and the identifier must be chosen server-side from the plan the user selected, not read from the request body. The fails, in ascending order of severity: an amount rendered from a hardcoded constant that differs from the provider's price object, which is a display bug; a price id sent from the client and used without validation against an allowlist, which lets a user check out on any price in the account including a one-cent test price; and `unit_amount` or `amount` passed straight into the charge from the request, which is the customer naming their own price and is the finding to lead with. Read the handler and say which of the three this is. Then check the neighbours that make a correct integration still inconsistent: a price shown per month that bills annually or the reverse (COMP-012 owns the disclosure obligation, this block owns the number); a currency displayed that differs from the currency charged; and a discounted or promotional price on the marketing page that no coupon in the account produces.
  local: **Confirm test-mode keys first per the header rule.** Where checkout is a provider-hosted link with no server-side creation route, record `n/a — checkout is a provider-hosted link, no server-side creation route at <file:line>` for the tampering half only, and **run the comparison half in full**: resolve the price object the link points at and compare it against every displayed number exactly as below, since a link whose price object disagrees with the pricing page is this block's defect with the provider hosting it rather than fixing it. Otherwise, against the running app, fetch the pricing page and the checkout entry for each plan and record the number the user sees at each step — `curl -s <local.url>/pricing` and the checkout route — saving what you read to `.pre-launch/payments/prices.txt` as one line per plan per surface. Then read the price the app actually sends to the provider: where the provider CLI is installed and keys are test-mode, resolve each price id the code uses and record its `unit_amount`, `currency`, and `recurring.interval` (`stripe prices retrieve <id>`); where it is not, take the value from wherever the repo pins it and label it as such. Compare every number against every other and report the first disagreement rather than a matrix. Then run the adversarial half, which is cheap and is the reason this block is local: post the checkout-creation request with a tampered body — a different price id, and separately an explicit amount field the API does not expect — and confirm both are rejected or ignored rather than honoured. A session created at the attacker's number is a critical finding recorded here and cross-referenced to SEC-037, which owns server-side validation of client-supplied input, and to SEC-011 where the tampered id reaches an object belonging to someone else. Record every request as `METHOD /path → STATUS`, and do not complete any checkout.
evidence: `test-mode keys confirmed: <prefixes seen>` or `error: live keys detected`; the price inventory as one line per occurrence — `<plan> <amount> <currency> <interval> at <file:line or route>` — grouped by plan with the disagreements marked; the provider's own price objects resolved, with `unit_amount`, `currency`, and `interval`; the checkout construction's file:line with `price id chosen server-side`, `price id accepted from client`, or `amount accepted from client`; `POST /api/checkout (tampered price id) → <status>` and `POST /api/checkout (explicit amount) → <status>`; any interval or currency mismatch between what is displayed and what is charged. Evidence consumed by COMP-026 (the price components and when each is first shown), COMP-012 (the cadence a price is presented at), and PAY-005.
fix_hint: Make the provider's price objects the single source of truth and render the pricing page from them — fetched at build time or cached — so the marketing number cannot drift from the billed one; where that is too large a change, keep one constants file that every surface imports and delete the duplicated literals, naming each file:line to change. In the checkout handler, map the user's plan selection to a server-side allowlist of price ids and pass only the id, never an amount, and reject any price id that is not in the allowlist rather than trusting it.

### PAY-015 Promo and trial abuse limited: one trial per person; single-use codes
severity: medium
tier: static
fix: guided
why: A free trial with no identity check is a free product for anyone willing to type a second email address, and the cost of that is not the trial itself but the infrastructure the serial trialists consume — which on an AI product is a real bill. Promotional codes have a sharper edge: a code intended for one customer that has no redemption limit gets shared, posted to a coupon site, and applied to every subscription for months before anyone reads the revenue report closely enough to notice.
verify:
  static: A product with no trial passes that half with the header's reason. Otherwise find how a trial is granted (stack ref: "routes and handlers") — `trial_period_days` on a subscription or price, `trial_end`, or the app's own trial column — and then find what stops the same person taking it twice. The mechanisms that work, in rough order of strength. First, and this is the one to lead with: reuse one provider customer object per user, so a returning person is the same customer rather than a new one, and keep the app's own record of who has already had a trial — a `trial_started_at` or a prior-subscription row keyed on the user id **and** on the payment method fingerprint, since an email address is free and a card is not. Second, requiring a card at trial start, which is a product decision that happens to be an abuse control. Third, whatever eligibility control the provider itself offers, which varies by provider and is **not** Stripe's `trial_settings` — that parameter governs what happens when a trial ends with no payment method on file (`end_behavior.missing_payment_method`) and grants no once-per-customer guarantee, so do not report it as one; take the actual eligibility mechanism from the provider stack ref and, where the stack ref does not establish one, say `provider-side trial eligibility not established — see the provider stack ref` rather than naming a parameter. The mechanism that does not work, and is the common one: a check on the email address alone. Record which is in place. Then check the adjacent leak that makes any of them moot — whether a returning user gets a **new** provider customer object every time they check out, which resets whatever the provider was tracking; find where the customer id is looked up before creating one and confirm the lookup exists. For promotion codes, list how discounts enter the system: provider-managed coupons and promotion codes, or an app-side code table. For each code, record four things and keep the last two apart, because they are different controls that get conflated. The account-wide redemption limit (`max_redemptions`), which caps total uses by anyone. The first-purchase restriction (`restrictions.first_time_transaction` on a Stripe promotion code), which allows the code only for a customer with no prior successful payment — that limits who may use it, not how many times one person may. Pinning the code to a single customer, which is the promotion code's own `customer` field and is the control to reach for when a code was issued to one named person. And the expiry, plus whether the discount applies once or to every renewal forever — the last one is the expensive default nobody reads, since a percentage-off coupon applied to a subscription usually recurs. Where codes live in the app's own table, check for the same four properties plus the thing the provider gives you for free: an atomic redemption that cannot be used twice concurrently, which is a unique constraint on the redemption row rather than a count-then-insert; cite PERF-017 for that shape. Finally, note whether promo codes are enabled on the checkout surface at all (`allow_promotion_codes`), since a code the user can type into a field you did not intend to expose is its own surprise.
evidence: `trials found at <file:line>` or the no-trial exemption; the trial-eligibility mechanism with file:line, classified provider-tracked, app-tracked on user and payment method, app-tracked on email only, or none; whether a returning user reuses the stored provider customer id, with the lookup's file:line or `new customer created per checkout at <file:line>`; every promotion code or coupon with its redemption limit, per-customer restriction, expiry, and whether it recurs on renewals, or `codes are provider-managed — limits not visible from the repo`; the redemption write's file:line and whether it is atomic; whether promotion codes are enabled on the checkout surface, file:line. Evidence consumed by FLOW-007 (the trial it walks) and COMP-013 (the reminder that trial creates).
fix_hint: The implementation note reuses one provider customer object per user — look it up by the stored id before creating one, and store it on first creation — so the provider's own trial eligibility and coupon restrictions have something stable to attach to, and it names the file:line where a new customer is currently created each time. It sets trial eligibility to once per customer at the provider rather than checking an email address in application code, and where an app-side check is kept it keys on the payment method fingerprint as well as the user. For codes it sets an explicit maximum redemption count, a per-customer restriction, and an expiry on every code, states whether the discount should apply once or to every renewal and configures it that way rather than accepting the default, and backs any app-side redemption with a unique constraint.

why: A webhook endpoint that starts failing does so silently from the application's side, because the failure is a non-2xx the provider records and the application does not. A deploy that changes a route, an environment that loses its signing secret, a handler that starts throwing on a schema change — each of these keeps the checkout working perfectly while nobody gets what they paid for, and each is invisible until customers complain.   static: Read what the repository shows about failure visibility on the app's side, which is the half you can see. ### PAY-017 Price change notice and consent for existing subscribers
severity: high
tier: static
fix: guided
why: Raising the price of an existing subscription without telling anyone converts a renewal into a dispute, and the customer is right: they authorised one amount and were charged another. Several jurisdictions require advance notice for exactly this, the card networks treat an unexpected recurring amount as a legitimate dispute reason, and the app stores go further — Apple requires the subscriber's affirmative consent for a price increase, and without it the subscription simply does not renew, so an unhandled increase on an iOS product churns the entire cohort silently. What makes this a pre-launch check rather than a later one is that the mechanism has to exist before the first price change, and by then the subscribers are already there.
verify:
  static: A product with no recurring plan passes with the header's reason. Otherwise this block asks whether the product **can** change a price correctly, since at launch it has not yet had to. Establish four things (stack ref: "data access" for the subscription schema, "background jobs" for the send path a notice would use). First, whether existing subscribers are pinned to the price object they subscribed on or read a plan price from a table that a future edit would silently reprice — the second shape is the one where a routine constants change charges every existing customer more, with no code path aware that anything happened; find where the renewal amount comes from and say which it is. Second, whether any notification mechanism exists that can reach all current subscribers of one plan: a query that can select them, a template, a send path. It does not have to be built for price changes specifically, but if there is no way to email a plan's subscribers at all then a price change cannot be announced, and that is the finding. Third, the grandfathering question, which is a product decision the code either supports or does not: can two customers on the same plan be on different prices at once? A schema with a price id on each subscription supports it; a plan name plus a global amount does not, and that limitation should be recorded now rather than discovered during the first increase. Fourth, the platform rule where one applies: for a subscription sold through the app stores (RevenueCat and its underlying store), the consent requirement is the store's and it is enforced by the store — Apple requires the subscriber to agree to an increase or the renewal stops, with a limited exception the store defines, and Google has its own notice and consent process; take the current mechanics from the provider stack ref rather than from memory and mark them `verify current store policy` where the exact behaviour matters to the plan. Then read the terms of service for what the company has already promised about price changes — a notice period stated there is a commitment that binds regardless of what any statute requires — and COMP-012 owns the auto-renewal disclosure the same terms carry; cite it.
evidence: `recurring plans found at <file:line>` or the exemption; where the renewal amount is read from — `price id pinned on the subscription row at <file:line>` or `plan amount read from <file:line> — a change reprices existing subscribers` — with the schema quoted; whether subscribers of one plan can be selected and emailed, with the query or template file:line, or `no path to notify a plan's subscribers`; whether two prices can coexist on one plan, from the schema; the store consent mechanics where the product sells through an app store, with `verify current store policy`; the terms of service's stated notice period, quoted, or `terms are silent on price changes`; `COMP-012 owns the renewal disclosure`. Evidence consumed by COMP-012 (the renewal terms the same subscribers were told) and PAY-007 (the plan model that makes grandfathering possible).
fix_hint: The implementation note pins each subscription to the provider price object it was created on, so a new price is a new object and existing subscribers keep theirs until they are deliberately migrated — that single change makes grandfathering possible and makes an accidental repricing impossible, and it is much cheaper before launch than after. It adds the ability to select and email the subscribers of one plan, which is the mechanism a notice needs, and states the notice period the terms of service commits to so the two agree. Where the product sells through an app store, it records that the increase must go through the store's consent flow and that a subscriber who does not consent stops renewing, and it points at the provider stack ref for the current mechanics rather than restating them here.

### PAY-018 Entitlement granted only from webhook or server-verified session, never from success-URL params
severity: critical
tier: static
fix: guided
why: If `/success?session_id=...` or `?paid=true` flips the user to paid, anyone can type that URL. This is the single most common real-money bug in indie SaaS, and it survives review because the code looks reasonable: the redirect only happens after a real payment, so the developer reads the handler as being on the payment path. It is not — it is on the public internet, reachable by anyone, at a URL the user can bookmark, share, or edit.
verify:
  static: Find the checkout success route and any client code that runs after the redirect (stack ref: "routes and handlers"). Fail if a database write granting access happens there based on a query parameter alone. Pass if the grant happens in the webhook handler (PAY-002) or the success route retrieves the session server-side from the provider (`checkout.sessions.retrieve`) and checks `payment_status == "paid"` before writing. `payment_status == "no_payment_required"` is the second passing value and must be accepted alongside it: a session for a trial with no immediate charge, or one a 100% coupon zeroed out, completes legitimately with that status and nothing else, so a handler checking only for `"paid"` silently refuses to grant every trial and every fully discounted purchase — treat a check on `"paid"` alone as a finding in the opposite direction from this block's usual one, and treat `status == "complete"` with neither payment status read as the fail it looks like. Also confirm the client cannot call the grant endpoint directly (it must be webhook-only or require the retrieved session). Three variants of the same bug are worth grepping for by name because they do not look like the canonical one: a `?paid=true`, `?upgraded=1`, or `?plan=pro` parameter read anywhere on the success page and written; a client-side effect that calls an internal API on mount with values taken from the URL, where the endpoint itself does no verification; and a retrieve-then-write that fetches the session but never reads its status, or reads it and writes regardless. Where the retrieval shape is used, check two further things: that the session's own customer or `client_reference_id` is compared against the logged-in user, since retrieving someone else's session id is otherwise a way to claim their purchase, and that the write is idempotent against the webhook doing the same thing moments later (PAY-003), because the two paths racing is how one purchase becomes two subscription rows. Note also the legitimate pattern that looks like the bug and is not: a success page that reads the session id purely to display a confirmation and to poll the user's own entitlement until the webhook lands is correct, and the distinguishing question is always the same one — does anything on this path **write** entitlement, and on what evidence. For a mobile or in-app-purchase product the same rule takes a different form: a client-reported purchase receipt is the query parameter, and the grant must come from the store's server-side validation or the provider's webhook. FLOW-004 exercises this path end to end; cite its evidence where it ran.
evidence: file:line of the success handler and where the entitlement write lives; whether the session is server-verified; the query parameters the success path reads, listed, with what each is used for; where the retrieval shape is used, whether `payment_status` is checked and whether the session's customer is compared to the logged-in user, with file:line; whether the grant endpoint is reachable by the client directly, with the route and its guard; `FLOW-004 evidence reused` where that flow ran. Evidence consumed by FLOW-004 (which half of the grant path broke) and PAY-002 (whether the webhook can carry the grant on its own).
fix_hint: Move the grant into the webhook handler keyed on the customer or metadata user id; have the success page poll the user's entitlement state instead of setting it (stack ref stripe "webhook handlers"). Where a server-side retrieval is kept as a fast path so the user sees their upgrade immediately, the note keeps it strictly in addition to the webhook rather than instead of it, checks `payment_status` and the session's own customer against the session user, and makes both paths write the same idempotent update so the race between them is harmless (PAY-003).
