# Flow checks (FLOW)

Read `agents/domain-auditor.md` for procedure. Blocks below are checks; consult stack references for locations. Tools: `curl` with a cookie jar for driving the app's own endpoints, `python3` with only the standard library for reading the mail catcher's JSON API and for opening an export archive, the project's own database client (`psql`, `sqlite3`, `npx prisma studio --help` for the connection string, the Supabase CLI) for the row counts two blocks need, and the payment provider's CLI (`stripe listen`, `stripe trigger`) **only where it is already installed**. A browser driver is used **only if the project already depends on one** (`playwright`, `puppeteer`, `@playwright/test`, `cypress`, `selenium` in devDependencies or in a `playwright.config.*`). Never install anything to run this audit.

Flows are end-to-end walkthroughs against `local.url` using the test account. They run before other domains that need an account; FLOW-001 creates it. Each flow is one check: pass when every step behaves, fail naming the first broken step. Where email is involved, read the local mail catcher (Mailpit, Mailhog, Inbucket via Supabase local, Resend test mode logs) named under the stack ref "runtime probe hints"; if no catcher is reachable, mark the step `error: no mail capture` rather than pass. All flows have a static fallback: trace the code path and report what would happen, marked `verified_by: static`.

**This domain is the one that behaves like a user, and that is the whole point of it.** Every other domain reads the code, the config, or one response. These blocks press the buttons in order, and the defects they catch are the ones that only exist between two correct components: a sign-up that writes the user row and then redirects to a page the unverified user cannot load, a checkout that charges the card and grants nothing because the webhook never reached localhost, a delete button that removes the row and leaves the files. So a flow is never reported as a list of steps that individually worked. It is reported as one verdict with the **first** broken step named, because the steps after a break tell you nothing — a walkthrough that fails at step 3 and then reports steps 4 through 7 as "pass" is reporting on an app state no user will ever be in. Record the steps you did reach, mark the rest `not reached`, and stop.

**Order of execution, which matters here more than in any other file.** The order is: **FLOW-001 first**, because it creates the account; then **FLOW-016's empty-state half**, which must run while the account is still empty and which is the only reason that block moves; then everything else in file order; then **FLOW-009 last**. FLOW-009 is deferred to the very end of the domain and is **the last block that touches the shared test account**, because it deletes it: run every other block that needs a login first — FLOW-002 through FLOW-008 and FLOW-010 through FLOW-021 — then come back and run FLOW-009. FLOW-016's other halves (404, absent resource, error page) are not order-sensitive and stay in file order with the rest. **FLOW-019 (change email and password) and FLOW-020 (social login and account linking) never touch the shared account at all**: both mutate the credentials that every other block depends on, so each creates its own throwaway identity by repeating FLOW-001's sign-up with a fresh `{ts}` in the email pattern, records it in `.pre-launch/flows/throwaway-019.json` and `throwaway-020.json`, and leaves `.pre-launch/test-account.json` untouched. If a block is run out of order and the shared account is gone, do not improvise a second one silently: every block from that point records `error: test account deleted by FLOW-009 — re-run the domain` so the report shows a sequencing fault rather than a product fault.

**The test-account contract.** FLOW-001 owns the file `.pre-launch/test-account.json` — the one artifact this domain writes outside its own directory, because other domains read it and the path is fixed by the spec. Its shape is `{"email": "...", "password_env": "PRELAUNCH_TEST_PASSWORD", "user_id": "...", "created_at": "...", "cookie": "<session cookie if obtainable>"}`. The password itself is never written to the file: `password_env` names the environment variable that holds it, per config `test_account.credentials_env`, and every later block reads the value from the environment. Config `test_account.strategy` decides how FLOW-001 behaves: `create` builds the address from `email_pattern` (substitute `{ts}` with a unix timestamp so re-runs never collide with a previous account) and signs up with the password from the named env var; `provided` means the account already exists — read the values, verify a login works, write the same file with `strategy: provided` noted in evidence, and do not attempt a sign-up; `none` means there is no test account and no permission to create one, so FLOW-001 records `error: no test account` and **every block below that needs a login records the same error rather than a fail**, since an unrun flow is not a broken flow. FLOW-009 does not delete the file when it finishes — it rewrites it with `"deleted": true` added, so a later domain reads the reason its login fails instead of a missing file.

**Mail capture, because half of these flows end in an inbox.** Find the catcher through the stack ref "runtime probe hints": Mailpit and Mailhog expose an HTTP API on `:8025` (`curl -s http://localhost:8025/api/v1/messages` for Mailpit, `/api/v2/messages` for Mailhog), Inbucket ships with `supabase start` on `:54324` (`curl -s http://localhost:54324/api/v1/mailbox/<mailbox>`), and Resend, Postmark, and SendGrid in test mode log the send rather than delivering it, so the "inbox" is the provider's test-mode log or the application log line. Read the message body, extract the link with a regex rather than by eye, and follow it with `curl`. Three rules: a mail step that you could not observe is `error: no mail capture`, never a pass — "the code calls `sendMail` so the email was sent" is exactly the assumption that ships a launch with an unverified sending domain; an email that arrives but whose links point at `localhost` when the config says otherwise is a finding you hand to HYG-002 rather than swallow; and never point the app at a real SMTP provider with real delivery to make a step pass.

**Payment safety is absolute, and it is checked before the flow starts, not during.** Before FLOW-004, FLOW-005, FLOW-006, FLOW-007, or FLOW-021 does anything, confirm the environment's payment keys are detectably test-mode (stack ref: "env vars"): a `sk_test_` / `pk_test_` prefix for Stripe, a sandbox host or sandbox flag for PayPal, Paddle, Lemon Squeezy, or RevenueCat, a test-mode webhook signing secret. If they are not — or if you cannot tell — the block records `error: live keys detected` and **stops before any request that could create a charge**; do the static entry and report that. Use only the provider's published test cards from the stack ref "runtime probe hints" (`4242 4242 4242 4242` succeeds and `4000 0000 0000 0002` declines on Stripe; every provider publishes an equivalent pair) and never a real card number, including your own. Never fire a webhook at a production endpoint, never replay a captured real event, and never touch a customer record you did not create in this audit. **Never touch real user data anywhere in this file**: every row you read, mutate, or delete belongs to an account this domain created.

**How you drive the app, named per step.** There are three ways and you say which one you used, because the confidence differs. First choice: the app's own HTTP endpoints with `curl` and a cookie jar — `curl -s -c .pre-launch/flows/cookies.txt -b .pre-launch/flows/cookies.txt`, posting to the same routes the forms post to (stack ref: "routes and handlers" for the paths, "auth" for the session cookie's name and how a session is obtained). This reaches the server logic, which is where nearly every flow defect lives, and it is the default. Second: a browser driver the project already has, which is the only way to reach a flow whose critical logic is client-side (a Stripe Elements checkout, a consent banner, an OAuth popup) — write a short script under `.pre-launch/flows/` and run it with the project's own runner; never install a driver to get one. Third: the framework's own test client (`supertest`, Django's `Client`, Rails' `ActionDispatch::IntegrationTest`, Laravel's HTTP tests) where the project already uses it and the route is awkward to reach over the wire. A flow whose decisive step is client-only and where no driver exists is not a pass and not a fail: it is the static entry plus `error: no browser driver` naming the step. **Record every request as `METHOD /path → STATUS` in evidence**, in order, including the redirects — the redirect chain after a sign-up or a login is itself the finding more often than the status code is.

**Measure a production build, never the dev server.** This is the same rule the performance, SEO, accessibility, and compliance domains state, and it changes verdicts here for reasons of its own: consent banners and analytics are commonly guarded by `if (process.env.NODE_ENV === 'production')`, so FLOW-013 reads clean on a dev server that ships eight pixels; error and 404 pages are replaced by the framework's dev overlay, so FLOW-016 sees a stack trace where users will see a page; and email links, OAuth redirect URIs, and webhook URLs are built from environment values that differ between modes. Build and start the app in production mode on a port you record — `npm run build && PORT=<port> npm start` with `NODE_ENV=production` for a typical Node stack, and the equivalent for this one (stack ref: "build" for the build and production start commands, "dev server" for the port convention) — and point every request in this file at that URL, noting it in evidence alongside `local.url`. If the production build cannot be run, do not report a dev reading as a production one: mark the affected blocks `dev-server only` in `notes`, and treat FLOW-013 and FLOW-016 as unverified rather than passing.

**Every artifact this domain writes goes under `.pre-launch/flows/`, with the single exception of `.pre-launch/test-account.json`.** Create the directory once with `mkdir -p .pre-launch/flows` before the first request. A bare relative filename lands in the project root, where a stray `cookies.txt` holding a live session is both a leak and a file that can ship in the next deploy. The names used below are `cookies.txt`, `requests.log` (the running `METHOD /path → STATUS` transcript that every block appends to), `mail-<flow>.json`, `webhook.log`, `export/` (where an export archive is unpacked), `upload-<n>.txt`, `maintenance.txt`, `consent-decline-requests.txt`, `preconsent.html`, `browser-<name>.txt`, `throwaway-017.json`, `throwaway-019.json`, and `throwaway-020.json`. The consent log is deliberately **not** called `preconsent-requests.txt`: compliance's COMP-007 already owns a file of that basename under `.pre-launch/compliance/`, and two files with the same name in different directories is how one gets read for the other. Findings go under `.pre-launch/findings/`, one object per check ID, but this domain is dispatched in three passes and each writes its own file: the account-creation pass (FLOW-001 and FLOW-016's empty-state half) writes `flows-1.json`, the main pass (everything except FLOW-009) writes `flows.json` — the name every consuming check reads — and the teardown pass (FLOW-009 alone) writes `flows-3.json`. Write only the file your dispatch names.

**Never modify project files.** Everything here is a request, a read, or a mutation of data belonging to an account this domain created. Do not edit a route to make a flow reachable, do not flip a feature flag in the repo, do not add a test-mode key, and do not comment out a guard. Two blocks legitimately change runtime state outside the test account's own rows — FLOW-007 may move a trial end date and FLOW-012 toggles the kill switch — and both say in their own text to restore the previous value and to record that they did.

**Cross-references, so the same work is not done or reported twice, and so the checks that consume this domain's evidence can find it.** FLOW-001's step count is written for COMP-011, which compares it against the cancel path's; record it even when the flow otherwise passes. FLOW-005's revocation result is what COMP-011 cites for the entitlement half and what PAY-002 cites for the `cancelled` event. FLOW-009 is the runtime evidence that DAT-020 and COMP-010 both read out of `.pre-launch/findings/flows*.json` — it lands in `flows-3.json`, written after those domains have already run, so within a single full run they fall back to a previous run's `findings.json` or to their own disposable account; it must still actually run and must actually record per-table counts, because the next run's DAT-020 and COMP-010 read it. FLOW-013 is the full runtime version of COMP-007's consent gate, and reuses COMP-007's saved pre-consent request log if that domain ran. FLOW-014 is the runtime half of COMP-016, which owns what a marketing email must legally contain, and of HYG-016, which owns rendering. FLOW-008 pairs with MOB-001, which owns the store-required restore control, and with PAY-002 for the entitlement. FLOW-010 walks the upload as a user; **the adversarial probes belong to SEC-047 (disguised executable, size limit), SEC-048 (filename and storage origin), and SEC-049 (SVG)** — this block confirms the happy path and one obvious rejection, cites those checks for the rest, and never re-runs their payloads. Likewise **the forged-webhook probe is SEC-051's**, not FLOW-004's: this domain proves a legitimate webhook arrives and grants, security proves an illegitimate one does not. FLOW-002 and FLOW-019 hand the cookie-attribute and invalidation questions to SEC-025 and SEC-026; FLOW-003 hands token single-use and enumeration to SEC-021 and SEC-018; FLOW-020 hands `state`/PKCE to SEC-028 and the redirect-URI dashboard config to HYG-001; FLOW-017 hands org-scoped authorization to SEC-061; FLOW-012 hands kill-switch existence to REL-010; FLOW-015 hands the support-routing policy to REL-028; FLOW-016 hands the 404 status code to SEO-009, error boundaries to REL-016, and placeholder copy to HYG-003; FLOW-018 hands the browser matrix to HYG-010; FLOW-011 hands the legal shape of a data-export request to COMP-019; FLOW-021 hands proration correctness and server-side plan limits to PAY-007. In every case: run the flow, report what happened, and cite the other ID rather than restating its verdict.

### FLOW-001 Fresh sign-up end-to-end; verification email received
severity: critical
tier: local
fix: guided
why: Sign-up is the only flow every single user takes, and it breaks in the seams: a user row written but no session issued, a redirect to a page the unverified user cannot load, a verification email that never arrives because the sending domain was never configured. It is also this domain's setup step — if it fails, most of the file cannot run, so run it first and report its failure plainly rather than letting nine other checks report mysterious 401s.
verify:
  static: Trace the sign-up path (stack ref: "routes and handlers" and "auth"): the form and its fields, server-side validation, where the user row is written (stack ref: "data access"), whether a verification or magic-link email is sent and through which provider (stack ref: "env vars"), whether a session is issued immediately or only after verification, and where the user is redirected on success. Note whether verification is enforced before the app is usable or merely requested — both are legitimate, but the flow must be consistent with the redirect target. Record the step list even when the runtime half runs: each screen, the fields it demands, the verification method, the number of steps from landing page to first authenticated page, and the elapsed time if measured. That step count is written for COMP-011, which compares the cancellation path against it and cannot do so without this number.
  local: Against the production build. Read config `test_account`. With `strategy: create`: build the address from `email_pattern`, substituting `{ts}` with a unix timestamp, take the password from the env var named in `credentials_env`, and drive the sign-up by the header's first available method — POST the sign-up route with `curl` and the cookie jar, or the project's existing driver if the form is client-rendered. With `strategy: provided`: log in with the given values instead, confirm a session is issued, and skip creation. With `strategy: none`: write no file and record `error: no test account`. After the sign-up, fetch the verification message from the mail catcher named in the stack ref "runtime probe hints", save it to `.pre-launch/flows/mail-001.json`, extract the verification link with a regex, follow it, and then request the authenticated landing page with the session cookie. Pass only when all four hold: the account is created, the email arrives, the link verifies, and the landing page returns 200 with the user's own content on it. Then write `.pre-launch/test-account.json` per the header contract, including the session cookie if one can be captured. The email step has three shapes and you must pick the right one, because two of them look identical from the inbox. If the static trace found **no verification or welcome email in the sign-up path at all**, the product deliberately sends none: record `no sign-up email by design`, drop the email and link conditions, and pass on the remaining ones — an app that logs the user straight in is a legitimate design and this check must not invent a missing email for it. If an email is sent by the code and no catcher is reachable, the step is `error: no mail capture`. If an email is sent by the code and a reachable catcher stays empty, that is a `fail`. Those three are different defects and must not be reported as the same one.
evidence: the ordered request transcript from `.pre-launch/flows/requests.log` as `POST /api/auth/signup → 302 /verify`, one line per step including redirects; the step list and the count as `sign-up: 3 steps (landing → /signup → /verify → /dashboard), fields: email, password, name; verification: emailed link`; the mail catcher used and the message subject and link host, or `no sign-up email by design — send path absent at <file:line>`; the created user id; `.pre-launch/test-account.json written` or the reason it was not; the first broken step where one exists, with the rest marked `not reached`.
fix_hint: The implementation note names the first broken step and its handler file:line, and states the expected behaviour for that step specifically — a session issued on success, a redirect target the new user's permissions actually allow, a verification email sent through a configured and verified sending domain (stack ref: "env vars"), and links built from a configured public origin rather than the request Host (SEC-022). Where the account could not be created at all, the note says which config field was missing rather than describing the sign-up code.

### FLOW-002 Login, logout, session expiry behave
severity: critical
tier: local
fix: guided
why: Login that works and logout that does not is a shared-computer incident waiting to happen, and a session that never expires turns a stolen cookie into permanent access. The failure is almost always logout: the client drops the cookie, the server never invalidates the session, and the same cookie replayed from `curl` still works.
verify:
  static: Read the login, logout, and session-validation code (stack ref: "auth"). Confirm: login issues a new session identifier rather than reusing one that existed before authentication; the session has a finite lifetime, set explicitly rather than inherited from a library default; logout invalidates server-side (deletes the session row, revokes the refresh token, or adds the JTI to a denylist) and does not merely clear the cookie in the browser; and a request carrying an expired or unknown session is refused with a 401 or a redirect to login, not served as anonymous-but-fine on a page that should require auth. Note the session lifetime, the idle-timeout if any, and whether a refresh token exists and how long it lives. SEC-025 owns the cookie's `HttpOnly`, `Secure`, and `SameSite` attributes and SEC-026 owns rotation and invalidation as security controls; this block owns whether the user-visible behaviour matches. Cite them rather than re-deriving.
  local: With the shared test account against the production build: log in through the app's own login route and capture the session cookie into the jar; request an authenticated page and confirm 200 with the account's own data; call logout; then **replay the captured cookie directly with `curl` against the same authenticated page** — this is the step that matters, and a 200 here is a fail no matter what the browser shows. Then check expiry by the cheapest honest means: read `Max-Age`/`Expires` on the issued cookie and, for a JWT session, decode the `exp` claim with `python3 -c "import base64,json,sys; print(json.loads(base64.urlsafe_b64decode(sys.argv[1].split('.')[1] + '==')))"` and compare it to the configured lifetime. Do not sit and wait for a real expiry. Where the session is a server-side row and the local database is reachable, expire it directly (set the expiry into the past on that row only) and confirm the next request is refused; restore nothing, since the row is the test account's own. Record the three outcomes separately: login, logout invalidation, expiry enforcement.
evidence: `POST /api/auth/login → 200, set-cookie <name>`; `GET /dashboard (session) → 200`; `POST /api/auth/logout → 204`; `GET /dashboard (replayed cookie) → 200 (expected 401)` or `→ 401`; the session lifetime as configured and as observed on the cookie or the `exp` claim; whether rotation on login was seen; handler file:line for any half that failed.
fix_hint: The implementation note must make logout a server-side invalidation — delete or revoke the session record, and for stateless tokens either keep them short-lived with a revocable refresh token or maintain a denylist — rather than a cookie clear, and must set an explicit finite session lifetime with rotation on login. It names the logout handler file:line and the place the lifetime is configured (stack ref: "auth"), and cites SEC-026 so the security fix and this behavioural one are the same change rather than two.

### FLOW-003 Password reset end-to-end
severity: critical
tier: local
fix: guided
why: Password reset is the flow users hit on their worst day, and it is the flow most often shipped untested because it is tedious to test by hand. It is also an authentication bypass when it goes wrong: a token that never expires, that works twice, or that arrives in an email whose link was built from an attacker-supplied Host header.
verify:
  static: Trace the request-reset and confirm-reset handlers (stack ref: "auth" and "routes and handlers"). Confirm the token is random and stored hashed or is a signed single-use artifact, that it carries an expiry, that confirming the reset consumes it, that existing sessions are invalidated on a successful reset, and that the link's origin comes from configuration rather than from the request. Note whether the reset response differs for a known and an unknown address, which is the enumeration question SEC-018 owns; SEC-021 owns single-use and expiry as controls and SEC-022 owns the link origin. Cite those three and do not restate their verdicts — this block owns whether a user can actually get back into the account.
  local: Against the production build with the shared test account: request a reset for the account's address, read the message from the mail catcher, save it to `.pre-launch/flows/mail-003.json`, and extract the link. Follow it and set a new password — use a generated value or a second one from the environment. **This block runs on the shared account, not a throwaway**, because the point is that a reset reaches the real address through the real provider, so it must put the password back. **Restore it by a named mechanism**: the app's own change-password endpoint if one exists (log in with the new password and set it back to the `credentials_env` value in one request), and otherwise a second full reset cycle — request another reset, read the second emailed token from the catcher, and set the original value through it. State which you used. If the block aborts mid-way and neither restore succeeds, the shared account is stranded on an unknown password: **run the reset flow again to set it back before moving on**, and if that also fails, record `error: shared account password unrecovered — re-run domain` in this finding and in `notes` so every later block's login failure is attributed to this block and not to the product. Under `strategy: provided` the account is the user's, so the restore is not optional and the recovery step is not skippable. Confirm four things in order: the new password logs in; the old password no longer does; the reset link fails on a second use; and any session captured before the reset is refused afterwards. Then request a reset for an address that does not exist and record the response status and body verbatim for SEC-018 to read. If no mail catcher is reachable the flow stops at the email step with `error: no mail capture` and the static entry carries the verdict — never guess the token, and never read it out of the database to keep the flow moving, because the point of the check is that the delivery path works.
evidence: `POST /api/auth/forgot → 200`; the mail catcher used, the subject, and the link host; `GET /reset?token=... → 200`; `POST /api/auth/reset → 200`; `POST /api/auth/login (new password) → 200`; `POST /api/auth/login (old password) → 401 (expected)`; `POST /api/auth/reset (token reused) → 400 (expected)`; `GET /dashboard (pre-reset cookie) → 401 (expected)`; the unknown-address response quoted for SEC-018; `password restored to credentials_env value via <change-password endpoint|second reset cycle>` or `error: shared account password unrecovered — re-run domain`.
fix_hint: The implementation note names the failing half — delivery, token handling, or session invalidation — with its handler file:line, and specifies a single-use expiring token, consumption on confirm, invalidation of existing sessions on success, and link construction from a configured public origin. Where the email never arrived, the note is about the sending configuration (stack ref: "env vars") and cites REL-018, not about the reset code.

### FLOW-004 Test-mode checkout → webhook received → entitlement granted
severity: critical
tier: local
fix: guided
when: features.payments
why: The most expensive launch bug in this whole audit is a checkout that takes the money and grants nothing, and it is common because the two halves are tested separately: the developer sees the Stripe success page and stops. The grant happens later, in a webhook, over a network path that does not exist on localhost unless someone deliberately created it — which is why this flow is so often green in development and broken in production.
verify:
  static: Trace the full path (stack ref: "routes and handlers", "webhook handlers", "data access"): the checkout-session or payment-intent creation, the success and cancel redirect targets, the webhook route, which events it handles, and the exact write that grants the entitlement — the row, column, or claim that the app later reads to decide the user is paid. Then check the single most common defect in this path: whether anything grants entitlement from the success URL's query parameters or from a client-side confirmation rather than from the webhook or a server-side session retrieval. PAY-018 owns that rule; name any instance you find and cite it. Confirm the handler is idempotent on repeated delivery (PAY-003) and that the amount and currency written match the price object rather than being recomputed client-side.
  local: **Confirm test-mode keys first per the header rule; if they are not detectably test-mode, record `error: live keys detected` and stop before any request.** Then arrange webhook delivery, because without it this flow cannot pass: run the provider's forwarder — `stripe listen --forward-to <local.url>/<webhook path>` (stack ref: stripe "webhook handlers" for the path) or the provider's equivalent CLI — in the background, tee its output to `.pre-launch/flows/webhook.log`, and note the signing secret it prints, since a forwarder issues its own. If no forwarder or tunnel is available, record `error: webhook delivery not reachable locally`, quote the exact command a human should run, and complete only the checkout half. With delivery arranged: log in as the test account, start checkout for the cheapest plan, and complete it with the provider's published test card from the stack ref "runtime probe hints" (`4242 4242 4242 4242` on Stripe, with any future expiry and any CVC) — via the project's existing browser driver if the payment form is a hosted field, otherwise by driving the provider's test-mode API the way the app does. Then assert the grant, not the redirect: watch `.pre-launch/flows/webhook.log` for the event, and query the entitlement the app itself reads — the subscription row, the `plan` column, the claim — and load a page or endpoint that is gated on it. Pass only when the gated resource returns 200 for this user and did not before. This is the block that first writes the entitlement, so PAY-002 — which owns the entitlement being synced on every relevant event — cites this evidence for the grant case; record the row's fields exactly rather than "entitlement granted". The forged-signature probe belongs to SEC-051; do not run it here.
evidence: `test-mode keys confirmed: <prefix seen>` or `error: live keys detected`; the forwarder command and whether it ran; `POST /api/checkout → 200 {sessionId}`; the test card used; `webhook <event type> received at <ts>` from `.pre-launch/flows/webhook.log`, or `no webhook received in <n>s`; the entitlement row before and after as `subscriptions: 0 rows → 1 row (status=active, price=<id>)`; `GET /app/pro-feature → 403 before, 200 after`; the handler file:line that performs the grant.
fix_hint: The implementation note must move the grant into the webhook handler or a server-side session retrieval and out of the success redirect (PAY-018), keyed on the provider's customer or subscription id, and must make the handler idempotent on event id. Where the failure was delivery rather than logic, the note is about registering the endpoint and its signing secret for the production URL (PAY-001) and about local development using the provider's forwarder, and it says so instead of proposing a code change to a handler that was already correct.

### FLOW-005 Cancel subscription → entitlement revoked at period end
severity: high
tier: local
fix: guided
when: features.subscriptions
why: Two opposite bugs live here and both cost money. Access that never ends after cancellation is revenue given away silently; access that ends the instant a user cancels a plan they paid for through the end of the month is a refund request and a chargeback. The correct behaviour is boring and specific, and nobody notices it is wrong until the first period rolls over.
verify:
  static: Find the cancellation path (stack ref: "routes and handlers"; with Stripe it is usually a billing-portal session or a direct `subscriptions.update` with `cancel_at_period_end: true`) and read what it sets. Then find the code that decides whether a user has access and read what it compares — an `active` flag, a status string, a `current_period_end` timestamp. The two must agree: cancelling must leave access intact until the period ends and remove it after, which means the read side has to consider the period end and not just a boolean the cancel path flipped. Confirm the webhook handler processes the provider's cancellation and period-end events (`customer.subscription.updated` and `.deleted` on Stripe) and writes the same fields. COMP-011 owns whether cancelling is as easy as signing up and PAY-012 owns whether the provider's portal is configured to allow it; this block owns whether the entitlement actually changes.
  local: **Test-mode keys confirmed first, per the header rule.** Using the subscription FLOW-004 created (or one created the same way): cancel through the app's own cancel path, then check three states. First, immediately after cancelling: the gated resource must still return 200 and the UI must state the end date. Second, the stored record: the subscription row must show the cancellation scheduled with a period end, not deleted outright. Third, after the period end — which you do not wait for. ### FLOW-019 Change email and password: re-auth required; notification to old address
severity: high
tier: local
fix: guided
why: This is the account-takeover flow. An attacker with a borrowed session — a shared laptop, a stolen cookie, an XSS — turns temporary access into permanent ownership by changing the email and password, and the two controls that stop it are re-authentication before the change and a notification to the **old** address after it. Products routinely ship one and not the other, or send the notification to the new address, which tells the attacker and nobody else.
verify:
  static: Read the change-email and change-password handlers (stack ref: "auth"). Four requirements, each recorded separately: the current password (or a fresh re-authentication, or a second factor) is required — checked server-side, not merely rendered as a field; a notification goes to the **previous** email address on a change, not only to the new one; the new address is verified before it becomes the login identifier, so a typo does not lock the user out and an unverified address cannot claim the account; and other sessions are invalidated on a password change. SEC-026 owns invalidation on password change and SEC-023 owns verification before sensitive actions as security controls; this block owns whether the user-visible flow does all four.
  local: **This block never touches the shared test account** — changing its email or password would break `credentials_env` for everything else. Create a throwaway identity with FLOW-001's method and a fresh `{ts}`, record it in `.pre-launch/flows/throwaway-019.json`, and run the flow there. First, attempt the password change **without** supplying the current password (post the form with that field omitted or wrong) and expect a 4xx; a 200 is the finding. Then change it correctly and check: does a notification arrive for the old state, is any previously captured session for that account now refused, does the new password log in. Then change the email: attempt it without re-authentication and expect a refusal; then correctly, using a **new address generated from config `email_pattern` with a fresh `{ts}` so it lands on the same catcher domain** — an address the catcher does not receive makes the verification half unobservable and turns a working flow into an `error: no mail capture`; and check that a notification reached the **old** address in the mail catcher (save both to `.pre-launch/flows/mail-019.json`), that a verification was sent to the new one, and — the step most often missing — whether login with the new address works before that verification is completed. Record all four requirements separately, since partial implementations are the norm here.
evidence: the throwaway identity used; `POST /api/account/password (no current password) → 200 (expected 400)` or the observed status; `POST /api/account/password (correct) → 200`; `GET /dashboard (pre-change cookie) → 200 (expected 401)` or the observed status; `POST /api/account/email (no re-auth) → <status>`; `notification to old address: <subject>` or `no notification to old address`; `verification sent to new address: yes/no`; `login with new address before verification → <status>`; handler file:line per missing control.
fix_hint: The implementation note must require a server-side re-authentication on both changes, send the change notification to the previous address as well as the new one, hold the new email as pending until it is verified rather than switching the login identifier immediately, and invalidate all other sessions on a password change.
