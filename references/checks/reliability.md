# Reliability checks (REL)

Read `agents/domain-auditor.md` for procedure. Blocks below are checks; consult stack references for locations. Tools: `dig` for DNS records (REL-017, REL-018); `openssl s_client` piped into `openssl x509` for certificate dates (REL-017); `whois` for domain expiry where it is installed and the TLD answers (REL-017); `gh` for workflow and deployment history when it is authenticated — check with `gh auth status` before relying on it (REL-011, REL-012, REL-013); the error tracker's CLI if the project uses one (`sentry-cli releases list`, `sentry-cli sourcemaps explain`) for REL-002. None of these are required: if a tool is missing or unauthenticated, run the block's `static` entry, decide from that, and set `verified_by: static-fallback` with a note naming what you did not have.

**Restore whatever you change, as the last step, even when the probe fails.** Three checks here deliberately perturb the running app — REL-006 points a dependency at a closed port, REL-010 flips the kill switch, REL-023 fires analytics events and may need consent accepted first. Perturbing a process you started is fine: an environment variable on that process, a runtime feature flag in a local or dev-only flag environment, a settings row in the local database, a cookie in the probe's own session. Perturbing anything shared is not, and the flag case is the trap: a locally-run app usually reads the *production* environment of a hosted flag provider, so "toggle the flag" can put the live site into maintenance mode from your laptop. Editing files in the project is not permitted either — never write to `.env`, a config file, a migration, or a flag definition that is checked in, because a half-finished audit then leaves the repo in a state nobody asked for. Before you flip anything, write down the value you are replacing; after the probe, put it back and confirm the original behaviour returned, and do that on the failure path too. If you cannot restore it, say so loudly in `evidence` and name what is still flipped — that is a bigger finding than whatever the check was measuring.

**Most of this domain is static or attest, and that is the honest shape of it.** Backups, pagers, spend caps, and rollbacks live in provider dashboards you cannot see. For every attest block, look for the machinery in the repo first so the question you put to the user is specific — "is the Sentry alert rule routed to the PagerDuty service named in `sentry.yml`?" gets a real answer; "do you have alerting?" gets a shrug. Machinery found without confirmation is `attest`, not `pass`.

### REL-001 Crash/error reporting installed on frontend, backend, and mobile
severity: critical
tier: static
fix: guided
why: Without a crash reporter you learn about production errors from the one user in a thousand who bothers to email you, days later, with no stack trace. Every other broken session is invisible, and you will spend launch week guessing.
verify:
  static: Find the reporter and confirm it is initialised on every runtime the app actually has, not just one (stack ref: "error handling and logging"). Look for Sentry (`@sentry/nextjs`, `@sentry/node`, `@sentry/react-native`, `sentry-sdk`, `sentry-ruby`), Bugsnag, Rollbar, Honeybadger, Airbrake, Datadog RUM, or a platform-native reporter (Firebase Crashlytics, Vercel's runtime logs are not a reporter — they are logs, and they are dropped after retention). For each runtime, find the init call and the DSN or API key it reads: browser bundle entry or `instrumentation-client`, server entry or `instrumentation.ts`, edge/middleware runtime if the stack has one, worker or job process (stack ref: "background jobs"), and the mobile app's startup path. A DSN that is only in `.env.example` and never set in the deploy config means the reporter is installed and silent — that is a fail, not a pass, and REL-008 will see it too. Then confirm errors actually reach it: an unhandled error must not be swallowed by a bare `catch` that logs and continues, a global error handler must be registered (`process.on('uncaughtException')` / `unhandledRejection` where the stack does not do it for you), and the framework's error page or boundary must report before rendering the fallback (REL-016). Note the environment tagging too — a reporter that files production and local errors into the same unfiltered stream gets muted within a week.
evidence: one line per runtime — `frontend — @sentry/nextjs init at instrumentation-client.ts:8, DSN from NEXT_PUBLIC_SENTRY_DSN (set in vercel.json)` or `worker — no reporter found`; plus the global handler registrations and any swallow-and-continue catch you found in a top-level path.
fix_hint: Install the tracker's SDK for each runtime that has none and initialise it at that runtime's entry point, set the DSN in the deploy environment rather than only in `.env.example`, tag events with the environment and release, and remove the top-level catches that swallow errors before the reporter sees them.

### REL-002 Error tracker scrubs PII; source maps uploaded privately; releases tagged
severity: medium
tier: static
fix: easy
why: An error tracker collects whatever was in scope when things broke — request bodies, headers, tokens, email addresses — and turns your incident tool into a second copy of your user database held by a vendor. Meanwhile a minified stack trace with no source map is unreadable, and public source maps hand your server-side code to anyone who opens devtools.
verify:
  static: Three separate things; check each (stack ref: "error handling and logging", "build"). Scrubbing: find the SDK's data-scrubbing configuration — Sentry's `beforeSend` hook, `sendDefaultPii` (confirm it is false or absent, since sending PII is opt-in on current SDKs but a template may have turned it on), `denyUrls`, or the server-side scrubbing setting; Bugsnag's `redactedKeys`; Rollbar's `scrubFields`. Confirm the deny list covers `authorization`, `cookie`, `set-cookie`, `password`, `token`, `secret`, `api_key`, and the app's own session cookie name, and that request bodies are not attached wholesale. Source maps: find where they are generated and where they go — `hidden-source-map` or the framework's `productionBrowserSourceMaps` setting, a `sentry-cli sourcemaps upload` step or the bundler plugin's upload config, and crucially the delete-after-upload flag (`sourcemaps.deleteFilesAfterUpload`, `deleteSourcemapsAfterUpload`, or an explicit `rm` in the build script). A `.map` file left in the deployed public directory is the fail; verify by looking at what the build emits into the served asset directory, and read SEC-007's evidence for the URL-level confirmation — that check already fetches each deployed bundle URL with `.map` appended, so do not repeat the requests here, cite them. Releases: find where the release identifier comes from — a git SHA passed into the SDK's `release` option and into the upload command. Releases all reading `undefined` means every regression looks like it has existed forever.
evidence: `scrub — beforeSend at sentry.server.config.ts:14, denies [list]` or `scrub — none configured`; `sourcemaps — uploaded at .github/workflows/deploy.yml:31, deleteFilesAfterUpload: true` or `sourcemaps — emitted to public/ and not deleted`; `release — process.env.VERCEL_GIT_COMMIT_SHA at sentry.client.config.ts:6` or `release — unset`.
fix_hint: Add a `beforeSend` that strips the auth header, cookies, and any field whose name matches the secret patterns; switch source maps to hidden, upload them to the tracker in the build step and delete them from the output directory in the same step; and pass the commit SHA as the release to both the SDK init and the upload command.

### REL-003 Product analytics / monitoring installed
severity: high
tier: static
fix: guided
why: Errors tell you what broke; analytics tell you that nobody completed checkout on Tuesday. Launching with neither means your only signal is revenue, which arrives too late and too coarse to act on.
verify:
  static: Find the analytics or monitoring SDK and its initialisation (stack ref: "routes and handlers", "error handling and logging"): PostHog, Amplitude, Mixpanel, Plausible, Fathom, Vercel Analytics, GA4, Segment, or a self-hosted equivalent; server-side metrics via OpenTelemetry, Datadog, Grafana Cloud, or Prometheus. Confirm the key or host is set in the deploy config and not only in `.env.example`. Then check that something meaningful is actually instrumented, because an SDK that only records pageviews answers no question worth asking: list the tracked events by grepping the SDK's call sites (`posthog.capture`, `analytics.track`, `amplitude.track`, `mixpanel.track`, `gtag('event'`) and check they cover the funnel this product lives on — sign-up started and completed, the primary activation action, checkout started and succeeded, and the failure counterparts (payment declined, upload failed). Note which events exist and which stages have none; the gaps are the finding. Whether the events fire at runtime is REL-023, not this check. If the app is server-rendered or has server-side jobs that matter (email sends, payment webhooks), note whether anything at all is instrumented on the server or if all telemetry is browser-side and therefore invisible to ad blockers.
evidence: SDK name and init file:line, plus the key's source; a list of instrumented events with file:line each; the named funnel stages that have no event.
fix_hint: Initialise one analytics SDK with its key in the deploy environment, and instrument the funnel end to end — sign-up completed, activation, purchase, and the matching failure events — server-side for anything that must survive an ad blocker.

### REL-004 Uptime monitor on public URL and critical API
severity: high
tier: attest
fix: none
why: If the first person to notice the site is down is a customer, your mean time to detection is however long it takes someone to care enough to tell you, and at launch that is often hours. A homepage-only monitor is barely better: the marketing page is usually static and stays up while the API that everything depends on is dead.
verify:
  static: Look for monitoring configuration in the repo before asking: a `checkly.config.ts` or `.check.ts` files, a Better Stack / Betteruptime or Pingdom Terraform resource, an UptimeRobot or Cronitor config, a GitHub Actions workflow on a schedule that curls the site, a Grafana Synthetic Monitoring definition, or a `monitors/` directory. Note every URL each monitor hits and the interval. Also note the health endpoint REL-006 found, since that is the thing a monitor should be pointed at.
  attest: Ask the user, and record the answer: is there an external uptime monitor — running outside your own infrastructure — checking both the public URL and at least one authenticated or dependency-touching API endpoint, at an interval of five minutes or better, and does a failure notify a person? All four clauses need a yes. A monitor that only pings the homepage is a partial answer; say which half is covered. A monitor hosted on the same server as the app is not an uptime monitor, because it dies with the thing it watches.
evidence: monitor config found with file:line and the URLs it checks, or `no monitor config in repo`; the user's answer clause by clause — provider, URLs monitored, interval, notification target — or `unconfirmed`.

### REL-005 Alerts route to a human (pager, SMS, or push), not only a dashboard
severity: high
tier: attest
fix: none
why: A dashboard nobody is looking at is not an alert, and neither is an email into a shared inbox at 2am. Alerting configured but not routed is the most common way teams discover an outage from Twitter.
verify:
  static: Look for the routing machinery: a PagerDuty, Opsgenie, or Better Stack integration key in config or Terraform; a Slack incoming-webhook URL used by an alert path (and note whether the channel is one a person is paid to watch); Sentry alert rules in `sentry.yml` or a dashboard-as-code file; a CloudWatch alarm with an SNS topic and what subscribes to it; a Grafana notification policy. Record what each rule fires on and where it lands. Distinguish an integration that exists from one that is wired to a rule — a PagerDuty key in the environment with no rule referencing it routes nothing.
  attest: Ask the user, and record the answer: when the site is down at 3am, does something wake a specific named person — a phone call, an SMS, or a push notification from a pager app — and has that path been tested by firing a real test alert end to end? Both halves need a yes. Email-only or Slack-only routing is the finding, not a pass; say so plainly and name the person if the user gives one, because "the team gets notified" with no name means nobody does.
evidence: alerting rules and integrations found with file:line and their destinations, or `none found in repo`; the user's answer — named recipient, channel type, whether a test alert has been fired — or `unconfirmed`.

### REL-006 Health check endpoint exists and reflects dependency health
severity: medium
tier: local
fix: easy
why: A health endpoint that returns `{"ok": true}` unconditionally reports healthy while the database is unreachable, so the monitor stays green through the outage and the load balancer keeps routing traffic to a broken instance. A health check that does not check anything is worse than none, because it manufactures false confidence.
verify:
  static: Find the endpoint (stack ref: "routes and handlers"): `/health`, `/healthz`, `/api/health`, `/status`, `/_health`, or the platform's configured probe path. Read the handler and list what it actually touches. A useful one runs a trivial query against the primary database (`select 1`), pings the cache or queue if the app cannot serve without them, and returns a non-200 when any of those fail. Fails to record: a handler that returns a constant; one that reports on dependencies it never contacts; one that is so expensive it becomes a self-inflicted load test at a 30-second monitor interval (a full table count, a third-party API call billed per request); and one that leaks internals — version numbers, connection strings, environment variables, or dependency error text in the body of a public endpoint is an information disclosure, so note it and cross-reference the security domain. Check whether the route is excluded from auth and from the maintenance kill switch (REL-010) — a health check behind the maintenance page tells the monitor the app is down for the entire maintenance window, which may be what you want, but it should be a decision, not an accident.
  local: Against `local.url`, `curl -s -o /dev/null -w '%{http_code} %{time_total}\n' <local.url>/health` and then fetch the body. Expect a 200 and a body that names the dependencies it checked. Then break one dependency, using only something you own. The default and safest way is to start a second copy of the app on another port with the database URL pointed at a closed port (`postgres://user:pass@127.0.0.1:1/none` or any port nothing listens on) and probe that copy — it perturbs nothing but your own process. Stopping a service container is acceptable *only* when you started that container yourself in this run; never stop a database, cache, or queue that was already running, because it may be shared with the user's own work or another probe. Request the endpoint on the broken copy: it must return a non-200 (503 is the conventional answer). Then stop the second copy, or restore the dependency and re-request to confirm you got the healthy response back, and do that even if the probe failed part way. If neither option is available — no second port, no container you own — do not break anything: judge from the static entry and set `verified_by: static-fallback`. A dev server is a fine host for this check: the endpoint's dependency wiring is the same code in either build, so do not fail an app here for anything that is only a production difference — but if the health handler is behind a production-only middleware chain, say so and verify against a production build instead.
evidence: `GET /health → 200, body: {...}` with the dependencies named; `GET /health with db stopped → 503` or `→ 200 (expected 503)`; the handler file:line and the list of dependencies it contacts versus the ones it merely claims.
fix_hint: Make the handler run a cheap real query against each dependency the app cannot serve without, return 503 with a per-dependency status object when any fails, keep it under a few hundred milliseconds, and return no version or configuration detail in the body.

### REL-007 Test keys swapped for live keys in production env; no test-key prefixes in prod config
severity: critical
tier: attest
fix: none
why: Shipping with a payment provider's test key means every customer completes checkout, sees a success page, and is never charged — you find out at the end of the month. The mirror image, a live key in a place you thought was staging, means your test suite is charging real cards.
verify:
  static: Scan every place a production value could be written and list what you find, with file:line — `.env.production`, `.env.prod`, `.env` if it is committed (which is its own critical finding under the security domain), `vercel.json`, `fly.toml`, `render.yaml`, `app.yaml`, `docker-compose.prod.yml`, Kubernetes manifests and ConfigMaps, Terraform variable files, GitHub Actions environment blocks, and any deploy script that exports variables. Grep those for detectable test-mode markers: `sk_test_`, `pk_test_`, `rk_test_`, `whsec_test`, `sandbox` in a host name (`api.sandbox.paypal.com`, `api-m.sandbox.paypal.com`, `sandbox.plaid.com`, Twilio test credentials, `test.` prefixes on provider hosts), a mail catcher as the SMTP host (`mailhog`, `mailpit`, `localhost:1025`, `smtp.mailtrap.io`), a Supabase or Firebase project id that matches the one used for development, and `NODE_ENV`/`APP_ENV`/`RAILS_ENV`/`DJANGO_SETTINGS_MODULE` values that are anything other than the production one. Also grep the source for hardcoded keys of either kind — a `sk_test_` or `sk_live_` literal in code is a finding regardless of environment. Then check the direction of the mistake in the other lane: a `_live_` key or a production database URL appearing in a test fixture, a CI workflow, or a seed script is the same class of error and is arguably worse.
  attest: Ask the user, and record the answer: in the production environment as it is configured right now — the actual dashboard values, not the repo — is every provider key the live one, is `NODE_ENV` (or the stack's equivalent) set to production, and does no sandbox host remain? Name the specific providers you found in the code (payments, email, SMS, AI, storage) and ask about each by name rather than in general, because "yes we swapped the keys" almost always means the payment one. An unknown on any provider is the finding.
evidence: per file scanned — `vercel.json:22 — STRIPE_SECRET_KEY references sk_test_ prefix` or `none found`; the full list of providers whose keys the code reads; the user's answer per provider, or `unconfirmed`.

### REL-008 Every env var the code reads is defined for prod; no silent dev fallbacks
severity: high
tier: static
fix: guided
why: A missing environment variable in production either crashes the app at boot — loud, annoying, survivable — or, far more often, silently takes a fallback and runs the app in a subtly wrong mode: the analytics key is undefined so nothing is tracked, the webhook secret defaults to an empty string so signature verification passes for everyone, the base URL falls back to localhost so every email contains a broken link.
verify:
  static: Build the set of variables the code reads. Grep every runtime for the read patterns this stack uses (stack ref: "env vars"): `process.env.X` and `process.env['X']`, `import.meta.env.X`, `Deno.env.get('X')`, `Bun.env.X`, `os.environ['X']` and `os.environ.get('X')`, `os.getenv('X')`, `ENV['X']` and `ENV.fetch('X')`, `env('X')` (Laravel, Symfony), `System.getenv`, `config()` wrappers and typed-env schemas (`t3-oss/env`, `zod` env parsing, `pydantic-settings`, `envalid`) — read the schema file for those, since it is the authoritative list. Deduplicate into a set. Then build the second set: every variable defined in `.env.example` (or `.env.sample`, `.env.template`), plus every one set in deploy config (`vercel.json`, `fly.toml`, `render.yaml`, Kubernetes manifests, Terraform, the CI workflow's `env` blocks). Diff the two sets in both directions and report both: read-but-not-defined is the failure that takes the app down or degrades it silently; defined-but-never-read is dead config that misleads the next person and occasionally leaves a stale secret lying around. For each read-but-not-defined variable, read the call site and classify the consequence, because that is what makes this check actionable: a read with no fallback that throws at boot is loud and lower severity; a read with a hardcoded fallback that would silently run in production is a fail and the reason this check exists — `process.env.WEBHOOK_SECRET || 'dev-secret'`, `os.environ.get('API_URL', 'http://localhost:3000')`, `ENV.fetch('FEATURE_X', 'false')`, a `?? ''` on anything used in a comparison. Call out fallbacks on security-relevant values (secrets, signing keys, allowed origins, admin emails) individually with file:line, because those are the ones that turn into a security finding rather than a broken feature. Note where the deploy config's values live if they are not in the repo — a platform dashboard is a legitimate answer, but then say that the definitive list could not be read and cross-reference REL-007's attest.
evidence: a table of variable, read sites (file:line), whether it appears in `.env.example`, whether it appears in deploy config, and the fallback if any; a separate list of the fallback-in-production risks with the consequence spelled out per variable; the defined-but-unread leftovers.
fix_hint: Validate the environment once at boot with a schema that fails fast on anything missing, delete the inline fallbacks so a missing value cannot silently change behaviour, add every read variable to `.env.example` with a comment saying what it is for, and set the production values in the deploy environment.

### REL-009 Spend caps on every metered API; billing alerts on cloud providers
severity: high
tier: attest
fix: none
why: Metered APIs bill after the fact and do not stop on their own. One loop with a retry, one scraper hitting an AI endpoint, one runaway job, and the bill is four figures before anyone opens the dashboard — and the provider's position is that you used it.
verify:
  static: List every metered dependency the code actually calls, since that is the list the user needs to answer against: AI and LLM providers (OpenAI, Anthropic, Replicate, ElevenLabs), email and SMS (Resend, SendGrid, Postmark, Twilio), maps and geocoding, search (Algolia, Typesense Cloud), storage and bandwidth egress, serverless function invocations and edge middleware, managed database compute, and any usage-priced platform plan. For each, note where the client is constructed and whether the code imposes any ceiling of its own — a per-user quota (DAT-027), a rate limiter on the calling endpoint (SEC-015), a max-tokens or max-attempts argument, a monthly counter checked before the call. Application-level ceilings are the only ones you can see from the repo, and they are the ones that survive a provider without hard caps.
  attest: Ask the user, and record the answer per provider by name: is there a hard spend cap or usage limit configured at the provider, and a billing alert that notifies a person at a threshold below the point where it would hurt? Be precise about the difference, because providers blur it: OpenAI and Anthropic offer usage limits that stop serving; AWS Budgets, Google Cloud budgets, and Vercel spend alerts notify but do not by default stop anything. An alert-only answer is a partial pass with the gap stated — say which providers can actually be capped and which can only be watched.
evidence: the metered providers found with the client construction file:line and any application-level ceiling; per provider, the user's answer — hard cap value, alert threshold, alert recipient — or `unconfirmed`.

### REL-010 Kill switch exists and toggling it takes effect
severity: high
tier: local
fix: guided
why: When something is actively harming users or burning money, you need to stop it in under a minute without a deploy.
verify:
  static: Look for a maintenance or kill mechanism: a feature-flag provider (LaunchDarkly, PostHog flags, Vercel Edge Config, Statsig), a `MAINTENANCE_MODE` env var read in middleware, a database `settings` row checked on each request, or platform-level maintenance mode. Confirm it is checked before the expensive or risky paths (payments, AI calls, sign-ups), not only on the marketing page (stack ref: "routes and handlers").
  local: Probe `local.url` only, never `remote.url`. Flip the switch the way the code reads it, but only through a source that belongs to the process you started: the environment variable set on that process before you restart it, a settings row in the *local* database, a local flag file, or the flag provider's dev or local environment addressed by its own SDK key. Where the only mechanism is a hosted flag shared with production — a LaunchDarkly, PostHog, Statsig, or Vercel Edge Config project whose key is the same one production reads — do not flip it: a locally-run app reading the production flag environment means your toggle takes the live site down. Record the mechanism, decide from the static entry, set `verified_by: static-fallback`, and say in `notes` that the toggle was not exercised because the flag source is shared with production. Never edit a file that is checked into the repo. Where you can flip safely: write down the original value first, request the primary page and one protected API route, and expect the maintenance response. Then flip it back as the last step, including when the probe failed part way, and confirm normal behaviour returns; if it will not restore, say so in evidence and name what is still flipped. If the only way to flip it is a deploy, that is a fail.
evidence: file:line of the check and where it is read; probe lines before and after toggling, and an explicit line confirming the original value was restored.
fix_hint: Add a single middleware-level check of a runtime-readable flag (stack ref: "routes and handlers" for the middleware location) that returns a 503 with a maintenance page for all but health checks.

### REL-011 Hotfix path: OTA update (mobile) or fast deploy pipeline (web)
severity: medium
tier: static
fix: guided
why: The measure that matters during an incident is how long it takes a one-line fix to reach users. On the web that is usually minutes and nobody thinks about it; on mobile it is an app store review of a day or more unless an over-the-air update path exists, which is the difference between a bad afternoon and a bad week.
verify:
  static: Establish the actual path from commit to users and time each hop from what the config says (stack ref: "build"). Web: find the deploy trigger — a push to the default branch, a tag, a manual workflow dispatch — and read the pipeline for anything that would make an emergency deploy slow or blocked: a required manual approval gate, a long end-to-end suite in the critical path, a scheduled-only deploy, a build that takes many minutes. Note whether the platform offers instant rollback or promotion of a previous build (that is REL-012's evidence too). If `gh` is authenticated, `gh run list --workflow=<deploy workflow> --limit 10 --json displayTitle,conclusion,createdAt,updatedAt` gives real durations rather than guesses; if it is not, say the timing is estimated from config. Mobile: find whether an OTA mechanism exists at all — Expo Updates (`expo-updates` in dependencies plus an `updates` block in `app.json`/`app.config.js` with a channel), CodePush, or a React Native equivalent — and confirm the channel is wired to the production build and that the runtime version policy will not silently make updates incompatible. Note the boundary honestly: OTA covers JavaScript and assets, never native code, so a crash in a native module still needs a store release. If the project is web-only, say so and judge only the web half rather than inventing a mobile finding.
evidence: the deploy trigger with file:line, the gates and their cost, the measured or estimated commit-to-live time and its source; for mobile, the OTA package, channel, and runtime version policy with file:line, or `no OTA path — every fix requires a store release`.
fix_hint: Remove or make skippable the gates that block an emergency deploy (keep the fast tests, move the slow suite off the critical path), document the exact command or button that ships a hotfix, and for mobile add an OTA update channel wired to the production build so JavaScript fixes do not wait on review.

### REL-012 Rollback documented; previous deploy restorable in minutes
severity: high
tier: attest
fix: none
why: Under pressure, at speed, with users complaining, nobody invents a rollback procedure correctly. If the steps are not written down and have not been done once while calm, the actual rollback is a panicked forward-fix that makes things worse.
verify:
  static: Look for the machinery and the documentation separately. Machinery: platform instant rollback (Vercel deployment promotion, Netlify published-deploy switching, `fly releases` and `fly deploy --image` of a previous image, a Kubernetes Deployment with a `revisionHistoryLimit` and `kubectl rollout undo`, a blue-green or immutable-tag container setup), or a git-revert-and-redeploy path with a known duration from REL-011. Documentation: a `RUNBOOK.md`, `docs/rollback*`, `docs/operations*`, `docs/incident*`, or a section in the README that names the exact command or click path. Read it and judge whether someone who did not write it could follow it at 3am: does it say where to click or what to run, how to tell the rollback worked, and — the part everyone omits — what to do about database migrations, since a rollback of code onto a migrated database is a different and much harder operation than a rollback of code alone. Note whether the recent migrations are backward compatible (additive columns, no destructive drops in the last release) because that determines whether rollback is even possible; cross-reference the data domain's migration checks rather than repeating them.
  attest: Ask the user, and record the answer: is the rollback procedure written down, and has the previous deploy actually been restored at least once — as a rehearsal or a real incident — with the elapsed time known? Both halves need a yes and the second needs a number. "We would just redeploy the old commit" is the answer to record when that is what you get, with the untested gap stated.
evidence: the rollback mechanism found with file:line or platform feature, and the runbook path with a one-line judgement of whether it is followable; whether the last release's migrations are backward compatible; the user's answer and the recorded rollback time, or `never rehearsed`.

### REL-013 CI runs tests and blocks deploy on failure; no deploys from laptops
severity: high
tier: static
fix: guided
why: CI that runs tests but does not gate the deploy is a notification system, not a safety net — the red build and the broken deploy happen in parallel. Deploys from a laptop are worse: they ship whatever was in that working directory, including the uncommitted debug change and the local `.env`, and nobody can reproduce what is in production.
verify:
  static: Read the CI configuration (`.github/workflows/*.yml`, `.gitlab-ci.yml`, `.circleci/config.yml`, `bitbucket-pipelines.yml`, a `Jenkinsfile`) and answer three questions with file:line for each. First, do tests run at all, and on what — pushes to the default branch, pull requests, or only a manual trigger? Second, does a test failure actually block the deploy? This is the one people get wrong: a deploy job with no `needs:`/`requires:`/`dependencies:` on the test job runs in parallel with it and ships regardless; a step with `continue-on-error: true` or a command ending in `|| true` passes a failing suite; a test job that finds no tests and exits zero is a green tick over nothing. Check the branch protection too if `gh` is authenticated — `gh api repos/:owner/:repo/branches/<default>/protection` shows required status checks — and note it as unverified if it is not. Third, is the deploy performed by CI, or by a person? Look for a deploy step in the pipeline versus a `deploy.sh`, a documented `vercel --prod` or `fly deploy` run by hand, or a platform connected to a local CLI. A platform's own git integration deploying on push counts as CI-driven; someone running the CLI from their machine does not. evidence: `test job at .github/workflows/ci.yml:12 runs npm test on pull_request`; `deploy job at :40 — no needs: on test job (does not block)` or `needs: [test]`; branch protection status from `gh` or `not verified — gh unavailable`; who deploys and from where.

### REL-014 Automated tests cover critical paths: auth, payment, deletion
severity: high
tier: static
fix: guided
why: Coverage percentage is a vanity number; what matters is whether the three flows that cause irreversible harm are tested. A regression in auth exposes other people's data, one in payment takes money without delivering, and one in deletion destroys data you cannot get back — and all three are the flows least likely to be exercised by hand before a hotfix.
verify:
  static: Find the test suites and map them onto the critical paths rather than counting files. Locate the runner and the tests (`__tests__`, `*.test.*`, `*.spec.*`, `tests/`, `spec/`, `e2e/`, `cypress/`, `playwright/`) and read enough of each to know what it asserts. ### REL-015 Structured logs; no PII, tokens, or bodies logged; retention set
severity: medium
tier: static
fix: guided
why: During an incident you need to filter logs by request id and user, which unstructured string logs make impossible. And logs are the quietest data leak there is: an access token or a full request body written to stdout ends up in your platform's log store, your log vendor, and anyone's terminal, retained for as long as the default says and long outside whatever your privacy policy claims.
verify:
  static: Three things (stack ref: "error handling and logging"). ### REL-016 Frontend error boundaries; graceful degradation when a third party is down
severity: medium
tier: static
fix: easy
why: One thrown error inside a React tree with no boundary above it unmounts the whole application and leaves a blank white page — the user cannot even reach the navigation to try something else. The same brittleness applies to third parties: a payment widget or a chat script that fails should cost you that widget, not the page.
verify:
  static: Boundaries: find them (stack ref: "routes and handlers", "error handling and logging") — React `ErrorBoundary` components or `react-error-boundary`, Next.js `error.tsx` and `global-error.tsx` files, Vue's `errorCaptured`, SvelteKit's `+error.svelte`, Angular's `ErrorHandler`. ### REL-017 TLS cert auto-renews; domain not near expiry; www/apex redirect
severity: high
tier: remote
fix: guided
why: An expired certificate is a full outage with a browser warning that says your site is dangerous, and it happens on a schedule you can see in advance. An expired domain is worse and slower to undo. And an apex that does not redirect to www (or the reverse) splits your traffic, your cookies, and your SEO across two sites.
verify:
  static: Find what manages the certificate and note whether renewal is automatic (stack ref: "build"): a platform that provisions and renews on its own (Vercel, Netlify, Fly, Cloudflare, App Runner), a `cert-manager` Issuer or Certificate resource in Kubernetes manifests, a certbot cron or systemd timer, an ACM certificate in Terraform with DNS validation records also managed there — ACM only auto-renews while its validation CNAME still resolves, so a certificate managed in Terraform whose validation record was deleted by hand will silently fail to renew. A manually uploaded certificate with no renewal machinery is the finding. Then find the canonical host: the redirect config for apex-to-www or www-to-apex (`next.config` redirects, `vercel.json` redirects, an nginx server block, a Cloudflare rule) and what the app treats as its own base URL (`NEXT_PUBLIC_SITE_URL`, `APP_URL`, the canonical tag in the SEO domain). Note any disagreement between them, because a canonical tag pointing at a host that redirects elsewhere is a real bug.
  remote: Against the production host in `remote.url`. Certificate dates: `openssl s_client -servername <host> -connect <host>:443 </dev/null 2>/dev/null | openssl x509 -noout -dates` — read `notAfter` and compute the days remaining. Under 30 days with no auto-renewal machinery found is a fail; under 15 days is a fail regardless, because even auto-renewal should have fired by then. Also `openssl x509 -noout -subject -issuer` from the same pipe to confirm the certificate actually covers the host you asked for and, if the app uses a www or api subdomain, run the probe against each of those separately — a wildcard is not guaranteed and a subdomain with its own expired certificate is a real outage. Redirect behaviour: probe four URLs — the www and apex forms of the registrable domain, each over `http://` and `https://`. Derive both forms from the registrable domain rather than from `remote.url`, or you will probe `www.www.example.com`. For each, first read the single response without following — `curl -s -o /dev/null -w '%{http_code} %{redirect_url}\n' <url>` — to get the status code and target of the redirect itself, then follow it — `curl -sL -o /dev/null -w '%{url_effective} %{http_code}\n' <url>` — to confirm where it lands. Use GET, not `-I`: a HEAD request is rejected outright by some servers and CDNs, and a 405 there is your probe's fault, not the app's. Expect all four to converge on one canonical host over HTTPS with a 301 (a 302 on the canonical redirect is a weaker signal to search engines; note it rather than failing). On hop count, judge only the hops *after* the HTTPS upgrade: `http://www` to `https://www` to `https://apex` is two hops and is the normal, correct behaviour on Vercel, Netlify, and Cloudflare, so it is not a finding — more than one hop once the request is already on HTTPS is, and even then note it rather than failing, since it costs a round trip but breaks nothing. A TLS handshake failure on a non-canonical variant — `curl` exiting 35 or reporting status `000`, typically because the certificate does not cover that host — is a real finding and not a probe error: it means `https://www` (or `https://apex`, whichever failed) is unreachable for anyone who types it, and no redirect can rescue it because the browser refuses before the redirect is sent. Report it as a fail on certificate coverage, separately from the redirect verdict, and say which variant failed. Domain expiry: `whois <domain> | grep -iE 'expir|renew'` where `whois` is installed and the TLD returns a usable record — many do not, and some rate-limit, so treat a missing or unparseable answer as unknown, not as a pass. If you cannot read the expiry, say so and put the question to the user instead: is the domain registration more than 60 days from expiry and is auto-renew on, with a payment method that has not expired?
evidence: `notAfter=<date> (<n> days)` per host probed, with issuer and subject; the four redirect probes with their final URL and status; the domain expiry date and auto-renew state, or `whois unavailable — asked the user`; the renewal machinery found with file:line.
fix_hint: Move certificate issuance to something that renews automatically and alert on days-to-expiry as a backstop, pick one canonical host and 301 every other variant to it in one place, and turn on registrar auto-renew with a current payment method and a calendar reminder well before expiry.

### REL-018 Email deliverability: SPF, DKIM, DMARC published; bounce handling
severity: high
tier: remote
fix: guided
when: features.email_sending
why: Without SPF, DKIM, and DMARC your password reset emails land in spam or are rejected outright, and the user experience is indistinguishable from broken authentication. Gmail and Yahoo now require authentication for bulk senders, so this is not a deliverability optimisation any more, it is whether your mail is accepted.
verify:
  static: Find the mail provider and the sending domain (stack ref: "env vars", "background jobs"): Resend, SendGrid, Postmark, Mailgun, SES, or raw SMTP, and the `from` address used by each template. Note the DKIM selector the provider expects, because you cannot query DKIM without it — Resend and SES publish per-domain selectors named in the dashboard and usually visible in the provider's setup docs or in an infrastructure module (`aws_ses_domain_dkim` in Terraform emits three selector CNAMEs), SendGrid uses `s1`/`s2`, Postmark defaults to `<something>._domainkey`, Mailgun uses a selector you chose. Record the selector name and where you found it, or that you could not find one. Then check bounce and complaint handling: is there a webhook endpoint receiving the provider's bounce, complaint, and spam-report events, and does it do anything — suppressing the address, marking the user unverified, stopping further sends? A sender that keeps mailing hard bounces is a sender whose domain reputation is being actively destroyed. Also confirm the `from` domain matches the domain whose records you are about to check, and that transactional mail is not being sent from a free-mail address, which cannot be authenticated at all.
  remote: Query the live records for the sending domain. SPF: `dig +short TXT <domain>` and find the `v=spf1` record — there must be exactly one (two SPF records is a permanent error that fails both), it must include the provider's mechanism (`include:_spf.resend.com`, `include:sendgrid.net`, `include:amazonses.com`, and so on for the provider you found), and it should end in `~all` (softfail) or `-all` (fail) rather than a weak terminator: `+all` authorises the entire internet, a bare `all` means the same thing, and a record with no `all` mechanism at all ends in an implicit neutral, which asserts nothing. Check the record SPF is actually evaluated against, which is the Return-Path (envelope sender) domain, not the visible `From`: most providers set a custom bounce or Return-Path subdomain — `bounces.<domain>`, `mail.<domain>`, `em<digits>.<domain>` on SendGrid, `pm-bounces.<domain>` on Postmark — so where the provider config or the DNS records show one, run `dig +short TXT <that subdomain>` and judge SPF there. In that setup the `From` domain having no SPF record of its own is expected: with an aligned DKIM signature and a published DMARC, that combination passes DMARC and is a note, not a fail. Say which domain you evaluated SPF on. DMARC: `dig +short TXT _dmarc.<domain>` and read the policy — a missing DMARC record is a fail; `p=none` passes with a note, since it authenticates and reports without enforcing and is the correct first step, but say plainly that it does not yet protect against spoofing and that `rua=` should be set so the reports go somewhere. DKIM: `dig +short TXT <selector>._domainkey.<domain>` (or `dig +short CNAME` first, since most providers hand you a CNAME that points at their key) for the selector you found in the static entry; a published record containing `p=` with a key is the pass. If no selector could be identified, do not report DKIM as missing — report it as unverified and name what you would need. Missing DMARC is a fail on its own, and so is missing SPF on whichever domain is the Return-Path — but a `From` domain with no SPF is not, when the Return-Path subdomain has one and DKIM is aligned. Where the domain resolves but every query comes back empty, check you are querying the sending domain rather than a subdomain the mail is not sent from.
evidence: the raw `dig` output line for each of SPF, DMARC, and DKIM with the record quoted, naming the exact domain or subdomain each was queried on and which one is the Return-Path; the provider and selector with file:line; the bounce webhook handler file:line and what it does, or `no bounce handling`.
fix_hint: Publish the provider's SPF include (one record, ending `~all`), add the DKIM CNAMEs the provider gives you, and add a `_dmarc` TXT starting at `p=none` with a `rua=` address so you can read the reports before tightening to quarantine and then reject; wire the provider's bounce and complaint webhook to a handler that suppresses the address and flags the account.

### REL-019 Scheduled jobs monitored, idempotent, non-overlapping
severity: medium
tier: static
fix: guided
why: A cron job that silently stops running is the definition of an invisible failure — nothing errors, nothing alerts, the nightly digest just never goes out and you find out in a month. The two other classic failures are as quiet: a job that is not idempotent double-charges or double-sends when the scheduler retries, and a slow job that overlaps its next run corrupts whatever it is processing.
verify:
  static: Inventory every scheduled job (stack ref: "background jobs"): `vercel.json` `crons`, GitHub Actions with a `schedule` trigger, `pg_cron` entries, Supabase scheduled functions, Cloudflare Cron Triggers, a `Procfile` clock process, Celery Beat, Sidekiq-cron, `whenever`, systemd timers, a `crontab` in the repo. For each, record the schedule, the handler it calls, and then answer three things from the handler's code. Monitored: does anything know the job ran? Look for a heartbeat ping to a dead-man's-switch (Cronitor, Healthchecks.io, Better Stack heartbeat, Sentry Cron Monitors), a row written on completion that something alerts on, or nothing at all — nothing at all is the common answer and is the finding. Idempotent: if this ran twice with the same input, what happens? Check for a processed-marker column or a unique constraint that makes a second run a no-op, an idempotency key on outbound charges or sends, and a query scoped by a `processed_at is null`-style predicate rather than by a time window computed from `now()`, which double-processes on a retry and skips rows entirely if a run is missed. Non-overlapping: is there a lock? An advisory lock (`pg_try_advisory_lock`), a Redis `SET NX` with a TTL, the queue library's uniqueness option, or a database row acting as a mutex. Note the runtime honestly: a serverless invocation cannot rely on an in-process flag, because the next invocation is a different process. Also confirm the job's endpoint is not publicly triggerable (the security domain's cron secret check) and that a failure is reported to the error tracker rather than dying in a log nobody reads.
evidence: per job — `vercel.json:8 — /api/cron/digest, daily 03:00; heartbeat: none; idempotency: none (selects by now() window); lock: none`; the file:line of each handler.
fix_hint: Add a heartbeat ping at the end of each job to a dead-man's-switch that alerts when a run is missed, make the work idempotent by marking rows processed and selecting on that marker rather than a clock window, and take an advisory or Redis lock at the start of any job that could outlive its interval.

Flag email addresses, names, phone numbers, physical addresses, free-text the user typed, raw identifiers that resolve to a person outside your system, and whole objects spread into the payload (`analytics.track('signup', user)` sends every field the record has, including the ones added later by someone who was not thinking about analytics). A stable pseudonymous user id is fine and is the point; the email as the distinct id is the common mistake — check the SDK's `identify` call specifically, since that is where email usually enters. URLs: grep the route definitions and link construction for personal data in path segments or query strings (stack ref: "routes and handlers") — `?email=`, `/users/<email>`, a reset or magic-link token in a query parameter that will end up in the referrer and the access log, an invite code carrying the invitee's address. Note whether the analytics SDK captures the full URL including query string by default, since that is how a token in a URL reaches the vendor. IP anonymization: find the setting where the tool has one (GA4 anonymizes by default and has for years; PostHog, Plausible, and Matomo each expose their own control) and record what this config actually sets rather than what the tool's default is believed to be — if you cannot establish the effective behaviour from the config, say so instead of asserting a default. Also check the server side: an access log or an event table storing full IP addresses indefinitely is the same finding in a different place.
evidence: per event — `signup → properties: [email, name, plan] — email and name are PII (lib/analytics.ts:22)`; per URL — `GET /reset?token=... — token in query string (app/reset/page.tsx:11)`; the IP handling setting with file:line or `not determinable from config`.
fix_hint: Send a pseudonymous id and non-identifying properties only, keep the email in your own database rather than the analytics payload, move tokens and personal identifiers out of query strings into path-free POST bodies or short-lived server-side lookups, and turn on the tool's IP anonymization explicitly rather than relying on its default.

why: The knowledge of how to fix the three things most likely to break usually lives in one person's head. At 3am, or when that person is on a plane, it may as well not exist. Writing it down is an hour of work that pays for itself the first time.

### REL-027 Launch-day plan: DNS TTL lowered, cutover steps, rollback trigger
severity: medium
tier: attest
fix: none
why: DNS is the part of a launch you cannot undo quickly. A record with a 24-hour TTL means a bad cutover keeps sending some users to the old target for a day, no matter what you change. Lowering the TTL beforehand is free, has to happen a day ahead, and is invariably remembered an hour too late.
verify:
  static: Establish what the cutover actually involves from the repo: is DNS managed as code (Terraform `aws_route53_record`, a Cloudflare provider resource, a DNS zone file) where you can read the TTL values directly, or in a dashboard where you cannot? Where it is in code, record the current TTL on the apex and www records and note any that are hours long. Look for a documented launch or cutover checklist (`docs/launch*`, `LAUNCH.md`, a checklist issue template) and read whether it names the steps in order and the point of no return. Note whether the cutover involves a data migration, because that is the step that makes rollback hard and it should be called out separately. If `dig` is available you can also read the live TTL for the current records — `dig +noall +answer <domain>` shows the remaining TTL on the cached answer, and `dig +noall +answer @<authoritative ns> <domain>` shows the configured value — but this block is attest because the plan, not the record, is what is being judged.
  attest: Ask the user, and record the answer: has the DNS TTL on the records you will change been lowered to 300 seconds or less at least 24 hours before cutover, are the cutover steps written down in order, and is there a stated trigger that means "roll back now" — a specific symptom and a specific person who can call it? All three clauses need a yes. "We will keep an eye on it" is the answer to record when that is what you get, with the missing trigger named.
evidence: the DNS TTL values found in code with file:line, or `DNS managed outside the repo`; the launch checklist path and a judgement of its completeness, or `none found`; the user's answer clause by clause — TTL lowered and when, steps written, rollback trigger and who calls it — or `unconfirmed`.

### REL-028 Support flow: visible contact path, routed to a human, response target
severity: high
tier: static
fix: guided
why: On launch day the difference between a bug and a refund is whether the user could tell you. A contact route hidden behind a login is useless to the person who cannot log in, and a form posting into an inbox nobody reads is worse than no form at all, because it consumes the user's goodwill and returns nothing.
verify:
  static: Three properties, each checkable. Visible without login: find the contact path in the layout, footer, header, or help page (stack ref: "routes and handlers") and confirm it renders on public pages — the landing page, the pricing page, and the login and password-reset pages specifically, since those are where a locked-out user is standing. A support link only inside the authenticated dashboard fails this half; say which pages carry it and which do not. Reaches a human: follow where the path leads. A `mailto:` to an address that exists, a contact form whose handler actually sends somewhere (read the handler, confirm the recipient is not a placeholder like `you@example.com`, an unset environment variable, or a personal address that will be missed), a ticketing widget (Intercom, Crisp, Zendesk, Plain, HelpScout) with a real workspace configured, or a Discord or Slack community link that a maintainer reads. Fails: a form that only writes a database row nobody queries, a chatbot with no human handoff, an address that bounces. Also confirm the form has spam protection, since an unprotected public form becomes unusable within days of launch and then the support path is dead again (cross-reference the security domain's rate limiting). Response target: find a stated expectation on the page or in the confirmation the user sees — "we reply within one business day". A support path with no stated target is not a failure of the mechanism but it is the finding for this clause; note it separately so the fix is proportionate. Check the confirmation too: after submitting, does the user see or receive an acknowledgement, or does the form clear and leave them wondering?
evidence: `footer contact link — components/Footer.tsx:31, renders on public layout; absent on /login (app/(auth)/layout.tsx)`; the handler file:line and its resolved recipient; the widget and workspace config; the stated response target quoted, or `no response target stated`; the spam protection found or its absence.
fix_hint: Put a contact link in the public footer and on the login and password-reset pages, route it to a monitored shared inbox or a ticket tool rather than one person's address, add spam protection to any public form, and state the response target next to the form and in the acknowledgement the user receives.

### REL-029 Staging mirrors prod configuration
severity: medium
tier: attest
fix: none
why: A staging environment that differs from production tests a different application. The differences that matter are always the boring ones — a different Node or Python version, a missing environment variable, a different database version or extension set, no CDN in front, a different region — and each one is a class of bug staging is structurally incapable of catching.
verify:
  static: Compare what the repo can show you. Environment definitions per target: `vercel.json` or the platform config's per-environment blocks, `fly.toml` versus a `fly.staging.toml`, Terraform workspaces or per-environment variable files, Kubernetes overlays, GitHub Actions environments. Diff the variable sets between staging and production and list what one has that the other does not (this reuses REL-008's inventory). Then check the version-pinned things: the runtime version in the engines field or the platform config, the database version and extensions in the migration or infrastructure config, and whether both targets run the same build command. Note anything present in production only — a CDN, a WAF, a read replica, a queue worker — because those are the differences that make a staging pass meaningless.
  attest: Ask the user, and record the answer: does staging run the same runtime version, the same database version, the same third-party providers in their sandbox modes, and the same environment variable set as production, differing only in credentials and data? Also ask the question behind it: what is the last bug that reached production having passed staging, since that answer usually names the real difference faster than any comparison you can do. Where there is no staging environment at all, record that plainly — it is a legitimate choice for a small project, and then the finding is that every change is tested in production, which raises the weight of REL-012 and REL-010.
evidence: the per-environment configuration found with file:line and the diff between staging and production variable sets; the version pins compared; the user's answer, or `unconfirmed`; `no staging environment` where that is the case.

### REL-030 Feature flags on risky features
severity: low
tier: static
fix: guided
why: A feature behind a flag can be turned off in seconds by anyone with dashboard access; a feature not behind one needs a revert, a build, and a deploy. For the two or three parts of a launch most likely to misbehave, that difference is the entire incident response.
verify:
  static: Find the flag mechanism if there is one (LaunchDarkly, PostHog feature flags, Statsig, Unleash, Flagsmith, Vercel Edge Config, a `feature_flags` table, or a plain environment-variable check) and list the flags that exist with where each is evaluated. Then identify what should be behind one and is not — the features whose failure is expensive or embarrassing: anything calling a paid AI provider, a new payment or pricing path, an email or notification blast, a bulk import or export, a newly rewritten core flow, and anything shipped in the last week before launch. For each, note whether a flag guards it. Check the evaluation is runtime rather than build-time: a flag read from an environment variable inlined at build (`NEXT_PUBLIC_*` compiled into the bundle) cannot be turned off without a redeploy, which defeats the purpose, so record it as a flag in name only. Confirm the default is safe — a flag that defaults to on when the provider is unreachable turns a flag outage into a feature launch. Note stale flags too: a flag that has been permanently on for months is dead code with a branch in it, worth cleaning up but not a launch blocker; say so rather than inflating it.
evidence: the flag mechanism and file:line of each evaluation; per risky feature — `AI summary endpoint (app/api/summarize/route.ts:14) — no flag` or `guarded by flag <name>, runtime-evaluated, defaults off`; the build-time-inlined flags called out separately.
fix_hint: Put a runtime-evaluated flag in front of each risky feature with a safe default when the flag source is unreachable, evaluate it server-side so it cannot be flipped by the client, and remove the flags that have been permanently on once the feature is settled.

### REL-031 Rebuild-from-scratch documented; env config exported; infra reproducible

why: The state of production is usually a set of dashboard clicks nobody wrote down. If the account is lost, the region fails, or the only person who set it up leaves, the recovery is archaeology.
