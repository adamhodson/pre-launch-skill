# Hygiene checks (HYG)

Read `agents/domain-auditor.md` for procedure. Blocks below are checks; consult stack references for locations. Tools: `grep` and `git`, which do most of the work here; `python3` with only the standard library for extracting strings from templates and parsing manifests; `curl` for the three blocks that fetch from a running build (HYG-005, HYG-012, HYG-016); the package manager already in the repo (`npm`, `pnpm`, `yarn`, `pip`, `bundle`, `composer`) for HYG-007's dependency pass and HYG-015's clean build. Two optional tools are used if and only if they are already installed — `aspell` or `hunspell` in HYG-003 — and their absence is a documented fallback, not a skip. Never install anything to run this audit.

**This is the "someone forgot to flip it" domain.** Nothing here is subtle. Every finding in this file is a switch that was correct in development and was never changed for production, a piece of scaffolding that was meant to be temporary, or a fact about the repo that stopped being true three months ago. That is exactly why these are worth checking: they survive code review, because reviewers read diffs and none of these live in a diff — they live in a provider dashboard, in a string constant nobody has opened since week one, or in the gap between the README and reality. The launch-day incidents that embarrass a team most are almost never architectural. They are a Google OAuth app that only allows the staging redirect, a password-reset email linking to `http://localhost:3000/reset`, and a footer that says © 2024.

**Every artifact this domain writes goes under `.pre-launch/hygiene/` and nowhere else.** Create it once — `mkdir -p .pre-launch/hygiene` — before the first block that writes anything. A bare relative filename lands in the project root, which on many stacks is served content or is swept into the next build, so a stray `hosts.txt` can ship. `/tmp` is worse: it collides between concurrent runs, survives the audit, and puts evidence somewhere the report cannot cite. The saved names used below are `hosts.txt`, `placeholders.txt`, `strings.txt`, `spelling.txt`, `debug.txt`, `contacts.txt`, `repo.txt`, `forms.txt`, `link-status.txt`, `email-<name>.html`, `install.log`, `build.log`, `repo-status.txt`, `cookies.txt`, and the directory `clone/`. There is exactly one path outside `.pre-launch/hygiene/` this domain touches, and it is read-only: HYG-005 *reads* SEO-013's shared results table at `.pre-launch/seo/link-status.txt` when that block has already run, under the shared-evidence rule below. This domain never writes under `.pre-launch/seo/` — when HYG-005 runs first it writes its own `.pre-launch/hygiene/link-status.txt` and SEO-013 reads that.

**Never modify project files.** This domain is read-only on the project. In particular: do not run `npm install`, a build, a formatter, or a codemod in the project directory — HYG-015 exists precisely to run install and build, and it does so inside a throwaway clone for this reason. Do not `git stash`, do not switch branches, do not touch `package-lock.json`. If a check would need a file changed to be verifiable, that is a note in evidence, not an edit.

**Local-tier blocks measure a production build, never the dev server** — the same rule the performance and SEO domains state, and it changes verdicts here. Dev servers inject banners and overlays that look like leftover scaffolding (HYG-003), keep `console` output that the production bundle strips (HYG-004), serve unminified templates whose comments HYG-004 would otherwise never see, and disable the caching and minification that break an email template's inlined CSS (HYG-016). So build and start the app in production mode on a port you record (stack ref: "build" for the build and production start commands, "dev server" for the port convention) and point every `curl` in this file at that URL, noting it in evidence alongside `local.url`. If no production build can be run, say so and mark HYG-005, HYG-012, and HYG-016 `dev-server only` in `notes` rather than reporting a dev-server observation as a production fact — and note that HYG-015 has then already failed, because "the production build succeeds" is its entire claim.

**HYG-015 runs in a clone, and only in a clone.** `git clone <project_dir> .pre-launch/hygiene/clone` makes a local clone of the working tree's *committed* state. That is the point: it reproduces what a new engineer, or a CI runner, or the deploy pipeline actually gets, which is the commits — not the untracked `.env` you have had sitting there since March, not the `node_modules` you populated by hand, not the migration you wrote and never added. An uncommitted file that the build needs is therefore not an obstacle to the check, it is the finding. Run the documented install and build inside the clone, capture both logs, and delete the clone afterwards (`rm -rf .pre-launch/hygiene/clone`) so the audit does not leave a second copy of the source tree, possibly containing secrets, on disk.

**Shared evidence: four domains overlap this one — SEO, compliance, accessibility, and reliability — and each overlap has exactly one owner.** Do the work once, cite it in the other place.

- **Links (SEO-013 and HYG-005).** These two are scope-identical on link status and both would crawl the same URLs. Whichever runs second reads the first's results and re-requests nothing. The shared results file is `.pre-launch/seo/link-status.txt`, one `STATUS URL` line per link, written by SEO-013 — note that `.pre-launch/seo/links.txt` is a different file, SEO-013's bare URL list used as loop input, and is not the results table. If `link-status.txt` exists, HYG-005 reads it, says in evidence that the statuses came from SEO-013, and requests only the URLs it does not cover. If HYG-005 runs first, it crawls once and writes its own results to `.pre-launch/hygiene/link-status.txt` in the same `STATUS URL` form — this domain never writes under `.pre-launch/seo/`, so SEO-013 reads the hygiene file instead. Duplicated crawling is the single most likely way this audit trips a rate limiter and turns a working site into a page of false failures. HYG-005 additionally owns contact-email syntax, social-profile links, and the copyright year, which SEO-013 does not touch.
- **Hosts (SEO-006, SEO-007 and HYG-002).** SEO-006 and SEO-007 judge the canonical and OG tags on rendered pages. HYG-002 owns the repo-wide static grep for hardcoded hosts across source, email templates, configs, OG and canonical builders, and API base constants. The SEO blocks cite HYG-002's sweep for their call sites rather than re-deriving it; HYG-002 does not re-fetch pages.
- **Placeholder copy (COMP-018 and HYG-003).** COMP-018 owns fabricated social proof — testimonials, logos, review counts, user-number claims — because that is a truth-in-advertising problem with legal weight. HYG-003 owns everything that is merely unfinished: lorem ipsum, framework default titles, sample data, staging banners, and the proofread. A fake testimonial found here goes to COMP-018 with the file:line, not into this domain's count.
- **Legal page metadata (COMP-035, COMP-036 and HYG-006).** COMP-035 owns whether terms *acceptance* is recorded with a version, COMP-036 whether the pages are linked and reachable. HYG-006 owns whether the pages themselves carry an effective date and a version, and whether those agree with the versions the acceptance record and the changelog claim.
- **Licences (COMP-028 and HYG-007).** COMP-028 owns dependency, font, and image licence compliance and attribution. HYG-007 cites it for anything licence-shaped and confines itself to whether the repo has a `LICENSE` file of its own, a usable README, no large binaries, and no dead weight.
- **Password fields (A11Y-016 and HYG-011).** A11Y-016 owns the `autocomplete` token values. HYG-011 owns everything else that stops a password manager working: paste blocking, `autocomplete="off"`, and whether the field is a real `<input type="password">`. Whichever runs second cites the first rather than re-reading the forms.
- **Env values (REL-008) and the domain (REL-017).** REL-008 owns whether every variable the code reads is defined for production with no silent dev fallback; HYG-001 cites it for the *values* and concerns itself with whether the matching setting was made in the provider's dashboard, which no amount of env-var checking can see. REL-017 owns TLS and the apex/www redirect; HYG-001 includes the DNS records as one row of its cutover table and cites REL-017 rather than re-testing the certificate.

**Grep discipline.** Most of this domain is a static sweep, and a sweep with the wrong exclusions produces a hundred findings in `node_modules` and buries the two real ones. Use the same exclude set everywhere below, referred to as **the standard excludes**: `--exclude-dir={node_modules,.git,dist,build,.next,.nuxt,out,vendor,coverage,.venv,__pycache__,.pre-launch}` together with `--exclude={"*.lock","*-lock.json","*.min.js","*.map","*.snap"}` — quote each glob inside the braces, because zsh expands the brace and then tries to glob the result, and an unquoted `--exclude=*.lock` aborts the whole command with `no matches found` on a repo that happens to have no `.lock` file. Three further exclusions apply to this domain specifically and are named in the blocks that use them: test files and fixtures (a `localhost` in a test is correct), documentation and `README` (an example URL in prose is correct), and `.env.example` (a placeholder value there is the file working as intended). One caveat on the documentation exclusion: on a docs-site framework — Docusaurus, Nextra, VitePress, Starlight, MkDocs — `docs/` and the Markdown in it *are* the served content, so excluding them excludes the site. Check what the framework is before excluding, and where the Markdown ships to users, keep it in the sweep and exclude only genuine developer documentation. Record what you excluded — a sweep whose exclusions are invisible cannot be reproduced or argued with.

**When a product legitimately lacks the feature, say `n/a — <reason>` with an em dash** so the merged report reads the same as the other domains'. The legitimate paths: a product that sends no email at all makes HYG-016 `n/a — product sends no email` (name the greps for a mail client and templates that returned nothing, since otherwise this is indistinguishable from not looking); a product with no mobile web surface — a desktop-only internal tool, a CLI's documentation site — makes HYG-013 partial, with the viewport meta still required and the manifest and safe-area rows `n/a`; a single-locale product makes HYG-014 partial, with the `Intl` and hardcoded-separator rows still checked (they are what makes a second locale cheap later) and the RTL row `n/a — single locale`. A product with no legal pages is not an `n/a` for HYG-006, it is COMP-036's finding, and this block cites it.

### HYG-001 Third-party dashboards configured for prod domain: OAuth redirect URIs, auth site URL and redirect allowlist, Apple Sign In, email sender domain, error tracker project, analytics property, backend CORS allowlist
severity: critical
tier: attest
fix: guided
why: Everything works on localhost and staging, then the first real user cannot sign in with Google because the OAuth app only allows the staging redirect URI. This is the most common launch-day failure and no amount of code review catches it — the wrong value is not in the repo, it is in a web form on a provider's site that someone filled in during week one and has not opened since. It is also the failure with the worst shape: it passes every test, it passes in staging, and it fails for one hundred percent of real users at once.
verify:
  static: Build the list of externally configured URLs from the code, one row per setting, and record the value currently in code or env beside each. Work through these sources: the OAuth providers actually wired up (stack ref: "auth") and their redirect or callback URIs, one row per provider — Google, GitHub, Microsoft, Apple — since each has its own dashboard and they are configured separately; the auth provider's own site URL and redirect allowlist, which is a distinct setting from the OAuth app's (Supabase `Site URL` plus `Additional redirect URLs`, Firebase `Authorized domains`, Clerk and Auth0 allowed callback and logout URLs, NextAuth's `NEXTAUTH_URL`); Apple Sign In specifically, which needs its own row because it is configured differently from every other provider — the Services ID, the return URL registered against it, and the private key and Team ID — and because its return URL must be `https` and cannot be localhost, so it is the one provider that was never tested locally; the email sending domain and whether it is verified with SPF, DKIM, and a DMARC record at the provider (Resend, Postmark, SendGrid, SES), plus whether the account is still in a sandbox or test mode that only delivers to verified recipients; the error tracker's DSN and which project and environment it points at, since a DSN left on the dev project means production errors land where nobody looks; the analytics property or measurement ID and whether it is the production property; the payment provider's webhook endpoint URL and signing secret, one row, cross-referenced to PAY-001 which owns the live-endpoint check in full — record the value here and do not re-verify it; the backend CORS allowlist, cross-referenced to SEC-035 which owns whether it is correctly scoped — this row records only whether the production origin is in it; for a mobile app, the push credentials (APNs key or certificate, FCM server key or service account) and which bundle identifier and environment they are bound to, cross-referenced to MOB-009; the DNS records for the production domain — A or CNAME for the apex and www, MX and the mail TXT records if the domain sends email, and any provider verification TXT — cross-referenced to REL-017 which owns TLS and the apex/www redirect; and the storage bucket's CORS configuration if the browser uploads or reads directly from object storage, since a bucket that allows the staging origin only fails every upload on day one. For each row, take the current value from config or env (stack ref: "env vars"; REL-008 owns whether the variable is defined for production at all, so cite it rather than re-deriving) and flag any value that is `localhost`, a preview or platform-generated hostname, a test-mode key, or blank.
  attest: Present the list as a checklist for the human to confirm in each provider dashboard, one row at a time, and record the answer per row rather than in aggregate. The pass is the user saying, for each row, that they opened that provider's dashboard and saw the production value — "I checked them all" is not an answer to fifteen questions. Ask explicitly whether the localhost or staging entries were *removed* or merely joined by the production one: leaving `http://localhost:3000/callback` in a production OAuth app's allowlist is a real, if lower-severity, finding, because it lets an attacker who can get a victim to a localhost listener complete an auth flow. For any row the user cannot check now, record `unconfirmed` with the reason; do not carry it as a pass.
evidence: two other blocks consume this table, so write it once and completely — HYG-016 reads the email-sending-domain row rather than re-checking SPF and DKIM, and HYG-008 reads any credential with a stated expiry into its dated list; table of provider, setting, current value, source file:line, and the user's dashboard confirmation per row (`confirmed prod` / `still staging` / `unconfirmed`); the production origin you compared every row against and where you got it; the rows delegated to PAY-001, SEC-035, MOB-009, REL-017, and REL-008 named as delegated rather than repeated.
fix_hint: For each row, set the production value in the provider dashboard and in the prod env; keep localhost entries only in the dev allowlist, and where the provider has separate dev and prod applications, use them rather than one application with both origins. Then write the table into the repo as a deploy checklist so the next domain change is a fifteen-minute edit rather than a fifteen-hour incident.

### HYG-002 No hardcoded localhost or staging URLs in emails, OG tags, canonical, API base, or configs
severity: high
tier: static
fix: easy
why: A hardcoded `http://localhost:3000` in a password-reset email is invisible in every test — the developer clicks the link, it works on their machine, it ships. Then a user gets an email whose only button goes nowhere. The same constant in an API base makes the production frontend call a host that does not exist; in a canonical or OG tag it hands search engines and link previews an unreachable URL, which is SEO-006 and SEO-007's consequence and this check's cause. The distinguishing feature of this bug class is that the person who wrote it can never reproduce it.
verify:
  static: Sweep the repo for host literals with the standard excludes plus tests, docs, and `.env.example`: `grep -rnE "localhost|127\.0\.0\.1|0\.0\.0\.0|\.vercel\.app|\.netlify\.app|\.ngrok|\.loca\.lt|:3000|:5173|:8000|:8080" . --exclude-dir={node_modules,.git,dist,build,.next,.nuxt,out,vendor,coverage,.venv,__pycache__,.pre-launch,test,tests,__tests__,e2e,cypress,docs} --exclude={"*.lock","*-lock.json","*.min.js","*.map","*.snap","*.test.*","*.spec.*","*.md",".env.example"} > .pre-launch/hygiene/hosts.txt`. Run the environment-name patterns as a second, narrower pass, because bare `staging.`, `dev.`, and `test.` match half of every JavaScript codebase (`dev.dependencies`, `test.each`, `process.env.NODE_ENV`) and a hundred false positives is the same as no result: restrict them to URL context with `grep -rnE "(https?://|@)(staging|dev|test|preview|qa)\." . <same excludes> >> .pre-launch/hygiene/hosts.txt`, where the `@` catches email addresses and connection strings. Then read the hits rather than counting them, and sort each into one of three verdicts. **Pass, env-derived**: the literal is a fallback beside a variable read (`process.env.API_URL ?? "http://localhost:3000"`, `os.getenv("SITE_URL", "http://localhost:8000")`) and the production value of that variable is set — note it, and hand the fallback itself to REL-008, which owns silent dev fallbacks and whose finding this is. **Pass, dev-only**: the literal is inside a development branch, a dev-server config (`vite.config`'s `server.proxy`, `next.config`'s `rewrites` under a dev guard, `docker-compose.yml` for local work), or a script that only runs locally. **Fail**: the literal is on a path that executes in production. The four places that matter most, and that you should check by name rather than trusting the sweep to have reached them: email templates and the mailer's base URL (stack ref: "routes and handlers"; HYG-016 renders them and reads this block's result), the canonical and OG builders (SEO-006 and SEO-007 cite this sweep, so name the file:line of every hit on those paths), the API base constant the client bundle ships with — check the *built* output too if a production build exists, since a base URL can be baked in at build time from a variable that was wrong in the build environment — and any webhook or callback URL in config, which is HYG-001's table. Also grep the CI and deploy configs, where a hardcoded preview host in a build-time variable produces a production bundle pointing at a preview deployment.
evidence: per hit — file:line, the literal found, and the verdict (`fail` / `pass, env-derived: <VAR>` / `pass, dev-only: <reason>`); the exclusions used, quoted, so the sweep is reproducible; the four named paths (email, canonical/OG, API base, webhook config) each explicitly reported as clean or failing rather than left to inference; the hits handed to REL-008 as fallbacks and to HYG-001 as dashboard rows.
fix_hint: Replace each failing literal with a read of one environment variable holding the production origin, set that variable in every environment including CI, and delete the inline fallback so a missing value fails loudly at boot instead of quietly emailing links to localhost.

### HYG-003 Placeholder content removed: lorem ipsum, default framework titles, sample data, "coming soon" stubs, staging banners; copy proofread
severity: high
tier: static
fix: easy
why: A page of lorem ipsum below the fold, a tab that still says "Create Next App", a pricing table with `[Company Name]` in it — each one tells a visitor, in the first five seconds, that this is not finished. That judgement is not recoverable; they do not come back to check whether you fixed it. Typos do the same work more slowly: a landing page with three spelling errors reads as careless, and for a product asking for a credit card, careless reads as unsafe.
verify:
  static: Two passes, because the automatic one and the human one find different things. **Pass one, the tells.** Sweep user-facing content — page and route files, templates, components, content and MDX directories, email templates, and any CMS fixture or seed file — with the standard excludes plus tests: `grep -rniE "lorem ipsum|dolor sit amet|create next app|welcome to nuxt|vite \+ react|welcome to your new|coming soon|todo:? ?copy|\[company name\]|\[your |acme|example\.com|john doe|jane doe|555-" . <standard excludes, plus test and fixture dirs, plus *.md and .env.example> > .pre-launch/hygiene/placeholders.txt` — exclude documentation and `.env.example` for the same reason HYG-002 does, since an `example.com` in a README or a placeholder in `.env.example` is that file working correctly. Then triage the hits once, because several of these tells are also real words: a company genuinely named Acme, a product whose brand contains one of these strings, a support address really on a domain that matches a tell, or a `555-` number used deliberately is dismissed *once*, recorded as dismissed with the reason, and not re-raised for every later hit on the same string. Then check the specific places a default survives longest, which a keyword sweep often misses because the text is generic rather than distinctive: the `<title>` and meta description of the root layout and every route that does not set its own (a site where nine pages inherit "My App" from the layout is this finding, not SEO's); the favicon and OG image, if either is still the framework's default (SEO-002 owns the favicon's presence, this owns whether it is Vercel's triangle); the `name`, `description`, and `author` fields in `package.json` or the equivalent manifest; the app name in `manifest.json` (HYG-013 owns the manifest's existence, this owns whether it says "create-next-app"); the footer's company name and address; and any seed, demo, or sample-data flag still enabled in production config (`SEED_DEMO_DATA`, `USE_MOCK_DATA`, `demoMode`, a fixtures loader called at boot) — that one is a data finding as much as a copy one, because it puts fake rows in a real database. Check for a staging or environment banner component and read its condition: a banner that renders unless `NODE_ENV === "production"` is fine, one that renders unless a variable is set to a string that is never set in production is a banner in production. Anything found that is a *fabricated claim* rather than unfinished copy — an invented testimonial, a fake logo wall, "trusted by 10,000 teams" — goes to COMP-018 with its file:line and is not counted here. **Pass two, the proofread.** Extract the user-facing strings once — the visible text of the ten most-visited pages plus every email subject and body, with markup stripped — into `.pre-launch/hygiene/strings.txt`. If `aspell` or `hunspell` is already installed, run it over that file (`aspell --lang=en --mode=none list < .pre-launch/hygiene/strings.txt | sort -u > .pre-launch/hygiene/spelling.txt`) and triage the output, which will be mostly product vocabulary: keep a list of the words you dismissed as names, jargon, or brand terms, because an unfiltered spellcheck dump is not a finding and a reviewer cannot tell the difference between forty typos and forty product nouns. If neither is installed, read the ten pages yourself — that is the fallback, not a skip. Either way, what a proofread pass records is: the exact pages read and where the strings came from; each suspected error as the quoted string with its page and file:line and the correction; each dismissed word with why; and the three classes a spellchecker cannot catch, which are usually the ones that matter — the wrong homophone (`your`/`you're`, `its`/`it's`, `their`/`there`), inconsistent product or feature naming across pages (the same thing called "Workspace" in the nav and "Project" in the docs), and inconsistent casing or voice in buttons and headings (`Sign up` beside `Log In`). Note when the copy is British or American English so the pass judges by one standard rather than flagging `colour` as an error.
evidence: per placeholder hit — file:line, the string, and whether it renders to users; the named checks (root title and per-route titles, favicon and OG default, manifest name, package metadata, footer, seed/demo flags, staging banner condition) each reported explicitly; the proofread record — pages read, tool used or `manual read, no spellchecker installed`, suspected errors with quotes and file:line, words dismissed as product vocabulary, and the homophone/naming/casing findings; the items handed to COMP-018.
fix_hint: Delete or replace every placeholder string, set a real title and description on the root layout and on every route that inherits one, replace the framework's default icons and manifest name, turn off any seed or demo-data flag in production config, and gate the environment banner on `NODE_ENV` rather than on a variable that may be unset. Fix the spelling and pick one name per concept, then use it everywhere.

### HYG-004 No console logs, debug flags, TODO/FIXME in user-facing paths, or commented-out secrets
severity: medium
tier: static
fix: easy
why: Console output in production is a slow leak: it logs user identifiers, request payloads, and sometimes tokens into a place any visitor can read with two keystrokes, and it makes the console useless for the errors you actually need to see. A debug flag left on is worse — it turns a framework's error page from "something went wrong" into a full stack trace with environment variables and query strings, which is a security finding wearing a hygiene finding's clothes. A `TODO` rendered into the page is just embarrassing.
verify:
  static: Four separate sweeps, because they have four different verdicts. **Debug output in source**: `grep -rnE "console\.(log|debug|info|table|dir)|(^|[^A-Za-z0-9_.])(print\(|pp |dd\(|dump\(|var_dump\()|binding\.pry|byebug|debugger;?$" . <standard excludes, plus test, spec, script, and seed directories>` — the short patterns have to be anchored on a non-identifier character or they are pure noise: unanchored, `pp ` matches every `app ` in the codebase and `dd\(` matches `map.add(item)` — a `console.log` in a test, a build script, a migration, or a CLI entry point is correct and not a finding. Judge the survivors by whether the bundler strips them: many production configs drop `console` calls (`compiler.removeConsole` in Next.js, a Terser `drop_console`, a Vite `esbuild.drop`), so read the build config before reporting, and say in evidence whether stripping is configured — if it is, the finding downgrades to a note except for server-side logging, which no bundler touches. Server-side `console.log` is the one to insist on: it goes to the platform's log stream, is retained, and is where the leaked payloads end up (stack ref: "error handling and logging" for what the project uses instead). One exception, and it will be in the hit list of every project that has a logger: a `console` call inside the project's own logging module is the *implementation* of logging, not a leak — that is where a structured logger ultimately writes. Identify that file once, exclude its hits by name, and say which file you excluded. **Debug flags in production config**: grep the deploy and runtime config, not the source, for `DEBUG=true`, `APP_DEBUG=true`, `debug: true`, `NODE_ENV` set to anything but `production`, `FLASK_ENV=development`, `RAILS_ENV` not production, `DJANGO_DEBUG`, a Sentry or logger level of `debug`, and a framework's dev-error middleware registered unconditionally. Django's `DEBUG = True` and Laravel's `APP_DEBUG=true` are the two that leak the whole environment on any 500 and are worth naming individually. **`TODO`/`FIXME`/`HACK`/`XXX`**: sweep for them, then split the hits by path, because the verdict differs. In user-facing paths — route files, templates, components, content and copy files, email templates — a `TODO` is a fail if it renders (a literal `TODO` in a heading) and a high-priority note if it marks unfinished behaviour on a path a user reaches. In internal code — utilities, server modules, infrastructure — record the count and the ones that sit on a launch-critical path, as a note, not a fail: a codebase with forty `TODO`s is normal and reporting that as forty findings destroys the credibility of the rest of the report. **Commented-out code containing secrets**: grep for comment lines carrying key-shaped material (`grep -rnE "^[[:space:]]*(//|#|/\*).*(api[_-]?key|secret|token|password|bearer|sk_live|sk_test|-----BEGIN)" . <standard excludes>`). Anything found is SEC-001's finding, not this block's — a commented-out secret is in git history and is compromised regardless of the comment — so hand it over with the file:line and record here only that the sweep ran and what it passed on. Write all four sweeps' raw hits to `.pre-launch/hygiene/debug.txt` and cite it.
evidence: per sweep — the command's exclusions, the hit count, and the hits that survived triage with file:line; whether the production build strips `console` calls and the config line that does it; server-side logging hits listed separately from client-side; `TODO`-family hits split into user-facing (listed individually) and internal (counted, with the launch-critical ones named); the commented-secret hits handed to SEC-001 by file:line.
fix_hint: Delete the debug output on production paths and replace the server-side ones with the project's logger at an appropriate level, set the production config's debug flags off and `NODE_ENV` to production in every environment, resolve or delete the `TODO`s on user-facing paths, and delete commented-out code containing credentials — then rotate those credentials, because deletion does not remove them from history.

### HYG-005 No dead links, broken images, invalid contact emails, or broken social links; copyright year current
severity: medium
tier: local
fix: easy
why: The footer is the oldest text on any site. It has last year's copyright, a support address that bounces because the alias was never created, and a Twitter link to an account that was renamed. Each is small; together they are the strongest available signal that nobody is home. A dead `mailto:` on the contact page is worse than small — it silently discards every message a customer tries to send you before they have a chance to become a customer.
verify:
  static: Find the link surfaces before testing them: the footer and header components, the contact page, the legal pages, and any link list held in a config or content file rather than in code — that last one is the set nobody re-checks. Extract every `mailto:`, every `tel:`, every social-profile URL, and the copyright string, with file:line, into `.pre-launch/hygiene/contacts.txt`. Validate the email addresses by syntax and by intent: a syntactically valid address is not the check, because the failures here are `support@example.com` left from the template, `hello@yourcompany.com`, an address on a domain the project does not own, and an address whose local part does not exist as a mailbox or alias — you cannot confirm the mailbox from the repo, so record the address and the domain and make the existence of the mailbox an explicit question in the report (REL-028 owns whether the support path reaches a human, so cite it). Check the `tel:` links are in `+<country><number>` form with no spaces, since a formatted number in the `href` fails to dial on some platforms. If `.pre-launch/seo/link-status.txt` exists, SEO-013 has run: read the statuses from it, cite it, and never re-curl a URL it already has a status for — request only what it does not cover, which is typically the social profiles and any contact-page links not reachable from the home page. If the status file does not exist, this block crawls once and writes its own results to `.pre-launch/hygiene/link-status.txt`, one `STATUS URL` line per link so SEO-013 can consume it directly — write under `.pre-launch/hygiene/` and never under `.pre-launch/seo/`. evidence: the source of the link statuses (`from SEO-013` with the file, or `crawled here` with the counts checked); broken links with status, URL, and the page they were found on; unverified links with status and reason; per contact address — the address, file:line, syntax verdict, and whether the domain is one the project owns, with the mailbox-existence question raised explicitly; `tel:` format verdicts; each social link with its URL, status, and whether the handle was confirmed in the body; the rendered copyright year, the current year, and whether the year is hardcoded or computed, with file:line.
fix_hint: Fix or remove every dead link, replace template contact addresses with real monitored ones on a domain you own and confirm each mailbox delivers, put `tel:` links in `+<country><number>` form, correct the social URLs to the current handles, and render the copyright year from the server's current date so it never needs touching again.

tier: static
fix: easy
why: A privacy policy with no effective date is a document with no shelf life: nobody can tell whether it describes what the product does today or what it did two years ago, a user cannot know which text they agreed to, and if you ever have to demonstrate what was in force on a given date you cannot. ### HYG-007 Repo hygiene: README with setup, LICENSE, no large binaries, no unused dependencies or dead routes
severity: low
tier: static
fix: easy
why: The README is the only documentation anyone will read, and the version of it that ships at launch is usually the framework's default with three lines added in week one. That matters on the day you are ill and someone else has to deploy: undocumented setup is HYG-015's failure mode expressed as prose. Large binaries in git make every clone slow forever, unused dependencies are attack surface and audit noise, and dead routes are endpoints nobody is maintaining but everybody can reach.
verify:
  static: Five things, each cheap. **README**: does it exist, and does it contain the commands a new engineer needs — prerequisites and versions, install, the environment variables to set with where to get them, the dev-server command, the build command, and how to run the tests? HYG-015 executes these steps in a clean clone and reports every undocumented one; this block reports the gap statically so both findings agree. **LICENSE**: this is a conditional, not a requirement. evidence: README presence with the list of documented steps beside the list of steps the project actually needs, gaps named; LICENSE presence and the licence named in each of the three places with a match verdict, dependency licensing cited to COMP-028; the twenty largest tracked files with sizes and the ones flagged, with a note that history retains them; unused-dependency candidates with the evidence for each and an explicit confidence statement; dead-route candidates with paths and whether each requires auth.
fix_hint: Write the README's setup section by following it yourself on a clean clone and fixing what does not work (HYG-015 is that exercise), add a LICENSE that matches the manifest and the footer, move large binaries out of git to object storage or Git LFS, remove the dependencies you have confirmed unused, and delete dead routes rather than leaving them unlinked.

### HYG-008 Time bombs: hardcoded dates, expiring keys or trial licenses, lapsing free-tier limits
severity: high
tier: static
fix: guided
why: A time bomb is a bug that is not a bug yet. The code works today, passes every test today, and fails on a date nobody has written down — a promotional banner keyed to a hardcoded date, a `Date.now() < 1767225600000` that was a sensible guard in 2025, a JWT signing key with an expiry, an API certificate that renews annually and was set up by someone who has left. The reason these deserve a high severity despite never having failed is that they fail *unattended*, usually at midnight, usually with no error in the tracker because the code took a branch rather than throwing.
verify:
  static: Sweep for date and expiry literals and read each hit in context — this is a check where the grep is the start of the work, not the end. Patterns: ISO dates in source (`grep -rnE "20(2[4-9]|3[0-9])-[01][0-9]-[0-3][0-9]" . <standard excludes, plus tests and migrations>` — migrations legitimately contain dates), four-digit year literals near a comparison or a conditional, epoch-millisecond literals (a bare thirteen-digit number is almost always a hardcoded timestamp), and the keyword set `expires`, `expiry`, `expiration`, `valid_until`, `trial`, `trialEnds`, `license`, `licence`, `cutoff`, `deadline`, `launchDate`, `promoEnds`, plus the shapes `Date.now() <`, `new Date() >`, `datetime.now() <`, and `Time.now >`. Triage into: a date that gates *behaviour* (a banner, a discount, a feature flag, a beta gate, a redirect) — the classic time bomb, and each needs the date it fires named in the report; a date that is *content* (a copyright year — that is HYG-005's, a blog post date, a changelog entry) — not a finding; and a date inside a test fixture or migration — not a finding, though a test asserting against a hardcoded future date will start failing on that date and is worth a note. Then check the credentials and entitlements that expire outside the code. In config, README, and the deploy files, look for anything documenting an expiry: a JWT or signing key with a stated lifetime, an API certificate or client secret with a renewal date (Apple's Sign In key and push certificates and Microsoft/Azure client secrets are the ones that actually catch people, since they expire on a schedule and give no warning in the app), a service-account key rotation policy, a domain or TLS expiry — TLS and domain expiry are REL-017's, so cite it. Trial and plan entitlements are the third category: a third-party service on a free trial that converts or lapses, a plan tier whose limits are documented in config or the README, and any free-tier ceiling the code works around. REL-020 owns whether the tiers are sufficient and asks the user about them, so cite it and record here only the expiry dates and the fact that the entitlement is time-bound; ACC-011 owns whether auto-renew and a valid payment method are in place on each account, which is the mechanism by which most of these actually detonate, so cite it rather than asking again. The output is a dated list: every date the system will behave differently, in chronological order, with what happens on it.
evidence: a chronological table — date, what changes on it, file:line or the config/README line that documents it, and severity if it fires unattended; the hits triaged as content or test fixtures listed separately so the sweep is visible; expiring credentials with their stated renewal dates and owners where known; entitlement and trial expiries with the rows cited to REL-020 and ACC-011; TLS and domain expiry cited to REL-017.
fix_hint: Replace behaviour-gating date literals with a configured value or a feature flag that a human can change without a deploy, put every credential and entitlement expiry from the table into a shared calendar with a reminder at least two weeks ahead and a named owner, and where a key can be rotated on a schedule, rotate it once before launch so the procedure is known to work.

### HYG-009 Version bumped; changelog or release notes; launch commit tagged
severity: low
tier: static
fix: easy
why: When something breaks in week two, the first question is "what changed and when", and the answer has to be available in ten seconds from a phone. A version in the build, a tag on the launch commit, and a changelog entry are what turn that question into a `git diff` between two names. Without them the answer is an archaeology exercise across a deploy dashboard and a commit log at the exact moment nobody has time for one.
verify:
  static: Check the version is bumped in the place the project actually reads it: `package.json`'s `version`, `pyproject.toml`, `Cargo.toml`, `*.gemspec`, `composer.json`, or for a mobile app the version name and build number in the app config (`app.json`/`app.config.js`, `Info.plist`, `build.gradle`) — where a build number that is not incremented is a hard store rejection, not a nicety, so treat a mobile version row as a fail rather than a note. fix_hint: Bump the version in the manifest, add a dated changelog entry written for a reader rather than a compiler, wire the same version and commit SHA into the error tracker's release field and a runtime-reachable place, and add "tag the release commit" as an explicit step in the deploy runbook so it happens at release rather than being audited for beforehand.

### HYG-010 Browser matrix tested: Safari, iOS Safari, Chrome, Firefox, Edge
severity: medium

fix: none

### HYG-011 Password managers work: autocomplete attributes correct; paste not blocked
severity: low
tier: static
fix: easy
why: Blocking paste in a password field is a twenty-year-old habit that makes the product worse and less secure at the same time: it forces users off password managers and onto passwords they can type from memory, which are short and reused. The same is true of `autocomplete="off"` and of a "password" field that is a styled `<input type="text">` with a masking font — the manager cannot see it, will not fill it, and will not offer to save the credential, so the user picks something they can remember and your account-takeover rate goes up.
verify:
  static: Find the auth forms (stack ref: "routes and handlers", "auth") — sign up, log in, password reset, password change, and any credential entry inside settings or checkout — and check four things on each. **Paste is not prevented**: grep for `onpaste`, `onPaste`, `"paste"` event listeners, and `preventDefault` inside one (`grep -rnE "on[Pp]aste|addEventListener\([\"']paste" . <standard excludes>`), and check for the indirect versions too, which are more common than an explicit handler — an input that filters or rejects on every keystroke and so mangles a pasted value, a one-time-code field split into six single-character boxes with no paste handler that distributes the digits (paste is not blocked there, it is simply broken, and the user experience is identical), and a `maxlength` shorter than the password the manager generates. **No `autocomplete="off"`**: `grep -rnE "autocomplete=[\"']off[\"']|autoComplete=[\"']off[\"']" . <standard excludes>` on the form fields and on the `<form>` element itself. Report it, and report it accurately: modern browsers deliberately ignore `autocomplete="off"` on password fields precisely because this pattern was so widely abused, so the honest finding is that the attribute signals an intent that some managers and older browsers still honour, and that it should be deleted rather than that it definitely breaks filling today. A11Y-016 owns the *values* of the `autocomplete` tokens across auth and address forms — whether login uses `current-password` and sign-up uses `new-password`, and the address-field tokens — so read its results for those and confine this block to the `off` case; whichever of the two runs second cites the first rather than re-reading every form. **The field is a real password input**: confirm each is `<input type="password">` rather than a text input with a masking font, a `contenteditable`, or a custom component that renders a div — a masked text field also leaks the password into autofill history and into any screenshot-safe assumption the user makes. Check any show/hide toggle switches the `type` attribute between `password` and `text` on the same element rather than swapping between two elements, since swapping loses the manager's binding. **The form is fillable in principle**: the username or email field and the password field are inside the same `<form>` element, the form has a submit button of `type="submit"` rather than a click handler on a div, and the fields are not inside a shadow root or an iframe that a manager cannot reach. Then say plainly what could not be verified statically: whether a real password manager fills and saves the credential is a human check, so name it as a manual step in the fix hint and in evidence rather than implying the static pass proves it.
evidence: per auth form — path and file:line; paste-prevention hits with file:line, including the indirect forms (per-keystroke filtering, split code inputs, short `maxlength`); every `autocomplete="off"` with file:line and whether it is on a field or the form; the `type` attribute of each credential field and how any show/hide toggle is implemented; whether the identifier and password fields share a form and whether the submit control is a real submit; the `autocomplete` token verdicts cited to A11Y-016; the manual manager-fill check named explicitly as unverified.
fix_hint: Delete the paste handlers and the `autocomplete="off"` attributes, make every credential field a real `<input type="password">` whose show/hide toggle flips the `type` in place, put the identifier and password in one `<form>` with a real submit button, remove any `maxlength` below the length a generated password needs, and make one manual pass with a password manager installed: fill the login form and save a new credential at sign-up.

### HYG-012 Forms preserve input on validation error; destructive actions confirm
severity: low
tier: local
fix: easy
why: A form that clears itself on a validation error is the fastest way to lose a signup: the user typed nine fields, one was wrong, and now all nine are blank with no explanation of which. It is a server-rendered classic, and it comes back with every new framework. The mirror image is the destructive action with no confirmation — a "Delete project" button that deletes on the first click, with no undo and no way back, which converts a mis-tap into a support ticket you cannot resolve.
verify:
  static: Find every form that validates server-side (stack ref: "routes and handlers") and read what the failure path renders. The pass shapes: POST-redirect-GET carrying the submitted values back into the re-rendered form, a framework mechanism that does this for you (Rails' `render :new` with the object, Django's bound form, a Next.js server action returning the previous state, a Remix `useActionData`), or a client-side form library holding the state so the server round-trip never clears it. The fail shapes: a redirect back to a blank form, a re-render that passes the errors but not the values, and — the subtle one — a form that preserves text fields but drops selects, checkboxes, radios, and file inputs, which is the most common partial failure and the most annoying, since a file input cannot be repopulated at all and the user must be told that rather than left to discover it. Separately, enumerate the destructive actions: delete account, delete project or workspace, cancel subscription, remove a member, revoke an API key, empty or reset data, and any bulk delete. For each, find whether there is a confirm step or an undo, and judge which is appropriate — a `window.confirm` is weak but real; a modal that requires typing the resource name is right for account and workspace deletion; a soft delete with a restore window is better than any confirmation for anything a user might regret; and for a subscription cancellation the appropriate thing is usually a confirmation that states plainly what happens and when (access until the period ends, data retained for N days), because the harm is not the click but the surprise. Note any destructive action reachable by a GET request or a plain link, which is both this finding and a security one, since a prefetcher or a link scanner can trigger it.
  local: Against the production build, exercise the two behaviours rather than inferring them. For the highest-value form — sign-up, then checkout if there is one, then any long settings form — submit it with a deliberate validation error in one field and every other field filled, and record which values survive the response: `curl -s -c .pre-launch/hygiene/cookies.txt -b .pre-launch/hygiene/cookies.txt -L "<local.url><path>" -d "<fields>" -o .pre-launch/hygiene/forms.txt` — `-d` already makes it a POST, and do not add `-X POST`, which forces the method to persist across the `-L` redirect and so re-POSTs to the redirect target, misreading the POST-redirect-GET pattern this check is looking for and then grep the saved response for each submitted value. Where the form is client-rendered and a `curl` POST cannot reach it, say so and report the static verdict rather than a false observation — this is a real limit of the tier, not something to paper over. For the destructive actions, confirm the confirmation exists in the rendered page: fetch the page holding the action and check the control is wired to a confirm step, and check that the action's endpoint is not a GET. Do not actually perform a destructive action against any environment.
evidence: per form — path, the failure-path mechanism found with file:line, and the verdict; for the forms exercised, the fields submitted beside the fields found in the response, with the dropped ones named and file inputs called out; per destructive action — the action, its endpoint and HTTP method, the confirm or undo mechanism found with file:line, and whether it is proportionate to the harm; any destructive action reachable by GET, flagged for the security domain; forms that could not be exercised at this tier, named with the reason.
fix_hint: Re-render the form with the submitted values on validation failure — use the framework's bound-form mechanism rather than hand-rolling it — and preserve selects, checkboxes, and radios as well as text, telling the user explicitly that a file must be re-attached. Add a confirmation proportionate to the harm for each destructive action (type-the-name for account and workspace deletion, a plain confirm elsewhere), prefer a soft delete with a restore window where the data has value, and make sure every destructive endpoint is a POST or DELETE, never a GET.

### HYG-013 PWA/mobile-web basics: viewport meta, theme-color, manifest if installable, safe-area insets
severity: low
tier: static
fix: easy
why: A missing viewport meta renders the site at desktop width on a phone, zoomed out to unreadability — one line of HTML between a usable mobile site and an unusable one, and more than half the traffic arrives on a phone. The rest of this list is what separates a page that happens to load on a phone from one that behaves like an app: a status bar that matches the design instead of flashing white, a home-screen icon that is not a screenshot of the page, and a bottom button that is not underneath the iOS home indicator.

  static: Check each, in the root layout or base template (stack ref: "routes and handlers"). **Viewport meta**: present, and sane — `width=device-width, initial-scale=1` is the correct content. Two failure shapes matter beyond absence: `user-scalable=no` or `maximum-scale=1`, which blocks pinch-zoom and is an accessibility failure (WCAG 1.4.4) as well as a hygiene one — report it as both; and a fixed `width=1024`, which is the desktop-width rendering with extra steps. If the app draws behind the notch, the viewport also needs `viewport-fit=cover`, without which the safe-area environment variables are all zero and the insets below do nothing. **`theme-color`**: a `<meta name="theme-color">`, ideally with `media="(prefers-color-scheme: dark)"` variants if the site has a dark mode, so the browser chrome does not stay light against a dark page. **Manifest**: if the app is installable or wants to be — check for a service worker, a PWA plugin in the build config, or an existing `manifest.json`/`site.webmanifest` — verify the manifest is linked from the head, is served (a manifest referenced but 404ing is the usual state), and contains `name`, `short_name`, `start_url`, `display`, `background_color`, `theme_color`, and an `icons` array with at least 192px and 512px entries plus a `maskable` icon. Check `start_url` is a path the app actually serves and that it matches the scope; and check `name` is not still the framework default, which is HYG-003's placeholder finding surfacing here. If the app is plainly not installable, mark the manifest rows `n/a — not an installable app` rather than inventing a requirement. **`apple-touch-icon`**: a `<link rel="apple-touch-icon">` at 180x180, since iOS ignores the manifest icons for the home-screen icon and will otherwise use a screenshot of the page. SEO-002 owns the favicon's presence and format; this block owns the apple-touch-icon, the manifest, and `theme-color`, so cite SEO-002 for the favicon rather than checking it twice. **Safe-area insets**: where the app is a mobile web app with anything fixed to the bottom or top — a sticky action bar, a bottom nav, a floating button, a full-screen modal — grep the stylesheets for `env(safe-area-inset-` and confirm the fixed elements use it (`padding-bottom: env(safe-area-inset-bottom)`, or the `max()` form that keeps a minimum padding on devices with no inset). Absent, the bottom button sits under the iOS home indicator and is hard to hit. **`100vh` versus `100dvh`**: `grep -rn "100vh" . <standard excludes>` and read each hit — on iOS Safari, `100vh` is the viewport *without* the collapsing toolbar, so a `height: 100vh` layout is taller than the visible area and its bottom is cut off until the user scrolls. Report each use with whether `dvh` or `svh` is appropriate, and note the fallback pattern (declare `100vh` then `100dvh` on the next line, so older browsers keep the old value).
evidence: the viewport meta tag as written with file:line and the verdict, `user-scalable`/`maximum-scale` flagged for accessibility if present, and whether `viewport-fit=cover` is needed and present; the `theme-color` tags with any dark-mode variant; whether the app is installable and on what evidence, then the manifest path, whether it is linked and served, and each required key present or missing with the icon sizes found; the `apple-touch-icon` link and size, with the favicon cited to SEO-002; the fixed-position elements and whether each uses `env(safe-area-inset-*)`; every `100vh` hit with file:line and a `dvh` verdict; rows marked `n/a` with the reason.
fix_hint: Add `<meta name="viewport" content="width=device-width, initial-scale=1">` (plus `viewport-fit=cover` if anything draws to the edges) and remove `user-scalable=no`, add a `theme-color` for each colour scheme, fix or add the manifest with real names and 192/512/maskable icons and a `start_url` the app serves, add a 180x180 `apple-touch-icon`, pad bottom-fixed elements with `env(safe-area-inset-bottom)`, and replace full-height `100vh` rules with `100dvh` after a `100vh` fallback line.

### HYG-014 Internationalization sanity: dates, currency, and numbers formatted per locale; RTL if supported
severity: low
tier: static
fix: easy
why: `03/04/2026` is the third of April to most of the world and the fourth of March to the United States, and there is no way for a reader to tell which you meant. A price rendered as `"$" + amount` is wrong for every currency you later add and, more immediately, is wrong the first time an amount arrives in cents or as a float and prints `$19.9` or `$1990`. These are cheap to get right at the start and expensive to retrofit, because by then the concatenation is in forty components.
verify:
  static: Find where dates, times, currencies, and numbers are rendered and check they go through a formatter rather than string work. The pass shapes: `Intl.DateTimeFormat`, `Intl.NumberFormat` with `style: "currency"`, `Intl.RelativeTimeFormat`, `toLocaleDateString`/`toLocaleString` with an explicit locale, or the framework's or library's i18n formatter (`next-intl`, `react-intl`, `i18next` with a formatter, `date-fns` with a locale, Rails' `l`/`number_to_currency`, Django's `date` template filter with `USE_L10N`). The fail shapes to grep for: a hardcoded currency symbol adjacent to a value (`grep -rnE "[\"']\\\$[\"']? *\+|\\\$\\\$\{" . <standard excludes>` — the first alternative catches a `"$"` string concatenated onto a value, the second catches a literal `$` immediately before a template interpolation; do not simplify the second to `\$\{`, which matches every interpolation in the codebase), a manual thousands separator built with `replace(/\B(?=(\d{3})+(?!\d))/g, ",")` or similar, `toFixed(2)` used as the money formatter, a manual date format built from `getMonth()`/`getDate()` and slashes, and a hardcoded month or weekday name array. Note that `getMonth()` is zero-based, so a hand-rolled formatter is also the place off-by-one date bugs live. Check the currency itself is not assumed: if the product charges in more than one currency, the currency code must travel with the amount rather than being inferred at render time, and the payments domain will care about that too. **Timezones**: check that a timestamp rendered to a user is converted to their timezone rather than printed in the server's — DAT-023 owns whether timestamps are *stored* in UTC, so cite it and confine this block to display: whether the rendered value states or respects a timezone, whether a date-only value (a birthday, a due date) is being run through a timezone conversion that can shift it a day, and whether any "today" comparison uses the server's day boundary for a user in another hemisphere. **RTL**: determine whether an RTL locale is supported at all — check the configured locale list for `ar`, `he`, `fa`, `ur`. If one is, check the `dir` attribute is set on `<html>` from the active locale rather than hardcoded to `ltr`, and that the layout uses logical CSS properties (`margin-inline-start`, `padding-inline-end`, `inset-inline-start`, `text-align: start`) rather than `left`/`right`, since a `margin-left` does not flip. If no RTL locale is supported, mark the row `n/a — no RTL locale configured` and say which locales are. **Single-locale products**: the `Intl` and hardcoded-separator rows still apply and are still worth fixing — they are what makes adding a second locale a configuration change rather than a rewrite — so report them as findings with a note that the impact today is limited to correctness (the cents and off-by-one bugs), not to translation.
evidence: per rendering site — file:line, what is rendered, and whether it uses a formatter or string concatenation, with the concatenation cases quoted; the currency handling, including whether a currency code travels with each amount; the timezone display verdicts with date-only values called out and storage cited to DAT-023; the configured locale list; the RTL verdict with the `dir` attribute's source and any physical CSS properties found, or the `n/a` with the locales named; a statement of which rows are limited by the product being single-locale.
fix_hint: Route every date, number, and currency through `Intl` or the framework's i18n formatter with an explicit locale, keep money as integer minor units with a currency code beside it and format at the edge, render timestamps in the viewer's timezone and leave date-only values unconverted, and if an RTL locale is supported set `dir` from the active locale and replace `left`/`right` CSS with logical properties.

### HYG-015 Production build succeeds from a clean clone with documented steps
severity: high
tier: local
fix: guided
why: The build works on the machine where it was written, which proves nothing — that machine has a `.env` nobody committed, a globally installed CLI, a `node_modules` populated over six months, and a system library installed for something else. The clean clone is the only way to find out what the deploy pipeline and the next engineer will actually get. Every undocumented step this check finds is a step someone will be missing at 2am, and a build that fails from a clean clone is a build that will fail in CI the first time the cache is cold.
verify:
  static: Read the documented steps before running any of them, so you have something to check reality against. From the README and the manifest's scripts, write out the exact sequence a new engineer is told to follow: prerequisites and their versions, install, environment setup, any code generation or migration, and the build. Beside it, write the sequence the repo implies: the declared runtime version (`engines`, `.nvmrc`, `.python-version`, `.tool-versions`, the `ruby` line in the Gemfile), the lockfile present and which package manager it belongs to (a `pnpm-lock.yaml` beside a README that says `npm install` is a fail before you run anything), any `postinstall` or `prepare` script that runs implicitly, and every environment variable the build reads at build time rather than at runtime (stack ref: "env vars"; REL-008 owns whether they are set for production). Note any step that exists only in CI config and not in the README — a workflow that runs a generator before the build is a documented step in the wrong document. HYG-007 reports the same README gap from the other direction, so the two findings should name the same missing steps.
  local: Run this inside a clone and never in the project directory — do not install, build, or generate anything in the project itself, because that mutates the tree the rest of the audit is reading. Clone the committed state: `git clone <project_dir> .pre-launch/hygiene/clone`. That gives you the working tree's *commits*, which is the point: whatever is untracked or uncommitted stays behind, and if the build then needs it, that is the finding. Before building, capture what was left behind — `git -C <project_dir> status --porcelain > .pre-launch/hygiene/repo-status.txt` — and read it: an uncommitted or untracked file that the build requires (a generated schema, a config, a certificate, a locale file, an asset) is a fail in its own right, separate from whether the build succeeds, because CI does not have it either. Two entries in that output are not findings and should be named as such rather than reported: `.pre-launch/` itself, which is this audit's own artifact directory, and any file this audit created. An untracked `.env` is likewise expected and is not that finding — environment variables are supposed to come from the environment — but note which variables the build needs and where their values would come from (stack ref: "env vars"; REL-008 owns whether they are set for production), and if the build cannot run at all without secrets you do not have, say exactly that rather than reporting a failure you caused. Then follow the *documented* steps, from the README and the manifest's scripts, in the order they are written, in the clone: install (`npm ci`, `pnpm install --frozen-lockfile`, `yarn install --immutable`, `pip install -r requirements.txt`, `bundle install`, `composer install` — use the frozen or locked form, since the whole point is reproducing the lockfile's resolution rather than a fresh one), then the build command from stack ref "build". Capture both logs, and write them **outside** the clone — the clone is deleted at the end of this block, so a redirect that resolves inside it destroys the only evidence of what happened. Stay in the project directory and point the package manager at the clone rather than `cd`-ing into it: `npm --prefix .pre-launch/hygiene/clone ci > .pre-launch/hygiene/install.log 2>&1` and `npm --prefix .pre-launch/hygiene/clone run build > .pre-launch/hygiene/build.log 2>&1`. For a stack with no `--prefix` equivalent, run the command in a subshell and give the redirect an absolute target so it lands outside the clone: `(cd .pre-launch/hygiene/clone && bundle install) > "$PWD/.pre-launch/hygiene/install.log" 2>&1`, and the same shape for `pip install -r requirements.txt`, `composer install`, and the build. Record three things as you go. **Every undocumented step**: anything you had to do that the README did not say — set a variable, install a system dependency, run a code generator or a migration, use a specific runtime version, run a step in a different order. Each is a finding with the step written out, and each should end up in the README (HYG-007 reports the same gap statically, so the two should agree). **Every error and every warning that matters**: a failed build is the headline; a build that succeeds with peer-dependency errors, deprecation warnings on a package that no longer builds on the current runtime, or a lockfile that `npm ci` reports as out of sync with `package.json` is a build that will fail on the next clean run, so report those too. **The runtime versions used**: the Node, Python, Ruby, or JVM version you built with, beside whatever the repo declares (`engines`, `.nvmrc`, `.python-version`, `Gemfile`'s `ruby`, `.tool-versions`) — a mismatch here is the single most common cause of "works locally, fails in CI". Also note the wall-clock time of a cold install and build, since a fifteen-minute cold build is a deploy-and-rollback constraint worth knowing before you need to roll back. Then delete the clone: `rm -rf .pre-launch/hygiene/clone`. Do this even if the build failed — the logs are saved, and leaving a second copy of the source tree on disk is a footgun, particularly if the build wrote any secret into it.
evidence: the exact commands run in the clone, in order, with pass/fail and duration for each; the tail of `install.log` and `build.log` for any failure, quoted; the undocumented steps as an ordered list, each phrased as the README line it should become; peer-dependency, lockfile-sync, and deprecation warnings listed even where the build succeeded; the runtime versions used beside the versions the repo declares, with a mismatch verdict; `git status --porcelain` output with each uncommitted or untracked file classified as build-required or not; confirmation that the clone was deleted; if the build could not run for want of secrets, exactly which and where they come from.
fix_hint: Fix the build until it succeeds from a clean clone with only the documented steps, then add every undocumented step to the README in order — including the runtime version, which belongs in `engines` or a version file so it is enforced rather than remembered. Commit anything the build needs that was untracked, pin the runtime in CI to the same version, and resolve the lockfile-sync and peer-dependency warnings before they become the next cold-cache failure.

### HYG-016 Email templates: absolute prod links, rendered across major clients, from-name set, reply-to monitored
severity: high
tier: local
fix: easy
why: Transactional email is the one part of the product that runs entirely outside the browser you tested in, and the failures are total rather than cosmetic: a relative link in a password-reset email goes nowhere at all, a `from` address of `noreply@` with no name reads as spam and is often filed as such, and a reply-to nobody monitors means every customer who hits reply — which is what people do — is talking to a void. And these emails are the highest-stakes messages you send: the verification and reset ones are the ones a user cannot proceed without.
verify:
  static: Find the mail machinery (stack ref: "routes and handlers", "background jobs") — the mail client and its config, and every template. If there is no mail sending at all, mark this block `n/a — product sends no email`, and name the greps for a mail provider package, an SMTP config, and a template directory that returned nothing, so the `n/a` is distinguishable from not having looked. Otherwise enumerate the templates and check four things across them. **Links are absolute and on the production host**: a relative `href` in an email is dead on arrival, since there is no base document. HYG-002 owns the repo-wide hardcoded-host sweep, so read its results for the template directory rather than re-grepping, and check here that the base URL each template uses comes from config and that the configured production value is the production domain — a link built from a variable that is localhost in this environment is fine, a hardcoded one is not, which is the same judgement SEO-006 makes for canonicals. **From-name and reply-to**: the `from` should carry a display name (`Acme Support <support@acme.com>`, not a bare address), the sending address should be on a verified domain (HYG-001's row), and `reply_to` should be set to an address a human reads — REL-028 owns whether the support path reaches a human, so cite it and record here only which address is configured and whether it differs from a `noreply@` sender. A `noreply@` sender with no reply-to is the finding. **Required content**: an unsubscribe link on anything that is not strictly transactional, an honest subject, and a physical address where required — all three are COMP-016's, and FLOW-014 owns whether the unsubscribe link actually works, so cite both and do not duplicate the judgement; record only which templates lack an unsubscribe link so the cross-reference is actionable. **Plain-text alternative**: check a text part is generated or authored, since an HTML-only message scores worse with spam filters and is unreadable in a text-only client.
  local: Render each template with sample data through the project's own preview mechanism rather than by reading the source, because the source does not show you what the data does to it: React Email's `email dev` server, Rails' `/rails/mailers` preview routes, Django's template rendering or a preview view, Laravel's mailable preview route, or whatever the project already has (stack ref: "known traps"). This is the one local probe in this file that may legitimately need the dev server rather than the production build, and that is worth stating rather than treating the header rule as absolute: Rails mailer previews are mounted only when `config.action_mailer.show_previews` is on, which is the development default and off in production, and React Email's `email dev` is itself a dev server. So if the preview route exists only in development, use it there and record `rendered via dev preview route` in evidence — the template body is identical either way, and the only thing you lose is the production base URL and asset host, which you read from config in the static pass anyway. To avoid the dev server entirely, render the template directly against the production build's configuration instead: `rails runner` or a one-off script that instantiates the mailer or template with a sample context and prints the HTML, with the production environment loaded so the base URL and asset host are the production values. If a preview route exists, fetch each template from it and save the output: `curl -s "<local.url>/rails/mailers/<mailer>/<template>" -o .pre-launch/hygiene/email-<name>.html`. If no preview mechanism exists, render the template directly with the project's own template engine and a sample context, and say that you did — do not send a real email to test, and do not add a preview route to the project. Then read each saved render for the things only a render shows: an unsubstituted variable left in the output (`{{name}}`, `%{name}`, `undefined`, `null`, `[object Object]` — grep every saved file for these, since a template that renders `Hi undefined,` passes every static check), a link whose `href` is empty or relative (extract every `href` from the saved files and check each is absolute and on the configured production host), an image with no `src` or one pointing at a host that will not be reachable from a mail client (and note whether images are attached inline or hot-linked, since most clients block remote images by default — the email must be readable with images off, so check there is alt text and that no critical content is inside an image), and whether the CSS is inlined, since Gmail strips `<style>` blocks and a template that relies on them renders as unstyled text. Check the subject line renders with its variables too, and check its length — a subject truncated at around 40 characters on a phone should still carry the point. The cross-client render — Gmail, Outlook desktop, Apple Mail, and their mobile apps, where Outlook's Word rendering engine breaks flexbox, modern CSS, and anything but table layout — cannot be verified from here and is an attest item: report it as such, name the clients, and say what would be needed (a real send to a test address in each, or a rendering service if the project already has one). Do not claim client compatibility from a browser render.
evidence: the template inventory with paths; per template — the rendered output's path under `.pre-launch/hygiene/`, unsubstituted-variable hits quoted, every `href` with an absolute/relative and host verdict, image `src` verdicts with whether the message reads with images blocked, and whether CSS is inlined; the `from` display name and address, the sending domain's verification status cited to HYG-001, the `reply_to` address cited to REL-028, and whether a plain-text part exists; the unsubscribe and content requirements cited to COMP-016 and FLOW-014 with the templates lacking a link named; the cross-client render declared unverified with the clients listed; if `n/a`, the greps that returned nothing.
