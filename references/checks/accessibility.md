# Accessibility checks (A11Y)

Read `agents/domain-auditor.md` for procedure. Blocks below are checks; consult stack references for locations. Tools: `npx @axe-core/cli <url> --save .pre-launch/a11y/axe-<page>.json` is this domain's main instrument (A11Y-001, 003, 004, 005, 007, 008, 011, 012, 017); `npx lighthouse` with `--only-categories=accessibility` is the fallback when axe-cli will not install or run (same coverage, different report shape); `jq` for reading either report; `curl` plus `grep` and `python3` with only the standard library for the markup-level checks that do not need a browser (A11Y-006, 007, 010, 011, 013, 014, 016, 017); a browser driver the project *already* has for the handful of checks that need a live DOM.

**The standard is WCAG 2.2 Level AA.** Every block below names the success criteria it is testing, because "it fails accessibility" is not a finding anyone can act on and because half the arguments in this domain come from confusing an AA requirement with a AAA one or with a platform guideline. Two that recur: target size is **24x24 CSS px** under 2.5.8 Target Size (Minimum), which is AA in WCAG 2.2 — the 44px figure is 2.5.5 Target Size (Enhanced), which is AAA, and the Apple HIG 44pt / Material 48dp numbers are platform guidance, not WCAG at all (A11Y-012). And honouring `prefers-reduced-motion` is not itself an AA criterion — it is the mechanism by which you satisfy 2.3.3 Animation from Interactions, which is AAA, and it helps with 2.2.2 Pause, Stop, Hide, which is A (A11Y-010). Say which is which in evidence so nobody blocks a launch on a AAA nicety or waves through an AA failure.

**An automated scan finds roughly a third of the problems, and a clean scan is not a pass.** This is the single most important thing to know before running anything in this file. axe and Lighthouse detect what is machine-decidable: a missing `alt`, a missing label, a computable contrast ratio, an invalid ARIA attribute. They cannot tell you whether alt text is *meaningful*, whether focus order is *logical*, whether colour is the *only* carrier of a status, whether a modal returns focus to the thing that opened it, or whether the primary flow is usable at all. Those are A11Y-002, 006, 009, 015, and 018, and they are the checks most likely to matter to a real user. So a block's `local` entry running axe never replaces its `static` entry — run both, and when they disagree the static reading usually explains why. Never report "axe found zero violations" as this domain's verdict.

**The four pages every scan covers.** Unless a block says otherwise, run the scan against four pages: the home page, the sign-up page, the primary authenticated page (the dashboard or whatever the user lands on after login), and the most form-heavy page in the app (checkout, settings, profile, the longest create form). These four cover the four distinct shapes of markup a typical app has — marketing, an unauthenticated form, an app shell with navigation, and a dense form — and scanning ten marketing pages instead teaches you nothing new after the second. Find their paths from config and from the route list (stack ref: "routes and handlers"); record the four URLs in `.pre-launch/a11y/pages.txt` in A11Y-001 and read that file in every later block rather than picking a different four. Name the saved reports after the page — `axe-home.json`, `axe-signup.json`, `axe-app.json`, `axe-form.json` — and use the same four names throughout.

**Reuse the SEO sample for the cheap markup greps.** Several blocks here (A11Y-007, 010, 011, 013, 016, 017) only need raw HTML or source, not a browser, and they benefit from breadth rather than depth. If SEO-001 has already run it wrote a ten-page sample to `.pre-launch/seo/sample.txt` along with the fetched pages at `.pre-launch/seo/home.html` and `.pre-launch/seo/page-<n>.html`; read those rather than re-fetching, and say in evidence that the sample came from SEO. If SEO has not run, build the sample the same way it does — from the home page's links, resolve each href against the base URL, drop `mailto:`, `tel:`, `javascript:`, and bare `#` fragments, drop off-host links, strip fragments and query strings, deduplicate, and take up to ten preferring one of each route shape — write the paths to `.pre-launch/a11y/sample.txt`, and fetch each to `.pre-launch/a11y/page-<n>.html` with `curl -s`. Either way, grep the saved files; do not re-request the same page in six blocks.

**Every artifact this domain writes goes under `.pre-launch/a11y/` and nowhere else.** A bare relative filename lands in the project root, and on a static site the project root is served content, so a stray `axe.json` can ship in the next deploy. `/tmp` is no better: it survives the audit, collides between concurrent runs, and puts the evidence somewhere the report cannot cite. Create the directory once with `mkdir -p .pre-launch/a11y` before the first tool run. The names used below are `pages.txt`, `sample.txt`, `axe-<page>.json`, `lh-<page>.json`, `page-<n>.html`, `tab-order.txt`, and `greyscale-<page>.png`.

**Measure a production build, never the dev server.** This is the same rule the performance and SEO domains state, and it changes verdicts here for a specific reason: dev builds inject overlay markup that is not in production (error overlays, route announcers, hot-reload iframes, devtools portals), and axe scans whatever is in the DOM. A React error overlay with a low-contrast toolbar produces contrast and landmark violations that will never ship, and chasing them wastes the domain's budget. In the other direction, some accessibility bugs only appear in production, where CSS is minified and purged — a Tailwind class used only in a rarely-rendered branch can be purged out, taking a focus ring with it. So before any local-tier work here, build and start the app in production mode on a port you record — `npm run build && PORT=<port> npm start` with `NODE_ENV=production` for a typical Node stack, and the equivalent for this one (stack ref: "build" for the build and production start commands, "dev server" for the port convention) — and point every scan at that URL, noting it in evidence alongside `local.url`. If the production build cannot be run, mark every local measurement in this domain `dev-server only` in `notes`, and discount any violation whose selector points into a dev overlay rather than reporting it.

**Authenticated pages need the test account's session, and getting it wrong silently scans the login page four times.** Two of the four pages are behind auth. Before scanning them, log in as the test account from config and capture the session cookie — its name is stack-specific (stack ref: "runtime probe hints" names the cookie for this stack; "auth" says how the session is issued), and it is typically something like `next-auth.session-token`, `__Secure-authjs.session-token`, `sb-<ref>-auth-token`, `_myapp_session`, `sessionid`, or `connect.sid`. Both tools can carry it, but the flag names differ by version and neither is stable across releases, so **run `npx @axe-core/cli --help` and `npx lighthouse --help` once and read the actual options before writing the command** rather than copying one from memory; look for a cookie, header, or Chrome-flag passthrough option. Lighthouse's `--extra-headers` is the usual route there. Then verify the session actually took: the saved report records the page title and the scanned URL, so check that the authenticated scan's title is the dashboard and not "Sign in", and check the violation counts differ from the sign-up page's. Two identical reports means you scanned the login page twice. If you cannot authenticate the scanner at all, do not fake it — scan the two public pages, fall back to the `static` entry for the authenticated ones, and say exactly which pages were covered and which were not in evidence.

**Missing tools.** If neither axe-cli nor Lighthouse is installed and the user declined installing them (config `tools.declined`), do not stop and do not mark the whole domain `error`. Run each block's `static` entry, decide from that evidence, and set `verified_by: static-fallback` with a note naming the tool you did not have. A static-fallback pass in this domain is meaningfully weaker than a measured one — say so in `notes`. The same applies to the blocks that want a live DOM: use a browser driver **only if the project already depends on one** (check `package.json` devDependencies or the Python equivalent for `playwright`, `puppeteer`, `@playwright/test`, `cypress`, `selenium`; stack ref: "known traps"). Never install a driver to run an audit.

**Cross-references, so the same work is not done or reported twice.** SEO-010 owns heading hierarchy (a single H1 and no skipped levels) — that is a 1.3.1 finding as much as an SEO one, so cite it from A11Y-008 rather than re-extracting outlines. SEO-013 hands this domain its `images_without_alt` count for the home page; A11Y-006 owns the judgement about it. A11Y-007 (`lang`) is cited by SEO-011 for hreflang consistency. HYG-011 (password managers) overlaps A11Y-016 on `autocomplete`: A11Y-016 owns whether the tokens are correct and standards-conformant, HYG-011 owns whether a manager can actually fill the form; whichever runs second cites the first.

**Never modify project files.** Everything in this domain is a read, a request, or a scan. Do not add an `alt`, a label, a `lang` attribute, or a focus ring while auditing, however small the diff looks — findings and `fix_hint` text are the output, and the fix workflow applies them later with the user watching.

### A11Y-001 axe / Lighthouse a11y scan: zero critical or serious
severity: high
tier: local
fix: guided
why: This is the floor, not the ceiling. Everything an automated scanner flags as critical or serious is a defect that is machine-provable, cheap to fix, and impossible to argue about — a control with no accessible name, an invalid ARIA reference, a contrast ratio you can compute. Shipping with those outstanding means the manual checks in the rest of this file are being run on top of a broken foundation. It is also the block that produces the reports every other block in this domain reads, so run it first even when you expect it to pass.
verify:
  static: Before scanning, find out what the project already knows about its own accessibility (stack ref: "build", "known traps"). Look for `eslint-plugin-jsx-a11y` (and whether the config runs it as `error`, as `warn`, or via `next/core-web-vitals` which enables only a subset), `eslint-plugin-vuejs-accessibility`, `svelte-check`'s a11y warnings, `axe-core` in tests (`jest-axe`, `vitest-axe`, `cypress-axe`, `@axe-core/playwright`), `@storybook/addon-a11y`, or a Lighthouse CI budget. Then grep the source for suppressions — `eslint-disable jsx-a11y`, `svelte-ignore a11y-`, `<!-- eslint-disable vuejs-accessibility -->` — and read each one, because a suppression comment is a developer telling you where a known violation lives. Also check whether the a11y lint runs in CI or only locally; a rule set that is `error` in `.eslintrc` but whose lint step is not in the pipeline is decoration.
  local: `mkdir -p .pre-launch/a11y`, write the four page URLs to `.pre-launch/a11y/pages.txt` per the header rule, then scan each: `npx @axe-core/cli <url> --save .pre-launch/a11y/axe-home.json` (run `npx @axe-core/cli --help` first and confirm the flag names in the installed version — `--save`, `--include`, `--exclude`, `--load-delay`, `--tags`, and the cookie or Chrome-flag passthrough have all moved between releases). Confirm the report shape before parsing it, because the CLI writes an array with one entry per URL scanned rather than a bare object: `jq 'type, (.[0]|keys)' .pre-launch/a11y/axe-home.json`. Then pull the failures: `jq -r '.[0].violations[] | select(.impact=="critical" or .impact=="serious") | "\(.impact) \(.id) nodes=\(.nodes|length) \(.help)"' .pre-launch/a11y/axe-home.json`. Zero rows on all four pages is the pass. Read `.[0].incomplete` as well — those are axe's "needs review" items, things it could not decide (contrast over a background image, an element it could not compute), and they are not passes; list them for manual follow-up in the block that owns each one. If axe-cli will not run, use Lighthouse: `npx lighthouse <url> --only-categories=accessibility --output=json --output-path=.pre-launch/a11y/lh-home.json --quiet --chrome-flags="--headless"`, then extract with `jq -r '.audits | to_entries[] | select(.value.score != null and .value.score < 1) | "\(.key) score=\(.value.score) items=\(.value.details.items|length? // 0)"' .pre-launch/a11y/lh-home.json`. **Never `cat` either report** — an axe run on a real page is hundreds of kilobytes of JSON with full DOM snippets per node, and printing it will blow the context for the rest of the domain. Lighthouse does not label by impact, so map its failing audits to axe's severity yourself: `color-contrast`, `label`, `button-name`, `link-name`, `image-alt`, `html-has-lang`, `aria-required-attr`, and `aria-allowed-attr` failing are serious or worse. Report the per-page counts by impact, not one total, so a single catastrophic page is visible rather than averaged away.
evidence: one row per page — URL, scanned page title (proof the authenticated scan reached the right page), tool and version, and counts by impact (`critical=0 serious=3 moderate=7 minor=2`); every critical and serious violation as `rule-id — node count — one representative CSS selector`; the `incomplete` rule ids with counts and which block will follow each up; the lint configuration finding (`jsx-a11y at warn, not run in CI`) and the file:line of every a11y suppression comment.
fix_hint: Fix every critical and serious violation before launch, starting with whichever rule has the highest node count — those are almost always one shared component rendered many times, so one fix clears dozens of nodes. Then turn the a11y lint rules from `warn` to `error` and add the lint step to CI so the next regression is caught at the pull request rather than at the next audit, and delete the suppression comments as you fix what they were hiding.

### A11Y-002 Full keyboard reachability; logical focus order; no traps; skip link
severity: high
tier: local
fix: guided
why: Keyboard access is the substrate every other assistive technology sits on — screen readers, switch devices, voice control, and anyone with a tremor or an injured wrist all drive the page through the same focus model. WCAG 2.1.1 Keyboard requires every function be reachable; 2.1.2 No Keyboard Trap requires you can always get back out; 2.4.3 Focus Order requires the sequence preserve meaning; 2.4.1 Bypass Blocks requires a way past the repeated navigation. A trap is the worst of these: a user who tabs into a widget they cannot tab out of has to close the tab and lose their session, and it is invisible to every automated scanner.
verify:
  static: Five patterns to grep for (stack ref: "routes and handlers" for where components live). First, positive tabindex: `grep -rnE "tabindex=['\"]?[1-9]|tabIndex=\{?[1-9]" <source dirs>` — any value above 0 pulls the element to the front of the tab sequence globally and desynchronises the whole page's order from its visual order; `0` and `-1` are both legitimate and are not this finding. Use a double-quoted shell string with a literal `['\"]` class as written, not `\x27` inside a single-quoted one: portable `grep` does not expand `\x27`, so that form silently matches only the double-quoted attributes and reports a clean result on a codebase full of single-quoted ones. Second, unreachable controls: a `<div>` or `<span>` carrying `onClick`/`@click`/`v-on:click` with no `role` and no `tabIndex={0}` never receives focus at all, so a keyboard user cannot reach it — search for click handlers and check the element they sit on, and treat `<a>` with no `href` the same way, since it is not focusable either. Third, and separately, inoperable controls: a `<div role="button" tabIndex={0} onClick={...}>` with no `onKeyDown` (or `@keydown`, or a framework equivalent) handling Enter and Space is reachable but cannot be activated — focus lands on it and pressing Enter does nothing. This is the most common half-fix in the wild, because adding `role` and `tabIndex` looks like the whole job and silences the linter, and it fails 2.1.1 exactly as hard as the first case. Report both, distinguished by which half is missing, since the fixes differ. Fourth, the skip link: search the root layout or base template for a first-in-DOM link to `#main`, `#content`, or `#main-content`, and confirm the target element actually has that id and is focusable (a skip link pointing at a non-existent or non-focusable id does nothing). A visually hidden skip link is correct and normal — check it becomes visible on focus rather than staying hidden, since `display: none` or `visibility: hidden` removes it from the tab order altogether. Fifth, trap sources: custom key handlers that call `preventDefault()` on Tab, `focus()` calls in a loop or an effect that runs on every render, embedded third-party iframes (video players, chat widgets, payment fields, maps) which are the most common real-world trap, and any `keydown` listener on `document` that swallows Tab.
  local: axe's `bypass` rule covers the skip-link half only; read it from the saved reports (`jq -r '.[0].violations[] | select(.id=="bypass")' .pre-launch/a11y/axe-home.json`). The order-and-trap half needs a live DOM, so use a driver **only if the project already has one** (see the header rule): navigate to the primary page, then drive Tab repeatedly and record what receives focus — with Playwright, loop `await page.keyboard.press('Tab')` and read `document.activeElement` each time, capturing tag name, accessible text, and `getBoundingClientRect()`, and write the sequence to `.pre-launch/a11y/tab-order.txt`. Judge three things from that list. The sequence should broadly follow reading order — top to bottom, left to right for a left-to-right language — so flag any point where the y-coordinate jumps backwards by more than a row. Every interactive thing you can see on the page should appear in it; diff the list against the interactive elements present in the DOM (`a[href], button, input, select, textarea, [tabindex]:not([tabindex="-1"]), [contenteditable]`) and report anything visible that never gets focus. And the sequence must eventually leave the page and reach the browser chrome; if pressing Tab 100 times cycles inside one widget forever, that is the trap, and name the widget. If no driver is available, do not install one: report from the static entry, set `verified_by: static-fallback`, and say plainly that focus order and traps were not exercised.
evidence: the tab sequence as an ordered list of `n. <tag> "<accessible name>" @(x,y)` for the primary page, or `not exercised — no driver` with the reason; every interactive element present in the DOM but absent from the sequence, with its selector; the file:line of each positive `tabindex`, of each unreachable click-handling element (no `role`, no `tabIndex`) and of each inoperable one (`role` and `tabIndex` present, no Enter/Space key handler) kept as two separate lists since the fixes differ, and of each Tab-swallowing key handler; the skip link's markup and its target id, or `absent`; the axe `bypass` result.
fix_hint: Replace click-handling `div`s with real `<button>` and `<a href>` elements — that fixes reachability *and* activation in one edit, since a native button responds to Enter and Space for free, and it deletes the `role`, `tabIndex`, and key-handler code rather than adding more of it. That is the fix for both the unreachable and the inoperable case; only where an element genuinely cannot be a button does the ARIA route apply, and then it needs all three of `role`, `tabIndex={0}`, and an `onKeyDown` handling Enter and Space, not two of them. Remove every positive `tabindex` and let DOM order carry the sequence, reordering the markup where the visual order differs. Add a skip link as the first focusable element in the layout, pointing at a `<main id="main-content" tabindex="-1">`. For the traps, release Tab in the widget's key handler and give any third-party iframe a documented way out.

### A11Y-003 Visible focus indicators
severity: medium
tier: local
fix: easy
why: A keyboard user who cannot see where focus is has a page they can technically operate and practically cannot — they are pressing Enter and guessing. WCAG 2.4.7 Focus Visible (AA) requires the indicator to exist; 1.4.11 Non-text Contrast (AA) requires it to reach 3:1 against what surrounds it, so a mid-grey ring on a mid-grey button fails even though it is present; and 2.4.11 Focus Not Obscured (Minimum), new in WCAG 2.2 at AA, requires the focused element not be entirely hidden behind other content — which is exactly what a sticky header does to the element you just tabbed to at the top of a scrolled page. The cause is almost always the same one line: someone removed the browser's default outline because it looked wrong on one button and never replaced it anywhere.
verify:
  static: Grep the stylesheets, CSS-in-JS, and component classes for `outline: none`, `outline: 0`, `outline-none`, and `outline-style: none` (stack ref: "build" for where styles live; check the global reset or `preflight` layer first, since a blanket `*:focus { outline: none }` there disables the indicator for the whole app in one line). For each hit, look for the replacement in the same rule or the adjacent `:focus-visible` block — a `box-shadow` ring, a `border-color` change, a background change. Tailwind's `focus:outline-none` is idiomatic and fine *only* when paired with `focus-visible:ring-2` or equivalent on the same element; `focus:outline-none` alone is the finding, and it is worth grepping for the pair explicitly. Note the distinction between `:focus` and `:focus-visible`: styling `:focus-visible` only is correct modern practice (it suppresses the ring on mouse clicks while keeping it for keyboard), but a rule that removes `:focus` styling without adding any `:focus-visible` styling removes it for everybody. Also check the indicator's colour against both the element and the page background for the 3:1 requirement, using the ratio snippet in A11Y-004. Finally, for 2.4.11, list the `position: sticky` and `position: fixed` elements in the layout — headers, footers, cookie banners, chat launchers — since those are what obscure a focused element.
  local: Read the saved axe reports for `focus-order-semantics` and any focus-related rule the installed version ships, but do not rely on axe here — visible focus is largely outside what it can decide. If a driver is available, measure it directly: for each interactive element on the primary page, capture `getComputedStyle(el)` for `outline-width`, `outline-style`, `outline-color`, `box-shadow`, `border-color`, and `background-color` before and after calling `el.focus()`, and flag every element where none of those changed. That comparison is the whole check and it is objective. For 2.4.11, scroll the page down, focus an element near the top of the viewport, and compare its `getBoundingClientRect()` against the bounding boxes of the sticky and fixed elements found statically; full occlusion is the fail, partial is a note. Without a driver, take the static reading and set `verified_by: static-fallback`.
evidence: the file:line of every `outline: none` or `outline-none` with its replacement or `no replacement found`, and whether it sits in a global reset or on one component; the before/after computed-style table for the sampled interactive elements, or the reason it was not run; the indicator's contrast ratio against the adjacent colours; the list of sticky/fixed elements and any element they fully obscure when focused.
fix_hint: Delete the blanket outline reset and let the browser default stand where nothing better exists — that is a deletion, and it fixes every element at once. Where a custom ring is wanted, style `:focus-visible` (not `:focus`) once in the global stylesheet with at least a 2px indicator at 3:1 contrast against both the component and the page background, so every control inherits it. For the sticky header, add `scroll-margin-top` equal to its height on focusable elements so the browser scrolls focus clear of it.

### A11Y-004 Contrast 4.5:1 text, 3:1 UI components
severity: medium
tier: local
fix: easy
why: Low contrast is the most common accessibility failure on the web and the one that affects the most people — not only users with low vision, but everyone reading on a phone in sunlight. WCAG 1.4.3 Contrast (Minimum) requires 4.5:1 for body text and 3:1 for large text, where "large" means at least 24px, or 18.66px if bold. WCAG 1.4.11 Non-text Contrast requires 3:1 for user interface components and their states — input borders, toggle tracks, icon-only buttons, focus rings, chart series — and that half is the one everybody misses, because axe does not check it. The usual cause is a design system that adopted a grey ramp without testing it: `gray-400` (`#9ca3af`) on white is 2.54:1 and fails, `gray-500` (`#6b7280`) is 4.83:1 and passes, and the two look nearly identical in a mockup.
verify:
  static: Find the palette rather than auditing pixels (stack ref: "build" for the style config). Read `tailwind.config.*` theme colours, CSS custom properties in `:root` and any `[data-theme]` block, a design-token file, or the component library's theme object. List every text-on-background pair the app actually uses — body text, muted or secondary text, placeholder text, disabled text, link text, text on coloured buttons, text on the brand colour, text in badges and toasts — and compute each ratio: `python3 -c "import sys;f=lambda c:c/12.92 if c<=0.03928 else ((c+0.055)/1.055)**2.4;L=lambda h:0.2126*f(int(h[1:3],16)/255)+0.7152*f(int(h[3:5],16)/255)+0.0722*f(int(h[5:7],16)/255);x,y=L(sys.argv[1]),L(sys.argv[2]);print(round((max(x,y)+0.05)/(min(x,y)+0.05),2))" '#9ca3af' '#ffffff'`. Two exemptions to apply so you do not report non-findings: text in a disabled control is exempt from 1.4.3, and pure decoration is exempt — but a greyed-out control that is not actually disabled, and placeholder text that is carrying the field's only label, are both real failures. Then do the 1.4.11 pass separately, since nothing automated will: check input and select borders against the page background, unchecked checkbox and radio outlines, toggle-switch tracks in the off state, disabled-looking-but-enabled buttons, icon-only button glyphs, and chart or status colours against their background. If the app has a dark theme, run the whole list again for it — dark themes are usually added late and tested least.
  local: Read `color-contrast` from the saved axe reports: `jq -r '.[0].violations[] | select(.id=="color-contrast") | .nodes[] | "\(.target[0]) \(.failureSummary|split("\n")[1])"' .pre-launch/a11y/axe-home.json`, and do the same for all four pages. Then read the `incomplete` entries for the same rule — `jq -r '.[0].incomplete[] | select(.id=="color-contrast") | .nodes|length'` — because axe reports as "needs review" every case it could not compute: text over a background image, over a gradient, over a video, or where the background is set by a parent it could not resolve. Those are not passes, and hero sections put text over images constantly, so check each one by eye against the darkest and lightest part of what sits behind it. Remember axe's scope: it judges text only, at the computed colours of the page as loaded, so it will not see the 1.4.11 component failures, will not see hover or focus or error states, and will not see a theme you did not scan. Trigger the error state on the form-heavy page and re-scan if the driver allows it, since error text is very often red on white at around 3.5:1.
evidence: a table of every colour pair with its computed ratio, the required threshold, and pass/fail — including the dark theme as its own rows if one exists; the axe `color-contrast` violations as selector plus the observed and required ratios; the `color-contrast` incomplete count with each case judged by hand and the verdict stated; the 1.4.11 component list with ratios, marked clearly as the part no tool checked.
fix_hint: Fix the palette, not the pages — darken the one or two grey ramp steps that fail (typically the muted-text and placeholder tokens) in the theme config and every usage follows. Where a brand colour cannot move, change the text colour on it rather than the brand colour, or increase the text size past the large-text threshold where the design allows. Give input borders and unchecked control outlines a 3:1 token of their own instead of the lightest grey in the ramp.

### A11Y-005 Form labels; error messages associated; required fields marked
severity: high
tier: local
fix: easy
why: An unlabeled input is invisible to a screen reader, and an error message that is not tied to its field leaves the user knowing something is wrong but not what. This is WCAG 1.3.1 Info and Relationships and 4.1.2 Name Role Value for the label, 3.3.2 Labels or Instructions for the required marker, and 3.3.1 Error Identification for the error text — and it is the highest-value block in the domain, because a form nobody can complete is a sign-up nobody completes.
verify:
  static: Search form components for `<input`, `<select`, `<textarea` (stack ref: "routes and handlers" for where forms live). Each needs a `<label for>` matching its id, a wrapping `<label>`, or `aria-label`/`aria-labelledby`; a `placeholder` is not a label, because it disappears the moment the user types, and neither is adjacent text that is not programmatically associated. Error text should be referenced by `aria-describedby` on the field and the field should carry `aria-invalid="true"` when in error, so the message is announced when focus lands rather than only being visible. Required fields should use the `required` attribute or `aria-required="true"`, and the visual marker must not be the only indicator — a red asterisk with no legend and no attribute communicates nothing to a screen reader and nothing to a colour-blind user either (A11Y-018 owns that second half). Check the grouped controls too: a set of radios or checkboxes needs a `<fieldset>` with a `<legend>`, not a floating `<p>` above it, and a date split across three selects needs the same. tier: static
fix: easy

### A11Y-008 Landmarks present; ARIA used correctly, no redundant roles
severity: medium
tier: local
fix: easy
why: Landmarks are how a screen reader user skips the navigation on every page after the first — the rotor or landmarks list is their table of contents, and a page built entirely from `<div>`s presents as one undifferentiated block. That is WCAG 1.3.1 Info and Relationships. The ARIA half is the same criterion approached from the other side: incorrect ARIA is worse than no ARIA, because it actively lies to the assistive technology. The first rule of ARIA is not to use ARIA — a `<button>` already has the button role, `<nav>` already has navigation, and `role="button"` on a native button is at best noise and at worst a sign someone is fighting the platform.
verify:
  static: Read the root layout and the page shells (stack ref: "routes and handlers") for the landmark set: exactly one `<main>` per page, a `<header>` and `<footer>` that are children of `<body>` rather than nested inside another landmark (nesting demotes them from `banner` and `contentinfo` to generic), `<nav>` for navigation blocks with a distinguishing `aria-label` when there is more than one on a page (`aria-label="Primary"` and `aria-label="Footer"`), and `<aside>` or `role="search"` where they apply. Confirm all visible content sits inside some landmark, since anything outside is content a landmark-navigating user will never reach. Then grep the source for the ARIA misuse patterns and read each hit rather than counting them. Redundant roles: `role="main"` on `<main>`, `role="navigation"` on `<nav>`, `role="button"` on `<button>`, `role="banner"` on `<header>`, `role="list"` on `<ul>` — harmless individually, but a reliable signal that the codebase treats ARIA as decoration. Actively wrong usage: `aria-label` on a plain `<div>` or `<span>` with no role (labels on generic elements are ignored, so the text you thought you provided does not exist), `aria-hidden="true"` on an element that contains something focusable (the worst common ARIA bug — the control stays in the tab order but has no accessible name, so the user tabs to nothing), a `role` that requires companion attributes without them (`role="checkbox"` with no `aria-checked`, `role="tab"` with no `aria-selected`, `role="combobox"` with no `aria-expanded`), `aria-labelledby` or `aria-describedby` pointing at an id that does not exist anywhere in the DOM, and `aria-expanded` on an element that controls nothing. Heading structure is 1.3.1 too, but SEO-010 owns it — cite that check's outline rather than re-extracting one, and pull its skipped-level findings into this block's evidence as accessibility findings.
  local: Read the landmark and ARIA rules from the saved reports across all four pages: `jq -r '.[0].violations[] | select(.id|test("^aria-|^landmark-|^region$|^heading-order$")) | "\(.id) nodes=\(.nodes|length)"' .pre-launch/a11y/axe-app.json`. The ones to expect are `landmark-one-main` (zero or multiple `<main>`), `region` (content not inside a landmark, which axe classes as best-practice rather than a WCAG violation but which is the finding a real user feels), `aria-allowed-attr`, `aria-required-attr`, `aria-valid-attr-value` (this is what catches the dangling `aria-labelledby` reference), and `heading-order`. Run this on the authenticated page especially: app shells accumulate ARIA over time and are usually worse than the marketing pages. Then check the thing axe cannot — that the landmarks *mean* something: open the page and list the landmarks in DOM order with their labels, and confirm a stranger could navigate the page from that list alone.
evidence: the landmark inventory per page as an ordered list of `role — element — label` with anything missing named (`no main on /dashboard`); the percentage or count of content outside any landmark from the `region` rule; every ARIA misuse as file:line, the attribute, and why it is wrong (`aria-hidden on <div> containing <button>`); every dangling `aria-labelledby`/`aria-describedby` target id; the redundant-role hits as a count with two or three examples; SEO-010's heading-order findings cited, not repeated.
fix_hint: Wrap the page shell in real semantic elements — `<header>`, `<nav aria-label="Primary">`, `<main id="main-content">`, `<footer>` — which fixes the landmark set, the skip-link target from A11Y-002, and the `region` rule together. severity: medium
tier: local
fix: guided
why: A modal that does not move focus into itself leaves the screen reader user reading the page behind it while a dialog they cannot see blocks every click; a modal that does not trap focus lets Tab wander into the inert page behind the overlay; and a modal that does not return focus to the trigger on close dumps the user back at the top of the document, having lost their place. Those are WCAG 2.4.3 Focus Order and 4.1.2 Name Role Value, and the failure to release focus on Escape or on a close button is 2.1.2 No Keyboard Trap — the one hard failure in this block, since a user who cannot escape a dialog has to close the tab.
verify:
  static: First find out whether there is anything to check and what is rendering it (stack ref: "routes and handlers", "known traps"), because the answer usually decides the check. A headless dialog primitive — Radix `Dialog`, Headless UI `Dialog`, `react-aria`/`react-modal`, MUI `Dialog`, Vuetify, Ariakit, or a shadcn component wrapping Radix — implements focus trapping, initial focus, focus return, `aria-modal`, and Escape correctly out of the box, so the audit becomes checking that nobody turned it off: grep for `modal={false}`, `disableEnforceFocus`, `disableRestoreFocus`, `disableEscapeKeyDown`, `closeOnEscape={false}`, and `onOpenAutoFocus`/`onCloseAutoFocus` handlers calling `preventDefault()`. fix_hint: Replace hand-rolled modals with the dialog primitive the project already depends on, or with the native `<dialog>` opened via `showModal()` — that is a deletion of the trap, focus, and Escape code rather than a fix to it, and it gets the ARIA right for free. Where one must stay hand-rolled, store the trigger element on open and call `.focus()` on it in the close handler, add the Escape listener on the dialog rather than on `document`, and mark the background container `inert` while the dialog is open.

### A11Y-011 Usable at 200% zoom; no maximum-scale=1
severity: medium
tier: local
fix: easy
why: The title names the practical test; the criteria are two. WCAG 1.4.4 Resize Text (AA) requires text to scale to 200% without loss of content or functionality, and 1.4.10 Reflow (AA) requires content to work in a 320 CSS px viewport — which is what you get at 400% zoom on a 1280px screen — without two-dimensional scrolling. Failing them means a low-vision user gets a page with text running off the side, buttons pushed out of reach, or a fixed header eating the whole viewport. The viewport half is separate and worse: `user-scalable=no` or `maximum-scale=1` in the meta tag disables pinch-zoom on mobile entirely, taking away the primary accommodation an entire class of users relies on, and it is usually copied in from a decade-old boilerplate that nobody has re-read since.
verify:
  static: Grep for the viewport meta wherever the document head is composed (stack ref: "routes and handlers"): `grep -rn 'viewport' <source dirs>` and read every hit, including Next.js `viewport` exports and `themeColor`/`viewport` metadata objects, since those set the same tag through an API rather than as literal markup. The correct value is `width=device-width, initial-scale=1` and nothing more. Then look for the reflow hazards in the styles: fixed pixel widths on containers without a `max-width: 100%`, `height: 100vh` on a content container (which clips rather than scrolls when the text grows), `overflow: hidden` on `body` or a main wrapper, `white-space: nowrap` on anything that is not a short label, absolutely positioned layout (as opposed to absolutely positioned decoration), fixed-height buttons or cards with text inside, wide tables with no horizontal-scroll wrapper, and a sticky header with a fixed pixel height that will occupy most of a zoomed viewport. Also check whether font sizes are set in `px` on the root — that alone does not fail 1.4.4, since browser zoom scales `px` too, but it does break users who set a larger default font size rather than zooming.
  local: axe's `meta-viewport` rule catches the scaling half directly: `jq -r '.[0].violations[] | select(.id=="meta-viewport") | .nodes[].html' .pre-launch/a11y/axe-home.json`. Without a driver, narrow a real browser window if one is available, or fall back to the static reading and say so — the viewport-meta half is fully covered statically either way, so this check never comes back with nothing.
evidence: the viewport meta tag exactly as emitted, with its file:line in source, and the axe `meta-viewport` verdict; for each of the four pages at 320px width, `scrollWidth` versus `clientWidth` and the selector of the widest overflowing element; the reflow hazards found statically as file:line with the property responsible; whether the zoom test was run in a browser or fell back to static.
fix_hint: Set the viewport to exactly `width=device-width, initial-scale=1` and delete `user-scalable` and `maximum-scale` — that is a one-line deletion and it is the whole mobile-zoom fix. For reflow, replace fixed widths with `max-width` plus a percentage, swap `height: 100vh` for `min-height`, wrap wide tables in an `overflow-x: auto` container, and remove `overflow: hidden` from `body`.

### A11Y-012 Touch targets meet WCAG 2.2 (24px; 44px on mobile)
severity: low
tier: local
fix: easy
why: A target too small to hit reliably is a control that does not work for anyone with reduced dexterity, a tremor, or a phone in one hand on a train. The familiar 44pt and 48dp figures are the Apple Human Interface Guidelines and Material Design platform guidance for touch input, not WCAG conformance criteria at all.   static: Find the small interactive elements by their sizing classes rather than by measuring everything (stack ref: "routes and handlers"). Report the under-24 set as the AA finding and the 24-to-44 set separately as the platform-guideline note, and apply the spacing exemption to both before concluding.

fix_hint: Fix the shared button component rather than each call site: give icon-only buttons a minimum box with `min-height: 24px; min-width: 24px` (or the mobile-friendly 44px where the design allows) and grow the hit area with padding rather than the icon. tier: static
fix: guided
why: Captions are the accommodation with the widest audience of anything in this file — deaf and hard-of-hearing users need them, and so does everyone watching without sound, which on mobile is most people. The criteria stack up quickly: 1.2.1 Audio-only and Video-only (A) needs a transcript for an audio-only recording and a description for a silent video; 1.2.2 Captions (Prerecorded, A) needs captions on any prerecorded video with audio; 1.2.3 (A) needs an audio description or a full text alternative; 1.2.5 Audio Description (Prerecorded) is the AA addition. A marketing site with one hero video and no captions fails 1.2.2 at level A, which is a lower bar than the rest of this file and still not met.
verify:
  static: Inventory the media first, and if there is none the check is `n/a` with the search shown — say what you searched so the verdict is checkable. Grep the source and content for `<video`, `<audio`, `<source`, `<track`, `<iframe` pointing at YouTube, Vimeo, Wistia, Loom, Mux, Cloudflare Stream, or a `<script>` embed for the same, plus any player component (`react-player`, `video.js`, `plyr`, `@mux/mux-player`, `hls.js`) and any MDX or CMS content type that can embed media (stack ref: "routes and handlers", "file uploads"). For each self-hosted `<video>`, the requirement is a `<track>` child with `kind="captions"` and a `srclang` — and note the distinction that trips people up: `kind="subtitles"` is a translation of the dialogue for people who can hear, while `kind="captions"` also carries speaker identification and non-speech audio, and only the latter satisfies 1.2.2. Check the referenced `.vtt` file actually exists in the repo or at its URL rather than trusting the attribute. For third-party embeds, the captions live in the provider — record which video ids are embedded and hand the list to the user to confirm each has captions uploaded (auto-generated captions on YouTube are a starting point, not a pass, since 1.2.2 requires accuracy and auto-captions routinely mangle names and technical terms). Then check the surrounding page for a transcript: a link or a disclosure near the player. For audio-only content — a podcast player, an embedded recording — a transcript is the requirement, not captions. Note `autoplay` on any of it, which is A11Y-010's 2.2.2 concern as well as this one, and check that `controls` is present so the user can pause.
evidence: the media inventory as one row per item — file:line or content path, type (video with audio, video only, audio only), self-hosted or provider plus the video id, whether a `<track kind="captions">` is present and whether its file resolves, whether a transcript exists and where, and `autoplay`/`controls` state; the exact search performed if the verdict is `n/a`; for provider-hosted media, the explicit list handed to the user to confirm.
fix_hint: Add a `<track kind="captions" srclang="en" label="English" default>` to every self-hosted video and commit the `.vtt` alongside the media, and upload captions in the provider's dashboard for embedded video, correcting the auto-generated ones rather than shipping them as-is. Publish a transcript next to any audio-only content — it is also the version search engines can read. Remove `autoplay` or pair it with `muted` and a visible pause control.

### A11Y-014 Accessibility statement page
severity: low
tier: static
fix: easy
why: An accessibility statement is not a WCAG success criterion — it is the page that tells a user what to expect and how to reach a human when something blocks them, and increasingly it is a legal expectation rather than a courtesy: the European Accessibility Act requires one for in-scope services sold in the EU, public-sector rules in the UK and EU mandate it outright, and it is settled practice in US ADA and Section 508 contexts. It is also the cheapest honest thing you can ship: a statement that names the known gaps found by this very audit is worth more than a boilerplate claim of full conformance that the audit contradicts.
verify:
  static: Look for the page and the link to it (stack ref: "routes and handlers"). Search the route tree and content directory for `accessibility`, `accessibility-statement`, `a11y`, and check the footer component, which is where it belongs alongside the privacy policy and terms — a page that exists but is linked from nowhere is a page nobody reads. If one exists, read it against the five things a usable statement contains: the conformance target it claims (`WCAG 2.2 Level AA`, and specifically whether it claims full conformance, partial conformance, or none), the known limitations stated honestly, a contact method for reporting a barrier along with a commitment to respond within a stated time, the date of the assessment and who performed it, and the scope of what was assessed. Then check the claim against reality — if the statement says "fully conformant with WCAG 2.1 AA" and A11Y-001 through 018 have just produced serious violations, the false claim is itself the finding and a more consequential one than a missing page, since it is a public assertion the audit disproves. Note whether the contact route is a real monitored address rather than a form nobody reads (HYG-005 already validates contact emails; cite it rather than re-checking). If the app has none, check whether COMP's legal-page inventory expects one for this product's markets before deciding the severity.
evidence: the statement's path and file:line, or `absent` with the searched paths listed; where it is linked from, or `not linked`; the conformance target claimed and whether the claim is contradicted by this audit's own findings, quoting the specific claim and the contradicting check ids; the presence or absence of each of the five elements; the contact method and the response commitment.
fix_hint: Publish a short accessibility statement at `/accessibility`, link it from the footer next to privacy and terms, and write it from this audit's actual results — the standard targeted, the known gaps with the checks that found them, a monitored email for reporting barriers with a response commitment, and today's date. Say "partially conformant" and list what is outstanding rather than claiming full conformance you cannot evidence.

### A11Y-015 Screen reader pass of primary flow
severity: medium
tier: attest
fix: none
why: Every other check in this file tests a property; this one tests whether the product actually works. A page can pass axe cleanly, have perfect landmarks, and still be unusable end to end — because a toast confirming the payment is never announced, because focus lands nowhere after a route change, because the loading state reads as an empty page, because "Continue" is announced three times from three different elements. Nothing but a human driving a real screen reader through the real flow finds those. This check produces no fix of its own; it produces the list of what broke, which then feeds the other blocks.
verify:
  static: Prepare the script so the attestation is a real test rather than a memory. Identify the primary flow from config and the route list (stack ref: "routes and handlers", "auth") — typically land on the home page, sign up or log in, complete the core action the product exists for, and see the confirmation — and write it down as numbered steps with the expected outcome of each. Then, from the source, pre-identify the moments that most often fail so the tester knows where to listen: client-side route changes (does anything announce the new page, or does focus stay where it was?), `aria-live` regions and toasts (grep for `aria-live`, `role="status"`, `role="alert"`, and the toast library's usage — a toast rendered into a portal with no live region is silent), loading and skeleton states (an empty region with a spinner announces nothing), async form submission (is the result announced, or only rendered?), and any step where a modal or drawer opens (A11Y-009's territory). List those moments with their file:line so the attestation can be checked against them.
  attest: Ask the user, and record the answer: has someone actually driven the primary flow start to finish with a screen reader — VoiceOver in Safari on macOS or iOS, NVDA in Firefox or Chrome on Windows, or TalkBack in Chrome on Android — and what broke? Both halves need an answer; "we ran axe and it was clean" is not this check and should be recorded as the gap rather than as a pass, since automated scanning covers roughly a third of the problem space (see the header). Give them the script from the static entry so the answer is checkable, along with the minimum they need to run it: VoiceOver is Cmd+F5 to start, Ctrl+Option+arrow keys to navigate, Ctrl+Option+U for the rotor; NVDA is Ctrl+Alt+N to start, arrows to read, Insert+F7 for the elements list. Ask specifically about the pre-identified moments — was the route change announced, was the toast heard, was the loading state audible, did the submit result reach them — because "it seemed fine" from someone unfamiliar with a screen reader usually means they could not tell what was missing. Record what was tested, on which platform and browser pair, by whom, and every barrier they hit, verbatim.
evidence: the primary flow written as numbered steps with the expected outcome of each; the pre-identified risk moments as file:line with what could fail at each; the attestation verbatim — who ran it, which screen reader and browser, which steps completed, and each barrier described in their words; or the gap stated plainly (`no screen-reader pass has been performed`) with the script left behind for someone to run.

### A11Y-016 Correct autocomplete attributes on auth and address forms
severity: low
tier: static
fix: easy
why: WCAG 1.3.5 Identify Input Purpose (AA) requires the purpose of common input fields be programmatically determinable, which is what the `autocomplete` token does. The practical effect is larger than the criterion suggests: correct tokens let the browser and the password manager fill the form, which is the difference between a two-second checkout and a ten-minute one for a user with a motor or cognitive impairment, and they let personalisation tools relabel fields with familiar words or icons. The failure mode is usually `autocomplete="off"` added to a password field years ago to stop a browser prompt, which now blocks every password manager — HYG-011 owns that consequence, this check owns whether the tokens are right; whichever runs second cites the first rather than re-reading the forms.
verify:
  static: Find the auth and address forms (stack ref: "routes and handlers", "auth") — sign up, log in, password reset, two-factor entry, profile, checkout shipping and billing, and any address book. Read the `autocomplete` (or `autoComplete` in JSX) attribute on every field and check it against the correct token for that field's purpose. The set that matters: `username` for the login identifier and `email` for a genuine email field; `current-password` on login and `new-password` on both the create and confirm fields at sign-up and password reset (this is what makes a manager offer to generate and then save a new password, and getting it wrong makes the manager fill the old one); `one-time-code` on a 2FA or verification-code input; `name` or the parts `given-name` and `family-name`; `organization`; `street-address`, or `address-line1` and `address-line2`; `address-level2` for the city and `address-level1` for the state, province, or region — those two are the ones everybody gets backwards; `postal-code`; `country` for the code and `country-name` for the display name; `tel`; `bday`; and for payment fields `cc-name`, `cc-number`, `cc-exp`, `cc-csc` (payment fields inside a hosted iframe from the payment provider are the provider's responsibility — note that and move on). Three specific failures to report: `autocomplete="off"` on any of these fields, which is the finding this check exists for; a non-existent token such as `autocomplete="false"`, `autocomplete="nope"`, or `autocomplete="address"`, which browsers ignore and which therefore behaves as if the attribute were absent while looking to a reviewer as if it were handled; and a missing attribute on an address or payment form, where the whole point is that the browser can fill twenty fields at once. Also check for `autocomplete="off"` set on the `<form>` element itself, which applies to every child and is easy to miss when the fields all look correct.
evidence: one row per field across the auth and address forms — form, field name, file:line, the `autocomplete` value found, the correct token, and pass/fail; every `autocomplete="off"` and every invalid token listed separately with its file:line; any `autocomplete="off"` on a `<form>` element; whether the tokens on the login form distinguish `username` from `email`; a note where payment fields are provider-hosted and out of scope.
fix_hint: Set the correct `autocomplete` token on every field in the auth and address forms, using `new-password` at sign-up and reset and `current-password` at login, and `address-level2`/`address-level1` for city and state. Delete every `autocomplete="off"` on these forms — that is the deletion that fixes both this check and HYG-011 — and replace any invalid token with a real one from the HTML spec's list.

### A11Y-017 Meaningful link text and button labels; no bare "click here"
severity: low
tier: local
fix: easy
why: Screen reader users navigate by pulling up a list of the page's links, out of context — a list of nine entries all reading "Read more" is a list of nine identical unusable choices, which is what WCAG 2.4.4 Link Purpose (In Context) is about at level A. An icon-only button with no accessible name is worse and is a 4.1.2 Name Role Value failure: it is announced as "button" with nothing else, so the user knows a control exists and not what it does. There is also a trap in the fix, 2.5.3 Label in Name (A): if a button visibly reads "Search" but carries `aria-label="Submit query"`, a voice-control user saying "click Search" cannot activate it, because the accessible name does not contain the visible label. Adding an `aria-label` that contradicts the visible text makes things worse, not better.
verify:
  static: Grep for the low-information link texts across templates and components — `>click here<`, `>Click here<`, `>read more<`, `>learn more<`, `>more<`, `>here<`, `>this<`, `>link<`, `>details<`, `>download<` — and for each hit read whether an `aria-label` or visually hidden span supplies the real purpose. Then find the unnamed controls (stack ref: "routes and handlers"): a `<button>` whose only child is an icon component or an `<svg>` with no `aria-label`, no `title`, and no visually hidden text; an `<a>` wrapping only an image (its name comes from the image's `alt`, so a missing or empty `alt` there leaves the link nameless — that overlaps A11Y-006's functional-image bucket, so cite it rather than reporting twice); a control named only by a `title` attribute, which is unreliable and invisible to touch users. Then run the 2.5.3 pass in the other direction: for every element that has both visible text and an `aria-label`, check the accessible name contains the visible text; flag every case where the label replaces rather than extends it. Finally, check the repeated-text case that a grep alone will not find — a card component rendering a fixed "Read more" once per item, which is one file:line producing a page full of identical links.
  local: Read `link-name` and `button-name` from the saved reports across all four pages: `jq -r '.[0].violations[] | select(.id=="link-name" or .id=="button-name") | "\(.id) \(.nodes|length)" ' .pre-launch/a11y/axe-app.json` plus a representative selector per node. Those catch the wholly nameless controls; the low-information ones pass axe entirely, so extract the link text yourself from the saved markup and look at the list the way a screen reader user would: `python3 -c "import re,sys; h=open(sys.argv[1]).read(); print('\n'.join(sorted(set((re.sub(r'<[^>]+>',' ',m.group(2)).strip()[:60] or '(no text)')+'  ->  '+m.group(1) for m in re.finditer(r'(?is)<a[^>]+href=\"([^\"]*)\"[^>]*>(.*?)</a>', h)))))" .pre-launch/a11y/page-1.html`. Two faults in that output: any entry whose text is one of the low-information phrases or `(no text)`, and any text that appears more than once pointing at different hrefs. Repeat across the sample so the pattern is visible rather than a single page's accident.
evidence: the extracted link list per page as `text -> href` with every low-information and duplicate-text-different-href entry marked; the axe `link-name` and `button-name` node counts with a representative selector each; the file:line of each icon-only button with no accessible name and of each shared component producing repeated link text; every 2.5.3 mismatch as `visible "X" vs accessible name "Y"` with its file:line.
fix_hint: Make the link text describe the destination on its own — "Read the 2026 pricing guide" rather than "Read more" — or, where the design requires short text, append a visually hidden span carrying the context so the visible label stays intact and the accessible name grows (which keeps 2.5.3 satisfied). Give every icon-only button an `aria-label` naming the action, fix the shared card component once rather than each instance, and never replace visible text with a different `aria-label`.

### A11Y-018 Information not conveyed by color alone
severity: medium
tier: local
fix: easy
why: WCAG 1.4.1 Use of Color (level A) says colour must never be the only visual means of conveying information, indicating an action, prompting a response, or distinguishing an element. Around one man in twelve has some form of colour vision deficiency, and they are joined by anyone on a bad screen, in bright sun, or in a high-contrast OS mode that flattens the palette. This is the check with no automated coverage at all — axe cannot evaluate it, Lighthouse cannot evaluate it, and it will pass every scan while a red-only error state leaves a user staring at a form they cannot see the problem with. Note it is not the same as contrast: A11Y-004 asks whether you can see the thing, this asks whether you can tell what it means.
verify:
  static: Work from the places colour is asked to carry meaning, which are the same in almost every app. Form validation: an invalid field marked only by a red border or red text, with no icon, no prefix such as "Error:", and no text at all in the worst case — grep the field and error components for `border-red`, `text-red`, `--color-error` and check what accompanies them. Status: badges, pills, dots, and health indicators rendered as a coloured circle with no shape difference, no label, and no title — a green dot and a red dot are indistinguishable to a deuteranope. Required fields: a red asterisk with no legend and no `required` attribute (A11Y-005's other half). Links in body copy: distinguished from surrounding text by colour alone, which is only acceptable when the link colour reaches 3:1 against the surrounding *text* — not the background — and a non-colour cue appears on hover and focus; an underline removes the problem entirely and is the reason the convention exists. Data visualisation: chart series, map regions, heatmaps, and legends keyed only by colour, which need a pattern, a shape, a direct label, or an accessible data table alongside. Diffs and changelogs: added and removed lines coloured but not prefixed. Calendars and availability grids. Also check any UI that says "click the green button" or "the items in red" in its own copy, which is the same failure in prose. Read the components rather than the pages, since one badge component usually accounts for every status indicator in the app.
  local: There is no rule to read, so make the failure visible: with a driver already in the project, load each of the four pages, inject `document.documentElement.style.filter = 'grayscale(1)'`, screenshot, and look at each of the places the static pass identified — in greyscale, a genuine dual encoding still reads and a colour-only one collapses. Do the same with the form-heavy page in its error state, which is where it usually collapses. Save them as `.pre-launch/a11y/greyscale-<page>.png` and cite them. Without a driver, the greyscale test can be done by reading the computed styles of each identified element and checking whether anything other than a colour property differs between its states — an icon child, a different `border-style`, a text prefix, an `aria-label`. Either way, the verdict comes from the static inventory; the local step only confirms it, so this check never depends on the tool being present.
evidence: an inventory of every place colour carries meaning — component, file:line, what the colour signals, and what non-colour cue accompanies it or `none`; the greyscale screenshots with each identified element judged readable or collapsed, or the computed-style comparison used instead; the error-state form judged specifically; any body copy that refers to a colour to identify something.
fix_hint: Add a second channel wherever colour is the only one — an icon plus the word "Error" in validation messages, a shape or text label on status badges, an underline on in-content links, direct labels or patterns on chart series. Fix it in the shared badge, field, and link components so every instance follows, and check the result by looking at the page in greyscale rather than by inspecting the palette.
