# Compliance checks (COMP)

Read `agents/domain-auditor.md` for procedure. Blocks below are checks; consult stack references for locations. Tools: `curl` for fetching policy pages, footer links, and the consent probes; `grep` and `python3` with only the standard library for reading the saved text and for the licence and inventory work; the package manager already in the repo (`npm ls --json`, `pnpm ls`, `pip freeze`, `bundle list`, `composer show`) for the dependency half of the inventory. One block (COMP-007) is better with a network log and uses a browser driver **only if the project already depends on one** (`playwright`, `puppeteer`, `@playwright/test`, `cypress`, `selenium` in devDependencies; stack ref: "known traps"); otherwise it reads the served HTML. Never install anything to run this audit.

**This domain is not legal advice, and the report says so.** What these checks produce is a discrepancy list: a sentence in a policy page next to the line of code that contradicts it, or a legal obligation next to the mechanism that does not exist. That is something a lawyer can act on in ten minutes. A verdict of "you are in breach of the GDPR" is not — it depends on facts you cannot see from the repo (where the customers are, what contracts exist, what the company's revenue and record counts are, whether it is a controller or a processor) and it is not yours to give. So write findings in the form `policy says "<quote>" — code does <X> at file:line`, or `<law> requires <mechanism> — not found`. Name the law and the specific requirement, cite an article or section number only where it is stable and you are certain of it, and where the rule depends on jurisdiction, customer base, or a threshold you cannot observe, end the finding with `verify current text with counsel`. Never invent a statute number to look authoritative: an article number that turns out to be wrong discredits the twelve findings around it that were right.

**Find the legal pages once, save them, and read the saved copies.** Search the routes and the content directories for `privacy`, `terms`, `tos`, `eula`, `cookie`, `dmca`, `refund`, and `legal` (stack ref: "routes and handlers" for where routes live; also check MDX and Markdown content directories, a CMS client, and the footer component, since on many projects the pages are content rather than code). Record the discovered paths in `.pre-launch/compliance/pages.txt`, then fetch each one from the production build with `curl -s -L "<local.url><path>" -o .pre-launch/compliance/<name>.html` and render it to text once: `python3 -c "import re,sys,html; h=open(sys.argv[1]).read(); h=re.sub(r'(?is)<(script|style)[^>]*>.*?</\1>', ' ', h); print(html.unescape(re.sub(r'\s+', ' ', re.sub(r'(?s)<[^>]+>', ' ', h))))" .pre-launch/compliance/privacy.html > .pre-launch/compliance/privacy.txt`. Every text check below greps the `.txt`; nothing re-fetches. A page that does not exist is recorded once here as `no <name> page` and every block that needed it cites that line rather than searching again. A page that exists but renders empty because the content is client-side is a different finding from a missing page — say which. **If no build can be run, do not skip the text checks**: most of this domain is static tier and the text is in the repo, so read the page source instead — the route file, the MDX or Markdown content, the CMS fixture — write it into the same `.txt` files, and record `source: repo` rather than `source: rendered` in evidence, because a rendered page can include text a template pulls in from somewhere you did not read.

**Build the third-party inventory once, at the start of this domain.** Five blocks (COMP-001, 002, 003, 007, 014) are diffs against this list, and building it five times produces five different lists. Assemble it from four sources. First, the dependency manifest and lockfile: `package.json` plus the lockfile for anything that pulls a tracker transitively, `requirements.txt`/`pyproject.toml`, `Gemfile`, `composer.json`, and for mobile the `Podfile`, `build.gradle`, and the Expo config's plugin list. Second, script tags and inline snippets in the root layout or base template (stack ref: "routes and handlers": `app/layout.tsx`, `pages/_app.tsx`, `app.vue`, `+layout.svelte`, `src/layouts/*.astro`, `app/views/layouts/application.html.erb`, `templates/base.html`) — grep for `<script`, `next/script`, `gtag(`, `dataLayer`, `fbq(`, `_hsq`, and any `src=` pointing at a host you do not own. Third, environment variables (stack ref: "env vars"), because a key names a vendor even when no package is installed: `NEXT_PUBLIC_GA_ID`, `GTM_ID`, `SENTRY_DSN`, `POSTHOG_KEY`, `SEGMENT_WRITE_KEY`, `MIXPANEL_TOKEN`, `HOTJAR_ID`, `CLARITY_ID`, `INTERCOM_APP_ID`, `RESEND_API_KEY`, `SENDGRID_API_KEY`, `STRIPE_SECRET_KEY`, `OPENAI_API_KEY`, `ANTHROPIC_API_KEY`, `TWILIO_AUTH_TOKEN`. Fourth, the hosting and CDN layer, which sees every request: `vercel.json`, `netlify.toml`, `wrangler.toml`, `fly.toml`, plus any third-party origin the page loads fonts, icons, or scripts from (`fonts.googleapis.com` receives the visitor's IP on every page view; a self-hosted font does not).

**Package names map to vendors like this.** Analytics: `@vercel/analytics` (Vercel), `posthog-js`/`posthog-node` (PostHog), `mixpanel-browser` (Mixpanel), `@amplitude/analytics-browser` (Amplitude), `@segment/analytics-next` (Segment, which is itself a fan-out to whatever destinations the workspace has enabled — a Segment key means the vendor list is not fully knowable from the repo, so say so), `plausible-tracker` (Plausible), `fathom-client` (Fathom), `react-ga4` or a `gtag`/`googletagmanager.com` snippet (Google Analytics). Ads and attribution, usually recognised by host rather than package: `connect.facebook.net` (Meta pixel), `googleadservices.com` or a `gtag('config', 'AW-` line (Google Ads), `analytics.tiktok.com`, `snap.licdn.com` (LinkedIn Insight), `static.ads-twitter.com`, `sc-static.net` (Snap). Error tracking: `@sentry/*`, `@bugsnag/js`, `rollbar`, `@highlight-run/*`, `@datadog/browser-rum`. Session recording, which is the category most often mis-declared: `@fullstory/browser`, `logrocket`, `@hotjar/browser`, `clarity-js`, and `posthog-js` when session recording is enabled in its init options — check the options, because the same package is analytics or a screen recorder depending on one flag. Email: `resend`, `@sendgrid/mail`, `postmark`, `mailgun.js`, `@aws-sdk/client-ses`, `loops`, `customerio-node`, and `nodemailer`, whose vendor is whatever SMTP host the config points at. Payments: `stripe` and `@stripe/stripe-js`, `@lemonsqueezy/lemonsqueezy.js`, `@paddle/paddle-js`, `braintree`, `razorpay`, `react-native-purchases` (RevenueCat). AI: `openai`, `@anthropic-ai/sdk`, `@google/generative-ai`, `replicate`, `groq-sdk`, `@huggingface/inference`, `langchain`, and `ai` (the Vercel AI SDK, which is a wrapper — the actual processor is whichever provider key is configured, so resolve it from the env vars rather than recording "Vercel"). Auth and identity: `@supabase/supabase-js`, `next-auth`/`@auth/core`, `@clerk/nextjs`, `firebase`, `@auth0/*`, `@workos-inc/node`. Support and chat: `@intercom/messenger-js-sdk`, `crisp-sdk-web`, `@zendesk/*`, `react-live-chat-loader`. A tag manager container (`GTM-`) is the one entry you cannot resolve from the repo at all: the tags inside it are configured in a web UI, so record it as `unknown contents — ask the user for the container's tag list` rather than as zero vendors.

**Write the inventory to `.pre-launch/compliance/inventory.json` and record for each vendor whether it runs in the browser or on the server.** One object per vendor: `{"vendor": "PostHog", "category": "analytics", "source": "package.json:31 posthog-js; app/providers.tsx:14 init()", "side": "client", "data_seen": "page URLs, IP, distinct_id cookie, autocaptured clicks"}`. The `side` field is what makes the file reusable: a client-side tag fires in the visitor's browser and by itself collects an IP address, the page URL, and a cookie, which is exactly the set that a consent banner must gate (COMP-007) and that a "we don't share your data" sentence contradicts (COMP-003). A server-side SDK only ever receives what your code hands it, so its finding is about disclosure (COMP-001, COMP-002) and about a processor contract (COMP-019), not about consent. Record `data_seen` from what the code actually sends, not from the vendor's marketing page.

**A keyword group tells you where to look; it never tells you the clause is adequate.** Most of the text checks here work by grepping the saved policy text case-insensitively for a named group of related terms — each block states its group. Finding the words proves only that the topic is mentioned. So every clause gets one of exactly three verdicts, and each one quotes: `present` with the sentence quoted; `absent` naming the keyword group that returned nothing; or `generic` with the sentence quoted plus the reason it does not fit this product. Never report a hit count as a verdict, and never pass a clause you did not read. Two commands do all of it: `grep -ioE "limitation of liability|as is|indemnif[a-z]*|terminat[a-z]*" .pre-launch/compliance/terms.txt | sort -u` to find which groups are represented, then `python3 -c "import re,sys; t=open(sys.argv[1]).read(); [print('-', s.strip()) for s in re.split(r'(?<=[.!?]) ', t) if re.search(sys.argv[2], s, re.I)]" .pre-launch/compliance/terms.txt "indemnif"` to pull the sentences out for quoting.

**Template residue and tailoring are the fastest tells in this domain.** A pasted policy announces itself: `[Company Name]`, `[COMPANY]`, `Your Company`, `[Insert`, `YOUR_SITE`, `example.com` in a contact address, `Lorem`, `TODO`, a generator credit still in the footer, or no effective date at all. Grep the saved text for all of those in one pass. Tailoring is the subtler half and matters more: a marketplace's terms must speak about buyers and sellers and about who holds the money; a single-tenant SaaS's terms must not refer to "the Marketplace", "the Platform's sellers", "your listings", or "the App Store" if it never ships an app. A policy that names Google Analytics when the repo runs PostHog, or that describes a mobile app for a web-only product, is `generic` even though every clause is nominally present. HYG-003 owns placeholder copy across the product generally and HYG-006 owns effective dates and versions on legal pages; this domain owns the instance of both on the legal pages themselves, so cite those checks rather than restating their findings.

**Every artifact this domain writes goes under `.pre-launch/compliance/` and nowhere else.** A bare relative filename lands in the project root, and on a static site the project root is served content, so a stray `privacy.html` can overwrite a real page or ship in the next deploy — a uniquely bad outcome for the one domain whose subject is what the published pages say. `/tmp` is no better: it survives the audit, collides between concurrent runs, and puts the evidence somewhere the report cannot cite. Create the directory once with `mkdir -p .pre-launch/compliance` before the first fetch. The names used below are `inventory.json`, `pages.txt`, `privacy.html`/`privacy.txt`, `terms.html`/`terms.txt`, `cookies.html`/`cookies.txt`, `eula.txt`, `dmca.txt`, `refund.txt`, `home-preconsent.html`, `preconsent-requests.txt`, `gpc.html`, `plain.html`, `footer.txt`, `checkout-<n>.html`, `emails.txt`, `licenses.txt`, and `marketing-<n>.txt`.

**Measure a production build, never the dev server.** This is the same rule the performance, SEO, and accessibility domains state, and it changes verdicts here for reasons specific to legal pages. Consent management platforms are routinely disabled in development (a `if (process.env.NODE_ENV === 'production')` guard around the CMP init is the single most common pattern in this domain), so a dev server shows no banner on a site that has one, and shows no tracker on a site that fires eight. Dev builds also inject their own scripts, which pollute the pre-consent network log with framework requests that will never ship. And several stacks serve MDX legal pages differently in dev than through the built route manifest. So before any local-tier work here, build and start the app in production mode on a port you record — `npm run build && PORT=<port> npm start` with `NODE_ENV=production` for a typical Node stack, and the equivalent for this one (stack ref: "build" for the build and production start commands, "dev server" for the port convention) — and point every fetch and probe in this file at that URL, noting it in evidence alongside `local.url`. COMP-006, COMP-007, COMP-020, COMP-026, and COMP-036 are the blocks where a dev server produces a confident wrong answer. If the production build cannot be run, mark those five `dev-server only` in `notes` rather than reporting a dev reading as a production one.

**Probe safety: two blocks in this domain change state, and both have a rule.** COMP-010 walks the account deletion path and COMP-011 walks the cancellation path. Use only the test account from config for anything requiring a login, and run the destructive step only when the environment's provider keys are detectably test-mode (stack ref: "env vars" — a `sk_test_` prefix, a sandbox host, a test-mode webhook secret); if they are not, walk the path up to the final confirmation, record what you saw, and note `error: live keys detected` for the step you did not take. COMP-010's runtime half specifically: look for the FLOW-009 object in `.pre-launch/findings/flows*.json` (this run) or in `.pre-launch/findings.json` (a previous run), whichever is newer — a file existing is not the same as that check having run, and a file containing nine other flows and no FLOW-009 means the evidence is not there — and if it is present reuse its evidence rather than deleting a second account. Otherwise take the disposable-account branch: create a disposable account for the destructive step. **Never delete the shared test account**: every check after this one needs it, and an audit that deletes its own credentials halfway through reports errors for reasons that have nothing to do with the product. COMP-020's GPC probe is a plain GET with one extra header and mutates nothing.

**Never modify project files, and remember what a fix looks like here.** Everything in this domain is a read or a request. Do not add a missing clause, correct an effective date, or drop a consent script while auditing. Nearly every fix in this file is `guided` for a reason that is stronger than usual: policy text is a legal document, and the fix workflow writes drafts to `.pre-launch/drafts/` for a human — usually with counsel — to review and publish, rather than editing a live policy page. So each `fix_hint` below names what the draft has to contain and which facts from the audit it must be built from, not prose to paste into the page.

**Cross-references, so the same work is not done or reported twice.** COMP-007 owns whether consent gates the trackers in the code; FLOW-013 owns the runtime proof that declining consent fires no pixels. COMP-010 owns discoverability of account deletion; FLOW-009 and DAT-020 own whether the deletion actually removes the data. COMP-011 owns whether cancelling is as easy as signing up; FLOW-005 owns whether the entitlement is revoked and PAY-012 owns whether the billing portal is configured for it. COMP-016 owns the legally required contents of a marketing email; FLOW-014 owns whether the unsubscribe link works and HYG-016 owns rendering and deliverability. COMP-022 sits alongside the PAY domain and the Stripe stack reference, which own the integration's correctness; this check owns only whether card data can reach your servers. COMP-036 cites HYG-001 for the third-party dashboard fields. COMP-018's placeholder half overlaps HYG-003, and COMP-028's licence half overlaps HYG-007 — HYG-007 owns the project's own `LICENSE` file, COMP-028 owns compliance with everyone else's. COMP-013 pairs with FLOW-007, which runs the trial-conversion flow. COMP-014 pairs with MOB-004: this check produces the inventory-versus-label diff, MOB-004 confirms the store form itself. A11Y-014 owns the accessibility statement; do not audit or report it here.

### COMP-001 Privacy policy exists and matches actual data practices
severity: critical
tier: static
fix: guided
why: The policy is the promise and the code is the practice, and the cheapest enforcement action in existence is one where the regulator reads your own published page back to you. At launch the gap is almost always in the same direction: someone pasted a template that describes an analytics vendor the product never installed and says nothing about the two it did, and nobody has compared it to the schema since.
verify:
  static: Read the saved text per the header rule and check six things, each against the code rather than against the reader's expectations. What is collected: diff the categories the policy lists against the columns of the user-facing tables (stack ref: "data access") and the fields of every form and sign-up handler (stack ref: "routes and handlers") — an `ip_address`, `phone`, `date_of_birth`, `precise_location`, or `device_id` column with no counterpart in the policy is a line of evidence, and so is a policy saying you collect only an email when the sign-up form asks for a company and a job title. Why: a stated purpose for each category, since a list of collected data with no purposes is `generic` under GDPR Art. 13(1)(c) and under every US state law's notice requirement. Who receives it: COMP-002 owns the vendor diff; cite it rather than redoing it. How long: some retention statement, even an approximate one, measured against what the deletion path actually removes (DAT-020) and against any backup or log retention you can see. Rights and how to exercise them: COMP-019 owns the GDPR machinery, so here only confirm the policy names a route or address for requests and then check that route exists — a `privacy@` address with no mailbox, or a form posting to an unset environment variable, is the fail. Who the controller is: COMP-027 owns the legal identity; confirm the policy names it rather than `[Company Name]`. Then hunt the contradictions, which are the critical half of this check: "we do not use cookies" beside an analytics script in the layout; "we never share your information with third parties" beside an eleven-entry `inventory.json`; "all data is encrypted at rest" with no encryption anywhere (DAT-021); "we do not sell your data" beside an ad pixel (COMP-003); a policy describing a mobile app for a web-only product. Each contradiction is a separate line and each is worth more than any missing-clause finding.
evidence: `privacy page at <route> — <file:line>` or `no privacy page found (searched routes and content for privacy)`; per clause `present — "<sentence>"`, `absent (keyword group: <group>)`, or `generic — "<sentence>" (names <vendor>, not installed)`; the collected-fields diff as `<table>.<column> — not disclosed`; each contradiction as `policy says "<quote>" — code does <what> at <file:line>`; the template tells found.
fix_hint: The draft in `.pre-launch/drafts/` must be built from three artifacts rather than from a template: the column and form-field list for the categories collected, `.pre-launch/compliance/inventory.json` for the recipients, and the deletion path for the retention statement. It needs a purpose per category, a working contact route for rights requests, the legal entity's name and address, and an effective date; and every clause describing a practice this product does not have must be deleted rather than left in as harmless filler.

### COMP-002 Every third party receiving data is named (cross-check against SDK inventory)
severity: high
tier: static
fix: guided
why: The vendor list is the part of a privacy policy that goes stale fastest and the part a regulator or an enterprise buyer checks first, because it is the only claim in the document that can be verified from outside. A policy that omits the session recorder capturing every keystroke is not a paperwork slip; it is the difference between disclosed analytics and undisclosed surveillance.
verify:
  static: Read `.pre-launch/compliance/inventory.json` (built once per the header rule) and walk it against the saved policy text. For each vendor, grep for the vendor name and its plausible aliases, since policies rarely use the package name — Google Analytics may appear as `Google`, `gtag`, or `Google LLC`; Meta as `Facebook` or `Meta Platforms`; PostHog as `PostHog Inc`. Then decide by category, not just by name: naming a **category** of recipient is legally permitted under GDPR Art. 13(1)(e), which asks for "recipients or categories of recipients", so a policy saying "analytics providers" is not automatically a fail — but it is a fail when the category is wrong or too narrow for what the vendor does, and the case that recurs is a session recorder or a heatmap tool folded into "analytics", which hides from the reader that screens, form inputs, and mouse movement are captured. Session recording, advertising, AI processing, and payment vendors need their own category at minimum and are better named outright, because store privacy labels (COMP-014) and enterprise DPA requests (COMP-033) both need the names anyway. Check the reverse direction too, which is the template tell: any vendor named in the policy that appears nowhere in the inventory is residue from whatever document this was copied from, and it is evidence the whole list was never reviewed. Finally note international transfers: if any vendor processes outside the region the users are in, GDPR Chapter V requires the policy to say so and to name the transfer mechanism (an adequacy decision, standard contractual clauses); record whether that statement exists rather than judging whether the mechanism is valid, and mark it `verify current text with counsel`.
evidence: one row per vendor — `<vendor> (<category>, <client|server>) — named at "<sentence>"`, `covered only by category "<sentence>"`, or `NOT disclosed`; one row per policy-named vendor absent from the inventory; the transfer statement quoted or `no international transfer statement`; `GTM container <id> — contents unknown, ask user` where a tag manager is present.
fix_hint: The draft must carry the vendor list generated from `.pre-launch/compliance/inventory.json`, one row per vendor with its category and its purpose, session recording and advertising broken out as their own categories rather than folded into analytics, every vendor named in the current text but absent from the inventory removed, and a statement of international transfers and their mechanism for the vendors that process outside the users' region. Add a note that the list has to be regenerated whenever a dependency or a tag-manager tag is added.

### COMP-003 Sale/share disclosure present if ad pixels or data-selling SDKs installed
severity: high
tier: static
fix: guided
why: The word "sell" in California law does not mean what it means in English. Under the CCPA as amended by the CPRA, a "sale" is any disclosure of personal information to a third party for monetary **or other valuable consideration**, and "sharing" is separately defined as disclosure for cross-context behavioural advertising. An advertising pixel is therefore a share even though no money moves, which makes "we do not sell your personal information" — the sentence in almost every template — an affirmative misstatement on a site running a Meta or Google Ads tag, and a misstatement in a privacy policy is the kind of thing the FTC treats as a deceptive practice independently of any state privacy law.
verify:
  static: Filter `.pre-launch/compliance/inventory.json` to the advertising, attribution, and data-broker categories, plus any analytics vendor whose configuration enables ad-network integrations or audience syncing (check the init options, not just the package name). If that list is empty and no tag manager is present, the check passes with the reason recorded — the finding here is only ever about a mismatch. If it is not empty, three things must be in the policy text: a section that acknowledges sale or sharing as those terms are defined in the law, a description of the categories of information involved and the categories of third parties receiving them, and a route to opt out (COMP-020 owns the runtime existence of the link and the Global Privacy Control handling; this block owns whether the document says any of it). Then grep for the flat denial specifically — the keyword group is `do not sell`, `does not sell`, `never sell`, `we do not share`, `no sale of` — and quote any sentence you find next to the pixels in the inventory, because that pairing is the finding. Two more to check: if the product may be used by anyone under 16, CCPA requires opt-in consent before selling or sharing their information rather than an opt-out, so a general opt-out link is not sufficient there (cross-reference COMP-021); and the notice-at-collection requirement means the disclosure has to be available at or before the point of collection, not only buried in a policy the user reaches after signing up. Whether the business meets the CCPA's applicability thresholds at all — annual gross revenue above 25 million dollars (a figure adjusted annually for inflation, so check the current one rather than quoting this), personal information of 100,000 or more consumers or households bought, sold, or shared, or 50 percent or more of revenue derived from selling or sharing — is a question about facts you cannot see, so state the thresholds, note that a pre-launch company is often under all three, and mark it `verify current text with counsel`. Say plainly in the finding that the denial sentence is worth removing regardless of thresholds, because it costs nothing and it is the sentence that turns a paperwork gap into a misrepresentation.
evidence: the advertising and attribution vendors from the inventory with their file:line; the sale/share section quoted or `absent (keyword group: sell, share, cross-context, behavioral advertising)`; any flat denial quoted verbatim beside the pixels that contradict it; the notice-at-collection statement or its absence; the threshold note.
fix_hint: The draft needs a sale-and-sharing section written in the statutory vocabulary — categories of personal information sold or shared, categories of third parties, and the opt-out route — plus a notice at collection on the pages where data is first collected, plus the under-16 opt-in carve-out if minors are possible. Most important, it must delete or correct any flat "we do not sell or share your data" sentence while an advertising pixel is installed; that single sentence is the difference between a disclosure gap and a misrepresentation.

### COMP-004 AI use disclosed in privacy policy
severity: medium
tier: static
fix: guided
when: features.ai
why: Sending a user's text, files, or support conversation to a model provider is a disclosure to a third party, and it is the one users are most surprised by. The policy question is separate from the interface question: COMP-029 owns telling the person in front of the chatbot that they are talking to a machine, while this block owns telling them, in the document that lists recipients, that what they type leaves your systems and goes to a named company.
verify:
  static: From `.pre-launch/compliance/inventory.json`, take the AI vendors and resolve any wrapper to the real processor — the Vercel AI SDK's `ai` package is not a vendor, whichever provider key is set is. Then read the call sites (stack ref: "routes and handlers", "background jobs") and write down what is actually in the payload: the user's prompt, obviously, but also whether uploaded file contents, database rows, other users' content, the user's email or id in a metadata field, or a whole conversation history is included. That payload description is what the policy has to match. Four statements to look for. First, that user inputs are processed by a third-party model provider, with the provider named or at least categorised. Second, whether inputs are used to train the provider's models — the answer depends on the provider's API terms and the account's settings rather than on your code, so read what the code can show (an explicit opt-out flag, a zero-retention endpoint, an enterprise base URL) and record the rest as a dashboard question for HYG-001 rather than asserting it. Third, retention: how long the provider keeps the payload and how long you keep the outputs, which for most APIs is a provider-side setting. Fourth, human review — if support staff or an evaluation pipeline reads real user conversations, that is a use the policy must state and it is the one that gets omitted. Also check for the reverse tell: a policy with an AI section for a product whose AI feature was removed, or one naming a provider that is not the one configured.
evidence: each AI vendor with its call site file:line and the payload fields actually sent; the policy's AI statements quoted, or `absent (keyword group: artificial intelligence, AI, machine learning, model provider, large language model)`; whether training use is addressed and what the code shows about it; the human-review statement or its absence.
fix_hint: The draft must name the model provider (or the category plus a maintained list), state exactly which user data is sent to it — derived from the call-site payload, not from a guess — say whether inputs are used for training and on what basis you know, give the retention period on both sides, and disclose any human review of real user content. Pair it with a note that the training and retention claims need confirming in the provider's dashboard before publication.

### COMP-005 Terms cover UGC, data ownership, privacy, liability limit, as-is, indemnification, termination, class waiver, arbitration, governing law; tailored to the business
severity: critical
tier: static
fix: guided
why: Terms of service are the only document that limits what a bad day costs. Without a liability cap, an as-is warranty disclaimer, and a termination right, a single outage or a single abusive user is an uncapped, unbounded exposure. And a terms page copied from another company is worse than a short honest one, because it purports to govern a relationship that does not exist — it will be read against the drafter, and the drafter is you.
verify:
  static: Work the saved terms text clause by clause, one keyword group each, and give each the `present` / `absent` / `generic` verdict with the sentence quoted. User content and licence: `user content`, `your content`, `licen[sc]e`, `grant us`, `royalty-free`, `sublicense` — a product accepting uploads or posts needs a licence broad enough to host and display them and no broader. Data ownership: `own`, `ownership`, `intellectual property`, `retain all rights` — who owns customer data and who owns the product. Privacy: an explicit incorporation of the privacy policy by reference, with a working link. Limitation of liability: `limitation of liability`, `liab`, `consequential`, `aggregate liability`, and a cap that is an actual number or formula (fees paid in the preceding twelve months is the usual one) rather than a sentence that says liability is limited without saying to what. Warranty disclaimer: `as is`, `as available`, `warrant`, `merchantability`, `fitness for a particular purpose`. Indemnification: `indemnif`. Termination: `terminat`, `suspend`, `discontinue` — both parties' rights, and what happens to the user's data afterwards. Class action waiver: `class action`, `class-wide`, `collective action`, `representative action`. Arbitration: `arbitrat`, `JAMS`, `AAA`, `binding` — and note whether it has an opt-out window, which is what makes such clauses hold up in several jurisdictions. Governing law: `governing law`, `jurisdiction`, `venue`, `courts of` — and check the named state or country is the one the company is actually in, since a mismatched jurisdiction is the single loudest sign the document was copied. Then judge tailoring across the whole document, which is this check's other half: a marketplace's terms must address buyers, sellers, listings, fees, and who holds the funds; a single-tenant SaaS's terms must not mention "the Marketplace", "sellers", "your listings", or an app store it does not ship to; a free product's terms should not describe a refund process that does not exist. Take the jurisdiction from the governing-law clause and the company's actual location, say which you used, and where the two disagree report that mismatch as the finding instead.
evidence: one row per clause — `<clause> — present: "<sentence>"`, `<clause> — absent (keyword group: <group>)`, or `<clause> — generic: "<sentence>" (<why it does not fit>)`; the governing-law jurisdiction beside the company's actual location; every product-type mismatch quoted; the template tells; `no terms page found` if there is none.
fix_hint: The draft must be assembled clause by clause from the list this check produced, with the liability cap expressed as a real number or formula, the governing law set to the company's actual jurisdiction, and the user-content licence scoped to what the product genuinely needs to do with uploads. Everything describing a business model this product does not have has to be cut rather than left in. Flag the arbitration, class waiver, and liability cap for counsel review before publication, since their enforceability depends on where the customers are.

### COMP-006 Cookie/consent banner exists where required
severity: high
tier: local
fix: guided
why: Both failure directions are real and they are not symmetric. A site setting analytics or advertising storage for EU or UK visitors with no prior consent is doing the thing ePrivacy actually prohibits, and it is trivially provable from outside with a browser. But a site that sets nothing but a session cookie and shows a consent banner anyway has added a click, a compliance surface, and a support question to every visit in exchange for nothing — and it is usually a sign the banner was installed instead of finding out what the site stores.
verify:
  static: First enumerate what is actually stored, because "where required" is the whole check and it turns on this list. Grep the source for `document.cookie`, `Set-Cookie`, `cookies().set`, `res.cookie`, `localStorage.setItem`, `sessionStorage.setItem`, and `indexedDB`, and add every client-side vendor from `.pre-launch/compliance/inventory.json`, since each of those sets its own storage. If everything is strictly necessary, the correct outcome is a pass with a note that no banner is required and that adding one would be a regression. Judge three things: whether any non-essential storage exists before consent (that is COMP-007's finding; record it here as the trigger and cite that block), whether the banner renders at all on a clean load, and whether the reject control is present in the initial markup rather than only inside a preferences dialog. fix_hint: The draft and the accompanying code note must say which storage is strictly necessary and which is not, based on the inventory this check produced, so the banner gates exactly the second list. Requirements for the implementation: reject offered at the same level and in the same click count as accept, every non-essential category defaulting to off with no pre-ticked boxes, the choice stored and re-readable, and a persistent way to change it. ### COMP-009 DMCA policy, takedown clause, designated agent registered
severity: medium
tier: static
fix: guided
when: features.user_content
why: The DMCA safe harbour is what stops a platform being liable for what its users upload, and it is conditional: it is available only to a service provider that has designated an agent with the US Copyright Office, published that agent's contact details, implemented notice-and-takedown, and adopted and reasonably implemented a repeat-infringer termination policy. Miss any one of those and the protection is not merely weakened, it is unavailable — which turns one user's uploaded photo into your problem.
verify:
  static: Four separate things, and a page mentioning the DMCA satisfies at most two of them. The published agent details: a page or policy section naming the designated agent with a physical address, telephone number, and email — grep the saved text for the keyword group `DMCA`, `designated agent`, `copyright agent`, `infringement`, `takedown`, `counter-notice`, and quote what you find. The notice procedure: what a rights holder must include and where to send it, which should track the statutory elements of a compliant notification. The counter-notification procedure, which is the half most often missing and the one that protects your users from bad-faith takedowns. And the repeat-infringer policy, which must live in the terms of service and must be something the product can actually do — check whether there is any mechanism to count strikes against an account, because a policy promising termination of repeat infringers on a platform with no way to record a strike is not "reasonably implemented". The registration itself cannot be seen from the repo: the Copyright Office maintains a public directory of designated agents, registrations must be renewed periodically, and a lapsed registration is the same as none. Check the directory by the company name if you have network access, and otherwise record it as a question for the user with the renewal requirement stated; either way put the result in evidence rather than assuming. Finally, note the jurisdictional limit plainly: the DMCA is US law and a DMCA page does not satisfy the EU Digital Services Act's notice-and-action obligations for hosting services, which are a separate regime with their own requirements (COMP-034 covers the broader trust-and-safety side). Mark that split `verify current text with counsel`.
evidence: the DMCA page route and file:line, or `absent`; the designated agent's name, address, phone, and email as published, or which of those are missing; the notice and counter-notice procedures quoted or marked absent; the repeat-infringer clause quoted from the terms plus whether any strike-tracking mechanism exists in the code (file:line or `none`); the Copyright Office directory result or `registration unconfirmed — ask user; renewal is periodic`.
fix_hint: The draft needs all four pieces, not just the page: agent contact details matching what is filed with the Copyright Office, a notice procedure listing the elements a valid notification must contain, a counter-notification procedure with the statutory waiting period, and a repeat-infringer termination policy in the terms. Pair it with a note that the agent must actually be registered and the registration kept current, and with a code note that the platform needs somewhere to record strikes for the termination policy to be implementable.

### COMP-011 Cancellation as easy as sign-up, in-app, no dark patterns
severity: high
tier: local
fix: guided
when: features.subscriptions
why: Subscription cancellation is the most regulated user flow in a consumer product, and it is regulated because making it hard works. The rule the various regimes converge on is simple to test: a subscriber must be able to cancel through the same medium they used to sign up, and it must not be materially harder. Two clicks to subscribe and an email to a support address to cancel is the archetype, and it also generates chargebacks, which cost more than the churn it prevented.
verify:
  static: Find the cancellation path (stack ref: "routes and handlers"; with Stripe it is usually either a billing-portal session or a direct `subscriptions.update` with `cancel_at_period_end`) and find its entry point the same way COMP-010 does — the component, the page, the navigation. Read the cancel flow's copy for the patterns that turn a compliant flow into a non-compliant one: confirmshaming ("No thanks, I like wasting money"), a retention offer that must be declined more than once, a required reason with no neutral option, a cancel button that opens a chat widget or a phone number, a countdown or a deliberately slow step, a control that is visually de-emphasised relative to the "keep my plan" button. Note what the flow promises about the end date, since a cancellation that revokes access immediately on an annual plan is its own kind of complaint. On the law, be precise about the state of play rather than confident: several US state auto-renewal statutes, California's Automatic Renewal Law foremost, independently require that a consumer who accepted online be able to cancel online, promptly and without engaging another person; the FTC has separately pursued negative-option cases under the ROSCA statute and its 2024 negative-option rule has been through litigation, so cite the state requirement as the stable one and mark the federal rule's current text `verify current text with counsel`. The practical standard does not move either way: cancel in the same medium, no more steps than sign-up.
  local: Against the production build, log in as the test account and walk the cancel path from the account page, counting clicks and naming each screen, and compare that count with the sign-up flow's. Fail if cancellation requires contacting support, requires leaving the app, or takes more steps than sign-up. Complete the cancellation only when the subscription is a test-mode one and the provider keys are detectably test-mode (stack ref: "env vars"); if it is not, stop at the final confirmation and record `error: live keys detected` for that step. When you do complete it, record what the confirmation says about the end date, and hand the entitlement question to FLOW-005, which owns whether access is actually revoked at period end. PAY-012 owns whether the provider's customer portal is configured with cancellation enabled; if a portal is the mechanism here, cite that check rather than re-testing the dashboard configuration.
evidence: `sign-up: <n> steps (<screens>)`; `cancel: <n> steps (<screens>)`; the cancel entry point file:line or `no in-app cancel path found`; every dark-pattern instance quoted with its file:line; what the confirmation states about the end date; `cancellation completed in test mode` or `stopped before confirmation — <reason>`.
fix_hint: The implementation note must put a working cancel control in the account or billing page, reachable in no more clicks than sign-up takes and without contacting a human, and must remove the specific dark patterns this check found rather than describing them generally. Retention offers may stay if they are one screen with a plainly labelled decline that completes the cancellation. The confirmation should state the exact date access ends, and the flow should cancel at period end rather than immediately unless the user chose otherwise.

### COMP-012 Auto-renewal terms disclosed at checkout with affirmative consent
severity: high
tier: static
fix: guided
when: features.subscriptions
why: Automatic renewal statutes exist because people agreed to something recurring while believing it was one-off. The requirements are consistent across the state laws: the renewal terms must be presented clearly and conspicuously, in visual proximity to the control the consumer uses to agree, **before** the subscription starts; consent must be affirmative and specific to those terms rather than bundled into a general terms-of-service checkbox; and an acknowledgement containing the terms and the cancellation instructions must be sent afterwards in a form the consumer can keep. Getting this wrong makes every renewal charge disputable.
verify:
  static: Read the checkout surface, which on most stacks is one of three shapes (stack ref: "routes and handlers"): a hosted page created server-side (a Stripe Checkout session with `mode: "subscription"`, where the disclosure is partly the provider's and partly yours via `custom_text` and `consent_collection`), an embedded element with your own surrounding markup, or a fully custom form. "Visual proximity" is the operative phrase, so a footnote at the bottom of a long pricing page or a link to the terms does not satisfy it — record where each fact appears relative to the button. tier: static
fix: guided
when: features.biometrics
why: Illinois's Biometric Information Privacy Act carries a private right of action with statutory damages, which is why it produces class actions where other privacy statutes produce letters. A 2024 amendment settled how those damages accrue: repeated collections from the same person by the same method are a single violation rather than one per scan, so the exposure is per person per modality — a material reduction from the per-scan reading, and still a class-wide number on any product with users in Illinois. Its requirements are specific and none of them are satisfied by a general privacy policy: a written release obtained before collection, a publicly available written retention and destruction schedule, no sale or profit from biometric identifiers, and no disclosure without consent. Texas and Washington have comparable statutes enforced by their attorneys general.
verify:
  static: Establish first what the product actually does, because this is where most findings in this check evaporate and the distinction is the single most useful thing to get right. `expo-local-authentication`, `react-native-biometrics`, `LocalAuthentication`, `BiometricPrompt`, and WebAuthn platform authenticators all ask the operating system to verify the user; the template stays in the device's secure enclave, your code receives a boolean or a signed assertion, and you never collect a biometric identifier at all. That is not in scope for BIPA-style consent and saying it is wastes everyone's time. What is in scope is the app collecting or deriving a biometric identifier itself: face matching or liveness checks on an uploaded selfie, voiceprints, fingerprint templates, retina or hand geometry, or sending an image to a third-party identity-verification or face-recognition vendor. Grep the call sites and the storage layer for which of the two shapes this is, and say so in the first line of evidence. If it is the second shape, check four things. Consent: a written release captured before collection, specific to biometrics, separate from the general terms checkbox, stored with a timestamp and the text version (the COMP-035 pattern) — a policy paragraph is not a release. Retention schedule: a published, written schedule with a destruction trigger; the statutory default to compare against is destruction when the purpose is satisfied or within three years of the individual's last interaction, whichever comes first. Storage: the identifier stored with at least the care used for other confidential information, which in practice means encrypted at rest and access-controlled (DAT-021), plus an actual deletion job implementing the schedule rather than a promise of one. Disclosure: whether any vendor receives the biometric, which needs its own consent, and whether anything about the arrangement could be characterised as profiting from it. Check the platform purpose strings too (`NSFaceIDUsageDescription`), since a missing one is a store rejection independent of any of this. Mark the state-by-state details `verify current text with counsel`.
evidence: `on-device OS authentication only — no biometric identifier collected` with the call-site file:line, or the collection path file:line and what is stored where; the consent capture mechanism and its record fields, or `no separate biometric consent`; the published retention schedule quoted or `absent`; the destruction job file:line or `schedule with no implementation`; the encryption and access controls on the stored identifier; any vendor receiving it; the purpose string.
fix_hint: If the product only asks the OS to verify the user, the fix is to say so accurately in the privacy policy and stop there. If it collects or derives a biometric identifier, the draft needs a standalone written release presented before the first capture and stored with a timestamp and version, plus a published retention and destruction schedule with a concrete trigger, and the implementation note needs an actual scheduled destruction job, encryption at rest, and a named list of any vendor that receives the identifier. Route all of it past counsel before launch; this is the check where the statutory damages accrue per person per modality and there is a private right of action behind them.

### COMP-016 Emails: unsubscribe link, honest subject, physical address
severity: high
tier: static
fix: easy
when: features.email_sending
why: CAN-SPAM's requirements are few, mechanical, and each carries a per-message penalty: a functioning opt-out mechanism in every commercial message, opt-outs honoured within ten business days, a valid physical postal address, non-deceptive subject lines and headers. The reason to fix it before launch rather than after is deliverability: the mailbox providers enforce the same list harder and faster than the regulators do, and a template missing its unsubscribe footer teaches Gmail to file the whole domain in spam.
verify:
  static: Enumerate every template the product sends (stack ref: "routes and handlers", "background jobs" — an `emails/` or `templates/` directory, React Email components, ActionMailer views, Django templates, or a provider-hosted template referenced by id, which you must note as unreadable from the repo rather than passing silently). Write that list to `.pre-launch/compliance/emails.txt` — one row per template with its path and its send path — because COMP-017 works from the same enumeration and building it twice produces two different lists. Classify each as transactional or commercial; COMP-017 owns the separation, this block owns the required contents. For every commercial one, check three things and quote them: an unsubscribe link that is present in the template body and resolves to a real route rather than a placeholder or a bare `#`; a physical postal address, which must be a real mailing address and not `[Your Address]` or an email address; and a subject line that describes the message honestly, with the specific fails being a marketing message dressed as a transactional one ("Your account requires attention" for a feature announcement) and a false `Re:` or `Fwd:` prefix. Then check the two things around the templates: that the unsubscribe route actually records the opt-out in a way the sending path reads before every send, rather than only writing a row nobody queries — that is the ten-business-day requirement in code — and that suppression is checked at send time for every commercial send path including any one-off script. Add the deliverability layer, since it is the same footer work: the `List-Unsubscribe` and `List-Unsubscribe-Post: List-Unsubscribe=One-Click` headers are required by the major mailbox providers' bulk sender rules, and most providers add them only if you configure it. FLOW-014 owns whether the link works end to end and HYG-016 owns rendering and from-address configuration; cite both rather than duplicating them.
evidence: one row per template — `<template file:line> — <transactional|commercial> — unsubscribe: <present with route | absent>, address: <quoted | absent>, subject: "<line>"`; the suppression check at the send path file:line or `opt-out stored but not checked before send`; the `List-Unsubscribe` header configuration or `not set`; any provider-hosted template noted as unread.
fix_hint: Add one shared footer partial carrying the unsubscribe link and the company's real postal address, and include it in every commercial template so a new template inherits it by default. Make the send path check the suppression list before every commercial send, including one-off scripts, and enable the `List-Unsubscribe` and one-click post headers in the email provider's configuration. Rewrite any subject line that describes a marketing message as an account or transactional one.

### COMP-017 Transactional vs marketing email separated; double opt-in for EU
severity: medium
tier: static
fix: guided
when: features.email_sending
why: These are two different legal categories with two different rules, and the failure is always the same: a "product update" that is really an upsell, sent to everyone including the people who opted out, through the transactional path because that path has no suppression check. That single decision turns a compliance question into a deliverability incident, because recipients who cannot unsubscribe mark it as spam instead.
verify:
  static: Read `.pre-launch/compliance/emails.txt` and classify every template COMP-016 enumerated into transactional (a password reset, a receipt, a security alert, a shipping notice — messages the user's own action triggered and that carry no promotional content) and commercial (announcements, newsletters, re-engagement, upgrade prompts, anything with a call to action to buy). Watch for the hybrid, which is the actual problem: a receipt with a "try our Pro plan" block at the bottom is commercial for the purposes of the rules. Then read the sending code and confirm the two categories travel different paths — different sending function, different provider stream or subdomain, and a suppression check on the commercial one only. Look for the consent state itself in the schema: a marketing opt-in column, a subscription record, or a list membership at the provider, with a timestamp. Then check how consent is collected at sign-up: a pre-ticked marketing box is invalid consent under GDPR Art. 7, and so is bundling marketing consent into the same checkbox as the terms of service, because consent must be freely given and specific and cannot be a condition of the service (Art. 7(4)). Be precise about the double opt-in question rather than repeating the folklore: the GDPR requires that consent be demonstrable (Art. 7(1)), and confirmed opt-in is the mechanism most commonly used to demonstrate it, and is effectively the expectation in some member states, notably Germany — but the legal requirement is provable consent, not the double opt-in mechanism specifically. Note also the soft opt-in available under ePrivacy for existing customers being emailed about similar products, where an opt-out was offered at collection and in every message. Record which basis this product is relying on and mark the member-state specifics `verify current text with counsel`.
evidence: the template classification table with any hybrid flagged; the two send paths with file:line and which one checks suppression; the consent column or list membership with whether a timestamp is stored; the sign-up consent control quoted with `pre-ticked`, `bundled with terms`, or `separate and unticked`; whether a confirmation step exists for new subscribers; the basis being relied on for EU recipients.
fix_hint: The implementation note must separate the send paths so commercial mail cannot leave without a suppression check, move any promotional block out of transactional templates, and record marketing consent as its own column or list membership with a timestamp and the text the user agreed to. The sign-up form needs a separate, unticked marketing checkbox that is not a condition of registration. For EU recipients, add a confirmation step for new subscribers so consent is demonstrable, and note that the exact requirement varies by member state.

### COMP-018 No fake or placeholder testimonials, reviews, logos, or stats
severity: high
tier: static
fix: easy
why: The FTC's rule on consumer reviews and testimonials, in force since 2024, makes fake and misrepresented reviews and testimonials a violation carrying civil penalties per violation, and it covers testimonials from people who do not exist, insider reviews without disclosure, and unsubstantiated claims about a product's popularity. But the reason this is high severity at launch is more prosaic: pre-launch marketing pages are full of the template's placeholder quotes, and shipping "Sarah M., Marketing Director" over a stock avatar next to "Join 10,000+ happy customers" on day one, with a users table holding four rows, is a claim you have made about a product nobody has used yet.
verify:
  static: Sweep the marketing surfaces — the landing page, pricing, about, and any content directory feeding them (stack ref: "routes and handlers") — for four things, and save what you find to `.pre-launch/compliance/marketing-<n>.txt` so the quotes can be cited. Testimonials and quotes: find the component or data array holding them and check each attributed person and company against reality. The tells are generic names (`Jane Doe`, `John Smith`, `Sarah M.`), a company that does not exist, a photo from a stock or avatar service (`unsplash`, `pexels`, `randomuser.me`, `pravatar`, `avatar-1.jpg`, `user-2.png`), and the giveaway of a testimonial array committed alongside a `TODO` or `// replace with real quotes` comment. Customer or press logos: a logo wall is a claim of a relationship, so check whether each named company is a customer, and treat "as seen in" logos with particular care since those are the ones that get litigated. Counts and ratings: grep for the pattern group `\d+[,\d]*\+? (users|customers|companies|teams)`, `\d+(\.\d)? stars`, `\d+ reviews`, `trusted by`, `join \d+`, and for each ask where the number comes from — a hardcoded string in a component with no query behind it and no external source is unsubstantiated by definition, and comparing the claim against the actual row count in the relevant table (stack ref: "data access") turns this from an opinion into evidence. Ratings pulled from a real review platform pass; ratings typed into the page do not. Finally, badges and certifications, which overlap COMP-030: a `SOC 2` or `HIPAA compliant` badge with no report behind it belongs in that check, but note it here if the sweep finds it. HYG-003 owns placeholder copy generally; this block owns the subset that is a claim about other people.
evidence: one row per item — `<file:line> — testimonial "<quote>" attributed to <name>, <company>; photo <src>` with the verdict and the tell that produced it; each logo with `customer confirmed` or `relationship unknown`; each number quoted with its source (`hardcoded, no query`, `queried from <table>`, `from <review platform>`) and, where checkable, the actual count beside it.
fix_hint: Remove every testimonial, logo, count, and rating that cannot be sourced, rather than softening the wording — an unattributable quote is not fixed by removing the surname. Replace placeholder quotes with real ones carrying the person's consent, use only logos of companies that are actually customers, and drive any count or rating from a query or from the review platform's own widget so it cannot drift from the truth. If there are no customers yet, ship the page without a social-proof section.

### COMP-019 GDPR: lawful basis documented; export and delete request flow; DPAs with processors; breach plan
severity: high
tier: static
fix: guided
why: The GDPR's obligations are machinery, not text: a basis for each processing purpose, a way for a person to get their data out and get it deleted inside a deadline, a contract with every company you hand data to, and a plan that works at 2am when the deadline is 72 hours. A privacy policy describing all four while none exist is the finding this check is for, and it is a worse position than having no policy, because the policy is the evidence.
verify:
  static: Four parts, each with its own evidence. Lawful basis, Art. 6: for each processing purpose the product has — running the account, billing, product analytics, marketing, AI features, support — find whether a basis is identified anywhere, whether in the policy, a record of processing activities, or an internal document in the repo. Contract covers running the service; legitimate interests requires a balancing assessment you should look for rather than assume; consent requires the record COMP-007 checks. Note that the Art. 13/14 notice content is COMP-001's territory and cite it. Export and delete, Arts. 15, 17, and 20: look for actual routes, not an email address — a data export that produces a machine-readable file of the user's own data, and the deletion path COMP-010 and DAT-020 cover. Check the response deadline is achievable: Art. 12(3) gives one month from receipt, extendable by two for complex requests, and a manual process where one engineer writes SQL is achievable at ten users and not at ten thousand, so record which it is. If the flow is an inbox rather than a route, say so and say who reads it. Processor contracts, Art. 28: every vendor in `.pre-launch/compliance/inventory.json` that processes personal data on your behalf needs a written contract containing the Art. 28(3) terms; in practice most vendors publish a standard DPA accepted in their dashboard or incorporated by reference into their terms. The repo can rarely prove this, so the honest output is a list — vendor by vendor, whether a DPA is known to be in place, unknown, or absent — which doubles as the input to COMP-033's subprocessor page. Breach plan, Arts. 33 and 34: notification to the supervisory authority within 72 hours of becoming aware of a personal data breach, and to affected individuals without undue delay where the risk to them is high. Look for a documented plan naming who decides, who notifies, and what gets logged, plus the detection that makes "becoming aware" possible at all (the alerting the reliability domain owns). A plan that exists only as an intention is the common state; record it as absent rather than partial. Whether the GDPR applies is itself a question: Art. 3(2) reaches companies outside the EU that offer goods or services to people in the EU or monitor their behaviour, so a publicly reachable product that accepts EU customers should be assumed in scope unless counsel says otherwise — say that rather than deciding it.
evidence: per processing purpose, the basis found and where, or `no basis documented`; the export route file:line and its output format, or `no export mechanism`; the deletion route with a cite to COMP-010 and DAT-020; the request deadline mechanism and whether it is manual; the vendor-by-vendor DPA status table; the breach plan document or `no documented breach plan`, plus the detection path that would trigger it.
fix_hint: The drafts and implementation notes must cover four separate deliverables rather than one document: a short record of processing purposes with a basis for each, a self-service export producing the user's own data in a machine-readable format, a tracked intake for rights requests with the one-month clock on it, and a breach response plan naming the decision-maker, the notification path, and the 72-hour deadline. Alongside them, a checklist of vendors whose standard DPA still has to be accepted in their dashboard, generated from the inventory.

### COMP-020 CCPA/CPRA: Do Not Sell or Share link; Global Privacy Control honored
severity: high
tier: local
fix: guided
why: This is the rare privacy obligation with a mechanical, externally testable answer: either the footer has the link and the site honours the browser signal, or it does not. California regulators have already brought enforcement over exactly this pair, and the Global Privacy Control half is the one that gets missed because it is invisible — nothing in the interface shows whether the header was read.
verify:
  static: Determine first whether the obligation is triggered, using COMP-003's vendor list: an advertising or cross-context behavioural advertising vendor means sharing, which means the opt-out applies. Then look for four things in the code. The opt-out link itself, conventionally titled "Do Not Sell or Share My Personal Information", in the footer and reachable from every page; note that a business may instead process opt-out preference signals and say so in its policy, which is an alternative route to the same obligation rather than an exemption. The notice at collection, which must appear at or before the point of data collection. A rights request route for the access, deletion, and correction rights, which may be the same one COMP-019 found. And the Global Privacy Control handling: the browser sends `Sec-GPC: 1` as a request header and exposes `navigator.globalPrivacyControl` in the page, and California's regulations treat that signal as a valid opt-out request that must be honoured without asking the user to confirm. Grep the source for `Sec-GPC`, `globalPrivacyControl`, and the CMP's signal option, and check whether the CMP is configured to read it — most support it behind a flag that is off by default, which is the single most common failure here.
  local: Against the production build, make the same request twice and compare. First plain: `curl -s "<local.url>/" -o .pre-launch/compliance/plain.html`. Then with the signal: `curl -s -H "Sec-GPC: 1" "<local.url>/" -o .pre-launch/compliance/gpc.html`. Diff them and inspect the consent state the page renders — the consent cookie in the response headers, the initial state embedded in the markup, whether the advertising script tags from the inventory are present, and whether the banner defaults to reject. A byte-identical response with the ad tags in both is the fail; it means the signal was not read on the server, and if the CMP does not read the client-side property either, nothing honours it. Then confirm the footer link exists and resolves: `grep -io "do not sell[^<]*" .pre-launch/compliance/plain.html` and fetch whatever it points at. Note honestly what a header probe cannot see: a purely client-side CMP may honour `navigator.globalPrivacyControl` while the server response is identical, so if the static half found that configuration, record the server result as inconclusive rather than as a failure and say which evidence you have.
evidence: the advertising vendors that trigger the obligation; the footer link's markup and the URL it resolves to, or `no Do Not Sell or Share link`; the notice at collection or its absence; the `Sec-GPC` and `globalPrivacyControl` handling with file:line or `signal not read anywhere`; the plain-versus-GPC response diff summarised — consent cookie, ad tags present or absent, banner default — for each of the two requests; the CCPA threshold note.
fix_hint: The implementation note must add the opt-out link to the global footer pointing at a working request route, add the notice at collection to the pages where data is first collected, and turn on the consent tool's Global Privacy Control option so the signal is treated as an opt-out without a confirmation prompt — naming the specific configuration flag for the CMP in use. The privacy policy draft must describe the opt-out route and say that opt-out preference signals are honoured. Note that other state laws also require honouring universal opt-out signals, so the same switch covers more than California.

### COMP-021 COPPA / age gating if minors may use the product
severity: high
tier: static
fix: guided
when: features.minors_possible
why: COPPA applies to operators of services directed to children under 13 and to any operator with actual knowledge that it is collecting personal information from a child under 13 — and "actual knowledge" is the trap, because a birthday field or a support email saying "I'm 11" creates it. Once it applies, the requirement is verifiable parental consent before collection, which is a mechanism, not a checkbox, and it is not something to discover after launch.
verify:
  static: First decide, and record, whether the service is child-directed on the factors that matter (subject matter, visual and audio content, animated characters, child celebrities, advertising placed in child-oriented media) or merely general-audience with minors possible, because the obligations differ sharply. Then look for the age gate: a date-of-birth or age field at sign-up, or an age screen. Two properties decide whether it works. It must be neutral — asking for a birth date or an age, not "Are you over 13?" with a yes button, because a gate that signals the right answer is not a gate. And it must be non-retryable: check whether a user rejected for being under 13 can immediately reload and enter a different date, which requires a session or cookie flag; without one the gate records nothing and blocks nobody. Then check what happens on an under-13 answer: collection must stop, which means no account row, no email captured, and no analytics or advertising SDK firing for that visitor. Grep the sign-up handler for what is written before the age check runs — an email stored on the first step of a multi-step form, before the birthday screen, is collection from a child. If the product is child-directed or has actual knowledge, look for the rest of the machinery: a direct notice to the parent, a verifiable parental consent mechanism, a children's section in the privacy policy, no conditioning participation on collecting more than is reasonably necessary, deletion on parental request, and no behavioural advertising to children. Note the neighbouring regimes without conflating them: the UK's Age Appropriate Design Code applies to services likely to be accessed by children up to 17 and is a design standard rather than a consent rule; several US states have added minor-safety and age-verification duties; and the GDPR's age of consent for information-society services is 16 by default and may be lowered to as young as 13 by member state law. All of that is `verify current text with counsel`.
evidence: `child-directed` or `general audience, minors possible` with the factors that decided it; the age gate's field and file:line, or `no age gate`; whether it is neutral and whether a rejected user can retry, with the flag's file:line or its absence; what the sign-up handler writes before the age check; the parental consent mechanism or `none`; whether analytics and advertising SDKs are suppressed for under-13 visitors; the children's policy section quoted or absent.
fix_hint: The implementation note must put a neutral, non-retryable age screen before any collection — a date field, a stored rejection flag, and no data written until it passes — and must suppress every analytics and advertising SDK for a visitor who has not cleared it. If the product is child-directed or will knowingly have under-13 users, the draft needs a children's privacy section, a direct notice to parents, and a described verifiable parental consent mechanism; that mechanism is a build, not a paragraph, so flag it as scope rather than as copy, and get counsel to confirm the age thresholds for each market.

### COMP-022 PCI: card numbers never touch application servers
severity: critical
tier: static
fix: guided
when: features.payments
why: There is one scope decision in payments that determines everything else, and it is made in the first hour of the integration: if a card number never reaches your servers, your PCI obligations collapse to the shortest self-assessment questionnaire and a breach of your database exposes no card data. If it does reach them, you have inherited an audit programme, encryption and key management requirements, and a class of incident you are not staffed to handle. This check exists because the second path is one hand-rolled form away, and because it is very hard to reverse after launch.
verify:
  static: Establish which shape the integration is (stack ref: "routes and handlers" for the checkout surface, "known traps" for this processor's integration pitfalls; the PAY domain owns the integration's correctness and this block owns only the scope question, so cite its findings rather than re-deriving them). The shape that passes: the card is entered into a surface the processor owns and your origin cannot read — a hosted checkout page or payment link, an embedded iframe such as Stripe Elements or the Payment Element, Braintree hosted fields, a PayPal button — and your server only ever sees an opaque token or payment method id. The shapes that fail, and the greps that find them: a form field for the number in your own markup, `grep -rniE "card_?number|cardnumber|\bcvv\b|\bcvc\b|card\[number\]|expiry|exp_month" <source dirs>` over components and handlers; a server-side call constructing a card object directly (`paymentMethods.create` with raw card fields, a gateway call taking a PAN); or any storage of the number or the security code, which is the absolute rule — the security code must never be stored after authorisation under any circumstances, and the PAN must not be stored unless you have built the encryption and key management to do it. Then check the two indirect leaks, which are how card data reaches servers on integrations that got the form right. Logging: a request logger or an error tracker capturing form bodies or breadcrumbs will happily ship a PAN to a third party (stack ref: "error handling and logging"); look for redaction or field allowlists and check the error tracker's default capture settings. And support tooling: a free-text field where an agent pastes a card number is the same problem with a slower fuse. Finally, name the scope question rather than answering it: hosting the page that embeds the processor's iframe puts a merchant in a different self-assessment category from using a fully hosted page, because scripts on your page can affect the payment surface, and the applicable questionnaire and any script-integrity requirements depend on the processor's guidance and, above certain volumes, on a qualified assessor. State the shape you found, state that the questionnaire determination belongs to the processor and counsel, and do not assert a level.
evidence: the payment surface with its component file:line and which shape it is; every grep hit for card fields with file:line and whether it is a real card field or a false positive; any schema column holding card data; the logging and error-tracker configuration with what it redacts; `no PAN reaches application servers` or the exact path by which it does.
fix_hint: If any card field is your own, the implementation note must replace it with the processor's hosted field, iframe, or checkout so the browser posts the card directly to the processor and your server receives only a token — that is the whole fix and everything else is downstream of it. Then add redaction for payment fields in the request logger and the error tracker, remove any card column from the schema, and never store the security code. Record the resulting scope with the processor before completing any self-assessment.

### COMP-023 HIPAA / health-data handling and BAAs
severity: critical
tier: attest
fix: none
when: features.health_data
why: The most valuable output of this check is usually the finding that HIPAA does not apply. A direct-to-consumer wellness or symptom app with no provider or plan relationship is typically neither, and is instead governed by the FTC's Health Breach Notification Rule and by state health-privacy laws, which have different and sometimes stricter duties. verify:
  static: Gather the facts the determination needs. What health-shaped data does the product store — diagnoses, medications, symptoms, treatment, appointments, insurance or claims identifiers, provider names — and where (stack ref: "data access")? Are there integrations that only exist in a covered context (an EHR or FHIR client, an Epic or Cerner integration, an eligibility or claims API, an e-prescribing service)? And which vendors from `.pre-launch/compliance/inventory.json` would touch that data if it is PHI — the hosting provider and database, but also the two that are always forgotten, the error tracker (which captures request payloads) and the AI provider (which receives whatever is in the prompt).   attest: Ask the user, and record the answers verbatim: is the company a covered entity or acting as a business associate for a covered-entity customer; has counsel made that determination or is it an assumption; if it is in scope, is a signed business associate agreement in place with every vendor on the list above; and has the customer-facing BAA been reviewed by counsel. If the determination is that HIPAA does not apply, record the reason given, and note that the FTC Health Breach Notification Rule and state consumer-health-data laws (COMP-024) apply instead rather than leaving the impression that nothing does.
evidence: the health-data fields and where they are stored, file:line; the customer type and any covered-context integration; the vendor list that would need a BAA, error tracker and AI provider included; the user's verbatim answers on covered status, counsel involvement, and each vendor's BAA; `HIPAA determined not to apply — <reason given>` where that is the answer, with the alternative regime named.

### COMP-024 Other US state privacy laws; Washington MHMD if health-adjacent
severity: medium
tier: attest
fix: none
why: There is no longer a single US privacy answer. Roughly twenty states have comprehensive privacy laws with broadly similar duties and materially different thresholds, and tracking them individually is not something a pre-launch team can do. The practical approach is to build to the strictest common denominator and to know which of the outliers apply. Washington's My Health My Data Act is the outlier that catches products nobody thinks of as health apps, and it has a private right of action, which is what makes it worth naming separately.
verify:
  static: Establish the exposure. Which states' residents will realistically use this, and does the product do any of the things the state laws single out: targeted advertising, sale of personal information, profiling with legal or similarly significant effects, or processing sensitive data (which in most of these statutes includes health, precise geolocation, biometrics, race, religion, sexual orientation, immigration status, and children's data)? Those are the triggers for opt-out rights, consent requirements, and data protection assessments across the group. Check whether the product recognises universal opt-out signals, since several of these states require it (COMP-020's switch covers this too). Then run the Washington test carefully, because its definition of consumer health data is far broader than HIPAA's PHI: it reaches information that identifies a consumer's past, present, or future physical or mental health status, including inferences drawn from non-health data. A cycle tracker, a fitness or sleep app, a meditation or mood product, a supplement store, and a symptom search feature can all be in scope. Where it applies, it requires a separate consumer health data privacy policy with its own homepage link — not a section inside the main policy — separate consent before collection, separate authorisation before sharing or selling, and it comes with a private right of action. Nevada has a comparable but narrower law. Record whether such a policy and link exist. Mark all thresholds and state lists `verify current text with counsel`.
  attest: Ask the user, and record verbatim: which states they expect residents in, whether counsel has scoped which comprehensive privacy laws apply at their expected volumes, whether the product handles anything that could be consumer health data under a broad definition, and whether a separate Washington-style health data policy has been prepared. Note in the finding that the comprehensive-law duties overlap heavily, so a single build — notice, opt-out of targeted advertising and sale, consent for sensitive data, honouring universal opt-out signals, a documented assessment for the risky processing — satisfies most of them at once and is a better use of pre-launch time than a state-by-state matrix.
evidence: the sensitive-data categories the product actually processes with file:line; whether targeted advertising, sale, or profiling occurs, citing COMP-003; universal opt-out signal handling, citing COMP-020; the Washington analysis with the health-data inference argument stated either way; the separate health policy and its homepage link, or `absent`; the user's verbatim answers on states, counsel scoping, and health-adjacency.

### COMP-025 TCPA consent for SMS
severity: high
tier: static
fix: guided
when: features.sms
why: The TCPA carries statutory damages of several hundred to fifteen hundred dollars per message, with a private right of action and a healthy plaintiffs' bar, which makes a marketing SMS list built without documented consent one of the few compliance failures that can be arithmetically fatal. Marketing texts require prior express **written** consent with specific disclosures; informational and transactional texts require prior express consent, a lower bar but still consent.
verify:
  static: Find the send path (stack ref: "background jobs", plus the Twilio or Vonage client) and separate marketing sends from transactional ones — a one-time passcode is not a marketing message, and a "we miss you, here's 20% off" is, regardless of which function sent it. Then find where consent is captured and what was disclosed at that moment, because the disclosure is the requirement. For marketing, the consent capture should sit next to language stating that the consumer agrees to receive marketing text messages at the number given, that consent is not a condition of any purchase, the message frequency, and that message and data rates may apply. Check that the checkbox is unticked by default, that it is not bundled with the terms of service, and that the phone number field is not being repurposed from a 2FA or shipping context — consent given for a security code does not extend to marketing. Then check the consent record: it must be retrievable per recipient with a timestamp, the number, and the exact disclosure text or a version identifier for it (the COMP-035 pattern), because in a dispute the record is the entire defence. Then the operational requirements: STOP must unsubscribe and HELP must return a response; the aggregator handles those for its own numbers but the application must also stop sending, so look for the opt-out state being written back and checked before every send. Quiet hours — no marketing calls or texts outside 8am to 9pm in the recipient's local time — need the recipient's time zone, so check whether one is stored at all. And check for A2P 10DLC brand and campaign registration, which US carriers require for application-to-person messaging and without which delivery is filtered regardless of consent; that is a provider-dashboard fact, so record it as a question for HYG-001.
evidence: the marketing and transactional send paths with file:line; the consent capture control quoted with its disclosure text, or `no marketing SMS consent captured`; whether the box is pre-ticked or bundled; the consent record's fields per recipient; the STOP and HELP handling with file:line and whether the app checks opt-out before sending; whether a recipient time zone is stored; the 10DLC registration status or `unconfirmed`.
fix_hint: The implementation note must put the four required disclosures immediately beside an unticked, unbundled consent checkbox on the number capture, store a per-recipient consent record with the timestamp, the number, and the disclosure version, and make every marketing send check the opt-out state first. Add STOP and HELP handling that writes back to that state, store a time zone so quiet hours can be respected, and confirm 10DLC brand and campaign registration with the provider before the first campaign.

### COMP-026 All fees, tax, and currency shown before checkout; refund policy stated
severity: high
tier: local
fix: guided
when: features.payments
why: A price the customer sees for the first time on the confirmation screen — or on their card statement — is the most reliable source of chargebacks and refund requests there is, and it is a regulated failure in most markets: EU and UK consumer rules require prices shown to consumers to include VAT, and US price-transparency rules have moved sharply against mandatory fees disclosed late. Currency is the version that surprises everyone: a European customer charged in dollars pays a conversion fee they were never shown.
verify:
  static: Read the pricing page and the checkout construction together (stack ref: "routes and handlers"). List every component of the final amount: the base price, any platform or service fee, tax, shipping, and currency conversion. For each, find where it is first shown to the user. Then check the tax configuration specifically, since it is the piece most often left at its default — with Stripe that is `automatic_tax` and each price's `tax_behavior`, where `exclusive` means tax is added on top and `inclusive` means the displayed price already contains it. Selling to EU or UK consumers with tax exclusive and no automatic tax means the price displayed is not the price they must legally be shown, and separately means you may be under-collecting VAT; flag both, and mark the registration and OSS questions for the company's accountant and counsel. Currency: find how it is chosen and whether the displayed currency is the one that will be charged. Mandatory fees: any fee the customer cannot avoid must be in the price the customer first sees, not added at the end — that is the direction of both the FTC's rule on unfair or deceptive fees and California's pricing law, and while their exact scope differs, an unavoidable fee revealed at the last step fails the principle in every version. Then the refund policy: it must exist as a page or a clearly headed section, state the conditions and the window, and be reachable before purchase. For EU and UK consumers there is a further point: distance selling gives a 14-day right of withdrawal, and the exception for digital content supplied immediately applies only where the consumer expressly consented to immediate performance and acknowledged losing the right — so check whether the checkout captures that acknowledgement, since almost none do. Mark the jurisdiction-specific parts `verify current text with counsel`.
  local: Walk the flow against the production build as the test account with test-mode keys, saving each step as `.pre-launch/compliance/checkout-<n>.html`, and write down every number the user sees at each screen: the pricing page, the plan selection, the checkout page before payment details, and the confirmation. The fail is any component of the total that appears for the first time at a later step than the one where a reasonable person decided to buy — most often tax on the final screen, a platform fee inside the checkout, or a currency that changes at the processor. Stop before completing the payment if keys are not detectably test-mode and record `error: live keys detected`. Also confirm the refund policy is linked from the checkout page itself and not only from the footer.
evidence: the price components with `first shown at <step>` for each; the tax configuration values quoted with the consumer market they will apply to; the currency selection logic file:line and the currency shown at each step; the per-step totals from the saved checkout pages; the refund policy route with its conditions and window quoted, or `no refund policy`; whether the immediate-performance acknowledgement is captured.
fix_hint: The implementation note must show the full amount the customer will be charged — base price, mandatory fees, tax, and the correct currency — on the first screen where the price is presented, with tax configured inclusive for consumer markets that require it and automatic tax enabled where you sell across borders. The refund policy draft needs the window, the conditions, and the process, published at a stable URL and linked from the checkout page. For EU and UK digital sales, add the express consent to immediate performance and the acknowledgement of losing the withdrawal right, and have the tax registration position confirmed by an accountant.

### COMP-027 Legal name, address, and contact on site
severity: medium
tier: local
fix: easy
why: Every regime that governs online selling requires the customer to know who they are contracting with and where that entity is: the EU's e-commerce rules require the provider's name, geographic address, and contact details, with Germany's Impressum requirement the strictest implementation; UK company law requires the company name, registered number, and registered office on the website; US state privacy laws require a contact route in the policy. It is also the cheapest trust signal on the site, and its absence — a product taking card payments from an anonymous entity with a Gmail address — reads exactly as it sounds.
verify:
  static: Look for the identity in the four places it should agree: the footer, a contact or about page, the terms of service, and the privacy policy. Grep the saved text and the footer component for an entity suffix (`Ltd`, `Limited`, `LLC`, `Inc`, `Corp`, `GmbH`, `UG`, `B.V.`, `Pty`, `S.r.l.`, `AB`, `Oy`), a street address, a company or VAT registration number, and a contact route. The failures are specific: `[Company Name]` or `Your Company` left in the template; an `example.com` or personal address as the only contact; a footer naming a trading name with no legal entity behind it anywhere; and, the one worth catching, a terms page naming one entity and a privacy policy naming another, which happens when two templates were pasted from two sources and means neither document says who the counterparty is. Note that a home-based founder using their home address is a real problem with real solutions (a registered office or agent service), so the finding should say the address is missing rather than instructing anyone to publish their flat.
  local: Fetch the home page from the production build and extract the footer to `.pre-launch/compliance/footer.txt`, then check the same details render on the pages a customer actually sees before paying — the pricing page and the checkout page — rather than only on a contact page. Follow the contact route: a `mailto:` address should be at a domain you control and, where possible, confirm it is not a placeholder; a contact form's handler should have a real recipient (REL-028 owns whether that path reaches a human, so cite it). Record what a visitor can actually learn about who they are buying from without logging in.
evidence: the legal entity name and address as they appear in each of the four places, with file:line, or `absent` per place; any mismatch between the entity named in the terms and in the privacy policy, both quoted; the registration or VAT number if required for this market; the contact route and where it leads; the footer as rendered on the home, pricing, and checkout pages.
fix_hint: Put the legal entity name, its registered address, a company or VAT registration number where the market requires one, and a contact email in the global footer so every page carries it, and make the terms and the privacy policy name the same entity. Where the founder's home address is the registered one, use a registered office or agent service rather than omitting the address.

### COMP-028 Open-source, font, and image licenses complied with; attributions present
severity: medium
tier: static
fix: guided
why: Every dependency arrived with a contract attached, and two of those contracts can change what you are allowed to do with your own product. A copyleft licence in code you distribute — a browser bundle counts as distribution, and the AGPL's network clause reaches server-only code — can require you to publish source you did not intend to publish. A commercial font or icon set used without a web licence is a straightforward invoice from a company whose business model is finding exactly this. Both are cheap to fix before launch and awkward afterwards.
verify:
  static: Get the licence list without installing anything. If a licence tool is already a dependency, use it. Otherwise, if `node_modules` is present, read the fields out of the installed manifests — `python3 -c "import json,glob,collections;exec('def lic(p):\n try: l=json.load(open(p)).get(\'license\')\n except Exception: return \'UNREADABLE\'\n return (l.get(\'type\') if isinstance(l,dict) else l) or \'MISSING\'');print(collections.Counter(map(lic,glob.glob('node_modules/*/package.json')+glob.glob('node_modules/@*/*/package.json'))).most_common())" > .pre-launch/compliance/licenses.txt` — which gives the distribution and the counts of unlicensed and unreadable packages. Two things in that command are load-bearing and a shorter version of it is wrong: `license` may be a string or the legacy object form `{"type": "MIT", "url": "..."}`, so it is normalised with `isinstance` before counting (feeding the dict straight into a `Counter` raises `TypeError: unhashable type: 'dict'` and kills the whole scan), and one malformed or truncated manifest in a large tree would otherwise abort it, so the parse is wrapped and counted as `UNREADABLE`. If there is no `node_modules` — a clean checkout, or a Python, Ruby, or PHP project — fall back to the lockfile or the environment metadata instead: `package-lock.json` and `pnpm-lock.yaml` carry a `license` field per package, and `pip show`, `bundle list`, or `composer show` give the equivalent. Save whatever form you use to that file and cite it, because the list is long and evidence needs to point at it rather than reproduce it. Three groups matter. Copyleft in distributed code: GPL and AGPL, and to a lesser degree LGPL where static linking applies, plus the SSPL — for each hit, decide whether it actually ships (a build-time devDependency is a different question from a package imported into the client bundle or linked into a mobile binary) and say which, because the answer changes the finding entirely. Missing or non-standard licences: a package with no `license` field, `UNLICENSED`, or a custom text is unresolved rather than permissive, and should be listed for a human. Notice retention: MIT, BSD, and Apache-2.0 all require the copyright notice and licence text to travel with distributed copies, which for a web app means a licences page or a bundled notice file — check whether one exists, since almost none do and it is a genuine, if minor, obligation. Then the assets, which is where the real money is. Fonts: check `public/fonts` or the equivalent for font files and find the licence for each — Google Fonts are typically OFL or Apache-2.0 and fine to self-host, but a commercial face from a foundry almost always needs a separate webfont licence with a pageview tier, and a `.woff2` sitting in the repo with no licence file beside it and no receipt is the case to flag. Icon sets: check for a Pro or paid set (Font Awesome Pro, Nucleo, Streamline) against a licence key or purchase record, and note the permissive ones that need no action. Images: stock photos need a licence covering commercial use, and an image whose filename or metadata points at a stock site with no licence record is the finding; AI-generated marketing images raise their own questions that belong with counsel rather than here. Attribution: OFL and CC-BY require it and it is usually missing; say where it should go. HYG-007 owns the project's own `LICENSE` file and repo hygiene; this block owns compliance with everyone else's licences, so cite it rather than reporting the missing README twice.
evidence: the licence distribution with counts; every copyleft package named with `ships to client`, `ships in binary`, or `build-time only` and its file:line of import; every package with a missing or non-standard licence; whether a notices or licences page exists; each font file with its licence source or `no licence found`; each paid icon set with its purchase record or `unverified`; each stock image with its licence record or `unverified`; the attributions present and the ones required but absent.
fix_hint: The implementation note must resolve each copyleft dependency that actually ships — replace it, or accept and document the obligation — and get a licence or a replacement for every font, icon set, and stock image without one. Add a notices page or a bundled third-party licence file generated from the dependency metadata so the MIT and Apache notice requirements are satisfied by the build rather than by hand, and put the OFL and CC-BY attributions on it. Flag anything unresolved for counsel rather than guessing at the terms.

### COMP-029 AI disclosure to users; chatbot transparency (EU AI Act)
severity: medium
tier: static
fix: guided
when: features.ai
why: The transparency rule is narrow and easy to satisfy, and it is about the moment of interaction rather than about a document: a person talking to a machine has to be able to tell. The EU AI Act's Article 50 requires systems that interact directly with people to be designed so the person is informed they are interacting with an AI unless that is obvious from the context, requires AI-generated or manipulated content to be disclosed, and requires synthetic content to be marked in a machine-readable way. California's bot-disclosure law (SB 1001) reaches a narrower case — bots used to incentivise a sale or influence a vote — but the practical answer to both is the same label.
verify:
  static: Find every surface where model output reaches a user: a chat or assistant panel, a support widget, generated copy in the product, generated images or audio, an automated email or reply. For each, check for a visible indication that it is AI — a label on the assistant, a first message that says so, a badge on generated output. Then look for the fail that is not merely an omission: model output presented as a human, which means a support persona with a human name and an avatar, a signature on a generated email implying a person wrote it, or a "we usually reply in a few minutes" line above a bot. That is the case both regimes were written for and it should be reported as a distinct, more serious finding than a missing label. Then check the accuracy disclaimer where the output is advice-shaped: health, legal, financial, or safety-relevant output needs a statement that it may be wrong and is not professional advice, positioned where the user reads the output rather than buried in the terms. Then check whether users can tell generated media apart from real media, and note the machine-readable marking obligation for synthetic content, which most products do not implement at all — say so rather than skipping it. On timing: the AI Act phases its obligations in over several dates, and the Article 50 transparency obligations apply from 2 August 2026, so state that date, note that they reach providers and deployers placing systems on the EU market regardless of where they are established, and still mark it `verify current text with counsel` — the Act's timetable has been the subject of amendment proposals, so a date that is correct today is worth confirming rather than relying on. Also check the reverse direction: a product advertising "AI-powered" features that are a rules engine is COMP-030's problem, so hand it over rather than judging it here. COMP-004 owns the privacy-policy half of AI disclosure; cite it.
evidence: each AI surface with its component file:line and the disclosure it carries, or `no AI indication`; any human persona, name, avatar, or signature attached to model output, quoted; the accuracy disclaimer where output is advice-shaped, quoted or absent; whether generated media is labelled and whether any machine-readable marking exists; the regime note with its counsel caveat.
fix_hint: The implementation note must add a visible, persistent label wherever a user interacts with model output — on the assistant surface itself, not only in the terms — and must remove any human name, avatar, or signature attached to generated messages. Where output is advice-shaped, add an accuracy and not-professional-advice line adjacent to the output. Label generated media, and record machine-readable marking of synthetic content as scope to plan for rather than as copy to write, since it is an implementation task.

### COMP-030 Marketing claims substantiated: "free", comparative, health, results
severity: medium
tier: static
fix: guided
why: The FTC's baseline is that an advertiser must have a reasonable basis for an objective claim before making it, with health claims needing competent and reliable scientific evidence, and that requirement applies to a landing page written in an afternoon exactly as it applies to a television campaign. The launch-day pattern is a page full of numbers nobody can source, plus two specific claims that are also factually checkable against the code: "free" and any security or compliance badge.
verify:
  static: Sweep the marketing pages and content directory — reusing the `.pre-launch/compliance/marketing-<n>.txt` files COMP-018 saved rather than re-fetching — and grep for the claim vocabulary — `free`, `no credit card`, `guaranteed`, `unlimited`, `#1`, `best`, `fastest`, `most secure`, `save \d+%`, `\dx (faster|more)`, `up to`, `in minutes`, `HIPAA`, `SOC 2`, `ISO 27001`, `GDPR compliant`, `bank-level`, `military-grade`, `end-to-end encrypted`, `clinically`, `proven`, `doctor` — and for each hit ask two questions: is there a source, and does the code agree? Four claim types need separate treatment. "Free" claims: the conditions must be disclosed clearly and next to the offer, so a "free" plan that requires a card, or a "free trial" that converts automatically, must say so at the point the word appears rather than three screens later; and `no credit card required` beside a sign-up flow that collects a card is a factual falsehood you can prove from the handler in one grep. Comparative claims: naming or implying a competitor requires substantiation of the comparison as made, and "3x faster than <competitor>" with no benchmark is the archetype. Results and performance claims: a specific number ("save 10 hours a week", "2x conversions") needs a basis, and where the result is not what a typical user gets, that has to be clear from the claim itself. Health claims: the standard is high and the appropriate output here is to flag every one for counsel rather than to assess the evidence. Then the two claims that are really security findings wearing marketing clothes. Compliance badges: `SOC 2 Type II`, `HIPAA compliant`, `ISO 27001`, and `PCI compliant` each mean a specific artefact exists — a report, a BAA programme, a certificate, an attestation — so record whether one does, since an unearned badge is both an FTC exposure and the fastest way to fail an enterprise security review. Encryption claims: `end-to-end encrypted` has a technical meaning that most products claiming it do not implement, and `bank-level` and `military-grade` mean nothing at all; check them against what the security domain found rather than against the copy. And `unlimited` next to a rate limit or a quota is the same class of error, checkable in the code.
evidence: one row per claim — `<file:line> — "<claim>"` with `substantiated by <source>`, `unsubstantiated`, or `contradicted by <file:line>`; the credit-card claim beside what the sign-up handler actually collects; each compliance badge beside whether the underlying artefact exists; each encryption claim beside the security domain's finding; each `unlimited` beside the quota that limits it.
fix_hint: The implementation note must pair every objective claim with its source or remove the claim; there is no third option and softening the wording does not create substantiation. Specifically: make `no credit card required` true or delete it; give comparative and results claims a linked benchmark or methodology; remove any compliance badge without the report, certificate, or programme behind it; replace `bank-level` and `military-grade` with what the system actually does; and reconcile `unlimited` with the real quota. Route health claims to counsel before publication.

### COMP-031 Affiliate and sponsorship disclosures
severity: low
tier: static
fix: easy
why: The FTC's Endorsement Guides require a material connection between an endorser and a seller to be disclosed clearly and conspicuously, close to the endorsement itself. The operative word is close: a disclosure in the footer, on a separate disclosures page, or below the fold does not cure an affiliate link at the top of a review post. ### COMP-032 Age of majority for contracts; beta/experimental disclaimers
severity: low
tier: static
fix: easy
why: A contract with a minor is generally voidable by the minor, which makes the terms of service unenforceable against exactly the users most likely to cause a dispute. And a product still finding its shape needs its terms to say so: shipping beta software under terms that promise availability and fitness creates a gap between what the document guarantees and what the product can deliver, which is the same gap COMP-030 finds in the marketing copy.

### COMP-033 B2B: DPA available to customers; subprocessor list published
severity: medium
tier: attest
fix: guided
when: features.b2b
why: When your customer is a business handling its own users' personal data, it is the controller and you are its processor, and Article 28 requires a written contract between you with prescribed contents. This is not merely a legal box: the DPA and the subprocessor list are the first two documents an enterprise buyer's procurement team asks for, and not having them stalls the deal for weeks at exactly the moment momentum matters.
verify:
  static: Look for the documents in the repo and on the site: a `/dpa`, `/legal/dpa`, `/subprocessors`, or `/trust` route, a downloadable agreement, or a data processing addendum incorporated by reference into the terms of service — which is the pattern that scales, because it means every customer has one without a signature round. Check international transfer terms too — standard contractual clauses, the UK addendum, and the equivalents — and note their presence rather than judging their currency, which is `verify current text with counsel`.
  attest: Ask the user, and record verbatim: is a DPA offered to customers and by what mechanism (click-through, incorporated by reference, or signed per customer); who has reviewed it; is the subprocessor page maintained and by whom; and is there a process for notifying customers before a new subprocessor is added. Note that a security questionnaire or SOC 2 report is a related but separate ask from procurement, and that claiming either without the artefact is COMP-030's finding.
evidence: the DPA route or file with the Art. 28(3) elements present and absent, one line each, or `no DPA available`; the subprocessor page with its entries; the diff against `.pre-launch/compliance/inventory.json`, one line per missing vendor; the change-notification mechanism or `none`; the transfer terms named; the user's verbatim answers.
fix_hint: The draft DPA must contain the Art. 28(3) elements as a checklist rather than as prose, and should be incorporated by reference into the terms so every customer has one without a signature round, with a signable version available for those who need it. The subprocessor page must be generated from the vendor inventory rather than maintained by hand, list each vendor's purpose and processing location, and be paired with a way for customers to be notified before a new subprocessor is added. Route the transfer terms past counsel.

### COMP-034 Trust and safety: report, block, moderation queue; legally required abuse reporting
severity: high
tier: static
fix: guided
when: features.user_content
why: Any product where strangers can send each other content will be used to send abuse, and the question at launch is only whether there is anywhere for the recipient to go. There is also a hard legal floor that is not a matter of policy preference: US federal law requires providers to report apparent child sexual abuse material to the NCMEC CyberTipline, with penalties for knowing failure to report and rules about preserving the reported material. If the product accepts image or video uploads from people who do not know each other, that obligation exists from the first upload.
verify:
  static: Inventory every surface where one user's content reaches another — posts, comments, direct messages, profiles, uploaded media, display names and bios, which are the ones forgotten — and for each check three controls. A report control on the item itself, not only in a help page. A block or mute so the recipient can stop the sender without waiting for you. And a moderator path: where a report goes and who sees it. That last one is where this check usually fails, and it fails the same way REL-028's contact form does — reports written to a `reports` table that no interface reads and no notification announces are the same as no reporting at all, so trace the report handler to something a human will actually look at, whether that is an admin view, a channel notification, or a monitored inbox. Then check enforcement exists in the schema: some way to hide, remove, or suspend, since a queue with no actions is a to-do list. Then the legal floor. For products accepting user-uploaded images or video from strangers, check whether anything scans or hashes uploads, whether there is a defined path for reporting to NCMEC, and whether staff know the preservation rules; the absence of all three on such a product is a launch blocker to state plainly rather than a medium-severity note, and hash-matching services exist to make it tractable. Then the regime-specific duties, kept separate rather than merged: the EU Digital Services Act imposes notice-and-action mechanisms, statements of reasons for removals, and an internal complaint-handling path on hosting services and online platforms, with obligations scaling by size; COMP-009 owns copyright takedowns specifically. Finally check the terms actually contain a content policy that names the prohibited conduct the moderation will enforce, and that there is an appeal path for a user whose content is removed — enforcement without a stated rule is what generates the public complaints. Mark the DSA thresholds and the reporting mechanics `verify current text with counsel`.
evidence: one row per user-content surface — `<surface> — report: <file:line or absent>, block: <file:line or absent>`; the report handler traced to its destination, with `reaches <admin view | notification | inbox>` or `writes a row nothing reads`; the enforcement actions available in the schema; the CSAM position for upload-accepting products, stated plainly; the content policy and appeal path quoted or absent; the DSA note.
fix_hint: The implementation note must put a report control on every surface where users see each other's content, add block or mute, and route reports to something a person sees with an action they can take — a queue view or a notification, plus the hide, remove, and suspend actions the queue needs. For a product accepting media from strangers, a CSAM detection and NCMEC reporting path is scope to plan before launch, not after. The drafts need a content policy in the terms naming the prohibited conduct, a statement of reasons for removals, and an appeal route.

### COMP-035 Terms acceptance recorded with version and timestamp
severity: medium
tier: static
fix: guided
why: When a user disputes an arbitration clause, a price change, or a suspension, the only thing that matters is proof that this user agreed to this version of the document at this time. A checkbox that sets no column proves nothing, and neither does the current text of the terms, because the question is what they said the day the user signed up. This is also the cheapest thing on the list to build correctly at the start and the most painful to reconstruct later.
verify:
  static: Find the acceptance mechanism at sign-up and at checkout (stack ref: "routes and handlers"). Distinguish the two shapes and say which this is, because the difference is the whole point: clickwrap, where the user takes an affirmative action next to a visible link to the terms, is what courts routinely enforce, while browsewrap — a line saying "by continuing you agree to our terms" with no action — is routinely refused, particularly where the link is small or below the fold. Then find the storage. Look for a `terms_accepted_at`, `tos_version`, `accepted_terms`, or `agreements` table, or an entry in an audit log, and check five fields are captured: who, when, which document, which version, and ideally the request context. The version field is the one that is usually wrong: a constant `1` that nobody increments, or a boolean, tells you nothing a year later, so check it is tied to the actual document — a content hash, a dated slug, a git tag, or an effective date that matches the published page (HYG-006 owns the dates on the documents themselves). Then check three behaviours around it. Re-acceptance when the terms change materially: is there any mechanism to prompt existing users, or does a change silently apply to people who agreed to something else? Coverage: does the same record exist for the privacy policy, and for any separate DPA, biometric release (COMP-015), or SMS consent (COMP-025), since those consents have the same evidentiary problem and stricter rules. And retrievability: could you produce the record for one named user in a dispute — a row in a table you can query is a yes, a log line rotated out in 30 days is a no.
evidence: the acceptance control's markup file:line with `clickwrap` or `browsewrap`; the storage location with the fields actually written, or `no acceptance record stored`; the version value and what it is derived from; the re-acceptance mechanism or `none — changes apply silently`; which other consents are recorded the same way and which are not; the retention of the record.
fix_hint: The implementation note must make acceptance an affirmative action beside a visible link to the terms, and write a durable record carrying the user id, the timestamp, the document, and a version identifier derived from the document itself — a content hash or a dated slug, not a constant. Add a re-acceptance prompt for material changes, and use the same record shape for the privacy policy and for any separate consent the product collects, so one query answers the question for every agreement.

### COMP-036 Privacy policy and terms linked from footer, sign-up, checkout, and store listings; reachable logged out
severity: high
tier: local
fix: easy
why: A policy that exists but cannot be reached is, for every purpose that matters, missing: the notice obligations require the information to be available to the person at the point they need it, app stores reject listings whose privacy URL does not load, and a payment processor's review will check the same links. The failure mode this check exists for is specific and common — a legal page inside an authenticated layout, so it returns a redirect to the login page for exactly the visitor who has not signed up yet.
verify:
  static: Find the footer component and confirm it links to the privacy policy and the terms, then confirm the footer actually renders on the pages that matter rather than only on the marketing layout — a separate app layout without it is the usual reason the links vanish after login. Then check the sign-up and checkout surfaces carry their own links beside the acceptance control (COMP-035), since a footer link at the bottom of a long page is not adjacent to the action. Check the route definitions for the legal pages and, critically, which layout or middleware they sit under: a `/legal/*` route inside an authenticated route group, or matched by an auth middleware's matcher pattern, is the defect this check finds and it is invisible while you are logged in. Also note where the same URLs are needed outside the site — the app store listing's privacy URL, the payment processor's dashboard, an OAuth consent screen — and hand those to HYG-001, which owns third-party dashboard configuration.
  local: Against the production build, request each legal URL with no cookies and no authorization header and follow redirects, recording both the status and the final URL: `curl -s -o /dev/null -w "%{http_code} %{url_effective}\n" -L "<local.url>/privacy"`. A 200 that ends at the same path passes; a 200 that ends at `/login` is the fail, and it is the one a status code alone hides, which is why the effective URL is in the format string. Do the same for the terms and for any cookie, refund, DMCA, or EULA page in `pages.txt`. Then confirm the pages have content rather than being a client-rendered shell that returns 200 with an empty body: grep each saved response for a sentence you already extracted into the `.txt` files. Finally, grep the home page — `.pre-launch/compliance/plain.html` if COMP-020 saved it, otherwise fetch it the same way — plus the sign-up and checkout pages, for the policy links: `grep -ioE "href=[\"'][^\"']*(privacy|terms)[^\"']*[\"']" .pre-launch/compliance/plain.html`, written as a double-quoted shell string with both quote characters in the class so it matches single-quoted attributes too. Report which of the three carry both links.
evidence: per legal URL — `GET <path> (no cookies) → <status> <effective url>` and whether the body contains known policy text; the footer component file:line and the layouts it renders in; the sign-up and checkout link markup quoted or `absent`; any legal route sitting inside an authenticated group or matched by auth middleware, with file:line; the external placements handed to HYG-001.
fix_hint: Move every legal route out of the authenticated layout and exclude those paths from the auth middleware's matcher so they resolve for a logged-out visitor, then put the privacy and terms links in a footer that renders on both the marketing and application layouts, and add direct links beside the acceptance control on sign-up and checkout. Confirm the same URLs are entered in the app store listing, the payment processor's dashboard, and any OAuth consent screen (HYG-001).
