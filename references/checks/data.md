# Data checks (DAT)

Read `agents/domain-auditor.md` for procedure. Blocks below are checks; consult stack references for locations. Tools: `psql` or the Supabase CLI (`supabase db`, `supabase storage`) for the policy and storage probes (DAT-002, 005, 006, 007, 026); Firebase emulator or the `firebase` CLI for rules (DAT-003); the stack's migration tool against a scratch database (DAT-015). Probes that write data use only the test account and only when provider keys are detectably test-mode; if they are not, record `error: live keys detected` and fall back to the static entry.

### DAT-001 RLS (or equivalent rules) enabled on every table holding user data
severity: critical
tier: static
fix: guided
why: A Postgres table with row level security off is readable by anyone holding the anon key, and on Supabase or any PostgREST-style setup that key ships in the browser bundle by design. One forgotten table is a full export of whatever it holds.
verify:
  static: Build the table list from the schema (stack ref: "data access") — `supabase/migrations/*.sql`, `prisma/schema.prisma`, `drizzle/`, `db/schema.rb`, Django models, or `\dt` via `psql` if a connection is available. Mark every table that holds user-owned or tenant-scoped data (anything with a `user_id`/`owner_id`/`org_id`/`tenant_id` column, plus profiles, sessions, subscriptions, uploads, messages). For each, find `alter table <t> enable row level security` in a migration, or query `select relname, relrowsecurity, relforcerowsecurity from pg_class c join pg_namespace n on n.oid = c.relnamespace where n.nspname = 'public'` if `psql` works — the query beats grepping, because a later migration can disable what an earlier one enabled. Fail on any user-data table with RLS off. Two exceptions to reason about rather than wave through: a table only ever reached through a server-side connection with no client-reachable credential (verify that claim against DAT-004 before accepting it — then the equivalent rule is that every query in the data access layer is scoped by user, and say so in the evidence); and a genuinely public reference table (countries, plans, feature flags), which passes but must be named. Non-Postgres equivalents: Firebase goes to DAT-003; MongoDB Atlas needs per-collection rules or a server-only driver; DynamoDB needs IAM condition keys rather than a client credential.
evidence: one line per table — `public.<table> — rls enabled (migration.sql:NN)` or `public.<table> — rls DISABLED (pg_class query)`; name the tables you cleared as public reference data and the credential path for any server-only table.
fix_hint: Add `alter table <t> enable row level security;` to a new migration for each failing table, then write the owner policies (DAT-002) in the same migration — enabling RLS with no policy blocks all access, so the two must ship together.

### DAT-002 Policies tested as anon, owner, and another user
severity: critical
tier: local
fix: guided
why: RLS being enabled says nothing about whether the policies are right. A policy with `USING (true)` or a missing `WITH CHECK` passes DAT-001 and still leaks everything.
verify:
  static: For each table with RLS (stack ref: "data access"), read every policy. Fail if any policy on a user-data table uses `true` as its predicate, lacks `WITH CHECK` on insert/update, or is satisfied by any authenticated user rather than the row's owner — `auth.uid() is not null`, `auth.role() = 'authenticated'`, or any predicate that does not compare a column of this row to the caller's id. Note tables with no policy at all (RLS on with no policy blocks everyone, which breaks the app rather than leaking, but is still a fail). Check the policy covers each command separately — a `for select` policy leaves insert, update, and delete unprotected unless a `for all` policy or three more policies exist; list which of select/insert/update/delete each table actually has. On Supabase, also fail any server-side ownership check built on `supabase.auth.getSession()`: the session comes from a cookie the client can write, so it is not an auth check — `getUser()`, which re-verifies with the auth server, is.
  local: With the anon key and no session, select from each user-data table; expect zero rows. With the test account's JWT, insert a row, then with a second test JWT try to select, update, and delete it; expect zero rows or a permission error. Then exercise `WITH CHECK`, which the reads above never touch: as the second test JWT, insert a row carrying the first account's owner id, and update one of your own rows to set the owner column to the first account's id; both must be rejected. See stack ref "runtime probe hints" for how to obtain a JWT for the test account, and use only test accounts — never a real user's session.
evidence: per table: policy names, the command each covers, and predicates; probe results `select <table> as anon → N rows (expected 0)` and `update <table> as other user → N rows affected (expected 0)`.
fix_hint: Rewrite the policy predicate to compare the row's owner column to `auth.uid()` (or the equivalent claim) and add a matching WITH CHECK; snippet under stack ref "data access".

### DAT-003 Firebase rules contain no `if true`; rules tested
severity: critical
tier: static
fix: guided
when: stacks includes firebase
why: Firebase's test-mode rules allow the whole database to be read and written by anyone with the web config, which is public by design. Projects launch on those rules constantly, and scrapers find them the same day.
verify:
  static: Read `firestore.rules`, `storage.rules`, and `database.rules.json`, and confirm `firebase.json` actually points at them (a rules file that is not referenced is not deployed). Fail on: `allow read, write: if true;`; the dated test-mode rule `allow read, write: if request.time < timestamp.date(...)` whether or not the date has passed; any `allow write` without both `request.auth != null` and an ownership comparison (`request.auth.uid == userId` from the path, or `== resource.data.ownerId`); an update rule that checks `resource.data` but not `request.resource.data`, which lets a user rewrite the owner field and take over the document; recursive wildcards (`match /{document=**}`) granting more than the specific rules below them. Storage rules need the same treatment per bucket path. Then check the rules are tested: look for `@firebase/rules-unit-testing` specs or an emulator job in CI. If the `firebase` CLI is installed, `firebase emulators:exec --only firestore,storage "<test command>"` runs them; if there are no tests, that is part of the finding, not a blocker.
evidence: `firestore.rules:NN — allow read, write: if true` quoted per offending rule; whether each rules file is referenced from `firebase.json`; the rules test command and its result, or `no rules tests found`.
fix_hint: Replace each permissive rule with an auth-and-owner predicate scoped to the collection path, validate `request.resource.data` on writes so the owner field cannot change, and add a `@firebase/rules-unit-testing` spec that asserts a second user is denied; run it in the emulator before deploying.

### DAT-004 Service-role / admin credentials never reach the client
severity: critical
tier: static
fix: guided
why: The service-role key bypasses every policy you just wrote — it is the database with no rules. In a client bundle it hands a stranger the same access your server has, and no RLS policy will stop them.
verify:
  static: Grep the whole tree (excluding `node_modules`, `.git`, lockfiles) for admin credential names: `SUPABASE_SERVICE_ROLE`, `service_role`, `SERVICE_KEY`, `FIREBASE_PRIVATE_KEY`, `GOOGLE_APPLICATION_CREDENTIALS`, `serviceAccount`, `firebase-admin`, `DATABASE_URL`, `MONGODB_URI`, `AWS_SECRET_ACCESS_KEY`. Then check three paths to the client. (1) Env naming: any of these assigned to a variable carrying this stack's public prefix (stack ref: "env vars" — `NEXT_PUBLIC_`, `VITE_`, `EXPO_PUBLIC_`, `PUBLIC_`, `REACT_APP_`) is an immediate fail; on Supabase, `service_role` in any client-reachable env var is a fail regardless of what the code does with it. (2) Import graph: find where the admin client is constructed (`createClient(url, serviceRoleKey)`, `admin.initializeApp`, `new Pool(...)`) and confirm the file is server-only — `"use server"`, a `server/` or `app/api/` path, `server-only` imported, or the framework's equivalent (stack ref: "routes and handlers") — and that nothing under a `"use client"` boundary imports it, directly or through a barrel file. (3) Build output: if a build directory exists (stack ref: "build"), grep it for the key's actual value from `.env` and for `service_role`. Also fail a mobile app that embeds an admin key in `app.json`/`Info.plist`/`strings.xml`, where it is trivially extracted from the binary.
evidence: file:line for each admin credential use with the redacted first 6 characters; the server-only marker for each admin client file, or `imported from <client file>:NN`; grep hits in build output.
fix_hint: Move every admin-credential read behind a server-only module (stack ref: "routes and handlers"), drop the public prefix from the variable name, rotate the key because the old bundle is already public, and rebuild; client code uses the anon/publishable key and relies on the DAT-002 policies.

### DAT-005 Storage buckets private by default; per-bucket policies
severity: critical
tier: static
fix: guided
why: A public bucket is a directory listing on the open internet if object names are guessable, and object names are usually the user id or a sequential upload id. Users' documents end up indexed.
verify:
  static: Enumerate every bucket the app writes to (stack ref: "file uploads") and find where each is created or configured. Supabase: `insert into storage.buckets (id, name, public) values (..., true)` in a migration, or the bucket list from `supabase storage ls` — `public = true` on any bucket holding user files is a fail. S3: `PublicAccessBlockConfiguration` with all four settings true, no `"Principal": "*"` in the bucket policy, no `public-read` ACL in the upload call. GCS: no `allUsers`/`allAuthenticatedUsers` IAM binding, `uniformBucketLevelAccess` on. R2: no public dev URL or custom domain bound to a private bucket. Firebase Storage goes through DAT-003. Then confirm each private bucket has its own policies rather than one blanket rule: on Supabase that means `storage.objects` policies keyed on `bucket_id` and a path prefix matching `auth.uid()`; elsewhere it means the app mints signed URLs (SEC-050) instead of serving the bucket directly. A bucket that is deliberately public for site assets (logos, marketing images) passes but must be named, and you must confirm nothing user-supplied is written into it.
evidence: per bucket — `<name> — public: true|false (source file:line or CLI output)` plus the policies or IAM bindings found; the explicit list of buckets you cleared as intentionally public assets.
fix_hint: Flip the bucket to private (`update storage.buckets set public = false where id = '<b>'`, or enable S3 public access block / remove the `allUsers` binding), add per-bucket object policies scoped to the owner's path prefix, and switch the app to signed URLs for reads.

### DAT-006 No sensitive files in any public bucket
severity: high
tier: local
fix: guided
why: Buckets are usually made public early "just to get uploads working" and never audited, so invoices, ID scans, and database dumps sit next to the logo. Anyone who guesses one URL can often walk the rest.
verify:
  static: From DAT-005 you have the public bucket list and, from the upload code (stack ref: "file uploads"), which bucket each upload path writes to. Fail immediately on any code path that writes user documents, exports, avatars-with-PII, or generated PDFs into a bucket DAT-005 found public. Also check for a bucket used as a scratch/backup target (`pg_dump` output, CSV exports, log dumps) that shares the public bucket.
  local: List the objects in each public bucket read-only — `select name from storage.objects where bucket_id = '<b>' limit 500` via `psql` is the most reliable on Supabase, with `supabase storage ls` (run `supabase storage ls --help` for this CLI version's path syntax), `aws s3 ls s3://<bucket> --recursive`, or `gsutil ls -r gs://<bucket>` elsewhere. Scan the names for anything that should not be world-readable: `invoice`, `receipt`, `passport`, `id-`, `licence`, `contract`, `export`, `backup`, `dump`, `.sql`, `.csv`, `.env`, `.pem`, `.zip`, plus anything under a per-user path. Then fetch one such object's public URL with `curl -sI` and no credentials — a `200` confirms exposure. Never delete, move, or overwrite an object; this probe is read-only.
evidence: bucket name, object count, and up to ten offending object keys; `GET <public url of one object> → 200 (expected 403)`; the upload handler file:line that writes there.
fix_hint: Move the sensitive prefixes to a private bucket, rewrite the upload path to target it, serve them through signed expiring URLs (SEC-050), and then delete the copies left behind in the public bucket — the old URLs stay live until the objects are gone.

### DAT-007 Views and security-definer functions bypass RLS only intentionally
severity: high
tier: static
fix: guided
why: A view over an RLS-protected table runs as the view's owner, so it hands out every row the policies were written to hide, and PostgREST happily exposes it to the anon key. A `security definer` function without a pinned `search_path` is the same hole plus a privilege-escalation path.
verify:
  static: Grep migrations and the schema for `create view`, `create materialized view`, `create or replace function`, and `security definer` (stack ref: "data access"). For each view over a table with RLS: it must be declared `with (security_invoker = true)` (Postgres 15+) or live outside the API schema and not be granted to `anon`/`authenticated`. Check the grants — `select relname, relacl from pg_class` via `psql`, or `grant select on <view> to anon` in migrations. A materialized view never respects RLS at all, so one built over user data and exposed to clients is a fail whatever the flags say. For each `security definer` function: it must set `search_path` explicitly (`set search_path = ''` or `= public`) — without that, a caller can shadow a table name and run their own code as the owner — and it must filter by `auth.uid()` (or the equivalent) internally, since the definer's rights ignore the caller's policies. Supabase RPCs are exactly these functions, so check every function reachable over `/rest/v1/rpc/`. Where the bypass is deliberate (a leaderboard aggregate, an admin report reachable only from a server-side route), that is fine — say so and name what restricts access.
evidence: per view — `<name> — security_invoker true|false|absent, granted to <roles>`; per function — `<name> — security definer, search_path <value or MISSING>, uid filter <present or MISSING>`.
fix_hint: Add `with (security_invoker = true)` to the view (or revoke it from `anon`/`authenticated` and read it from server code only), and give every `security definer` function `set search_path = ''` plus an explicit `auth.uid()` predicate in its body.

### DAT-008 Database not reachable from public internet; connection pooling in place
severity: high
tier: attest
fix: none
why: A Postgres port open to the world gets credential-stuffed within hours of appearing in a scan, and a serverless app without a pooler exhausts the connection limit under its first traffic spike and goes down while the database is perfectly healthy.
verify:
  static: Find the connection string and pooling setup first (stack ref: "data access", "env vars"). Evidence that pooling exists: a pooler host or port in `DATABASE_URL` (Supabase pooler on `:6543`, `pgbouncer=true`, `?pgbouncer`, an RDS Proxy endpoint, `pgcat`, `pgbouncer.ini`), a pool configured in code (`new Pool({ max })`, SQLAlchemy `pool_size`, `DATABASES['CONN_MAX_AGE']`), or a driver that pools by default in a long-lived process. Treat as a strong fail signal: a serverless or edge deployment (stack ref: "build") holding a direct `:5432` connection, or Prisma on Vercel without `?pgbouncer=true&connection_limit=1`. For network exposure, look for what the repo can show — Terraform/CloudFormation security groups with `0.0.0.0/0` on the DB port, `fly.toml` or `docker-compose.yml` publishing `5432`, a database container with `ports:` rather than only `expose:`, `sslmode=disable` in the URL. Note that Supabase and Neon are internet-reachable by design, so there the controls are a strong password, IP restrictions, and RLS rather than a private subnet.
  attest: Ask the user, and record the answer verbatim: is the production database reachable only over private networking or an IP allowlist that does not include `0.0.0.0/0`, and is a connection pooler in front of it sized below the instance's `max_connections`? Both halves need a yes; a no or an unknown on either is the finding.
evidence: the connection host/port with credentials redacted; the pooling mechanism and its file:line, or `none found`; any `0.0.0.0/0` rule quoted from infra config; the user's answer to the attest question, or `unconfirmed`.

### DAT-009 Indexes on foreign keys and hot query columns
severity: medium
tier: static
fix: easy
why: Postgres indexes primary and unique keys automatically but never foreign keys, so a list query filtered by `user_id` sequentially scans the whole table. It is invisible at 100 rows and a timeout at 100,000.
verify:
  static: Read the schema (stack ref: "data access") and list every foreign key column — anything declared `references`, `@relation`, `ForeignKey`, `belongs_to`, or named `*_id` pointing at another table. For each, grep the migrations and schema for a matching index (`create index`, `@@index`, `index: true`, `add_index`, `db.index`); with `psql` available, `select tablename, indexdef from pg_indexes where schemaname = 'public'` is the authoritative list and beats grepping. An unindexed foreign key is a fail only when something actually scans it: the child table is filtered or joined on that column anywhere in the codebase, or the parent row is ever deleted or updated in a way that touches the key — a cascade, `set null`, or `restrict` check scans the child table on every parent delete, which is the case people miss because no query in the code mentions the column. A genuinely cold foreign key — never filtered, never joined, parent rows never deleted — passes; name it and say which of the three reasons cleared it, so the next auditor can re-check when a delete path appears. Then do the same for hot query columns: pull every `where` and `orderBy`/`order_by`/`sort` column out of the data access layer and list endpoints, and check each against the index list. Two things that look indexed but are not: a composite index `(a, b)` does nothing for a query filtering only on `b`; and an index on `created_at` does not serve `where user_id = ? order by created_at desc` — that wants the composite `(user_id, created_at desc)`. Also flag unique columns used for lookup (`slug`, `stripe_customer_id`, `email`) with no unique constraint, which is DAT-014's problem too. If a live connection exists, `explain (analyze, buffers) <query>` on the slowest list query turns this from a guess into a measurement; a `Seq Scan` on a large table is the fail. Run `analyze` only on a select — it executes the statement, so never point it at an insert, update, or delete; use plain `explain` for those.
evidence: per missing index — `<table>.<column> — FK, no index (pg_indexes)` or `<table>.<column> — filtered at <file:line>, no index`; any `explain` output showing a sequential scan.
fix_hint: Add one migration creating the missing indexes, composite and in query order where a filter and a sort combine (`create index concurrently on <t> (user_id, created_at desc)`); use `concurrently` so the migration does not lock a live table.

### DAT-010 No N+1 queries in list endpoints
severity: medium
tier: local
fix: guided
why: One query per row turns a 50-item list into 51 round trips, so the page is fine in development with ten rows and times out in production with a thousand. It is the single most common cause of a launch-day slowdown.
verify:
  static: Read every list endpoint and the components that render its results (stack ref: "routes and handlers", "data access"). Look for a query inside a loop: an `await` inside `for`/`forEach`/`map` over query results, an ORM relation accessed per row (`order.customer.name` in a render loop with lazy loading), a `Promise.all` over rows that each fetch, or a resolver that fetches per parent without a dataloader. Missing eager loading is the tell — no `include`/`with`/`select` on Prisma, no `select_related`/`prefetch_related` in Django, no `includes(:assoc)` in Rails, no `joinedload` in SQLAlchemy, no join in the raw SQL. Supabase's `select('*, author(*)')` nested syntax is one query and passes; a second `.from('authors')` call per row does not.
  local: Turn on query logging and count. Prisma: `new PrismaClient({ log: ['query'] })`. Django: `CaptureQueriesContext` or the debug toolbar's query count. Rails: the request log's `ActiveRecord` lines. Supabase/PostgREST: the local API logs, or `pg_stat_statements` before-and-after. Request the list endpoint with the test account twice — once with a handful of rows, once after seeding more into the test account's own data if the app has a create path — and compare counts. A query count that grows with the row count is the fail; a count that stays flat passes. Record the endpoint's wall-clock time too.
evidence: `GET /api/<list> → N queries for M rows (expected constant)` for both runs, plus the file:line of the per-row query.
fix_hint: Replace the per-row fetch with one eager-loaded query (`include`, `select_related`/`prefetch_related`, `includes`, `joinedload`) or a single `where id in (...)` batch, and re-count the queries to confirm the number is now flat.

### DAT-011 Pagination with max page size on every list endpoint
severity: medium
tier: static
fix: easy
why: An unbounded list endpoint returns the whole table once the table is big, which blows the server's memory and the client's. If the limit comes straight from the query string, `?limit=1000000` is a denial of service anyone can type.
verify:
  static: List every endpoint, server action, or loader that returns a collection (stack ref: "routes and handlers"). Each needs three things: a default page size, a clamp on the caller-supplied size (`Math.min(Number(limit) || 20, 100)`, a schema with `.max(100)`, `paginate_by`, `LIMIT` bound in the query), and a way to reach page two (offset or cursor). Fail on: a query with no `limit`/`take`/`first`/`LIMIT` at all; `Model.objects.all()` or `findMany()` serialized whole; `select('*')` on Supabase without `.range()` or `.limit()`; a limit read from the request and passed to the query without a ceiling; and a "load more" that fetches everything client-side and slices it. Check the export and search endpoints too — they are the ones people forget, and they are the biggest. Deliberately unpaginated small reference lists (plan tiers, countries) pass; name them and say why the row count is bounded.
evidence: per endpoint — `<method> <path> — default N, max M (file:line)` or `<method> <path> — NO LIMIT (file:line)`; the bounded-by-nature lists you cleared.
fix_hint: Parse the page size through a schema with a maximum, clamp it before it reaches the query, and add cursor pagination (`where id > lastId order by id limit n`) for the endpoints that will actually grow — offset pagination degrades on deep pages.

### DAT-012 No row-at-a-time writes in loops; batched
severity: medium
tier: static
fix: easy
why: A thousand inserts in a loop is a thousand round trips inside one request, which either times out or holds a connection long enough to starve everyone else. Batched, it is one statement.
verify:
  static: Grep the data access layer, importers, webhook handlers, and background jobs (stack ref: "data access", "background jobs") for a write inside an iteration: `await <insert|update|delete>` inside `for`, `while`, `forEach`, `map`, or a comprehension; `.save()` per object in a Django/Rails loop; `db.execute(insert)` per row. For each, confirm the batched form is used instead — `createMany`/`updateMany`, `bulk_create`/`bulk_update`, `insert_all`/`upsert_all`, `INSERT ... VALUES (...), (...)`, or one `update ... where id in (...)`. Two near-misses that still fail: `await Promise.all(rows.map(r => db.insert(r)))` is concurrent, not batched, and will exhaust the connection pool faster than the sequential version; and a batch with no chunking will hit the driver's parameter limit (65535 bound parameters on Postgres) on a large import, so a batched call over unbounded input needs chunking. Note whether the loop is over user-controlled input, which turns a performance smell into a DoS.
evidence: file:line of each write-in-loop with the loop's iteration source (`over request body items`, `over 1 row per CSV line`); the batched call where one is already used.
fix_hint: Collect the rows and issue one `createMany`/`bulk_create`/`insert_all` (or a single `update ... where id in (...)`) chunked at about 1000 rows per statement, inside the transaction from DAT-013 if the loop is part of a multi-step write.

### DAT-013 Transactions around multi-step writes
severity: high
tier: static
fix: guided
why: Without a transaction, a failure halfway through leaves the database in a state your code never expects — an order with no line items, a paid subscription with no user record, credits deducted for a job that never ran. These are the bugs that need manual data repair.
verify:
  static: Find every operation that writes more than one row or touches more than one table in a single logical step (stack ref: "routes and handlers", "data access", "webhook handlers"): signup creating user plus profile plus org membership; checkout creating an order, its items, and decrementing stock; a payment webhook marking an invoice paid and granting entitlement; credit or quota deduction paired with the work it pays for; any "delete X and its children" that is not a database-level cascade. Each needs one transaction — `prisma.$transaction([...])` or the interactive form, `db.transaction()`, `with transaction.atomic():`, `ActiveRecord::Base.transaction`, `BEGIN`/`COMMIT` — covering all of the writes, not one call per write. Fails to look for specifically: a transaction opened but the second write issued on a different client or pool connection outside it; an external API call (Stripe, email, an HTTP fetch) inside the transaction, which holds row locks for the length of a network call and is its own outage; `Promise.all` of writes passed to a transaction helper that does not actually wrap them; and a "transaction" that catches the error and continues. Where a write genuinely cannot be transactional because it spans systems (a database row plus a Stripe object), the correct pattern is an idempotency key and a reconciliation path — check one exists and say so rather than failing blindly.
evidence: per operation — `<name> — writes <table>, <table> at file:line — transaction <present at file:line | MISSING>`; any external call found inside a transaction with its file:line.
fix_hint: Wrap the whole sequence in the stack's transaction helper so all writes share one connection, move external API calls outside it (do the call first and record its id, or enqueue it after commit), and let the error propagate so the rollback actually happens.

### DAT-014 Unique and foreign-key constraints enforced at DB level
severity: medium
tier: static
fix: easy
why: An application-level "check if it exists, then insert" loses the race between two concurrent requests, so you get two accounts on one email or two active subscriptions for one user. Only the database can make that impossible.
verify:
  static: From the schema (stack ref: "data access"), check three families of constraint. Unique: every column the app treats as unique — `email`, `username`, `slug`, `stripe_customer_id`, `stripe_subscription_id`, invite tokens, `(user_id, key)` settings pairs, `(org_id, user_id)` memberships — must carry a `unique` constraint or unique index in the schema, not just a `findFirst` guard in code. Grep for the check-then-insert pattern (`findUnique`/`findFirst`/`exists()`/`filter(...).exists()` immediately followed by a create) and confirm a DB constraint backs it; without one, that is the fail. Foreign keys: every `*_id` column referencing another table must be declared as an actual foreign key with an explicit `on delete` behaviour (`cascade`, `set null`, or `restrict` — an unstated default of `no action` is worth naming, and it interacts with DAT-020). Note any FK declared only in the ORM's type layer but absent from the SQL — Prisma with `relationMode = "prisma"` and Django with `db_constraint=False` both do this, and neither enforces anything in the database. Not-null and check: required fields nullable in the DB, status/enum columns stored as free text with no check constraint or enum type, money stored as `float` rather than integer cents or `numeric`.
evidence: per issue — `<table>.<column> — treated as unique at file:line, no DB constraint`; `<table>.<column> — FK in ORM only (relationMode prisma)`; the constraints that are present, so a reviewer can see the list was complete.
fix_hint: Add the missing constraints in one migration (`alter table <t> add constraint <n> unique (<cols>)`, `... add foreign key (<col>) references <t2>(id) on delete cascade`); the migration will fail if duplicates already exist, which is the cheapest way to discover them — dedupe first, then apply.

### DAT-015 Migrations committed, apply cleanly to a fresh DB, rollback plan exists
severity: high
tier: local
fix: guided
why: If the schema only exists in the production database, there is no way to stand up a new environment, onboard a second developer, or restore after a failure. A migration that has been hand-edited after being applied is worse: it will run differently for the next person than it did for you.
verify:
  static: Confirm the migrations directory is committed and tracked (`git ls-files` over `prisma/migrations`, `supabase/migrations`, `migrations/`, `db/migrate`, `alembic/versions`) and not gitignored. Check for drift between the schema and the migrations — `prisma migrate diff --from-migrations --to-schema-datamodel` (empty diff expected), `python manage.py makemigrations --check --dry-run` (no changes expected), `alembic check`, `rails db:migrate:status`. Look for signs of editing after apply: a migration file modified in a commit later than the one that added it, or a Supabase project where the dashboard was used for schema changes and no matching migration exists. For rollback, look for `down`/`downgrade` functions with real bodies (not `pass` or an empty block), or a written plan (`docs/`, `RUNBOOK.md`, a deploy checklist). Also flag destructive migrations — `drop column`, `drop table`, a rename, a `not null` added without a default — that would break the currently deployed code the moment they apply; those need the expand/contract sequence rather than a rollback, and the rollback of a dropped column does not bring the data back.
  local: Create a brand-new, empty database and run every migration into it from zero. `createdb prelaunch_scratch` against the local Postgres, or a fresh SQLite file where the stack supports it. Then run the stack's migrate command with the scratch connection string passed in explicitly as a one-shot environment override, because every one of these tools reads `DATABASE_URL` from `.env` by default and will otherwise migrate whatever the app is pointed at: `DATABASE_URL=postgres://…/prelaunch_scratch npx prisma migrate deploy`, `DATABASE_URL=postgres://…/prelaunch_scratch alembic upgrade head`, `DATABASE_URL=postgres://…/prelaunch_scratch python manage.py migrate`, `DATABASE_URL=postgres://…/prelaunch_scratch bin/rails db:migrate`. Confirm the override took effect before trusting the result — the tool prints the target, or `\dt` on the scratch database shows the tables. Run no seed. Any error, any migration that depends on data or an extension that is not created by an earlier migration, and any need to run something manually first is a fail. `dropdb prelaunch_scratch` afterwards. Never run this, and never run a reset command such as `supabase db reset` or `prisma migrate reset`, against any database the app or this audit connects to: production, staging, or the local development database — a reset destroys that database in place and re-runs the seed, which would take the shared test account other checks depend on with it. If the only Postgres available is the local development database and you cannot create a second one, record `error` with that reason and keep the static result; do not reset it.
evidence: `git ls-files <migrations dir> → N files tracked`; the drift command and its output; `migrate from zero on scratch db → OK` or the exact error and the failing migration filename; the rollback mechanism found, or `no down migrations and no written plan`.
fix_hint: Generate a migration for whatever drifted so the files are the source of truth, fix the from-zero failure (usually a missing `create extension` or an ordering dependency), and write the rollback plan for the next destructive change as an expand/contract sequence: add the new column, backfill, switch the code, drop the old column in a later deploy.

### DAT-020 Account deletion cascades to every table and to storage objects
severity: critical
tier: local
fix: guided
why: Deleting the user row while their messages, uploads, and subscription records stay behind is a broken privacy promise and, in most jurisdictions, an unmet legal obligation. Orphaned rows also crash the app when something joins back to a user that no longer exists.
verify:
  static: Build two lists and diff them. First, from the schema (stack ref: "data access"), every table with a column referencing the user — `user_id`, `owner_id`, `author_id`, `created_by`, plus the auth provider's own tables (`auth.users`, `auth.sessions`, `auth.identities` on Supabase) and any join table. For each, note the FK's `on delete` behaviour; a cascade at the database level does the work for you, `no action` or an ORM-only relation (DAT-014) does not. Second, from the deletion path (stack ref: "routes and handlers" — the account settings handler, an RPC, or a background job), every table the code actually deletes from. The difference between the lists is the finding. Then check three things the schema will not tell you: storage objects under the user's prefix are deleted too (stack ref: "file uploads") — a cascade never touches a bucket; the external records are handled (Stripe customer deleted or detached, the auth provider's user removed, the mailing-list contact unsubscribed, search-index documents purged); and the whole deletion runs in one transaction (DAT-013) so a half-deleted account cannot exist.
  local: This is the runtime half of FLOW-009. If the flows domain has already run FLOW-009 in this audit, read its finding in `.pre-launch/findings/flows.json`, reuse its evidence, and record `verified_by: local` citing FLOW-009 rather than deleting a second account. Otherwise, run the probe only if you can create a second, disposable account — the shared test account must survive for the checks that come after this one, so never delete it here. With the disposable account: sign up, create one row in each user-owned table the app exposes and upload one file, then run the app's own deletion flow. Afterwards query each table for that user id (expect zero rows), list the storage prefix (expect no objects), and attempt a login with the old credentials (expect failure). If no second account can be created, record the static result and state plainly that the runtime half was not run and why; if you did run it on the shared account because no other was possible, say in the evidence that the account is gone and later checks must create their own.
evidence: the table-by-table diff — `<table> — user FK, on delete <behaviour>, deleted by code at file:line` or `<table> — user FK, NOT deleted`; storage prefix and object count after deletion; `login as deleted user → 200 (expected 401)`; when reused, `reused FLOW-009 evidence from .pre-launch/findings/flows.json`.
fix_hint: Make the deletion one transactional routine that removes the storage prefix and the external provider records first and then the rows, and add `on delete cascade` to the child foreign keys so a table added later is covered by default rather than by remembering.

### DAT-021 PII inventory exists; sensitive fields encrypted at rest
severity: medium
tier: static
fix: guided
why: You cannot honour a deletion or export request, or answer a breach notification question, for data you have not written down that you hold. And a column of plaintext government IDs or health notes turns any read-access bug into a reportable incident.
verify:
  static: Produce the inventory yourself from the schema (stack ref: "data access") — that list is the deliverable of this check. Walk every table and flag columns holding personal data: names, email, phone, postal address, date of birth, IP address, device id, precise location, government or tax identifiers, health or biometric data, uploaded documents, free-text notes about a person, and anything from a third party (Stripe customer id, OAuth provider id). Note the storage buckets too. Then check whether the project already documents this (`docs/`, a data map, a privacy policy listing categories) and whether the documented list matches what the schema actually holds — a mismatch is the finding, and the privacy policy is the version customers rely on. For encryption: managed Postgres and S3/GCS encrypt at rest by default, so say so and treat that as the baseline rather than a pass on its own. Above the baseline, the high-sensitivity columns you flagged should be encrypted or hashed at the column level — `pgcrypto`/`pgsodium`, Rails `encrypts`, Django field encryption, application-side envelope encryption with KMS — and third-party access tokens and refresh tokens stored encrypted rather than plaintext. Hard fails whatever else is in place: a raw card number or CVV stored at all, a full national identifier stored when a last-four would do, and passwords not hashed with a slow KDF.

fix_hint: Commit the inventory you just built as a data map in `docs/`, reconcile it with the privacy policy, and add column-level encryption for the highest-sensitivity fields (`pgcrypto`/`pgsodium` or the framework's encrypted attribute) plus encryption for stored third-party tokens.

### DAT-022 Retention and purge jobs for logs, soft-deleted rows, stale sessions
severity: medium
tier: static
fix: guided
why: Data you keep forever is data you can still leak, and a privacy policy that promises deletion within thirty days is a promise the database has to keep. Unpurged event and log tables also become the largest thing in the database and slow every backup and migration.
verify:
  static: List the tables that grow without bound and hold something worth expiring: soft-deleted rows (`deleted_at is not null`), sessions and refresh tokens, password-reset and email-verification tokens, webhook event logs, audit and activity logs, rate-limit counters, job queue history, analytics events, orphaned uploads. For each, look for a purge with a stated window (stack ref: "background jobs") — a scheduled function, a `pg_cron` job, a `vercel.json` cron entry, a Celery beat schedule, a Sidekiq cron, a `DELETE FROM ... WHERE created_at < now() - interval '...'`, or the provider's own TTL (a Postgres partition drop, a DynamoDB TTL attribute, an S3 lifecycle rule for old objects). Two things to check beyond existence: the job is actually scheduled somewhere, not just defined as a function nobody calls — trace it to a cron config or scheduler registration; and the window matches what the privacy policy says. ### DAT-023 Timestamps stored in UTC
severity: low
tier: static
fix: easy
why: A naive timestamp column silently records whatever timezone the writing process happened to be in, so rows written by a local machine, a CI job, and a production container in three regions cannot be ordered against each other. It surfaces later as off-by-hours bugs in schedules, trials, and billing periods.
verify:
  static: Read the schema (stack ref: "data access"). On Postgres, every timestamp column should be `timestamptz` (`timestamp with time zone`); a plain `timestamp` on anything time-ordered is the fail — check Prisma (`@db.Timestamptz`, since Prisma's `DateTime` maps to `timestamp(3)` on some setups), Drizzle (`timestamp(..., { withTimezone: true })`), and raw migrations. On MySQL, `TIMESTAMP` converts to UTC and `DATETIME` does not. Then check the writing side: `USE_TZ = True` in Django settings; `datetime.now()` without a timezone (use `datetime.now(timezone.utc)`); `Time.now` versus `Time.current` with `config.time_zone` in Rails; a timestamp formatted to a string with `toLocaleString`/`strftime` and stored in a text column; a default of `now()` in the database (good, one clock) versus a timestamp supplied by the application (many clocks). Finally confirm timezone conversion happens at display time only — a date rendered from the raw column without conversion is a presentation bug, but a date converted before storage is a data bug.
evidence: per column — `<table>.<column> — timestamptz | timestamp (naive) — file:line`; the settings flag (`USE_TZ`, `config.time_zone`) and any `datetime.now()` without tzinfo.
fix_hint: Alter the naive columns to `timestamptz` in a migration, stating the source timezone explicitly (`alter table t alter column c type timestamptz using c at time zone 'UTC'`) so existing rows are interpreted rather than shifted, and set database `now()` defaults so one clock writes them all.

### DAT-024 Database region matches residency claims in privacy policy
severity: medium
tier: attest
fix: none
why: "Your data is stored in the EU" is a contractual statement, and enterprise buyers and regulators both read it. Being wrong is a compliance problem the moment anyone checks, and backups or logs in a different region are the usual reason a true-sounding claim is false.

  static: Find the actual regions first. The database: a Supabase project ref plus its region, a Neon/PlanetScale region, an AWS region in Terraform/env (`RDS`, `AWS_REGION`), `primary_region` in `fly.toml`, `regions` in `vercel.json`, a GCP `location`. ### DAT-025 Soft vs hard delete consistent with privacy policy promises
severity: medium
tier: static
fix: guided
why: If the policy says data is deleted and the code only sets `deleted_at`, the data is still there — in the database, in every backup, and in any query that forgets the filter. The opposite mistake is as bad: a hard delete where the policy promised a recovery window destroys data a customer was told they could get back.
verify:
  static: Find the deletion model — grep for `deleted_at`, `is_deleted`, `archived_at`, `discarded_at`, `status = 'deleted'`, `acts_as_paranoid`, `SoftDeleteMixin`, Prisma middleware filtering deleted rows. Then check three things. (1) Consistency with the policy: read the deletion and retention sentences in the privacy policy and compare. Soft delete alone under a promise of erasure is a fail unless a purge job (DAT-022) hard-deletes on a stated timer — find that job or the check fails. A hard delete under a promise of a thirty-day recovery window is also a fail. (2) Query hygiene: every read path must exclude soft-deleted rows. Grep the data access layer for queries against soft-deletable tables that lack the `deleted_at is null` predicate — one missing filter and deleted content reappears in a list, a search result, or an export, which is the bug users report as "you didn't delete it". Check aggregates and counts too. (3) The traps soft delete creates: a unique constraint on `email` or `slug` (DAT-014) blocks a user from re-registering after a soft delete unless the constraint is partial (`where deleted_at is null`) or the value is tombstoned; and a cascade from the parent's hard delete will not fire from a soft delete, leaving children visible.
evidence: the deletion model per table with file:line; the policy sentence quoted beside what the code does; each read path missing the `deleted_at is null` filter as file:line; the purge job that eventually hard-deletes, or `none`.
fix_hint: Pick the model the policy promises and make the code match — either add the scheduled hard-delete purge that turns soft delete into a real erasure window, or switch to a hard delete inside a transaction — and enforce the `deleted_at is null` filter centrally in the data access layer or as a partial index rather than in each query.

### DAT-026 Application DB user has least privilege; not superuser
severity: high
tier: static
fix: guided
why: If the runtime connection is a superuser, a single SQL injection or a leaked connection string is not one table's worth of damage — it can drop the schema, disable RLS, read every other database on the instance, and in some setups read files from the host.
verify:
  static: Extract the username from the connection config (stack ref: "env vars", "data access") — the `user` in `DATABASE_URL`, the `POSTGRES_USER` in compose, the credentials in a Terraform module. Fail on the built-in superusers used directly for application traffic: Postgres `postgres`, MySQL `root`, SQL Server `sa`, Mongo's root user, and on Supabase the `service_role` key used for ordinary user requests rather than for a narrow set of admin operations (that overlaps DAT-004, which owns the exposure angle; this one owns the privilege level). With a connection available, get the facts rather than inferring them, and query the role by name rather than by session: `select rolname, rolsuper, rolcreatedb, rolcreaterole, rolbypassrls from pg_roles where rolname = '<the username you just extracted from the connection config>';` — `rolsuper` or `rolbypassrls` true on the application role is the fail, because bypassrls quietly undoes every DAT-002 policy. Do not substitute `current_user`: that reports whichever role your `psql` session opened with, which is usually an admin or the provider's default and not the role the app runs as — `current_user` is only the right answer if you opened the session with the app's own `DATABASE_URL`, and if you did, say so in the evidence. Also check whether the runtime role holds DDL rights on the application schema, naming the role the same way (`select has_schema_privilege('<app username>', 'public', 'create')`), and whether migrations run as a separate, more privileged role than the request path does; one role doing both is common and worth naming even where the platform offers no alternative. Where a managed provider ships exactly one role and no way to create another (some hosted plans), record that as the constraint rather than inventing a failure — but say what the blast radius therefore is.
evidence: `connection user <name>`; the `pg_roles` query output for `rolsuper`, `rolcreatedb`, `rolbypassrls`; whether migrations use a distinct role; the provider constraint if only one role exists.
fix_hint: Create a dedicated application role with `nosuperuser nocreatedb nobypassrls`, give it `grant usage on schema public` plus only `select, insert, update, delete` on the tables (and `usage` on sequences) — without the schema-level `usage` grant the role can see nothing at all and the app fails to start — keep DDL for the migration role, and swap the runtime `DATABASE_URL` to the new role before rotating the old password.

### DAT-027 Per-user storage and record quotas to prevent abuse
severity: medium
tier: static
fix: guided
when: features.uploads or features.user_content
why: A per-request size limit stops one huge file, not ten thousand small ones. Without a per-account ceiling, one script running overnight fills your storage bill or your table, and the cost lands on you before anyone notices.
verify:
  static: For each thing a user can create without limit — uploads, posts, comments, projects, API keys, invites, generated documents, AI outputs — look for a ceiling enforced server-side before the write (stack ref: "file uploads", "routes and handlers", "data access"). Acceptable forms: total bytes stored per user checked against a plan limit, a row count per user or per parent, a per-day creation cap, or a rate limit on the create endpoint. Fail on: only a per-request byte limit (SEC-047, SEC-067) with no cumulative total; a quota enforced only in the UI (a disabled button); a plan tier whose limits exist in the pricing page and Stripe but are never checked in code; and a quota checked with a `count()` immediately before an insert with no transaction or atomic counter, which two concurrent requests both pass (see DAT-013). Also check that the usage figure is derived from something that stays accurate — a counter column that is incremented on upload but never decremented on delete drifts until the quota is wrong in both directions. Where the app is genuinely invite-only or internal, a quota may be a considered omission; record that reasoning rather than failing silently.
evidence: per resource — `<resource> — quota <value> enforced at file:line` or `<resource> — NO per-user limit`; how usage is computed (live `sum`/`count` versus a counter column) and whether delete decrements it; the plan limits that exist in billing but not in code.
fix_hint: Enforce the cap in the create path inside the same transaction as the write — a `sum(size)` or `count(*)` against the user's rows compared to the plan limit, or an atomic counter with a check constraint — and return a clear quota error rather than a generic 500.
