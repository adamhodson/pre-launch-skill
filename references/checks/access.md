# Access checks (ACC)

Read `agents/domain-auditor.md` for procedure. Blocks below are checks; consult stack references for locations. Tools: `grep` and `git` for the repo half of every block; `python3` with only the standard library for reading policy JSON and writing the service inventory; `gh` for the GitHub half of ACC-006, and only when `gh auth status` exits zero; `dig` for the DNS half of ACC-009; `whois` for the registrar-lock half of ACC-009 where it is installed and the TLD returns a usable record; `curl` for ACC-010; `docker` for ACC-008, and only to read an image that already exists on the machine. None of these are required: if a tool is missing or unauthenticated, run the block's `static` entry, decide from that, and set `verified_by: static-fallback` with a note naming what you did not have. Install nothing.

**Most of this domain is attest, and unlike every other domain that is not a limitation, it is the subject.** The things that fail here — an account with one owner, a card that expired, a registrar login with no second factor, a former contractor who still has admin — are facts about people and provider dashboards, and no amount of reading the repository will produce them. What the repo does produce is the *list*: which services exist, which accounts they imply, and which of them the product cannot survive losing. That list is the deliverable. A founder answering eleven specific questions honestly at 11pm is worth more than a green tick derived from a config file, and an `unknown` recorded against a named service is a genuine finding, because it means nobody has checked either.

**Build the service inventory once, at the start of this domain, and write it to `.pre-launch/access/services.json`.** Five blocks (ACC-001, 002, 003, 004, 011) are questionnaires over this one list, and building it five times produces five different lists and five different question sets. Assemble it from six sources. First, source control and CI: `git remote -v` for the host and the org or user that owns the repo, plus the deploy and secret names in `.github/workflows/*.yml` or the equivalent. Second, the deploy platform and infrastructure config: `vercel.json`, `netlify.toml`, `wrangler.toml`, `fly.toml`, `render.yaml`, `app.yaml`, `Procfile`, `docker-compose*.yml`, `*.tf` provider and backend blocks, `Pulumi.yaml`, `serverless.yml`, a CloudFormation or SAM template — each names a cloud account, a project, or a hosting vendor. Third, environment variable names (stack ref: "env vars"), which name a vendor even when no package is installed: `STRIPE_SECRET_KEY`, `RESEND_API_KEY`, `SENDGRID_API_KEY`, `TWILIO_AUTH_TOKEN`, `SENTRY_DSN`, `POSTHOG_KEY`, `OPENAI_API_KEY`, `ANTHROPIC_API_KEY`, `SUPABASE_SERVICE_ROLE_KEY`, `DATABASE_URL` (read the host to identify the provider), `CLOUDFLARE_API_TOKEN`, `AWS_ACCESS_KEY_ID`. Fourth, the dependency manifest and mobile config for anything with a console behind it — an SDK implies an account. Fifth, the domain and DNS: the production hostname from the site URL config, plus whatever `vercel.json`, a Terraform DNS resource, a zone file, or a `CNAME` file says about who serves it; registrar and DNS are frequently two different companies and get two rows. Sixth, the README and any `docs/` operations page, which is often the only place the app store team, the analytics property, or the status page is named.

**One object per service, and the fields exist because the questions need them:** `{"service": "Namecheap", "category": "registrar", "account_hint": "domain example.com, from NEXT_PUBLIC_SITE_URL in .env.example:4", "source": "vercel.json:12 domains", "uptime_critical": true, "human_login": true}`. `account_hint` is what lets you ask about *this* account rather than about the vendor in the abstract, and a question that names the org, the project id, or the domain gets a real answer where "do you have MFA on GitHub?" gets a shrug. `uptime_critical` marks the services whose lapse takes the product down rather than degrading it, which is exactly the filter ACC-011 applies. `human_login` distinguishes a console somebody signs into from a machine-to-machine API that has no login at all and therefore no MFA question. Where the repo names an SDK but no account can be inferred, still write the row with `account_hint: unknown` — the row is the question. This inventory is not the same artifact as the compliance domain's `.pre-launch/compliance/inventory.json`, and neither replaces the other: that one is about what data flows to a vendor, this one is about who can log in and what happens when the card declines. Read it if it exists to save discovery work, and say in evidence that you did.

**Every artifact this domain writes goes under `.pre-launch/access/` and nowhere else.** A bare relative filename lands in the project root, which on a static site is served content, and `services.json` sitting in a repo root is both a stray file in the next commit and a published list of exactly which vendors hold this company's accounts. `/tmp` is no better: it survives the audit, collides between concurrent runs, and puts the evidence somewhere the report cannot cite. Create the directory once with `mkdir -p .pre-launch/access` before the first write. The names used below are `services.json`, `security.txt`, `security-legacy.txt`, `dns.txt`, and `workflows.txt`. Nothing in this domain is written into the project itself, ever.

**Never open a provider console, and never change anything at a provider.** This domain audits access; it must not exercise it. Do not attempt to sign into any dashboard, with the user's credentials or otherwise. Do not run a mutating API call: `gh api` read requests only, never `-X POST`, `-X PUT`, `-X PATCH`, `-X DELETE`, and never `-f`/`--field` on an endpoint that writes. Do not create, delete, rotate, or "test" a credential, an access key, a token, or a webhook. Do not test whether MFA works by triggering a challenge on somebody's account — an unexpected push prompt is indistinguishable from an attack, and it trains the owner to tap approve, which is the exact habit this check exists to protect. Do not claim, register, or purchase a DNS name to demonstrate a takeover; showing that the target does not resolve is the whole finding. Run `whois` against this project's own domain and against nothing else. All of this is what makes the questionnaire the right instrument: the human has the console, you have the list.

**Write the attest questions as a tick list, one line per service, phrased so the only answers are yes, no, and unknown.** Take the rows from `services.json`, name the account in the question, and record the answer against that row rather than in aggregate — a single "is MFA on everywhere?" gets a yes from everyone and evidences nothing, while `GitHub org acme — is 2FA required for every organisation member, not just enabled on your own account? [ ]` gets either a yes, a no, or a person opening a settings page. Record `unknown` where the user cannot check now, with the reason; `unknown` is `unverified`, never a pass, and it is a respectable answer. Where a product legitimately lacks the thing, record `n/a — <reason>` and move on: no containers means ACC-008 is `n/a — no container build`, no app store presence drops those rows out of ACC-001 and ACC-011, no production domain makes ACC-009 `n/a — no production domain configured`, and no GitHub leaves ACC-006's `gh` half `unverified` with its file-based half still run in full.

### ACC-001 MFA enabled on GitHub, cloud console, payment provider, registrar, DNS, email provider, app stores
severity: critical
tier: attest
fix: none
why: Every other control in this file assumes the account itself cannot be taken over. A password-only login on the registrar, the payment provider, or the source-control org is one reused password away from somebody else owning the domain, the money, or the ability to push code that deploys itself. It is also the failure with no technical remedy afterwards: you cannot patch your way out of a stranger holding your registrar login, and the recovery path runs through a vendor support queue that will take days it is not safe to spend.
verify:
  static: Build `.pre-launch/access/services.json` per the header rule if it does not exist yet, and keep only the rows with `human_login: true` — a machine-to-machine API key with no console behind it has no MFA question and saying so is better than a blank row. For each remaining row, sharpen `account_hint` so the question names the account: the org or user from `git remote -v`, the project or team id in a deploy config, the account id in a Terraform provider or backend block, the domain from the site URL config, the bundle identifier or Play package name for the store accounts. Then record what the repo shows about *how* machines authenticate, which is not the same question but changes what the human logins are for: `aws-actions/configure-aws-credentials` with `role-to-assume` and `id-token: write` is OIDC and has no standing key, a `google-github-actions/auth` block with `workload_identity_provider` is the same, while an `AWS_ACCESS_KEY_ID` or `GCP_SA_KEY` repository secret is a long-lived credential that a stolen console session can mint more of. Note also which provider is the password-reset root of trust — the email domain — because MFA on it protects every other account by transitivity, and its absence undoes MFA everywhere else.
  attest: One question per row, and ask for enforcement rather than presence wherever the service offers it, because "I have MFA" and "MFA is required for everyone on the account" are different facts and only the second one holds when a co-founder reuses a password. GitHub or GitLab — is two-factor required for the whole organisation, not merely enabled on your own account? Cloud console — two questions, not one, because they have different answers on almost every account and merging them lets a yes on the easy half hide a no on the hard one: is MFA enforced on the root or owner login, and separately, is it enforced on every other user with console access (ACC-005 owns whether root is used day to day, so ask only about the factor here)? Payment provider — is MFA on for every user on the Stripe, Paddle, Lemon Squeezy, or PayPal account, including the read-only ones? Registrar and DNS — as two separate questions, since they are usually two companies and the registrar is the one whose loss is unrecoverable. Email provider — including the shared mailbox or alias that receives password resets for all the others. App stores — Apple Developer and Google Play, separately, since a legacy account may predate the requirement. Error tracker, analytics, AI provider — lower stakes, still ask, since an AI provider console is a billing account with a spend limit somebody can raise. Then the question that decides how much the yes is worth: on the registrar, the email domain, and the cloud root, is the second factor an authenticator app or a hardware key rather than SMS? SIM-swap is the attack that takes registrar accounts, and an SMS second factor on the registrar is closer to a no than to a yes.
evidence: the inventory path and how many rows carry `human_login: true`; per service, the account identifier from `account_hint`, the answer as `enforced` / `on for my account only` / `off` / `unknown`, and the factor type where the user stated it; the services with no MFA listed first, since those are the finding; the machine-auth note per CI provider (`OIDC` or the long-lived secret name). ACC-002, ACC-003, ACC-004, and ACC-011 all read the same inventory and the account identifiers sharpened here, so write them once and cite this block rather than rebuilding the list.

### ACC-002 More than one owner on every critical service; recovery codes stored in password manager
severity: high
tier: attest
fix: none
why: The single-owner failure is not a security incident, it is a bus. One person holds the only login to the registrar, and then they are unreachable, or they leave badly, or they lose the phone with the authenticator on it — and with MFA correctly enforced and no recovery codes anywhere, the account is now as unavailable to you as you wanted it to be to an attacker. Recovery codes downloaded once and left in a browser downloads folder on the same laptop are the same as no recovery codes, because the event that loses you the phone is usually the event that loses you the laptop.
verify:
  static: From `.pre-launch/access/services.json`, mark the rows where a single owner is an existential risk rather than an inconvenience: registrar, DNS, cloud account, deploy platform, database, payment provider, source-control org, email domain, and the app store developer accounts. Then look for anything in the repo that names a second human: `CODEOWNERS`, a `MAINTAINERS` or `OWNERS` file, the distinct author identities in `git log --all --format='%an <%ae>' | sort -u`, a team handle in an alert route or on-call config, a `docs/` page listing account owners. Label this as weak evidence when you record it, because it shows who exists and has committed code, not who can log in to Namecheap — the two lists differ on almost every project and the gap between them is the point of the block.
  attest: Per critical row, three questions with a per-row answer. Does at least one other person have their own owner or admin login to this service — their own account with their own credentials, not the same shared username and password, which is ACC-004's finding and not a second owner? Where are this service's recovery or backup codes, and can the second person reach them: a shared vault in the team's password manager is the pass, and "in my downloads folder", "in a screenshot on my phone", "printed and in a drawer at my flat", or "in a vault only I can open" are all the finding. And on the email domain specifically, is there a second administrator, since the mailbox that receives every other service's password reset is the account whose sole ownership makes every other second owner theoretical. Then the question teams almost never have an answer to: is the password manager itself recoverable — an emergency access contact, a recovery kit held by somebody else, an organisation account with a second admin — because a team vault with one owner has simply moved the single point of failure one layer down and made it harder to see. Then the question that makes this block answerable for a solo founder, who has no second person to name and must not be graded as though they were hiding one: is there a break-glass path — a recovery kit, a sealed envelope, an emergency-access contact on the password manager, a trusted person holding credentials of their own — and specifically where is it and who can reach it? A solo operator with a real break-glass path is a note, not a failure; a solo operator with none is a fail, and it is the same fail as a two-person team with one owner.
evidence: per critical service, `owners: <n>` with the second owner named, or `sole owner`, or — for a one-person company — `sole owner — solo operator, break-glass: <where the recovery kit is and who can reach it>`, which is graded a note where that path exists and named credentials are reachable by somebody else, and a fail where it does not; where each service's recovery codes are held, or `not generated`; whether the email domain has a second administrator; whether the password manager has an emergency contact or recovery kit, or `unknown`; the weak repo evidence listed separately and labelled as such. MOB-013 owns the signing keystore and the iOS distribution credentials and cites this block for the general case, so read its answers rather than asking about keystores again here, and note in evidence that you did.

### ACC-003 No company service registered under a personal email
severity: high
tier: attest
fix: none
why: A service registered to a personal address is not the company's account, it is that person's, and every recovery path for it runs through a mailbox the company does not control and cannot revoke. When they leave, or their personal account is compromised, or the provider locks it for reasons nobody will explain, the company has no way to prove ownership to the vendor, because there is nothing to prove it with. It also breaks offboarding completely — ACC-004 asks whether a departure removes access, and you cannot remove somebody's access to their own email — and it is the reason the transfer, when it eventually happens, is a support ticket and a notarised letter rather than a settings change.
verify:
  static: Two sweeps, neither conclusive on its own, both cheap. Author identities: `git log --all --format='%ae' | sort | uniq -c | sort -rn` and the same for `%ce`, then reduce to domains and flag every commit authored from a free-mail domain (`gmail.com`, `googlemail.com`, `outlook.com`, `hotmail.com`, `live.com`, `yahoo.com`, `aol.com`, `icloud.com`, `me.com`, `proton.me`, `protonmail.com`, `pm.me`, `gmx.com` and the other `gmx.*` domains, `yandex.com` and the other `yandex.*` domains, `mail.ru`, `fastmail.com`, `hey.com`, `zoho.com`) or from a personal domain that is not the company's. This does not prove any service is registered to that address; it shows which identities are actually in play, and in a small team it is almost always the same address that registered the accounts. Note GitHub's `users.noreply.github.com` addresses separately — those are a privacy setting, not a personal-email finding. Contact and owner fields: `grep -rniE '(owner|maintainer|contact|author|notify|alerts?_to|billing_email|support_email)["]?[[:space:]]*[:=]' --include='*.json' --include='*.toml' --include='*.yml' --include='*.yaml' --include='*.tf' --include='*.tfvars' --include='CODEOWNERS' . <standard excludes>` and read each hit rather than counting them, since half will be package metadata that means nothing and half will be the address a provider actually mails. Then the addresses that will receive things, which matter more than the metadata: the `from` and `reply-to` in the email sending config (stack ref: "env vars"), the alert destination in the error tracker or on-call config, the `iodef` address in any CAA record the repo declares, and the billing or verification contact in any infrastructure code. Any of those on a personal domain is a finding in its own right regardless of what the user answers.
  attest: Per row of `.pre-launch/access/services.json`, one question: which email address is this account registered to, and is it on a domain the company controls? Then two follow-ups that decide how much a yes is worth. Is it a shared alias or group that more than one person can read — `billing@`, `ops@`, `admin@`, `founders@` — rather than one employee's named mailbox, because a named company mailbox is still a single-owner problem (ACC-002) even though the domain is right, and it is the one that bites when that person is the one who left. And for any service that is on a personal address, is there a plan and a date to transfer it, since the vendors differ wildly in how hard this is: a registrar transfer of account ownership and an Apple Developer account transfer to an organisation are both slow, manual, and identity-verified, and they are the two you least want to be doing during launch week.
evidence: the author-email domain histogram with counts, `noreply` addresses excluded and noted; every contact, owner, billing, or alert address found with file:line and its domain, personal ones first; per service, the registration address and a verdict of `company domain` / `shared alias` / `personal` / `unknown`; the transfer plan and date for anything personal, or `none`. ACC-010 reuses the address list when judging whether the `security.txt` contact is a real company mailbox, and ACC-011 reuses it for the billing-inbox question, so record it once here.

### ACC-004 Least-privilege service accounts; no shared logins; offboarding removes access
severity: medium
tier: attest
fix: none
why: A shared login turns every audit log into a record that says "somebody", which is the same as no audit log on the day you need one. An over-broad service account turns a leaked CI token from a bad afternoon into a full account compromise, because the token that was supposed to push a container image could also read every bucket and create users. And access that is never removed accumulates silently: the contractor from March, the co-founder who stopped coming to standups, the intern's personal access token still in the repository's deploy keys — nobody is being malicious, and every one of them is a live credential outside the company's control.
verify:
  static: Read the privilege material the repo does contain, which is more than teams expect, and keep `.pre-launch/access/services.json` open beside it so every principal you find can be attached to the service row it belongs to — a wildcard policy is a much larger finding on the row marked `uptime_critical` than on a scratch project, and the attest half below walks the same rows. Policy and role documents: `*.tf` and `*.tfvars` (`aws_iam_policy`, `aws_iam_role_policy`, `aws_iam_role` trust policies, `google_project_iam_member`, `azurerm_role_assignment`), Pulumi programs, CloudFormation and SAM templates, `serverless.yml` `iamRoleStatements`, Kubernetes `Role`, `ClusterRole`, and their bindings, and any bare policy JSON in the tree. In each, find the wildcard and the admin shortcut: `grep -rnE '"(Action|Resource)"[[:space:]]*:[[:space:]]*"\*"' .` plus the array form `"Action": ["*"]`, the managed-policy ARNs ending `AdministratorAccess` or `*FullAccess`, `roles/owner` and `roles/editor` in GCP bindings, `Owner` and `Contributor` in Azure assignments, and `verbs: ["*"]` or `resources: ["*"]` in Kubernetes rules. Every hit is a row with file:line and the principal it attaches to, and a wildcard `Resource` with a narrow `Action` is a different and much smaller finding than a wildcard `Action`, so say which. Service-account key material: search for `*serviceAccount*.json`, `*service-account*.json`, `*-key.json`, `credentials.json`, `*.pem`, and any file containing a `"private_key"` field, and for each run `git check-ignore -v <path>` and check whether it was ever committed with `git log --all --diff-filter=A --name-only`. Do not open, decrypt, print, or use the key material; path, ignore status, and history are the entire output, and SEC-001 and SEC-002 own the leak verdict, so cite them and keep this block to the privilege question. Then note the shape that removes the credential entirely: CI authenticating by OIDC or workload identity federation rather than a stored key, a Terraform backend using a role assumption rather than a static access key, a database connection using IAM auth. Where that shape is present, say so, because it is the answer to most of what this block is worried about.
  attest: Three questions, each answered per service rather than once. Shared logins: is there any account where two or more people use the same username and password — a `founders@` mailbox with one shared password, one registrar login everybody uses, a single database admin user in a team chat message — and if so, which ones, since the honest answer on a two-person team is usually yes for at least the registrar and that is worth knowing rather than hiding. Offboarding: has anyone left, been offboarded, or simply stopped working on this project, and if so was their access removed from every row of the inventory, including the ones nobody thinks of — the shared password-manager vault, the error tracker, the AI provider console, the app store team, their SSH keys and personal access tokens on the repository, and any deploy key or webhook they created? Is that list written down anywhere, so the next departure is a checklist rather than a memory test? Least privilege for humans: does everyone holding an owner or admin role actually need it, or is admin simply the role everybody got on day one because it was faster? DAT-026 owns the application database role's privileges and ACC-005 owns the cloud root account, so cite both rather than re-deriving them here.
evidence: every wildcard grant or admin-role assignment with file:line, the principal it attaches to, and whether the wildcard is on action or resource; every service-account key file with path, gitignore status, and whether it appears in history, cited to SEC-001 and SEC-002; whether CI uses OIDC or a stored long-lived key, per pipeline; the shared logins named; the offboarding answer with the list of services actually checked, or `no departures yet`, or `unconfirmed`; the offboarding checklist path or `none written`. ACC-007 reads the shared-login and offboarding answers when judging who can currently read production secrets, so record them in a form that block can quote.

### ACC-005 Cloud root/owner account not used daily; cloud audit logging on
severity: medium
tier: attest
fix: none
why: The root or owner account has no permission boundary. No policy restricts it, no service control policy applies to it, and it can change the billing details, close the account, and delete the audit trail that would have shown any of it happening. Using it for daily work means the one credential worth the most to an attacker is also the one typed most often, on the most machines, into the most password fields. Audit logging is the other half of the same problem: without it you cannot answer the only question that matters after any incident, which is what they did and when, and the answer "we do not know" is what turns a contained compromise into a full rebuild.
verify:
  static: Work out which cloud is actually in play from the inventory and the infrastructure code — a `provider "aws"` or `google` or `azurerm` block, a Terraform backend, a `fly.toml`, an `app.yaml`, a `wrangler.toml`, a `render.yaml` — and record the account, project, or subscription identifier wherever the repo names it, since the question has to name the account. If the product has no cloud console at all because everything is on a platform plus a hosted database, say so plainly and scope the questions to those platforms' own owner accounts and audit logs rather than inventing an AWS finding for a project with no AWS. Where there is a cloud, look for audit logging declared as code, which is the only half of this you can verify without a console: an `aws_cloudtrail` resource with `is_multi_region_trail` set and a log bucket, `google_project_iam_audit_config` with `DATA_READ` and `DATA_WRITE` log types enabled rather than only `ADMIN_READ`, an `azurerm_monitor_diagnostic_setting` on the subscription activity log, or a platform equivalent. Record the retention period and the destination, and note specifically whether the destination sits in the same account under a role that can delete it, because a trail an attacker with account access can wipe is a trail that will be wiped — an append-only or cross-account log bucket with object lock is the shape that survives. Note too whether anything reads the log: a metric filter and alarm on root login, on IAM policy changes, or on trail deletion, versus a bucket that has never been opened.
  attest: Ask about the root account first, since it is the shorter list. Is the cloud root or owner login used for day-to-day work, or only for the handful of operations that genuinely require it — billing changes, account closure, support plan changes, and enabling organisation-level features? Are there root access keys, which for AWS is the single worst credential that can exist in an account and whose correct count is zero, and if any exist can they be deleted today? Is the root login's second factor a hardware key or an authenticator rather than SMS, and is the recovery contact address one the company controls (ACC-003 owns the address question generally, so cite it and ask only about root here)? Then audit logging: is the trail or audit log actually enabled in the production account rather than only in the one where the Terraform was first run, does it cover every region rather than the one region you use today, and does anyone or anything read it — an alert, a weekly glance, a SIEM — or is it purely archival? A yes on logging with a no on reading is not a failure, but say so in the finding, because it changes the incident story from "we investigated" to "we have the tapes and no player".
evidence: the cloud and the account, project, or subscription identifier from the repo, or `no cloud console — platform-hosted only` with the platforms named; the audit-log resources found with file:line, their retention, their destination, and whether that destination is deletable from the audited account, or `not declared in code`; whether any alert reads the log, with file:line; the user's answers on root daily use, root access keys and their count, root second-factor type, and audit logging enabled and read, each as `yes` / `no` / `unknown`. ACC-004 reads the audit-logging answer when judging whether an offboarding can be evidenced rather than merely asserted.

### ACC-006 Branch protection, required review, secret scanning, Actions pinned by SHA, Dependabot on
severity: medium
tier: static
fix: easy
why: The CI pipeline is a deploy path with production credentials in scope, and it runs whatever the owner of a third-party action pushed to a mutable tag five minutes ago. A tag is not a version: `@v4` can be repointed at any commit by whoever controls that repository, which is how a supply-chain compromise reaches your secrets without anyone touching your code or your dependencies. An unprotected default branch is the same risk by a shorter route — anyone with write access, or anyone holding a stolen token, pushes directly to the branch that deploys, and the review that would have caught it never happens because it was never required.
verify:
  static: Read every workflow file — `.github/workflows/*.yml` and `*.yaml`, or `.gitlab-ci.yml`, `.circleci/config.yml`, `bitbucket-pipelines.yml` where the pinning question becomes image and orb versions instead — and answer four questions from the files plus two from the GitHub API. Pinning: list every reference first with `grep -rnE 'uses:[[:space:]]*[^ ]+@' .github/workflows`, then split that list rather than running a second search for the bad ones — the pinned subset is the lines matching `@[0-9a-f]{40}` and everything else is unpinned, which is the only classification that leaves no gap, since a tag with a trailing comment (`@v4 # v4.1.7`) escapes any pattern anchored to the end of the line and would otherwise be counted as neither. Two more forms have to be classified rather than left to escape the enumeration: a sub-path action, `org/repo/path/to/action@ref`, whose `@ref` is judged exactly like any other and which the enumeration already catches provided you read the whole reference rather than the first two path segments; and a container action, `uses: docker://image:tag`, which has no `@` at all and so never appears in the list — search for it separately with `grep -rn 'uses:[[:space:]]*docker://' .github/workflows` and judge it on the same rule, a digest reference passing and a mutable tag failing. A `uses:` naming a local path (`./.github/actions/<name>`) is first-party code in this repository and needs no pin; say so rather than counting it as unpinned. GitHub's own `actions/*` and `github/*` namespaces are lower risk but not zero, so list them separately rather than exempting them silently, and where an action is pinned by SHA note whether a trailing comment records which version it is, because an unlabelled SHA is one nobody will ever dare update. Token permissions: look for a `permissions:` block at workflow or job level; its absence means the repository default applies, which on repositories created before the default changed is read-write across the whole `GITHUB_TOKEN`, so record the absence as the finding and name `permissions: contents: read` as the baseline to add. The dangerous trigger: `grep -rn 'pull_request_target' .github/workflows` and for each hit read whether the job then checks out the pull request head (a `ref:` of `github.event.pull_request.head.sha` or `head.ref`) and runs anything from it — an install, a build, a test, a lint. That combination executes untrusted code from a fork with the repository's secrets in scope, and it is a critical finding wherever it appears regardless of this block's overall severity, so say so explicitly in the evidence; SEC-005 owns secrets leaking into build logs, so cite it for that half. Dependency updates: `.github/dependabot.yml`, a `renovate.json` or `.renovaterc*`, or a `renovate` key in `package.json`, and check the ecosystems it covers rather than just its existence — a Dependabot config watching `npm` but not `github-actions` leaves every pin above to rot, and one that ignores `docker` on a repo with a Dockerfile leaves the base image (ACC-008) unwatched. Then the two settings that live only on GitHub. Run `gh auth status` first, and if it does not exit zero record the whole `gh` half as `unverified — gh not authenticated`, keep every file-based finding above, and put the two questions to the user instead. With `gh` authenticated: `gh api repos/{owner}/{repo} --jq '{visibility, default_branch, security_and_analysis}'` gives the visibility, the real default branch name (read it rather than assuming `main`), and the `secret_scanning` and `secret_scanning_push_protection` states. **An absent `security_and_analysis` object is ambiguous in exactly the way the 404 below is** and must not be reported as "unavailable on this plan": the object is omitted both when the feature is not available to the repository and when the token lacks repository admin scope, and the response does not distinguish them. Record `absent — feature unavailable or no admin scope` and ask the user which it is; never assert either cause from the absence alone, and never record it as scanning being off. Branch protection: `gh api repos/{owner}/{repo}/branches/<default branch>/protection` and read `required_pull_request_reviews.required_approving_review_count`, `required_status_checks.contexts`, `enforce_admins`, and `allow_force_pushes`. **A 404 from that endpoint is ambiguous and must never be recorded as a fail:** it is returned both when no protection rule exists and when the token lacks the repository admin scope needed to read one, and the response does not distinguish them. Record `unverified` with both possibilities named and ask the user which it is. A branch protected by the newer rulesets feature can also leave this endpoint empty while being fully protected, so check `gh api repos/{owner}/{repo}/rules/branches/<default branch>` before concluding anything at all. REL-013 owns whether CI actually blocks the deploy when tests fail, so read its evidence for the required-status-check question rather than re-deriving it, and record the workflow inventory to `.pre-launch/access/workflows.txt` so both blocks quote the same file list.
evidence: pinned versus unpinned `uses:` lines with file:line and the tag named, first-party and third-party listed separately; the `permissions:` block or its absence per workflow with file:line; every `pull_request_target` hit with a verdict on whether it checks out and executes the pull request head, flagged critical where it does; the Dependabot or Renovate config path and the ecosystems it covers, or `none found`; from `gh`, the repository visibility, the default branch name, secret scanning and push protection state (or `absent — feature unavailable or no admin scope`, with the user's answer where they gave one), and the branch protection fields — or `unverified` with the exact reason, one of `gh not authenticated`, `404 — no rule or no admin scope`, or `ruleset API checked: <result>`. Never record the 404 as a fail. ACC-007 reads `.pre-launch/access/workflows.txt` for which production secrets CI injects at deploy time, and REL-013 reads the branch-protection output for its required-status-check verdict, so write the workflow list and the protection fields once here rather than twice.
fix_hint: Repin every third-party `uses:` to a full commit SHA with the version in a trailing comment, add `permissions: contents: read` at the top of each workflow and widen it per job only where a job genuinely needs more, remove any `pull_request_target` job that checks out and executes the pull request head by splitting it into a `pull_request` job that runs the untrusted code with no secrets plus a privileged `workflow_run` job that only posts the result, add a `.github/dependabot.yml` covering `github-actions` and `docker` alongside the app's own ecosystem, and in repository settings require a pull request with at least one approving review plus the CI status check on the default branch, disable force pushes, apply the rules to administrators, and turn on secret scanning with push protection.

### ACC-007 Prod secrets in a secrets manager; rotation runbook for a leaked key
severity: high
tier: attest
fix: none
why: Production secrets end up somewhere; the only question is whether that somewhere has an access log, a revoke button, and a second copy. A `.env.production` on one laptop, pasted into a chat thread when the second developer joined, has none of the three, and nobody can say who holds it. The runbook matters even more than the manager, because the hour after a key leaks is exactly when a team discovers that nobody knows which four places that value is set, what order to change them in, or how long the app is down in between — and that discovery, made under pressure with a key actively being abused, is how a contained leak becomes an outage.
verify:
  static: Establish how production secrets actually reach the running process (stack ref: "env vars", and the deploy platform's stack file, whose "env vars" and "known traps" sections say where values live and how they are scoped per environment). The shapes that pass: the platform's own encrypted environment store scoped to production (Vercel or Netlify environment variables with a production scope, `fly secrets`, Cloudflare Workers secrets, Render or Railway variables), a dedicated manager referenced from infrastructure code or a startup command (Doppler, 1Password Secrets Automation and `op run`, AWS Secrets Manager or SSM Parameter Store, GCP Secret Manager, Azure Key Vault, HashiCorp Vault, Infisical), or CI secrets injected at deploy time. The shapes that fail, each recorded with file:line: a committed `.env.production`, `.env.prod`, or `.env.live`, or a `secrets/` directory in the tree, each run through `git check-ignore -v` and checked against history — SEC-001 and SEC-002 own the leak verdict on those, so cite them and record here only the fact about where secrets are kept; plaintext `env:` values in a `docker-compose.yml` or a Kubernetes manifest where a `secretKeyRef` or an external-secrets operator belongs; a `terraform.tfvars` carrying credentials, and Terraform state either committed or stored in an unencrypted bucket, since state holds every secret in cleartext no matter how carefully it was passed in. Then check the scoping, which is the failure that looks fine: one environment store shared across preview and production means every preview deployment can read the production keys, and on a public repository that includes a preview built from a fork's pull request. Finally look for the rotation runbook — `docs/runbook*`, `docs/security*`, `docs/incident*`, `SECURITY.md`, or a README section — and judge it the way REL-026 judges runbooks rather than counting it: does it name, per credential, where the key is issued, every place it is set, the order to change them in so the app stays up mid-rotation, and how to confirm the old key is actually dead?
  attest: Take the production secret list from `.env.example` and the deploy config so the questions are concrete, then ask three things. For each secret, where is the production value stored and who can read it — and if the answer for any of them is a person's laptop, a chat message, a shared document, or a ticket, that is the finding and it is the one the repository could never have shown you. When was each last rotated, and does anyone besides the person who created it know how? And the rehearsal question, which is the whole point of the block: if the payment provider's secret key were published publicly right now, who rotates it, in what order, and how long is the app broken? A named person plus a rough number is the pass; "we would figure it out" is the finding, and it is worth writing down verbatim. Ask separately whether preview and staging share the production store, since users often do not know, and whether any former collaborator still holds a copy — ACC-004's offboarding answer is the input here, so read it rather than asking twice.
evidence: how production secrets are injected, named with file:line or the platform feature, noting per secret where it differs; whether preview or staging shares the production store; every plaintext secret store found in the tree with path, ignore status, and history, cited to SEC-001 and SEC-002; the rotation runbook path with a one-line judgement of whether it is followable, or `none found`; per secret, the last rotation date and who can rotate it, or `unknown`; the leaked-key walkthrough answer verbatim with the named person and the downtime estimate, or `unconfirmed`. SEC-062 owns whether each third-party key is scoped to the minimum and rotatable, so cite it for scope and keep this block to storage and procedure.

### ACC-008 Containers run non-root, minimal base image, no secrets in layers
severity: medium
tier: static
fix: easy
why: A container running as root is one escape or one writable host mount away from root on the machine, and in the meantime every file the process writes is root-owned in a way that breaks the next deploy. A base image pinned to `latest` means the software you tested and the software that deploys next Tuesday are different, with no record of the change and no way to reproduce the version that worked. And a secret baked into a layer is permanent: deleting the file in a later `RUN` leaves it intact in the layer beneath, readable with one command by anyone who can pull the image, which on a public registry is everyone.
verify:
  static: If there is no `Dockerfile`, no `Containerfile`, no `docker-compose*.yml` that builds an image, and no container produced by the deploy config, record `n/a — no container build in this project` with the searches that returned nothing and stop; a serverless or platform-managed deploy is a legitimate architecture and not a finding. Otherwise, per Dockerfile, five things. The user: a `USER` instruction naming a non-root user in the *final* stage, with that user created earlier by `adduser`, `useradd`, or `addgroup`, or supplied by a base image that ships one such as the `node` image's `node` user. No `USER` at all means root, `USER root` as the last one means root, and a `USER` set in a build stage but not carried into the final stage does nothing at all — that last one is the common miss and it looks correct on a skim. The base image: `grep -nE '^FROM ' <Dockerfile>` and read each line — a specific version tag such as `node:22.11.0-alpine` passes, a digest pin is better, an untagged image or `:latest` fails, and a heavyweight base in the final stage (a full `ubuntu` or `debian`, a language SDK image where a runtime image would do) is a note about attack surface rather than a fail. A multi-stage build ending in a slim, alpine, or distroless runtime stage is the shape to look for; a single-stage build that ships the compiler, the package manager, and the source tree is what most projects actually have. Secrets in layers: `COPY .env` or `COPY .env*` in any form, an `ADD` of a credentials file, `COPY . .` on a project with no `.dockerignore`, an `ARG` whose name matches `SECRET|TOKEN|PASSWORD|KEY|DSN|CREDENTIAL` and is referenced in a `RUN` — a build argument's value is visible in `docker history` even when it never becomes an `ENV` — any `RUN` that prints one (`RUN echo $NPM_TOKEN`, `RUN cat ~/.npmrc`, a `RUN` with `set -x` wrapped around a credentialed command), and an `.npmrc`, `.netrc`, or `pip.conf` copied in with a token in it rather than mounted with `RUN --mount=type=secret`. SEC-005 owns secrets in CI and in shipped images generally, so record the file:line here and cite its verdict rather than issuing a second one. The `.dockerignore`: present, and excluding at least `.env*`, `.git`, `node_modules`, and any local database or key files — a missing `.dockerignore` alongside a `COPY . .` ships the entire `.git` directory inside the image, which means every secret ever committed and later removed travels to whoever pulls it, the same finding as SEC-002 delivered by a different route. Finally, and only if an image for this project already exists on the machine (`docker images` lists it), you may read its layers with `docker history --no-trunc <image>` to see the build arguments and the command behind each layer. Do not build an image, do not pull one, and do not run one; if none exists locally, say so and let the Dockerfile evidence stand.
evidence: per Dockerfile — the final-stage `USER` line with file:line, or `runs as root`; every `FROM` with its tag or digest and whether the final stage is a runtime image; each secret-bearing instruction with file:line and the directive quoted, cited to SEC-005; the `.dockerignore` path and the patterns it excludes, or `absent`; `docker history` findings only where an image already existed, with the image named; or `n/a — no container build in this project`. No other block consumes this evidence; this one cites SEC-005 for the secret-in-layer verdict and SEC-002 for the shipped `.git` directory rather than repeating either.
fix_hint: Create a non-root user in the Dockerfile and add a `USER` line as the last instruction of the final stage, pin every `FROM` to an explicit version tag or a digest, split the build into a builder stage plus a slim or distroless runtime stage so the toolchain does not ship, replace every credential-bearing `ARG` or `COPY` with a BuildKit `RUN --mount=type=secret`, and add a `.dockerignore` covering `.env*`, `.git`, and `node_modules` before the next image is built.

### ACC-009 Domain: registrar lock, CAA records, no dangling CNAMEs
severity: medium
tier: remote
fix: guided
why: These are three separate ways to lose the domain or a piece of it. Without a transfer lock, one compromised registrar login moves the domain to a registrar you cannot reach, and getting it back is a dispute process measured in weeks. Without a CAA record, any certificate authority in the world will issue a certificate for your domain to whoever can satisfy their validation, which is a much lower bar than owning the domain. And a CNAME pointing at a host that was deprovisioned last quarter is a subdomain takeover waiting for someone to claim that name at the provider and serve their content on your domain — with your cookies in scope if any are set on the parent, and with your reputation attached to whatever they publish.
verify:
  static: Collect the domain and every DNS name this project owns before querying anything, because the query list is the check. The apex and www from the site URL configuration (`NEXT_PUBLIC_SITE_URL`, `APP_URL`, `PUBLIC_URL`, `SITE_URL`, the canonical tag, the sitemap config); every subdomain named in deploy or infrastructure config — `vercel.json` domains, `netlify.toml`, `wrangler.toml` routes, `fly.toml`, Terraform `aws_route53_record`, `cloudflare_record`, or `google_dns_record_set` resources, a checked-in zone file, a `CNAME` file for GitHub Pages; the mail and verification hosts from the email provider setup, which is usually a bounce or Return-Path subdomain plus one or more DKIM selector CNAMEs; and any `docs.`, `status.`, `blog.`, `app.`, `api.`, `staging.`, or `beta.` host that appears in the README, in link targets, or in old deploy config. HYG-001 owns whether the DNS record *values* are the production ones and REL-017 owns TLS expiry and the apex-to-www redirect, so cite both and keep this block to lock, CAA, and dangling targets. Write the collected list to `.pre-launch/access/dns.txt`. If the repository names no production domain at all, record `n/a — no production domain configured` for the whole block and stop.
  remote: Three read-only queries, all against this project's own domain and its subdomains and nothing else. CAA: `dig +short CAA <apex domain>` — CAA is inherited down the tree, but a subdomain that publishes its own CAA record overrides the apex rather than adding to it, so query the apex by default and query a subdomain separately where it has a record of its own. No CAA record at all is a **note, not a fail**: it is the default state of most domains and it breaks nothing, but say plainly what it means, which is that any public certificate authority may issue for you. Where records do exist, read the `issue` and `issuewild` values and check they name the authority your certificate actually comes from — take the issuer from REL-017's `openssl` output rather than guessing — or the platform's (`letsencrypt.org`, `pki.goog`, `amazon.com`, `digicert.com`, `sectigo.com`); a CAA that excludes your own issuer is a renewal failure already scheduled, and that is a fail. Note whether an `iodef` value is set so failed issuance attempts are reported somewhere a human reads. Dangling CNAMEs: for each name in `dns.txt`, `dig +short CNAME <name>` to get the target. **An empty answer means the name has no CNAME at all — an A record, or nothing — and there is no second query to run**: record it `no CNAME — not applicable` and move to the next name, because running `dig +short` with an empty target queries the root zone and returns an answer that reads as "the target resolves". Only where a target came back do you check it: `dig +short <target>` to see whether it resolves, and where *that* returns nothing run `dig +noall +comment <target>` to read the status — an `NXDOMAIN` is the takeover risk. Record the name, the target, and the provider the target belongs to, because whether the name is claimable depends entirely on the provider: `*.s3.amazonaws.com`, `*.herokudns.com`, `*.azurewebsites.net`, `*.github.io`, `*.netlify.app`, `*.cloudfront.net`, `*.ghost.io`, and `*.myshopify.com` are the ones that recur. Do not attempt to claim, register, or purchase the target to prove the point; showing that it does not resolve is the entire finding. A CNAME whose target resolves but serves a provider's "no such application" page is a weaker signal of the same problem — note it separately and say which of the two you observed. Registrar lock: where `whois` is installed, `whois <domain> | grep -iE 'domain status|clientTransferProhibited|clientDeleteProhibited|clientUpdateProhibited|registry expiry'` and read the status codes; `clientTransferProhibited` present is the lock. Many TLDs return thin records, some rate-limit aggressively, and some registrars proxy the whole response, so an unparseable or empty answer is `unknown` — never a pass and never a fail — and the question goes to the user instead: is the transfer lock on at the registrar? Run `whois` against this domain only, never against a third party's.
evidence: the domain list from `.pre-launch/access/dns.txt` with the source of each name; the CAA answer verbatim with a verdict of `matches issuer` / `excludes issuer — fail` / `absent — note`, and whether `iodef` is set; per CNAME, a line of `<name> → <target> → resolves` or `<name> → <target> → NXDOMAIN, takeover risk, provider <x>`; the `whois` status lines with a lock verdict, or `whois unavailable — asked the user` with their answer; REL-017 and HYG-001 named as owning TLS expiry, the apex redirect, and the record values respectively. ACC-010 takes the production base URL from this list, and ACC-011 takes the registrar row from it.
fix_hint: Turn on the registrar's transfer lock, and registry lock as well where the registrar offers it for a domain this load-bearing; publish a CAA record at the apex naming only the authorities that actually issue for you plus an `iodef` mailto so failed attempts are reported; and delete every CNAME whose target no longer resolves, removing the DNS record first and before deprovisioning anything else, since the record is the exposure and the deprovisioned resource is only the opportunity.

### ACC-010 security.txt and vulnerability disclosure contact
severity: low
tier: static
fix: easy
why: When somebody finds a real bug in your product, the default outcome is that they cannot work out who to tell and either give up or post it publicly. Ten minutes of work turns that into an email to an address you monitor, before it becomes a tweet. The failure mode is not an incident, it is hearing about the incident from your users, and the low severity here reflects the cost of the fix rather than the value of having it.
verify:
  static: Look in the repository first: `public/.well-known/security.txt`, `static/.well-known/security.txt`, a bare `.well-known/security.txt`, or a route or rewrite that serves the path (`next.config` rewrites, `vercel.json` routes, `netlify.toml` redirects, an nginx location block, a framework route handler), plus a `SECURITY.md` at the repository root or in `.github/`, which is GitHub's own disclosure mechanism and a reasonable partial answer on an open-source project but is not a substitute for a file served from the product's domain. Then confirm it is actually served, which is the half that fails on frameworks that route unknown paths into the app. Fetch it from the production host if a production URL is configured, otherwise from the local build, and save the response: `curl -sS -L -o .pre-launch/access/security.txt -w "%{http_code} %{content_type} %{url_effective}\n" "<base url>/.well-known/security.txt"`, then repeat for `<base url>/security.txt` **writing to a different file** — `curl -sS -L -o .pre-launch/access/security-legacy.txt -w "%{http_code} %{content_type} %{url_effective}\n" "<base url>/security.txt"` — because reusing one output path means the second fetch, usually a 404 body or an SPA shell, silently overwrites the canonical file you came for and you end up judging the wrong response. RFC 9116 permits `/security.txt` only as a legacy location: `/.well-known/security.txt` is the canonical path, and a file served only at the legacy one is a note. Judge the response body, not the status code alone: a 200 that returns the application's HTML shell because the client-side router caught the path is a fail that looks like a pass, so read what came back. Then parse the fields. `Contact:` is the only mandatory field — a `mailto:` or an `https:` form URL — and check the address is a real mailbox on a domain the company controls rather than a template leftover such as `security@example.com`; cross-reference the addresses ACC-003 collected rather than sending anything, and never send a test message to a disclosure address. `Expires:` is also required by RFC 9116, must be an ISO 8601 date-time, and a value in the past is a **fail** rather than a note, because the field exists precisely so that a stale file announces itself as stale. Record the optional fields where present — `Preferred-Languages`, `Canonical`, `Policy`, `Encryption`, `Acknowledgments` — and check `Canonical` against the URL you actually fetched it from, since a `Canonical` naming a different host is a real error and usually means the file was copied from another project. If neither a production URL nor a local build is available, record `n/a — no served URL available` for the fetch half and let the repository evidence stand with `verified_by: static-fallback`.
evidence: the repository path of the file, or `not in repo`; the fetched status, content type, and first lines for **both** URLs tried, named separately as `.pre-launch/access/security.txt` for the canonical path and `.pre-launch/access/security-legacy.txt` for `/security.txt`, with a note where a 200 returned HTML; the `Contact:` value and whether its domain is one the company controls, cited to ACC-003's address list; the `Expires:` value with days remaining, or `absent`; any `Canonical` mismatch; whether a `SECURITY.md` exists and what it says to do. No other block consumes this evidence: this one reads ACC-003's address list and cites nothing onward.
fix_hint: Write `public/.well-known/security.txt` with a `Contact:` pointing at a monitored address or form on your own domain, an `Expires:` no more than a year out, and a `Canonical:` matching the URL it is served from; confirm the framework serves `.well-known` paths as static files rather than routing them into the application, by fetching the deployed URL after the change; and put the `Expires:` date into the same reminder calendar HYG-008's table feeds, so it is renewed before it lapses rather than after.

### ACC-011 Auto-renew on and valid payment method for registrar, hosting, database, email, error tracker
severity: critical
tier: attest
fix: none
why: An expired card on the registrar or the database host takes the whole product down weeks after launch, usually on a weekend, and the only warning was an email to an address nobody reads. It is the cheapest outage in existence to prevent and the most embarrassing to explain, and unlike almost everything else in this audit it gets *more* likely the better the launch goes: a metered service that has been free all year suddenly bills real usage, the charge is declined for exceeding a limit nobody set deliberately, and the account is suspended in the middle of the week that mattered.
verify:
  static: From `.pre-launch/access/services.json`, take the rows marked `uptime_critical` and check the filter is right rather than trusting it — the domain registrar, DNS, the hosting or deploy platform, the database, object storage, the email provider, the error tracker, the payment provider itself, and the app store developer accounts, since an Apple Developer membership that lapses removes the app from the store rather than merely stopping updates. Add anything else whose absence breaks the product rather than degrading it: a CDN, an auth provider, a queue or cache, a metered AI provider in a hot path. For each, record the source that implied it — which config file, dependency, or environment variable — so the list is auditable, and record any renewal cadence the repository itself shows: an annual store membership, a registrar term in a comment, a plan name in infrastructure code, a reserved-instance or committed-use commitment in Terraform. REL-020 owns whether each plan tier is *sufficient* for launch traffic and HYG-008 owns the chronological list of everything that fires unattended, so gather the renewal dates here in the form HYG-008 can read straight into its table and cite REL-020 rather than asking about limits again.
  attest: For each service on the list, the human confirms three clauses and all three must be yes: auto-renew is on, the payment method on file expires more than six months out, and billing alerts and receipts go to a shared inbox somebody actually reads rather than one person's mailbox (ACC-003 owns whether that address is on a company domain, so cite it). Then three questions that catch the cases the three clauses miss. Is the card a personal card belonging to one person, which makes every renewal dependent on that person's bank and their continued goodwill, and is there a company card or a backup method on file for the two services it would be worst to lose — the registrar and the hosting platform? For any usage-metered service, is there a spend limit or a hard cap that would suspend the account rather than a card that will simply be charged, and does the user know which behaviour their account has, since "suspended" and "billed nine thousand dollars" are both bad and the mitigations are opposite? And has the domain registration itself got auto-renew on at the registrar rather than only a valid card, because those are two separate settings and the second without the first expires the domain on schedule with a working card sitting unused — REL-017 owns reading the expiry date, so cite it and ask here only about the renewal setting.
evidence: the service list with the source that implied each row and whether it is `uptime_critical`, taken from `.pre-launch/access/services.json`; per service, the three clauses answered `yes` / `no` / `unknown`, the payment method's stated expiry month where the user gives one, and the billing inbox address; the personal-card answer and which services have a backup method; the spend-cap behaviour per metered service; the registrar auto-renew answer separately from the card answer; renewal dates gathered for HYG-008's table, and REL-017 and REL-020 named as owning domain expiry and tier sufficiency respectively.
