# Mobile checks (MOB)

Read `agents/domain-auditor.md` for procedure. Blocks below are checks; consult stack references for locations. Tools: `plutil -p` or `python3 -c "import plistlib"` for reading `Info.plist` (a binary plist will not grep), `grep` and `python3` with only the standard library for the manifest, Gradle, and app-config reads, `unzip` and `strings` for looking inside a build artifact that already exists, `curl` for the two association files in MOB-008, and the stack's own dev tooling (`npx expo start`, `npx react-native run-ios`, `flutter run`) for the three local-tier blocks. Install nothing.

**This whole domain runs only when config `platforms` includes `ios` or `android`.** SKILL.md gates it; that is why no block below carries a `when` field. If the project is web-only, none of this file runs and none of it is reported — not even as `skipped` per block. One consequence worth stating: a Capacitor, Cordova, or Tauri wrapper around a web app is still a store submission and still lands here, but its stack reference is the web framework's, so read the native project through whatever the wrapper generates (`ios/App/App/Info.plist`, `android/app/src/main/AndroidManifest.xml`) and say in evidence that the app is a wrapper, because it changes what MOB-011 (the whole web bundle ships inside the binary) and MOB-006 (a web checkout inside your own wrapper is still an in-app purchase to Apple) mean.

**Where the platform files live, and the one command you must not run.** Bare React Native and Flutter projects keep the real files on disk: `ios/<App>/Info.plist`, `ios/<App>/<App>.entitlements`, `android/app/src/main/AndroidManifest.xml`, `android/app/build.gradle` (plus the root `build.gradle` and `gradle.properties`), and `pubspec.yaml` for Flutter versions. Expo managed projects usually have no `ios/` or `android/` directory at all: the same values live in `app.json` or `app.config.js` (`ios.infoPlist`, `ios.entitlements`, `android.permissions`, `android.intentFilters`, `expo.plugins`, and the `expo-build-properties` plugin for SDK levels), with build profiles in `eas.json`. Locate all of this through the stack reference's "detection signals" rather than guessing, and read the app config as the source of truth when the native directories are absent. **Do not run `npx expo prebuild`** to make the native files appear: it writes `ios/` and `android/` into the project, and this audit never modifies project files. A generated-but-uncommitted native directory is itself a finding worth one line — the values in it can drift from the app config that regenerates it.

**"Local tier" here means a simulator, emulator, or device build reachable through the stack's own dev tooling** — Expo Go or a dev client, `npx react-native run-ios` / `run-android`, `flutter run` — not a production store build. Three blocks use it (MOB-001, MOB-005, MOB-015). If no simulator, emulator, or device is available, if the build fails, or if the machine has no Xcode or Android SDK, those blocks do not stop: run the block's `static` entry, decide from that evidence, and record `verified_by: static-fallback` with a note naming what was missing. A static-fallback pass is weaker than a run one; say so in `notes`. Expo Go is also not the same app as a dev client or a release build — native modules and several config values behave differently in it — so name which of the three you used in evidence.

**Purchases are sandbox-only, always.** MOB-001 is the one block that touches billing. Run it with an App Store Connect sandbox tester account or a local StoreKit configuration file on iOS, and with a Google Play licence tester on Android. Never sign in with a real Apple ID or Google account that has a payment method, never buy a product from the live store, and never point the app at production RevenueCat or billing keys for this (stack ref: "env vars" — a sandbox or test key prefix is the tell). If only live credentials are present, do not purchase: verify the restore code path statically, note `error: live billing credentials detected`, and leave the runtime half unrun.

**Every artifact this domain writes goes under `.pre-launch/mobile/` and nowhere else.** Create it once with `mkdir -p .pre-launch/mobile` before the first write. A bare relative filename lands in the project root, and in a mobile repo the project root is where the tooling looks for `app.json` and `google-services.json`, so a stray file there can be picked up by the next build. The names used below are `sdk-inventory.json`, `permissions.txt`, `merged-manifest.txt`, `bundle-strings.txt`, `aasa.json`, `assetlinks.json`, `deep-links.txt`, and `offline-<n>.txt`. Nothing in this domain writes into `ios/`, `android/`, or any Gradle or Xcode build directory.

**Never submit, never upload, never touch a key.** No `eas submit`, no `fastlane deliver`, no `flutter build appbundle && upload`, no App Store Connect or Play Console write of any kind, and no store metadata edit. MOB-013 reads whether a keystore or `.p12` exists and whether it is ignored by git; it does not open one, export one, print a password, or copy a file anywhere. If a check needs something only the console can show, it is `attest` and you ask the user.

**Platform rules change every year, so hedge the numbers and never the mechanism.** The mechanism — a privacy manifest exists, an ATT prompt precedes IDFA access, Play has a rolling target-API floor — is stable and you can assert it. The specific number attached to it is not: the Play target-API level rises annually, Apple's required-reason API list and its list of SDKs that must ship manifests both grow, and the anti-steering and external-purchase rules have moved more than once in the last two years. So for anything numeric or list-shaped, read the current value from the stack reference's "known traps" section, write the finding as `current requirement per stack ref: <value>`, and where you state a remembered figure at all, label it as of a year and tell the user to confirm it — `as of 2025, API 35; confirm the current floor in Play Console`. A confidently wrong version number discredits the twenty findings around it that were right.

**Cross-references, so nothing is audited or reported twice.** COMP-008 owns whether a EULA document exists and fits a mobile app; MOB-002 owns only whether the store listing points at it. COMP-014 owns the SDK-to-label diff; MOB-004 owns confirming the submitted forms against it. COMP-010 owns in-app deletion generally and FLOW-009 owns whether the data actually goes; MOB-005 owns only the store-guideline shape of it. FLOW-008 walks restore as a user flow and the PAY domain owns the billing integration's correctness; MOB-001 owns the store-required restore control. SEC-003 owns the public env prefix audit and SEC-001 the secret patterns; MOB-011 owns the fact that the binary is unzippable. REL-001 owns crash reporting being installed; MOB-017 owns the mobile number that comes out of it. REL-011 owns how fast a hotfix reaches users; MOB-003 owns whether the OTA channel is configured and stays inside store rules. SEC-010 owns the server-side authorization that a deep link must not bypass; MOB-018 owns the client gate. ACC-002 owns account and credential ownership generally; MOB-013 owns the signing material. COMP-003 owns the sale-and-share disclosure that ad SDKs trigger; MOB-021 owns the ATT prompt those same SDKs require.

### MOB-001 Restore purchases works
severity: critical
tier: local
fix: guided
why: Apple requires a restore mechanism for any app selling non-consumable products or subscriptions, and a missing or broken one is both a routine rejection and, once you are live, the top source of refund requests: the user reinstalls, switches to a new phone, or logs out, and the thing they paid for is gone. The code path is easy to write and almost never exercised before launch, because the developer's own device has had the entitlement cached since the day they implemented it.
verify:
  static: Identify the billing layer first (`react-native-iap`, `expo-in-app-purchases`, `react-native-purchases` for RevenueCat, `in_app_purchase` or `purchases_flutter` for Flutter, or StoreKit / Play Billing directly), then find the restore call: `restorePurchases`, `Purchases.restorePurchases`, `InAppPurchase.instance.restorePurchases`, `getAvailablePurchases`, `queryPurchases`, `restoreCompletedTransactions`. Two things must both be true and they fail separately. The call must exist, and it must be reachable from the UI without support intervention — trace it back to a component and to a screen a user can actually navigate to, since a restore function exported from a hook that nothing renders is dead code. Then read what happens with the result: the entitlement must be recomputed from the receipt or from the provider's customer info, not from a local flag or a cached boolean that reinstalling has already wiped. Note the account-linking shape too, because it decides what the runtime half proves — a purchase tied to a server-side user row restores by logging in, a purchase tied only to the store account restores by the store, and an app that requires login before it will even show the restore button will fail the reviewer who tests restore on a fresh install.
  local: Build to a simulator or device through the stack's dev tooling and use sandbox credentials only per the header rule — an App Store Connect sandbox tester or a local StoreKit configuration file on iOS, a Play licence tester on Android. Buy the product in sandbox, confirm the entitlement is active, then destroy the local state the way a real user does: delete and reinstall the app, or clear its data (`xcrun simctl uninstall booted <bundle id>`, `adb uninstall <package>`), and reinstall. Launch, tap Restore, and confirm the entitlement comes back and the paid UI unlocks. Record how long it took and whether any manual step was needed. If the restore button is behind a login, test both orders — restore-then-login and login-then-restore — because reviewers do the first one.
evidence: the restore call at file:line and the UI entry point at file:line, or `restore call exists with no UI caller`; the billing SDK and whether entitlement is recomputed from the receipt or read from local state; the tier used (`Expo Go`, `dev client`, `simulator release build`); the sandbox account type used; the before-and-after entitlement state with the reinstall step named; or `error: live billing credentials detected` / `verified_by: static-fallback` with the reason.
fix_hint: Add a Restore Purchases control to the paywall and to the settings or account screen, wire it to the SDK's restore call, and make the entitlement derive from the restored receipt or customer-info object rather than from a persisted flag. Show an explicit result either way — restored, or nothing to restore — because a silent no-op is indistinguishable from a broken button, and make sure the control is reachable before login if entitlements are not account-bound. FLOW-008 walks this as a user flow and the PAY domain owns the billing integration behind it; ship this with those rather than in isolation.

### MOB-002 EULA linked in store listing
severity: medium
tier: attest
fix: none
why: The licence agreement is the document that limits what a user may do with the binary, and both stores have a field for it. The failure mode is not usually a missing document — it is a listing that points at a custom EULA URL that 404s, or a custom agreement configured years ago that no longer matches the product, which is a worse position than simply relying on the store's standard licence.
verify:
  static: COMP-008 owns whether the document exists, is reachable, and contains the store-required provisions including Apple's third-party-beneficiary term — read its finding rather than re-auditing the text. What this block adds is the listing side, and part of it is in the repo: search for committed store metadata that carries the URL — `fastlane/metadata/` (an `ios/license.txt` or a `license_url` entry), an Expo `app.json` or `app.config.js` block, an `eas.json` submit profile, a Play publishing config, or a release script that sets listing fields. Record whether the URL is committed at all, whether it is HTTPS, and whether it points at the same document COMP-008 found. Note whether the app is free or paid, since a paid or subscription app makes the licence terms operative rather than decorative.
  attest: Ask the user to open App Store Connect (App Information, License Agreement — either Apple's standard EULA or a custom one) and Google Play Console (the store listing and app content sections), and to read back which is configured and, if custom, the exact URL. Then confirm that URL loads today. Record the answer verbatim. Apple's standard EULA is a perfectly good answer and the check passes on it; the fail is a custom link that is dead, points at a website's terms of service rather than a licence, or is configured on one store and not the other.
evidence: the store metadata file:line holding the URL or `no listing metadata committed`; `Apple standard EULA` or the custom URL with its HTTP status; the same for Play; the user's verbatim answer or `unconfirmed`; a pointer to COMP-008's verdict on the document itself.

### MOB-003 OTA hotfix configured within store rules
severity: medium
tier: static
fix: guided
why: An over-the-air update is the difference between shipping a one-line fix in ten minutes and waiting on a store review, which is why it is worth configuring before launch rather than during the incident. It is also the mechanism most often configured wrongly in a way nobody notices until it is needed: a channel that the production build is not subscribed to, or a runtime version policy that silently makes every update incompatible with the binary already in users' hands.
verify:
  static: Find the mechanism — `expo-updates` in dependencies plus an `updates` block in `app.json`/`app.config.js` with a URL and a `runtimeVersion` policy, EAS Update channels mapped to build profiles in `eas.json`, `react-native-code-push`, or a Flutter equivalent such as Shorebird. Then check the four things that break it: the production build profile must be bound to the channel you actually publish to (a build on the `preview` channel will never see a `production` publish); `runtimeVersion` must be a policy the team understands, since `appVersion` invalidates every OTA on each version bump while `fingerprint` or a manual string does not, and a mismatch means updates are published and silently never applied; the update check must actually run (`checkAutomatically` set to a value that checks on load, and a `fallbackToCacheTimeout` that does not block the splash screen for seconds on a slow network); and there must be a way to know a rollback exists, since publishing a bad OTA to every user at once has no store review to catch it. Then the store-rules half: an OTA may deliver JavaScript, styling, and assets, and it may not add features or change the app's behaviour or purpose beyond what was reviewed, and it may never deliver native code — Apple's rule about interpreted code is narrow and the practical line is that a bugfix is fine and a new paid feature is not. State that boundary in the finding, flag any native module added recently as something OTA cannot fix, and mark the exact current wording `verify current rules`. REL-011 owns the end-to-end hotfix timing including the web half; cite it rather than re-timing the pipeline here.
evidence: the OTA package and version, the `updates` block and `runtimeVersion` policy at file:line, the channel-to-build-profile mapping at file:line, and the check-on-launch settings; `no OTA path — every fix requires a store release` where none exists; the native-versus-JS boundary noted for this app; any rollback or republish procedure found.
fix_hint: Wire the production build profile to the channel the release pipeline publishes to and verify it by shipping a trivial cosmetic change to a test build before launch, not after. Choose a `runtimeVersion` policy deliberately and write down what it means for compatibility. Leave the update check on launch enabled with a short fallback timeout so a slow network does not hold the splash screen. Document what may be shipped OTA (bugfixes, copy, styling) and what may not (native modules, new features, anything that changes what the app does), and record the command that republishes a previous known-good update.

### MOB-004 Privacy labels / data safety match actual SDKs
severity: high
tier: attest
fix: none
why: The App Privacy answers and the Data safety form are sworn declarations about what the app collects, made once at submission and then left alone while dependencies keep arriving. Every SDK added after that submission silently makes the declaration false. The enforcement is a rejected update or a pulled listing rather than a fine, which at launch is the same thing as an outage — and it lands on the release you most need to ship.
verify:
  static: Start from the diff rather than the form. If the compliance domain has already run, read `.pre-launch/compliance/inventory.json` and take its mobile subset — COMP-014 owns producing that diff and you should reuse it rather than rebuilding a second, different list. If compliance has not run, build the mobile subset yourself the same way and write it to `.pre-launch/mobile/sdk-inventory.json`: read `ios/Podfile` and `Podfile.lock`, the `dependencies` blocks in `android/app/build.gradle` and the root Gradle files, the Expo config's `plugins` array, and the JS or Dart dependency manifest, then drop the web-only vendors, because a tag that runs on the marketing site is not a store-label item. For each remaining SDK record the data types it collects and the two axes both forms ask about: whether the data is linked to the user's identity, and whether it is used for tracking. Flag separately every SDK that reads an advertising identifier or builds a device fingerprint, since those are the entries that flip the tracking answer and pull in ATT (MOB-021). Keep the Apple and Google lists apart — their categories do not map one to one, and a single merged answer will be wrong on one of the two stores.
  attest: Ask the user to open App Store Connect's App Privacy section and Google Play Console's Data safety form and read back the declared data types, their purposes, and the linked and tracking answers. Record the reply verbatim, then diff it in both directions against the inventory: an SDK in the binary with no matching declaration is a finding, and a declared category with no SDK or code behind it is also a finding, because it over-discloses and contradicts the privacy policy. Two Data safety questions are worth asking explicitly because they are commonly answered from optimism rather than from code: whether data is encrypted in transit (which MOB-010 can confirm or contradict) and whether users can request deletion (which MOB-005 and COMP-010 can).
evidence: the bundled-SDK list with the manifest file:line for each and the data types it collects, saved to `.pre-launch/mobile/sdk-inventory.json` or cited from `.pre-launch/compliance/inventory.json`; the identifier-and-fingerprint SDKs called out; the user's verbatim reading of both forms or `unconfirmed`; the two-direction diff, one line per discrepancy, kept separate per store.

### MOB-005 Account deletion discoverable per store guidelines
severity: high
tier: local
fix: guided
why: Both stores now treat account deletion as a listing condition rather than a nicety: Apple's guideline 5.1.1(v) requires any app that supports account creation to let the user initiate deletion from inside the app, and Google Play requires an in-app path plus a web URL declared in the Data safety form. The common launch failure is not a missing capability but a deactivate-only flow, or a settings screen whose deletion entry is a `mailto:` link, both of which a reviewer catches in about ninety seconds.
verify:
  static: COMP-010 owns whether an in-app deletion path exists and is discoverable in the product generally, and FLOW-009 and DAT-020 own whether the data actually goes; read their findings and do not re-derive them. What this block owns is the store-specific shape. Four things: deletion must be initiated from within the app rather than by email, a support ticket, or a web form the user has to find on their own; it must delete the account and not merely deactivate or sign the user out, or if a scheduled deletion with a grace period is used, the app must say so plainly; where the app offers only a partial option, the full-deletion option must also be available and equally reachable; and for Play, a web-accessible deletion URL must exist for users who no longer have the app installed, which means checking that the URL exists and is public rather than behind an app-only login. Also check the two mobile-specific traps: an app that requires an active subscription to be cancelled before deletion needs to say where and how, since store subscriptions are cancelled in the store and not in your app, and a deletion flow that only works for password accounts breaks on the Sign in with Apple users MOB-023 may require you to accept.
  local: Non-destructive and always worth running. Build to the simulator through the stack's dev tooling, log in as the test account from config, and start from the post-login landing screen. Navigate to the deletion control counting taps and naming each screen, and stop at the final confirmation without submitting. Read what the confirmation screen tells the user — what is removed, what is kept and why, whether it is immediate or scheduled — and record it verbatim. Do not run the destructive step here: COMP-010 and FLOW-009 own that, on a disposable account, and this block reuses their result. Never delete the shared test account.
evidence: the tap path as `home → Settings → Account → Delete account (3 taps)` with the screen names; the confirmation copy quoted; whether the flow deletes or deactivates; the Play web deletion URL with its HTTP status or `no web deletion URL`; any precondition the flow imposes (subscription, provider type); a citation to COMP-010 and FLOW-009 for the data-removal verdict; the tier used or `verified_by: static-fallback`.
fix_hint: Put a deletion control on the account or settings screen within two or three taps of the authenticated landing screen, performing deletion rather than opening a ticket or an email client, with a confirmation screen naming exactly what is removed, what is retained and for how long, and whether a grace period applies. Publish a web deletion page at a stable public URL and enter it in Play Console's Data safety form. If a store subscription must be cancelled first, do not block deletion on it — delete the account and tell the user, with a deep link to the store's subscription management screen, that the subscription is cancelled separately.

### MOB-006 IAP rules followed for digital goods
severity: high
tier: static
fix: guided
why: Selling digital content or features that are consumed inside the app through anything other than the store's own billing is the single most reliable way to be rejected, and unlike most rejections it is not fixable by editing a plist — it means rebuilding the paywall. The rules also have genuine exceptions, so the goal here is not to declare a verdict but to lay the app's actual payment paths next to the categories the guidelines use, and say which one this product is in.
verify:
  static: Find every path by which money can be spent in the mobile app. Store billing looks like `react-native-iap`, `expo-in-app-purchases`, `react-native-purchases`, `in_app_purchase`, StoreKit, or Play Billing. Everything else is the interesting half: `@stripe/stripe-react-native`, a Paddle or Lemon Squeezy SDK, a `WebView` or `Linking.openURL` / `url_launcher` call that opens a pricing, checkout, or upgrade page, a deep link into your own web app's billing screen, or a paywall screen whose primary button is an outbound link. For each path, classify what is being sold: digital content or features unlocked inside the app fall under Apple's guideline 3.1.1 and Play's billing policy and must use store billing; physical goods, real-world services delivered outside the app, and person-to-person services are exempt and must not use store billing; and a handful of narrow categories have their own rules. Name the exceptions rather than pretending they do not exist — the reader entitlement for apps whose content is purchased elsewhere, multiplatform accounts where an existing subscriber may sign in, the external purchase link entitlements, and Play's user-choice billing — and then say that all four have changed recently, that the US anti-steering position in particular has moved more than once since 2024, and mark the finding `verify current rules` rather than asserting a version. The two findings that are safe to state flatly: a digital-goods paywall whose button opens a web checkout is a rejection unless one of those entitlements is granted and configured, and a paywall that mentions cheaper pricing on the website without an entitlement is the anti-steering question, not a technical one.
evidence: one row per payment path — `paywall at app/paywall.tsx:44 → Linking.openURL(https://example.com/upgrade) — digital subscription, no store billing`; the store-billing SDK and product identifiers if present with file:line; what each path sells and which category it falls in; the entitlement or exception being relied on, if any, with `verify current rules` attached; the price-comparison or steering copy quoted if present.
fix_hint: Route every purchase of digital content or in-app features through StoreKit or Play Billing, keeping the products and price tiers configured in each console, and leave physical goods and real-world services on the existing web checkout where they belong. Where the business depends on an exception — reader app, multiplatform account, external purchase link, user-choice billing — apply for the entitlement and configure it before submitting rather than after the first rejection, and have someone confirm the current text of the rule that week, because this is the fastest-moving area of both guidelines.

### MOB-007 Permissions requested just-in-time with purpose strings; none unused
severity: medium
tier: static
fix: easy
why: A permission the app declares but never uses is a rejection on iOS and an unnecessary red flag on the Play listing, and a purpose string that says "This app needs camera access" tells the reviewer and the user nothing, which is exactly what the guideline is written against. The related failure is timing: an app that asks for location, notifications, and contacts in the first three seconds gets refused all three, permanently, by a user who has not yet seen what the app does.
verify:
  static: Build the two lists first and save them to `.pre-launch/mobile/permissions.txt`. On iOS read every `NS*UsageDescription` key from `Info.plist` (use `plutil -p ios/<App>/Info.plist` or `python3 -c "import plistlib,sys; print(plistlib.load(open(sys.argv[1],\"rb\")))"` — a binary plist will not grep) or from `ios.infoPlist` in the Expo config. On Android read every `<uses-permission>` from `android/app/src/main/AndroidManifest.xml` or `android.permissions` in the Expo config, and remember that libraries inject permissions through manifest merging, so an unexplained `RECORD_AUDIO` may come from a dependency — if a build output already exists, `android/app/build/outputs/logs/manifest-merger-*-report.txt` names which library contributed each one, and it is worth saving to `.pre-launch/mobile/merged-manifest.txt`. Then cross-check every entry against actual API usage in code: camera against a camera or image-picker call, location against a location call, contacts, calendar, microphone, photo library, Bluetooth, motion, tracking, and health the same way. Any declared permission with no call site fails, and it is the most common finding in this block because permissions arrive with libraries that were evaluated and dropped. Next read the purpose strings themselves: each must say what the app does with the data and why the user benefits, and a string that merely restates the permission name is a fail even though it is present. Then check timing — the request should sit at the point of use, behind the button that needs it, ideally after a short priming screen, rather than in an app-launch effect. Finally note the ones with extra process attached: background location, `QUERY_ALL_PACKAGES`, `SCHEDULE_EXACT_ALARM`, `MANAGE_EXTERNAL_STORAGE`, `READ_MEDIA_*`, and accessibility services all require a declaration form or extra justification on Play, and `POST_NOTIFICATIONS` became a runtime permission at target API 33 (MOB-009 owns that half).
evidence: a table of every declared permission with its purpose string and its call site as `NSCameraUsageDescription — "Scan a receipt to add an expense" — used at src/scan.tsx:31`, or `NSContactsUsageDescription — declared, no call site found`; the injecting library for any merged Android permission; each request's timing as `on launch` or `at point of use (file:line)`; the sensitive permissions needing a Play declaration listed separately.
fix_hint: Delete every declared permission with no call site, including the ones a removed library left behind — on Expo that means editing the app config, and on bare projects the plist and manifest, plus a `tools:node="remove"` entry where a dependency injects one you do not want. Rewrite each remaining purpose string to name the feature and the benefit in one specific sentence. Move each request to the moment the feature is first used, behind a short in-app explanation, so a denial costs one feature rather than the whole app.

### MOB-008 Universal / app links verified (AASA, assetlinks)
severity: medium
tier: remote
fix: guided
why: Universal links and Android App Links are the difference between a shared URL opening your app and opening a browser, and they are verified by the operating system against two small JSON files on your domain. They fail silently: nobody sees an error, the link simply opens Safari, and because iOS caches the association file at install time the failure often survives the fix. Marketing emails, password resets, and share links all quietly stop working.
verify:
  static: Confirm the app side declares the association before checking the server side. iOS needs the associated-domains entitlement listing `applinks:<domain>` — in `ios/<App>/<App>.entitlements` or `ios.associatedDomains` in the Expo config — and the domain there must exactly match the one you will fetch, apex and subdomain being different domains. Android needs an intent filter with `android:autoVerify="true"` on the activity, `android.intent.action.VIEW`, both `BROWSABLE` and `DEFAULT` categories, and a `<data>` element with `android:scheme="https"` and the host — in `AndroidManifest.xml` or `android.intentFilters` in the Expo config. Note any custom scheme (`myapp://`) separately: it works without any server file, it is not a universal link, and it is the thing MOB-018 cares about most because any app can register the same scheme. Record the app's bundle identifier, its Android package name, and its Apple team ID, since the two JSON files must contain exactly those.
  remote: Fetch both files from the production domain and save them under `.pre-launch/mobile/`. For Apple: `curl -sS -L -o .pre-launch/mobile/aasa.json -w "%{http_code} %{content_type} redirects=%{num_redirects} %{url_effective}\n" "https://<domain>/.well-known/apple-app-site-association"`. It must return 200 over HTTPS with a valid certificate, be served with `application/json`, have no `.json` extension in the path, and follow **no redirects at all** — a redirect is the single most common cause of a silently broken universal link, and a CDN or framework that redirects to a trailing slash or to `www` breaks it just as thoroughly as a 404 would. Parse it and confirm the `appIDs` entries are `<TeamID>.<bundle id>` for this app and that the paths section actually covers the routes you link to. For Android: fetch `https://<domain>/.well-known/assetlinks.json` the same way and confirm it lists this package name with the SHA-256 fingerprint of the certificate that will sign the **release** build — with Play App Signing that is the app signing certificate Google holds, shown in Play Console, not the upload certificate, and listing only the upload certificate is the classic failure that works in internal testing and breaks in production. Note that a file served as HTML because the SPA fallback caught the path is a fail even though it returns 200; look at what came back, not just the status.
evidence: the entitlement and intent-filter declarations with file:line; the bundle identifier, package name, and team ID as found; for each file the URL, status code, content type, redirect count, and whether the body parsed as JSON; the `appIDs` and package-plus-fingerprint entries found versus expected; `served as text/html — SPA fallback` where that happened; any custom scheme listed separately.
fix_hint: Serve `apple-app-site-association` from `/.well-known/` with `Content-Type: application/json`, no file extension, and no redirect of any kind — on most hosting platforms that means an explicit route or header rule rather than dropping the file in the public directory and hoping. Serve `assetlinks.json` the same way, containing the release signing certificate's SHA-256 fingerprint copied from Play Console's App signing page rather than from the local keystore. Then verify from a clean install on both platforms, since iOS caches the association at install time and Android reports verification state via `adb shell pm get-app-links <package>`.

### MOB-009 Push permission timing; token refresh; unsubscribe
severity: medium
tier: static
fix: guided
why: Push is the one permission a user can only grant once on iOS: if they decline, your app cannot ask again and the only path back is the Settings app, which nobody visits. Asking at first launch therefore permanently costs most of the audience. The second half is quieter — a token that is registered once and never refreshed goes stale, and the notifications you think you are sending land nowhere while the dashboard reports success.
verify:
  static: Find the push layer (`expo-notifications`, `@react-native-firebase/messaging`, `firebase_messaging`, OneSignal, or a bare APNs and FCM integration) and read three things. Timing: the permission request must be triggered by a user action or by a priming screen that explains the value, not by an effect that fires on app launch or during onboarding before the app has shown what it does; find the call site and say which it is. On Android, note that `POST_NOTIFICATIONS` is a runtime permission from target API 33 onward, so an app that only ever asked on iOS shows no prompt and sends nothing on modern Android — cross-check against MOB-022's target level. Token lifecycle: a refresh listener must be registered (`onTokenRefresh`, `addPushTokenListener`, or the SDK's equivalent), the token must be sent to the server and stored against the user rather than only held in memory, it must be re-sent when it changes, and it must be removed or unbound on logout, or the next person to log in on that device receives the previous user's notifications, which is a privacy incident rather than a bug. Also check that the server handles the unregistered-token error from APNs and FCM by deleting the row instead of retrying forever. Unsubscribe: there must be an in-app preferences screen that turns categories off, and marketing pushes must be separable from transactional ones — an all-or-nothing switch pushes the user to the OS-level toggle, which kills the transactional notifications too. Where push carries personal content, check whether it appears in the lock-screen preview.
evidence: the permission request call site with file:line and whether it is on launch, after priming, or at point of use; the Android `POST_NOTIFICATIONS` handling and the app's target API level; the refresh listener at file:line and where the token is persisted; the logout unbinding path or `token not cleared on logout`; the preferences screen and the categories it offers, or `no in-app notification settings`; the server's handling of unregistered tokens.
fix_hint: Move the permission request behind a priming screen shown at the first moment push is obviously useful, and request `POST_NOTIFICATIONS` on Android as part of the same flow. Register the refresh listener at startup, persist the token per user and per device server-side, delete it on logout and on the unregistered-token error, and add a notification preferences screen with transactional and marketing categories separated so a user can decline the marketing half without silencing the app.

### MOB-010 Release build tested; ATS not disabled; no cleartext traffic
severity: high
tier: static
fix: easy
why: Disabling App Transport Security or allowing cleartext traffic is usually done once, early, to make a local API work, and then ships — sending real user traffic over plain HTTP on hostile networks and inviting a review question you have no good answer to. The build-configuration half is the same story: a release that is still debuggable, still signed with the debug key, or still pointing at a development API is a build you cannot ship even though it installs and runs perfectly on your phone.
verify:
  static: On iOS read `NSAppTransportSecurity` from `Info.plist` or `ios.infoPlist` in the Expo config. `NSAllowsArbitraryLoads` set to true is a fail on its own. Narrower keys are not automatically fine either: enumerate every entry under `NSExceptionDomains` with `NSExceptionAllowsInsecureHTTPLoads` or a lowered `NSExceptionMinimumTLSVersion`, and every `NSAllowsArbitraryLoadsInWebContent` or `NSAllowsLocalNetworking`, and say which host each covers and why it exists — `localhost` for development is defensible and a production API domain is not. On Android read `android:usesCleartextTraffic` in `AndroidManifest.xml` (true is a fail) and open any `network_security_config.xml` the manifest references: a `<base-config cleartextTrafficPermitted="true">` is the same fail wearing a different hat, while the same setting inside `<debug-overrides>` applies only to debuggable builds and passes. Then grep the source for `http://` URLs that are not localhost or a comment, since an allowed cleartext policy and an actual cleartext request are separate findings and the second one is the real defect. For the build half, confirm the release variant is genuinely a release: `signingConfigs.release` in `android/app/build.gradle` must exist and must not simply reuse the debug config or an inline password, `debuggable` must be false, `minifyEnabled` and the shrinker settings should be deliberate, and the Expo `eas.json` production profile should not carry a development client or a development distribution. Confirm which artifact the rest of this audit is reading, and say so — several blocks in this file mean different things for a debug build.
evidence: every ATS key and exception domain with its value and the host it covers; the Android cleartext setting and the relevant lines of `network_security_config.xml`; each non-localhost `http://` URL in source with file:line; the release signing configuration and `debuggable` value at file:line; the build variant the audit examined, named explicitly.
fix_hint: Remove `NSAllowsArbitraryLoads` and `usesCleartextTraffic`, keeping only narrow exception entries for the specific hosts that genuinely need them and moving development-only allowances into `<debug-overrides>` or a debug-only plist. Switch every remaining `http://` endpoint to HTTPS. Give the release build its own signing configuration with credentials read from the environment or from Play App Signing rather than from literals in Gradle, and confirm `debuggable` is false in the variant you actually submit.

### MOB-011 No extractable secrets in app bundle
severity: critical
tier: static
fix: guided
why: A mobile binary is a zip file that anyone can download from the store and unpack in about thirty seconds, and everything the build inlined is inside it — `EXPO_PUBLIC_*` variables, `react-native-config` values, `--dart-define` constants, entries in the Expo config's `extra` block, and every string in the JavaScript bundle. Developers reason about it as if it were server code because they wrote it in the same repository, so admin API keys, service-role database keys, and third-party secrets end up shipping to every user, with rotation as the only remedy once they do.
verify:
  static: SEC-003 owns the public-prefix audit and SEC-001 owns the provider-secret patterns; this block owns the fact that mobile has no server side to hide behind, so treat every one of these as public by construction and check what is in them. Read the env layer for the stack (stack ref: "env vars"): every `EXPO_PUBLIC_*` variable, every key in `app.json`/`app.config.js` under `extra`, every `react-native-config` entry in `.env` files consumed by the native build, every `--dart-define` in the build scripts or `eas.json`, plus `Info.plist`, `strings.xml`, `google-services.json`, and `GoogleService-Info.plist`. Then grep the source itself for the SEC-001 patterns, since a literal in a JS or Dart file ships just as surely as an env var. Publishable keys are expected and pass — a Stripe `pk_`, a Supabase anon key, the Firebase web or mobile config, a RevenueCat public SDK key — and you should list the ones you cleared so the finding is not read as a false alarm; what fails is anything named `SECRET`, `SERVICE_ROLE`, `PRIVATE`, `ADMIN`, `WEBHOOK`, or `PASSWORD`, any `sk_` key, any database URL, and any third-party key that can do more than the client should. Then prove it rather than reasoning about it: if a build artifact already exists, `unzip -o <app>.apk -d .pre-launch/mobile/apk` and grep the extracted `assets/index.android.bundle` and `res/values/strings.xml`, or `unzip` the IPA and run `strings Payload/<App>.app/<App>` plus the JS bundle, saving hits to `.pre-launch/mobile/bundle-strings.txt`. If no artifact exists, `npx expo export --platform ios --output-dir .pre-launch/mobile/export` (or the stack's equivalent bundle command, always with an explicit output directory) produces the JavaScript bundle without a native build; grep that. Pass the output directory explicitly every time, because the default for several of these commands is `dist/` or `build/` in the project root, which is a project file this audit must not create — and redact matches in evidence to the first six characters.
evidence: one row per finding — `EXPO_PUBLIC_SUPABASE_SERVICE_KEY at .env:7 — service-role key, extractable`; the publishable keys explicitly cleared; the extraction method used (`unzip of existing APK`, `strings on IPA binary`, `expo export bundle`, or `not extracted — no artifact`) and the file the hits were saved to, with each match redacted to six characters; a citation to SEC-003 and SEC-001 for the non-mobile half.
fix_hint: Move every privileged key behind a server endpoint the app calls with the user's own session, and rotate every key that has already shipped in a released build, because it is public whether or not anyone has looked. For keys that legitimately live on the client, keep them publishable and scope them at the provider — restrict the Firebase or Maps key by bundle identifier, use the anon key with row-level security behind it (see the DAT domain), and give third-party SDKs their client-side key rather than their server one. Do not reach for obfuscation: it delays a determined reader by minutes and changes nothing about the exposure.

### MOB-012 Force-update mechanism; version and build bumped
severity: medium
tier: static
fix: guided
why: Mobile is the only platform where old versions of your client keep running indefinitely against your current API, so the day you must retire an endpoint, fix a security bug, or change a payload shape, you need a way to stop old builds rather than hope. The version-number half is smaller and bites sooner: a build number that was not incremented is rejected by App Store Connect and Play at upload, usually while someone is waiting.
verify:
  static: Look for a minimum-supported-version check: the app reads a value at startup from a remote source — a config endpoint, Firebase Remote Config, a field on an existing bootstrap API response, or an `expo-updates` manifest field — compares it against its own version, and shows a blocking screen with a link to the store when it is too old. Check three properties, because a half-built one is worse than none: the check must not be silently skipped when the network call fails in a way that leaves an old client running, the blocking screen must actually block rather than being dismissible if the intent is a hard gate, and there should be a soft variant too, since a hard gate is a blunt instrument and a dismissible prompt covers most releases. Then read the version fields and compare them against what is already released: `version` plus `ios.buildNumber` and `android.versionCode` in the Expo config, `CFBundleShortVersionString` and `CFBundleVersion` in `Info.plist`, `versionName` and `versionCode` in `android/app/build.gradle`, or the `version: x.y.z+n` line in `pubspec.yaml`. `versionCode` must be a strictly increasing integer and Play rejects a duplicate outright; iOS build numbers must increase within a version. Check whether the bump is automated in the release pipeline or done by hand, and compare the current values against the latest git tag or release commit to catch the repository that has been on `1.0.0 (1)` for three months.
evidence: the minimum-version check at file:line with the remote source it reads and its failure behaviour, or `no force-update mechanism`; whether the gate is hard, soft, or both; the current version and build values with file:line for each platform; the latest git tag or released version for comparison; whether bumping is automated and where.
fix_hint: Add a startup check that reads a minimum supported version from a remote value you can change without a release, and fail it closed enough to matter: block below the hard minimum with a store link, prompt above it, and treat a failed fetch as "allow" only if you are comfortable with an old client continuing. Automate the version and build bump in the release pipeline so nobody has to remember, and keep `versionCode` monotonic and independent of the marketing version.

### MOB-013 Signing keys and keystore backed up
severity: critical
tier: attest
fix: none
why: On Android, if you are not enrolled in Play App Signing and you lose the upload keystore, you cannot ship another update to that listing — ever. The app must be republished under a new package name and every existing install is orphaned. This is the most permanent failure mode in the entire audit, it is caused by a laptop dying, and it costs nothing to prevent. The related risk runs the other way: a keystore or `.p12` committed to the repository hands anyone with clone access the ability to sign as you.
verify:
  static: Look for signing material in the working tree and in history, and stop at looking. Search for `*.keystore`, `*.jks`, `*.p12`, `*.mobileprovision`, `*.cer`, `*.certSigningRequest`, `*.p8` (App Store Connect API keys), and files named like `upload-keystore` or `release.keystore`. For each one found, check whether it is ignored (`git check-ignore -v <path>`) and whether it was ever committed (`git log --all --diff-filter=A --name-only` piped through a grep for those extensions), because removing a key from the working tree does not remove it from history. Then check for passwords in plain text: `storePassword`, `keyPassword`, `keyAlias`, and `storeFile` literals in `android/app/build.gradle`, `gradle.properties`, `local.properties`, or an `eas.json` credentials block, and note whether they read from the environment instead. Do not open, decrypt, export, copy, or print the contents of any of these files, and do not run `keytool` against them; existence, path, ignore status, and history are the entire static output.
  attest: Ask the user four questions and record the answers verbatim. Is Play App Signing enabled for this app — because if it is, Google holds the app signing key and a lost upload key can be reset through support, which changes this from unrecoverable to inconvenient, and it is the single most useful answer in the block. Where are the keystore file and its passwords stored, and is that somewhere other than one laptop — a password manager, a team vault, an encrypted backup. Does more than one person have access, so that the launch does not depend on one individual being reachable. And for iOS, how are the distribution certificate, provisioning profiles, and App Store Connect API key managed — EAS-managed credentials, a `fastlane match` repository, or manual files on a machine — and who else can get to them. ACC-002 owns multi-owner access to services generally; cite it and keep this block to the signing material.
evidence: every signing-material file found with its path, gitignore status, and whether it appears in git history; any plaintext signing password with file:line, or `credentials read from environment`; the user's verbatim answers on Play App Signing, storage location, second holder, and iOS credential management, or `unconfirmed`.

### MOB-014 Review demo account and notes provided
severity: medium
tier: attest
fix: none
why: Review rejections are mostly not about policy — they are about a reviewer who could not get into the app, could not reach the feature, or did not understand what they were looking at. A demo account and a paragraph of notes turn a week of round trips into a same-day approval, and they cost ten minutes to write. The account that expires, gets rate-limited, or has its data wiped between submissions is the version of this that fails silently.

### MOB-015 Offline and poor-network handling
severity: medium
tier: local
fix: guided
why: Phones lose connectivity constantly — lifts, trains, basements, a hotel wifi that resolves DNS but routes nothing — and this is the class of bug that never appears on a developer's desk, where the API is on localhost and answers in two milliseconds. The visible failure is almost always the same: a spinner that never resolves, because the happy path was written and the error branch was not.
verify:
  static: Read the network layer for the three things that decide behaviour on a bad connection. Timeouts: every request must have one, since a fetch with no timeout on a captive-portal network hangs until the OS gives up, which can be over a minute. Retries: bounded, with backoff, and not applied to non-idempotent requests — a retried purchase or a retried post is a duplicate. Error branches: every screen that loads data needs a visible error state with a retry affordance, so look for query hooks whose error case renders nothing, and for `catch` blocks that swallow and leave the loading flag set. Then check what the app knows about connectivity (`@react-native-community/netinfo`, `connectivity_plus`) and what it does with it, whether any state is persisted for offline reads (a query-client persister, MMKV, AsyncStorage, SQLite, Hive), and whether writes made offline are queued and reconciled or simply lost. Note cold start specifically: an app launched with no network that shows a blank screen or crashes on a failed bootstrap request is the worst version of this, and it is common because the splash screen waits on a config call.
  local: Build to a simulator or emulator through the stack's dev tooling and run four scenarios, recording each. Cold launch with no connectivity (iOS Simulator: disable the host network or use the Network Link Conditioner; Android emulator: `adb shell svc wifi disable` and `adb shell svc data disable`, or the emulator console's cellular controls) — the app must reach a readable screen rather than hanging or crashing. Navigate the primary flow offline and look for infinite spinners, silent no-ops, and buttons that appear to succeed. Restore connectivity without restarting and confirm the app recovers on its own rather than needing a kill and relaunch. Then the harder case, which finds more bugs than plain airplane mode: a slow, lossy connection rather than no connection, using the Network Link Conditioner's poor profiles or the emulator's latency and speed settings, since code that handles a thrown error often mishandles a request that takes twenty seconds and then succeeds. Save observations to `.pre-launch/mobile/offline-<n>.txt`.
evidence: the timeout, retry, and persistence configuration with file:line; per scenario a line naming the screen and what happened, as `cold launch offline — splash screen, spinner forever, no error (2 min)`; the recovery behaviour after connectivity returns; any offline write queue and what it does on reconnect; the tier used or `verified_by: static-fallback` with the reason.
fix_hint: Give every request a timeout and every data-loading screen an error state with a retry button, then handle the cold-start case explicitly so the app opens to something readable with no network. Add a connectivity listener that refetches on reconnect rather than requiring a relaunch, cache the last successful response for the screens where stale data is better than nothing, and either queue offline writes with a visible pending state or disable the controls that cannot work — never let a write appear to succeed and vanish.

### MOB-016 Age rating, export compliance declaration, screenshots on all sizes
severity: medium
tier: attest
fix: none
why: These are the three submission fields that hold up an otherwise finished release. The export compliance question is asked at every single upload until it is answered in the plist, which turns each submission into a manual step somebody forgets at midnight. An age rating questionnaire answered carelessly — no, we do not have user-generated content, on an app with a comment box — is a misdeclaration the store treats seriously. ### MOB-017 Crash-free rate, app size, launch time acceptable
severity: medium
tier: attest
fix: none
why: These three numbers are what the stores and your users judge the build on, and none of them can be read from the repository. A crash-free rate below the high nineties means a visible fraction of sessions end in a crash and the reviews will say so; download size decides how many people abandon the install on cellular; and cold launch time is the first impression the app ever makes. This check produces measurements rather than a defect, which is why it has no fix of its own.
verify:
  static: Confirm the machinery that produces the numbers exists, since a crash-free rate is only meaningful if crashes are actually reported from the mobile target. REL-001 owns whether a reporter is installed across runtimes; here confirm the mobile half specifically — `@sentry/react-native`, `sentry_flutter`, `firebase_crashlytics`, or Bugsnag initialised in the app's startup path — and confirm the symbol upload that makes reports readable is configured: the Sentry Gradle and Xcode build phases with an auth token, `uploadDebugSymbols`, the Crashlytics Gradle plugin with mapping-file upload, or Flutter's `--split-debug-info` with a matching symbol upload step. Where the app is not yet released and no numbers exist, say so plainly and record the internal-testing figures if there are any.
evidence: the mobile reporter and its init call at file:line, plus the symbol or mapping upload configuration at file:line or `symbols not uploaded — crashes will be unreadable`; the artifact size and the largest contents if an artifact existed; the user's verbatim crash-free percentages with the release and window they cover, the store download sizes, and the cold launch time and device; or `not yet released — no production numbers`.

### MOB-018 Deep links into protected screens require auth
severity: high
tier: static
fix: guided
why: A deep link jumps straight into a screen and skips whatever navigation the login gate lives in. On a cold start the app often has no session loaded yet, so the target screen renders with whatever it can — sometimes another user's cached data, sometimes an empty shell that then fetches with no token and reveals which requests are unauthenticated on the server. Custom URL schemes make it worse, because any app on the device can register `myapp://` and hand you a crafted link.
verify:
  static: Enumerate the link surface and save it to `.pre-launch/mobile/deep-links.txt`: the custom scheme from the app config or `CFBundleURLTypes`, the universal-link domains and paths from MOB-008's declarations, and the route table itself — expo-router's file-based routes, the React Navigation `linking` config's screen-to-path mapping, or the Flutter router's route definitions. Mark which of those routes render authenticated data. Then follow the cold-start path for one of them and answer whether the gate runs before the screen: a root layout or navigator that waits for session restoration and redirects unauthenticated users to login is the shape that passes, while a screen that renders and fires its own query while the session is still hydrating is the shape that leaks. Check the return path too, because the common bad fix is to redirect to login and drop the intended destination, which makes every emailed link land on a home screen. Then three specific traps. A deep link that carries a credential — a magic-link token, a password-reset token, a session token as a query parameter — ends up in logs, in the OS's link history, and in any app that can observe the scheme; note it and cite SEC-064 territory. A parameter taken from a link and passed into a `WebView`, an `openURL`, or a fetch is an open-redirect and SSRF surface reachable by any app on the device; it must be validated against an allowlist. And most importantly, say plainly that the client gate is UX and not security: the server must authorize every request the deep-linked screen makes, which is SEC-010's and SEC-011's job — cite them, and if a deep-linked screen's data comes back for an unauthenticated request, that is their finding, not this one.
evidence: the deep-link route table with each route marked public or protected; the auth gate at file:line and whether it runs before protected screens render on cold start; the post-login return-to-intended-destination handling or `intended destination dropped`; any route whose parameters carry a token; any parameter that reaches a `WebView` or an outbound request unvalidated with file:line; a citation to SEC-010 for the server-side half.
fix_hint: Put the session check in the root layout or navigator so every route is gated before it renders, hold the incoming link while the session hydrates rather than rendering optimistically, and stash the intended destination so login returns the user to it. Validate every deep-link parameter against an allowlist before it reaches a `WebView` or a network call, and move credentials out of link parameters into a single-use exchange. Then confirm the server rejects the same requests without a session, because the client gate only hides the screen.

### MOB-019 Certificate pinning decision documented
severity: low
tier: attest
fix: none
why: Pinning raises the bar against traffic interception on a compromised device, and it is also the fastest way to brick every installed copy of your app: the certificate rotates, the pin no longer matches, and the only fix is a store release that users must install before the app works again. Neither choice is wrong. What is wrong is having no decision — pinning that someone enabled in a tutorial and nobody owns, or an assumption that it is handled when it is not.
verify:
  static: Look for an implementation: `react-native-ssl-pinning`, TrustKit, an okhttp `CertificatePinner`, a `<pin-set>` block in Android's `network_security_config.xml`, a Flutter `SecurityContext` with a bundled certificate or a `badCertificateCallback`, or a Dio interceptor doing fingerprint comparison. If pinning is present, check the things that decide whether it is survivable: is there a backup pin for the next certificate, when does the current pin expire (`network_security_config.xml` takes an `expiration` attribute, and an expired pin-set stops enforcing rather than failing closed — which is a fail-open worth knowing about), does the app pin the leaf certificate or the intermediate or the public key (leaf pinning breaks on every renewal, which with a 90-day certificate means quarterly), and is there a remote kill switch. If pinning is absent, note that as the normal and often correct state rather than as a defect — this is a low-severity documentation check, not a demand to add pinning. Separately, flag any `badCertificateCallback` or trust-manager override that accepts all certificates, which is the opposite failure and is a real high-severity problem that people leave in from debugging.
  attest: Ask the user whether the team has decided for or against pinning and why, and record the answer verbatim. If for, ask who owns pin rotation, where the backup pin is, and what the plan is when the certificate rotates unexpectedly. If against, ask whether the threat model was considered — an app handling payments, health data, or high-value accounts on shared devices is a different conversation from a content app — and note that transport security without pinning is still TLS, not nothing. Either answer passes with the reasoning recorded; only "we never discussed it" fails.
evidence: the pinning implementation with file:line, or `no pinning — recorded as a deliberate choice` / `no pinning — no decision on record`; the pin type, backup pin, and expiry if present; any all-certificates-accepted override with file:line, called out separately as a security defect; the user's verbatim reasoning and the named owner of pin rotation.

### MOB-020 Apple privacy manifest present; required-reason APIs declared
severity: high
tier: static
fix: easy
why: Since spring 2024 App Store Connect rejects builds that use required-reason APIs (UserDefaults, file timestamps, system boot time, disk space, active keyboards) without a `PrivacyInfo.xcprivacy` declaring the reason. Third-party SDKs trigger this too, and Apple maintains a list of commonly used SDKs that must ship their own manifest and signature, so an outdated dependency fails the build even when your own app is clean.
verify:
  static: Look for `PrivacyInfo.xcprivacy` in the iOS project (stack ref: "detection signals" for where the iOS project lives; Expo generates it from `app.json` `ios.privacyManifests`, so on a managed project read the config rather than expecting the file). Fail if absent. If present, list the declared `NSPrivacyAccessedAPITypes` with their reason codes, the `NSPrivacyCollectedDataTypes` entries, and the `NSPrivacyTracking` flag, and check them against reality: the accessed-API reasons must cover what the code actually does (a `UserDefaults` read anywhere in the app or in a dependency needs `NSPrivacyAccessedAPICategoryUserDefaults` with a reason code), and the collected-data types must agree with the App Privacy answers MOB-004 examines and with the tracking answer MOB-021 produces. Then check the SDK half, which is where most rejections come from: list the vendored pods and Swift packages and note which of them ship their own `PrivacyInfo.xcprivacy` (`find ios/Pods -name "PrivacyInfo.xcprivacy"` on a project with a Pods directory), calling out any SDK on Apple's commonly-used list — Firebase, the Facebook SDK, AppsFlyer, Adjust, Branch, older Sentry and other analytics builds — that is on a version predating manifest support. Apple's list grows, so read the current one rather than treating this sentence as complete, and mark the finding `verify current rules`.
evidence: path of the manifest or "absent"; declared API types with their reason codes and the tracking flag; SDKs lacking manifests, with the installed version of each; any accessed-API category used in code but not declared.
fix_hint: Add `PrivacyInfo.xcprivacy` with the accessed API types and reasons Apple lists, or the `ios.privacyManifests` block in `app.json` for Expo; update SDKs to versions that bundle their own manifest, and keep the collected-data types in the manifest identical to the App Privacy answers so the two declarations cannot drift apart.

### MOB-021 App Tracking Transparency prompt if tracking SDKs present
severity: high
tier: static
fix: guided
why: Reading the advertising identifier, or letting an attribution SDK correlate a user across apps and websites, requires the user's permission through the App Tracking Transparency prompt, and Apple enforces it both by rejecting builds that lack the usage string and by pulling apps that track before the prompt is answered. The failure is rarely deliberate: an attribution SDK is initialised at app launch and starts collecting before anything asks, which is a policy violation even if the developer never touched the IDFA directly.
verify:
  static: Detect the trigger first. Tracking SDKs in the dependency list — the Facebook SDK (`react-native-fbsdk-next`, `FBSDKCoreKit`, `flutter_facebook_auth` with app events), AppsFlyer, Adjust, Branch, Kochava, Singular, Google Mobile Ads or AdMob, Amplitude or Mixpanel configured to collect the IDFA — or any direct IDFA access (`expo-tracking-transparency`, `react-native-idfa`, `ASIdentifierManager`, `advertisingIdentifier`, `app_tracking_transparency` in Flutter). If none is present and the app does not share user data with data brokers or correlate identities across apps, the check passes and you record why, since a `NSUserTrackingUsageDescription` present with no tracking SDK is its own finding — an unnecessary prompt that costs conversions and contradicts an App Privacy answer of "not used for tracking" (MOB-004). If tracking is present, three things must hold. `NSUserTrackingUsageDescription` must exist in `Info.plist` or `ios.infoPlist` and must say specifically what the tracking is for, not "we use your data to improve the app". The code must call `requestTrackingAuthorization` (or the wrapper's equivalent) and must do so **before** any tracking begins, so read the initialisation order at app startup — an SDK initialised in a top-level effect that fires before the permission result is a fail. And each SDK must be configured to hold off until authorised: the Facebook SDK's `advertiser_tracking_enabled` and auto-init flags, AppsFlyer's start-deferral and ATT wait timeout, AdMob's delayed initialisation and non-personalised-ads path. Note also that the prompt may only be shown once meaningfully, so a request fired during the first launch splash wastes it; a priming screen before it is allowed as long as it does not misrepresent the choice or offer an incentive. COMP-003 owns the sale-and-share disclosure that these same SDKs trigger; cite it rather than repeating the analysis.
evidence: the tracking SDKs found with file:line and version; the `NSUserTrackingUsageDescription` string quoted or `absent`; the `requestTrackingAuthorization` call site at file:line and its position relative to each SDK's initialisation, stated as an order; per-SDK the deferral or tracking-enabled flag and its value; `usage description present with no tracking SDK` where that is the case; a citation to MOB-004 for the App Privacy tracking answer and COMP-003 for the disclosure.
fix_hint: Add a specific `NSUserTrackingUsageDescription` naming what the tracking does, request authorization from a screen the user reaches after seeing the app's value rather than from the launch path, and gate every tracking SDK behind the result — set the Facebook SDK's auto-init and advertiser tracking off until authorised, give AppsFlyer its ATT wait, and initialise ad SDKs in non-personalised mode until permission is granted. If no attribution is actually needed, remove the SDK and the usage string together and set the App Privacy tracking answer to no.

### MOB-022 Android targetSdk meets current Play requirement
severity: high
tier: static
fix: easy
why: Google Play enforces a rolling minimum target API level: new apps and updates must target a level roughly a year behind the newest Android release, and a build below it is rejected at upload rather than at review. The floor rises every August, so a project that shipped comfortably last year will be blocked this year, and the fix is never only a number — raising `targetSdk` opts the app into that release's behaviour changes, which is real work that should not be discovered on submission day.
verify:
  static: Read the value where this stack keeps it: `targetSdkVersion` or `targetSdk` in `android/app/build.gradle`, an `ext` block in the root `build.gradle`, `gradle.properties`, or — for Expo managed projects with no `android/` directory — the `expo-build-properties` plugin's `android.targetSdkVersion` in the app config, remembering that each Expo SDK version pins a default, so on a managed project the real answer is often "whatever this Expo SDK ships" and raising it means upgrading Expo. Record `compileSdk` alongside it, since it must be at least as high, and `minSdkVersion`, since it decides how much of the compatibility work is real. Then compare against the current Play requirement read from the android stack reference's "known traps" section, which is where this skill keeps the figure precisely because it moves: as of 2025 new apps and updates must target API 35 (Android 15), with the floor rising annually and a short extension process available — read the current value from the stack ref and from Play Console rather than trusting this sentence, and write the finding as `current requirement per stack ref: <value>`. Finally, name the behaviour changes the gap implies rather than only the number, since that is the work: 33 makes `POST_NOTIFICATIONS` a runtime permission (MOB-009) and splits the media permissions, 34 requires a declared type on every foreground service and tightens implicit intents, and 35 makes edge-to-edge display mandatory, which visibly breaks layouts that assumed system-bar insets. Check whether the app already handles the ones between its current target and the required one.
evidence: `targetSdk`, `compileSdk`, and `minSdk` with the file:line each was read from, or the Expo SDK version and the plugin default it implies; the current Play requirement as read from the stack ref, quoted with its source; the gap stated in API levels; the behaviour changes crossed by that gap, one line each, with whether the app already handles them.
fix_hint: Raise `targetSdk` and `compileSdk` to the level Play currently requires — on Expo that means moving to the SDK version that pins it rather than overriding the number by hand — and then work through the behaviour changes for every level crossed: request `POST_NOTIFICATIONS` at runtime, declare foreground service types, and apply edge-to-edge insets so the layout does not sit under the system bars. Test on an emulator running that API level before submitting, because these changes are visual and behavioural rather than compile-time.

### MOB-023 Sign in with Apple offered if other social logins are
severity: high
tier: static
fix: guided
why: Apple's guideline 4.8 requires an app that offers third-party or social login to also offer an equivalent privacy-focused option, and Sign in with Apple is the one everybody uses to satisfy it. It is a hard rejection, it is caught in the first five minutes of review, and it is not a small change — it needs a capability, a provider configured in your auth backend, and account-linking logic for users who already signed up with Google using the same address.
verify:
  static: Inventory the login options the iOS app actually offers: Google, Facebook, X, LinkedIn, GitHub, Microsoft, or any other login that uses an existing third-party account, read from the auth screen's components rather than from the backend's configured providers, since a provider enabled server-side but not shown in the app does not trigger the rule. If the only options are your own email-and-password or a magic link, the requirement does not apply and you record that. If a third-party login is offered, check for Sign in with Apple: `expo-apple-authentication`, `@invertase/react-native-apple-authentication`, `sign_in_with_apple`, or a native `ASAuthorizationAppleIDProvider`, plus the Sign in with Apple capability in the entitlements file or `ios.usesAppleSignIn` in the Expo config, plus the provider configured in your auth backend. Then check the parts that are wrong even when the button exists: it must appear on the iOS auth screen with equivalent prominence rather than buried below the others; the backend must verify the identity token's signature, audience, and issuer rather than trusting the client's claim; the private relay address must be handled as a real email, including for transactional sending, which needs the relay domain registered with Apple or the mail bounces; and the user's name is returned **only** on the very first authorization, so an implementation that expects it on later sign-ins creates nameless accounts and cannot recover them. Also confirm the same email arriving via Apple and via Google links to one account rather than creating a duplicate. State the exceptions accurately rather than treating the rule as absolute: apps that use only their own account system, education or enterprise apps where the user signs in with an existing institutional account, apps using a government or industry-backed citizen identity scheme, and apps that are specific clients for a third-party service (an email client signing into that mail provider, for instance) are outside it — and the guideline's wording about equivalent privacy-preserving options has been revised, so mark the verdict `verify current rules` and cite the guideline number rather than paraphrasing its scope.
evidence: the login options rendered on the iOS auth screen with file:line for each; the Sign in with Apple package, entitlement or config flag, and backend provider with file:line, or `not offered`; whether the identity token is verified server-side and where; the private-relay handling and whether the relay domain is registered; the first-authorization name handling; the account-linking behaviour for a duplicate email; any exception being relied on, with `verify current rules`.
fix_hint: Add Sign in with Apple on the iOS auth screen alongside the other providers with equal prominence, enable the capability in the app and the provider in the auth backend, and verify the identity token server-side. Store the name and email on the first authorization because they will not come again, treat the private relay address as the user's real address and register the relay domain with Apple so transactional mail delivers, and link an Apple sign-in to an existing account with the same verified email instead of creating a second one. If an exception applies, write down which one and why, so the next submission does not relitigate it.
